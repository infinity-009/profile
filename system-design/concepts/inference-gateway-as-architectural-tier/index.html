Tier 10 · AI-era systems Inference gateway tier

A request stops being a unit of work, so the limiter, the bill and the load balancer all break at once — and the gateway's 0.7 ms hop buys a 3,700 ms decision

api-gateway-and-bff settled that a choke point should exist and priced centralising a cross-cutting policy at it. This lesson is about the second gateway tier that appears once the thing behind the choke point is a model server, and about the single fact that makes it a different tier rather than the same one with new plugins: a request is no longer a unit of work. Measured on production agentic traffic, two turns that count identically to a requests-per-minute limiter differ by 43.1x in the tokens a limiter would charge, and by 45.2x in prompt tokens alone — which is the term prefill FLOPs are linear in. That one fact breaks four things simultaneously. It breaks rate limiting, because the quantity you want to limit is not knowable until generation ends — so every real token limiter reserves an estimate and reconciles later, and LiteLLM issue 18730 measured that hole at 6.6x overshoot. It breaks load balancing, because the replicas are not interchangeable: one card holds this prompt's KV blocks and the others do not, which is the difference between a 0.6-second and a 4.3-second first token. It breaks cost attribution, because a cached prefix read costs a tenth of an input token, so the bill is not linear in tokens. And it breaks cost-quality model routing, because switching model throws the prefix cache away — above a computable 81.0% cached prefix, routing DOWN to a model 3.3x cheaper on both input and output costs MORE per turn, and production agentic traffic sits at 95.4%.

01

Two gateways, two jobs: one faces price lists, one faces GPUs

api-gateway-and-bff already settled that a choke point should exist, and priced centralising one cross-cutting policy at it. What it did not settle is that by 2026 an inference stack has two gateway tiers, and blog content conflates them constantly.

A provider-facing gateway presents one OpenAI-shaped API over N hosted vendors. LiteLLM’s virtual keys with per-key, per-user, per-team and per-org budgets; Portkey’s fallbacks and circuit breakers over 250+ models; Kong’s ai-proxy-advanced; Cloudflare AI Gateway’s 24 native providers with unified third-party billing since 2026-08-07; Azure API Management’s llm-* policies. Its concerns are commercial and organisational — key virtualisation, spend attribution, provider failover. It never sees a GPU. It cannot hold a KV block. Its routing is over price lists.

A model-server-facing router picks which replica of a fleet you operate serves the request. Kubernetes Gateway API Inference Extension (InferencePool at v1, with an Endpoint Picker reached over ext_proc), llm-d, NVIDIA Dynamo’s KV router, vLLM’s Rust router (December 2025), GKE Inference Gateway. Its concerns are physical — land the prompt on the card whose HBM already holds its KV blocks, without hotspotting it. It does not know what a dollar is.

Envoy AI Gateway v1.0 (GA 2026-06-23) is the one product that is explicitly both: 16 providers, an MCP gateway and a token quota policy, plus Gateway API Inference Extension v1.0.2 embedded, with endpoint selection delegated to an EPP. That composition — provider policy at the edge, replica physics one hop in — is the honest 2026 architecture, and enterprises assemble a stack rather than picking one box.

The sentence that justifies a second gateway lesson at all: an API gateway’s routing decision is worth microseconds because every backend is interchangeable; an inference gateway’s routing decision is worth seconds because they are not — one replica holds this prompt’s KV blocks and the others do not — and its rate limiter cannot know the size of the work it is admitting. Neither property exists in tier 8.

Before anything else, the disambiguation that most content gets wrong. There are three caches, and the gateway owns exactly one of them.

The mechanical reason the KV row cannot move to the gateway: KV blocks are activation tensors resident in one card’s HBM, written in 16-token pages. A gateway holds bytes and has no attention kernel. So what it does instead is maintain a map of where the blocks are. The response cache — exact-match or semantic — is the one it genuinely owns, and semantic-caching prices that one completely, headline included; this lesson does not re-derive a single number of it.

02

The belief this breaks: 'a token limit is a rate limit with a bigger number'

It is not. Three properties break at the same time, and the first one is enough on its own: the quantity being limited has no stable relationship to the quantity being counted.

same nominal budget, four accounting policies, four different amounts of real load admitted

One budget of 20,378,374 tokens a minute — enough for thirty mean-sized agentic turns — offered sixty turns a minute. Measured in inference-gateway.mjs: a requests-per-minute limiter set to thirty admits 95.3% of that budget with a worst minute of 2.51x; a post-hoc token counter admits 200.0% with a peak of 4.93x; LiteLLM-shaped reserve-then-reconcile admits 193.5% at 4.89x; an oracle that charges the true total at admission admits 101.7% at 1.90x. The oracle is not implementable — output length does not exist at admission — which is the whole problem.

Predict An RPS limiter and an ORACLE token limiter -- one that somehow knows each turn's true total cost at admission -- are given the identical token budget on heavy-tailed agentic traffic. Compared with the oracle, what does the RPS limiter do?
Measured: the RPS limiter rejects 49.0% of callers against the oracle's 9.4% -- 5.2x as many -- runs at only 95.3% of the budget against the oracle's 101.7%, and STILL peaks at 2.51x against 1.90x. Dominated on all three axes, because the quantity it holds constant (request count) has no stable relationship to the resource (tokens). P90/P10 turn size is 43.1x. But note carefully what the comparison is against: the oracle is an UPPER BOUND, not a product. The best IMPLEMENTABLE token limiter in this sim is the reserve-then-reconcile lane, and it peaks at 4.89x and 193.5% utilisation -- WORSE than the RPS lane on two of the three axes, because it must reserve against a worst-case output it cannot know at admission. 03

A request is not a unit of work — and the work is on the input side

The distribution is the mechanism. Fitting a lognormal to the published per-turn medians and P90s from Microsoft Research’s Copilot characterisation — 3.2M users, 13.5M sessions, 760.5M LLM calls, 44.9T prompt tokens — and sampling 3,000 turns gives a P10 of 36,791 tokens and a P90 of 1,587,289: a spread of 43.1x between two requests an RPS limiter counts as one each. The mean sits 2.88x above the median, so a request limit derived from an average is wrong for almost every individual request.

Be precise about which quantity that 43.1x is, because three plausible ones differ. It is the P90/P10 of what a LiteLLM-shaped limiter would charge: prompt tokens plus the output capped at 4096. Prompt plus uncapped output is 40.8x. And prompt tokens alone — the only term prefill touches — is 45.2x.

That last one is the number that turns bookkeeping into GPU-seconds. Prefill FLOPs go as 2·N·T for N parameters and T prompt tokens, a linear term llm-inference-phases already established. Output tokens are decode, a different cost curve. So the GPU-seconds spread across the prefill of these two turns is 45.2x, not the 43.1x the limiter’s own unit reports — and a limiter that holds request COUNT constant controls neither.

The second surprise is the direction: the input side is where the work is, which is the opposite of the chatbot mental model most limiter designs assume, and the reason “limit output tokens” is not a substitute. On the per-turn medians this lesson’s model is built from, prompt over output is 227,600 / 1,900 = 119.8:1, and the sampled per-turn median is 119.4:1. The paper separately reports a median input-to-output ratio above 275:1, which is not those medians divided — divide them and you get less than half of it. Treat 275:1 as a figure at a different granularity (a turn is many LLM calls sharing one prefix) rather than as a per-turn ratio, and use 119.8:1 when the unit is a turn. Either way the sign is the same, and the sign is what breaks the limiter.

The third is that only half the quantity is knowable at admission. Input tokens can be counted before dispatch — Anthropic exposes a token-counting endpoint for exactly this. Output tokens cannot: they exist only when generation ends. Every real limiter therefore reserves an estimate and reconciles.

04

Reserve, forward, stream, reconcile — and the band where the counter is a guess

Every vendor documents its own version of this hole, and none of them hides it:

  • OpenAI enforces limits on “the maximum of max_tokens and the estimated number of tokens based on the character count of your request” — a character-count estimate, not a tokenisation, with max_tokens as the ceiling. Set max_tokens to 4096 for a 40-token reply and 4,056 tokens of quota are gone.
  • Azure APIM’s llm-token-limit states it flatly: because the exact consumption cannot be determined until the response arrives, concurrent requests can temporarily exceed the configured limit. With prompt estimation turned off, the over-limit prompt is sent, and blocking starts from the response — that is post-hoc accounting, not admission control. Counters are per-gateway and are not aggregated across instances. Under streaming both prompt and completion tokens are always estimated, and image inputs are overcounted at up to 1200 tokens each.
  • Envoy AI Gateway computes cost after completion, via a CEL expression over input_tokens, output_tokens, cached_input_tokens, cache_creation_input_tokens and reasoning_tokens. The request that breaks the budget succeeds; the next one gets the 429.
  • LiteLLM does it properly — reserve estimated_input + effective_output_cap, then replace the reservation with billable_input + completion_tokens where billable_input = prompt_tokens - cached_tokens, refunding on failure. And it still shipped issue 18730: a 100 TPM limit, five concurrent requests, 663 tokens admitted — 6.63x overshoot, root-caused as a read-then-write race with no atomic reservation, closed as not planned on 2026-01-07 against v1.80.11.

That last one is nine lines of arithmetic, and it is the difference between an atomic reservation and a read. Same five requests: atomically, the counter is checked and written together, so overshoot is bounded by one request — 138 tokens, 1.38x. Read-then-write with all five in flight, every one of them decides against the same zero — 663 tokens, 6.63x. At three concurrent readers it is 3.13x. An RPS limiter has no analogous hole, because a request is countable at the moment you admit it; there is nothing to reconcile.

05

The fifth column is the true range across all 49 full minutes, min to max, not a percentile band. The distinction matters enough to spend a sentence on, because reporting the 10th-to-90th percentile minute as if it were a range is the same error as an SLO that promises a P99: the RPS limiter’s P10-to-P90 band is a comfortable 0.60x–1.39x, a 2.33x spread, while its actual worst minute is 2.17x and its actual quietest is 0.41x — a 5.26x spread, more than double what the band suggests. The oracle’s band is 0.89x–1.14x and its true range is 0.79x–1.76x, a 2.21x spread. Both statistics are in the sim; only one of them is a bound.

Three readings, in order of how much they cost a team:

The RPS row is strictly dominated on three axes at once — 5.2x the rejections of the oracle, 4.7% of the budget left unspent, and a bigger peak. It is not buying safety with throughput; it is losing both, because the quantity it holds constant has no stable relationship to the resource. The post-hoc row is not admission control at all; it admits everything and discovers the overshoot afterwards. And the last column is the quiet one: reserve-then-reconcile charged 4.9% of the tokens that actually flowed, because the reservation is gross and the bill is net of the cached prefix. So a budget written as “20M TPM” has a ledger that sees roughly 1/20th of the GPU work it let through. What actually reached the GPUs is the fourth column — 193.5% of budget, not 2,000% — because the gross reservation still has to fit at admission even though the refund gives almost all of it straight back. Netting the bill is defensible for a dollar budget and wrong for a capacity budget, and nothing in the config distinguishes the two.

The sampled outputs have a median of 2,005 tokens and a P90 of 9,342 — close to the paper’s published 1.9K and 9.2K, which is the fit doing its job — so at LiteLLM’s default the median reply leaves 2,091 tokens of quota burned, and more than one reply in four would be truncated if the cap were enforced as max_tokens.

Finally, the argument for the tier, which is not the hop:

A vLLM instance answers a prompt whose prefix it already holds with a 0.6 s first token, and the same prompt cold at 4.3 s — 7.17x. Route to the warm replica and the request lands inside a 1-second TTFT budget with 399 ms to spare; route cache-blind and it overshoots by 4.3x. The hop that made the choice cost 0.7 ms.

Which also disposes of the stale figure. “An LLM gateway adds ~40 ms” was Python LiteLLM with callbacks; the same vendor now measures 0.7 ms p99 in Rust and 257.7 ms p99 for the old Python path, a spread of 368x between two builds of one product. Quoting 40 ms in 2026 is 57x too high for one and 6.4x too low for the other. And every one of these benchmarks runs against a local mock upstream, which deletes the dominant variable — second-to-second P99 swings at major providers exceed a well-built gateway’s entire overhead budget.

06

The trade-off: cache affinity and cost routing are adversaries

Both are called routing and they pull against each other. Cache-affinity routing chooses which replica of the same model, from live metrics — queue depth, KV utilisation, prefix overlap — in microseconds, and does not change the answer. Cost-quality routing chooses which model, from a prediction about the prompt, at about 85 ms P90 for Bedrock Intelligent Prompt Routing, and changing the answer is the entire point.

The conflict is quantified by one line in the Copilot traces: KV cache hit rates average ~90% within a turn, fall to 55% across turn boundaries, and drop to 8% on a model switch. Switching model throws the prefix cache away.

Before pricing that, a constraint the price list does not show, and the one this lesson got wrong on its first pass. The median turn here is 227,600 prompt tokens. The obvious cheap tier — Haiku 4.5 at $1/$5 per MTok, a fifth of Opus 5 on both axes — has a 200K context window, so it cannot accept the median turn at all, never mind price it. Measured on the 3,000 sampled turns, 54.5% of them are too large for a 200K window. A cost-quality router pointed at that model rejects the majority of this traffic before any cost question arises, so every saving computed for the pair is a saving on requests that would never have been served.

Which narrows the field hard: the candidate weak models for this workload are the 1M-context ones, a much smaller and much more expensive set, and that narrowing is itself the first thing that eats the projected saving. Check the context window before the price list — it is the cheaper of the two constraints to check and it disqualifies faster. Note also that 16.6% of these turns exceed 1M prompt tokens, so they fit in no current window at all and have to be compacted — and compaction, like a model switch, invalidates the prefix cache. The tail is not a rounding error.

So the pair priced below is two 1M-context models: Fable 5 at $10/$50 per MTok and Sonnet 4.6 at $3/$15 — 30% of the strong model’s price on both axes, a 3.3x gap. Combine that with cache reads at 0.1x input and writes at 1.25x, on the paper’s own median turn shape:

The break-even is closed form. Writing I and O for input and output prices, P for prompt tokens and U for output tokens, the strategies cost the same when

f* = [1 − I_w/I_s − (U/P)(O_w − O_s)/I_s] / 0.9

The 0.9 is one minus the cache-read multiplier: the fraction of the input price a cache read saves. At Anthropic list prices — Fable 5 at $10/$50 per MTok, Sonnet 4.6 at $3/$15 — and the median turn’s U/P of 1,900 over 227,600, f* is 81.0%. Production agentic traffic sits at 95.4%, on the losing side. A weak model at half the strong one’s price crosses over at 57.9%, and one at 80% of it at 23.1% — the smaller the price gap, the less cached prefix it takes to lose. Widen the gap far enough and the crossover leaves the interval entirely: below a price ratio of 13.61%, computed in closed form as 1 − 0.9/(1 + (U/P)(O_s/I_s)), there is no cached fraction at which routing down loses.

Note what the table below does and does not depend on. The break-even is a function of the price ratio and of the strong model’s own output-to-input ratio, which is 5:1 across the whole Anthropic lineup — so every row holds for Opus 5 and Fable 5 alike. What changes when you name a real pair is only which row you land on, and whether the weak model can hold the prompt.

The 20% row is where Haiku 4.5 against Opus 5 would sit, and it is worth seeing precisely because that pair cannot serve this workload: at 92.6% break-even against 95.4% production traffic the answer would still be “staying is cheaper”, and the model would refuse the prompt before the arithmetic ever ran. Two independent reasons to say no, from a price list that looks like an 80% saving.

The rule to leave with is not a percentage: measure your cached fraction before you buy a router. Every published routing saving comes with a benchmark and a model pair attached, and the sign of the answer depends on a number about your own traffic that the benchmark could not know. RouteLLM’s much-quoted “over 85% cost reduction” was MT-Bench with GPT-4 against Mixtral-8x7B; the same paper got 45% on MMLU and 35% on GSM8K. Bedrock Intelligent Prompt Routing’s measured GA figures are 35% (Nova), 56% (Anthropic) and 16% (Meta), pairwise and within-family only.

Two more failures with no analogue in an HTTP API gateway:

Failover has a point of no return. A gateway can retry or switch providers freely before the first byte reaches the client. After that the selected upstream owns the stream — partial SSE frames are already delivered, so a switch either restarts visible output or stitches two models’ text together. Vercel AI Gateway fails over to the same model on a different provider, preserving semantics; Cloudflare uses a manually ordered fallback array that may land on a different model, which does not. That distinction is the whole design question, and it is usually glossed as “fallbacks”.

The connection is held for the entire generation, so concurrency is bounded by sockets rather than by RPS. AWS ALB’s idle timeout and nginx’s proxy_read_timeout both default to 60 seconds, and GCP’s Application Load Balancer defaults to a 30-second backend-service timeout — which is worse, because it is a request-and-response deadline for HTTP(S) traffic rather than an idle timer, so a stream that is delivering bytes the whole time still dies at 30 seconds. A reasoning model can compute for longer than either without emitting a byte, and the balancer tears the connection down with no HTTP status while the client sees a truncated response. LiteLLM issue 31865 (opened 2026-07-01) added a configurable SSE heartbeat for exactly this. Any layer that buffers — nginx buffers responses by default at 4–8 KB — silently converts a streaming endpoint into a non-streaming one and destroys TTFT while every functional test still passes.

07

In the wild

Envoy AI Gateway v1.0 (GA 2026-06-23) is the composition argument shipping: 16 providers, an MCP gateway and a token quota policy at the edge, with Gateway API Inference Extension v1.0.2 embedded and endpoint selection delegated to an EPP. InferencePool reached v1/stable in the same window.

llm-d published the affinity numbers that justify the second tier: P90 TTFT of 0.542 s with precise, KV-event-driven scheduling against 31.083 s approximate and 92.551 s random (57x and 170x), with output throughput of 8,730 / 6,944 / 4,429 tokens per second — eight vLLM pods on two H100s each, Qwen-32B, 150 tenants, cache demand at 73% of cluster capacity. The precise index exists because vLLM publishes BlockStored and BlockRemoved events over ZMQ; the Endpoint Picker’s default index is the approximate one, which hashes prompts itself.

Baseten with NVIDIA Dynamo’s KV router (2026-03-16) measured −50% mean TTFT, −34% TPOT, +61% RPS and an 89% cache hit rate across four replicas against random routing, on Qwen3-Coder-480B with roughly 50K in and 1K out, confirmed against shadowed production traffic.

LiteLLM issue 18730 is the one to read as a design document rather than a bug: it was closed as not planned, which is the honest answer. Making token admission atomic across a distributed gateway fleet costs a coordination round trip per request — distributed-rate-limiting already prices that trade — and the vendor decided the overshoot was cheaper. That is a defensible call, and it is only defensible if you know it was made.

The 2026 wrinkle worth watching: LMCache- and Mooncake-style shared KV tiers make the cache cluster-visible, which changes the routing objective rather than removing it. Affinity routing stops being “avoid recomputing prefill” and becomes “avoid a network transfer of KV blocks”, so weights tuned for a GPU-local world are wrong once a shared tier exists.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • By 2026 an inference stack has TWO gateway tiers with different jobs: a provider-facing gateway (LiteLLM, Portkey, Kong AI Gateway, Azure APIM llm-* policies) whose concerns are commercial — virtual keys, per-team budgets, spend attribution, provider failover, and which never sees a GPU; and a model-server-facing router (Gateway API Inference Extension plus an Endpoint Picker, llm-d, NVIDIA Dynamo, the vLLM Rust router) whose concerns are physical — land the prompt on the replica that already holds its KV blocks, and which does not know what a dollar is. Envoy AI Gateway v1.0 is explicitly both, composed.
  • A request is not a unit of work. Measured on the sampled Copilot turn distribution, the P10 turn is 36,791 tokens and the P90 turn is 1,587,289 — a ratio of 43.1x — and the mean sits 2.88x above the median, so an RPS limit derived from an average is wrong for almost every individual request. Prefill FLOPs go as 2·N·T in the PROMPT tokens alone, whose P90/P10 is 45.2x on the same sample, so the error is a GPU-seconds error and not a bookkeeping one.
  • The quantity a token limiter wants to limit is not knowable at admission time. Input tokens can be counted before dispatch; output tokens exist only once generation ends. So every real limiter reserves an estimate and reconciles later, and the interval between those two moments is a hole every vendor documents — OpenAI charges the maximum of max_tokens and a character-count estimate, Azure APIM states outright that concurrent requests can exceed the configured limit, and LiteLLM issue 18730 measured 663 tokens admitted against a 100 TPM limit (6.63x) from a read-then-write race with no atomic reservation.
  • Token-aware limiting is therefore a different MECHANISM, not a different unit. Four accounting policies enforcing one identical budget admit 95.3%, 200.0%, 193.5% and 101.7% of it respectively, with worst-minute peaks of 2.51x, 4.93x, 4.89x and 1.90x — and the RPS limiter is strictly dominated on three axes at once: it rejects 5.2x more callers than a token limiter, leaves 4.7% of the budget unspent, AND still lets a bigger peak through.
  • There are THREE caches, not one, and the gateway owns exactly one of them. KV/prefix cache blocks are activation tensors in one specific card's HBM — a gateway holds bytes, not tensors, and has no attention kernel, so it can only route to them. A provider-side prompt cache belongs to the vendor; the gateway can only inject the breakpoints. The response cache, exact-match or semantic, is the one the gateway actually owns, and it hits on a completely different condition.
  • Prefix-cache affinity routing and cost-quality model routing are adversaries, not complements, because a model switch drops the prefix hit rate from ~90% within a turn to 8%. The break-even cached fraction is closed-form: f* = [1 − I_w/I_s − (U/P)(O_w − O_s)/I_s] / 0.9, which for a weak model at 30% of the strong one's price on both axes is 81.0% — and production agentic traffic sits at 95.4%, on the losing side. The cheapest tier is not even a candidate: a 200K-context model cannot accept the median 227.6K-token turn at all, so the price list is not the only thing that constrains cost routing.
  • The gateway hop is not the cost and never was. A well-built one adds 0.7 ms p99 (LiteLLM Rust, measured against a mock upstream 2026-07-22) while the decision it makes is worth 3,700 ms of avoided prefill — a leverage ratio of about 5,286 to 1. The stale "gateways add ~40 ms" figure is simultaneously 57x too high for the Rust build and 6.4x too low for the Python one.

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A platform sets a 20.4M tokens-per-minute budget and enforces it with a requests-per-minute limit sized so that thirty MEAN-sized turns fit the budget. Traffic arrives at sixty turns a minute. What does the limiter actually deliver, and why is it worse than a token limiter on EVERY axis rather than trading one for another?

    How sure are you, before you look?
    Measured: it rejects 49.0% of callers, admits 2.51x the budget in its worst minute, and still leaves budget on the floor — 95.3% utilisation overall. Across the 49 full minutes the load it admitted ran from 0.41x to 2.17x of budget, a 5.26x range end to end; even the robust middle, the 10th to the 90th percentile minute, spans 0.60x to 1.39x. An oracle limiter whose unit is tokens — one that knows each turn's true total cost at admission, which is precisely what no real gateway can do — given the identical budget rejects only 9.4%, peaks at 1.90x, runs at 101.7% utilisation, and holds its full range to 0.79x–1.76x — a 2.21x range against the RPS limiter's 5.26x, with its P10-to-P90 band inside 0.89x–1.14x. Note what that band is and is not: 80% of minutes sit inside it, and the worst minute still reaches 1.76x. A percentile band is not a guarantee. So the RPS limiter turns away 5.2x as many callers, wastes capacity, AND lets a bigger peak through — it is strictly dominated, not a trade. The reason there is no trade is that the two limiters are not measuring the same thing with different precision; the RPS limiter is holding constant a quantity that has no stable relationship to the resource. Prompt length is lognormal with a P90/P10 ratio of 45.2x, so capping the request COUNT leaves the token count free to vary by that factor — which is why it both starves quiet minutes and floods busy ones. The token limiter's 1.90x peak is not slop either: the weighted bucket in inference-gateway.mjs starts with one window of budget in hand and refills a second window's worth while that window runs, so no minute can exceed 2.00x by construction. 1.90x is the measured peak sitting just under that structural bound, and the bound is the honest price of allowing any burst at all.
    Did you have that?
  2. Cued recall

    LiteLLM reserves estimated_input + output_cap before the call and replaces it with billable_input + completion_tokens afterwards, where billable_input = prompt_tokens - cached_tokens. On agentic traffic that is 95.4% cached, what does that reconciliation quietly do to the operator's budget, and in which direction?

    How sure are you, before you look?
    It decouples the limiter's ledger from the GPU work by a factor of about 20x. Measured in the admission run: the tokens the limiter charged came to 4.9472% of the tokens that actually flowed, so 1 / 0.0495 = 20.2x. The mechanism is that the reservation is GROSS (the whole prompt plus the output cap) but the bill is NET of the cached prefix — so almost the entire reservation is refunded at reconcile, and the limiter's steady-state occupancy reflects only the 4.6% of the prompt that was fresh. Be careful about what that 20.2x is: it is charged-versus-flowed, NOT the multiple of the budget that reached the GPUs. Gross flow cannot reach 20x, because the gross reservation still has to fit at admission — measured, the run admitted 193.5% of budget. The two effects partly cancel: the refund loosens the limit between requests while the gross reservation throttles during each one, and the net is a limiter running at roughly double its nominal ceiling whose own accounting reports a twentieth of the traffic. Netting the bill is arguably correct for a DOLLARS budget, since a cache read really does cost 0.1x. It is wrong for a GPU-capacity budget expressed in tokens, and nothing in the configuration distinguishes the two. The direction matters: this failure is permissive, not restrictive — the operator who wrote "20M TPM" expecting a capacity ceiling got 193.5% of it, while the same policy is simultaneously conservative DURING each request, holding a gross reservation for the whole ~18-second generation before refunding it.
    Did you have that?
  3. Cued recall

    LiteLLM's reservation falls back to a hard-coded output cap of 4096 tokens when the client sets no max_tokens. The Copilot traces publish an output median of 1.9K and a P90 of 9.2K, and the 3,000 turns sampled from that fit come out at a median of 2,005 and a P90 of 9,342. What is wrong with 4096, and why is naming a single better number not the fix?

    How sure are you, before you look?
    It is wrong in both directions at once, because it is a constant sitting near the MEAN of a heavy-tailed distribution. Measured at 4096 on the sampled outputs: 45.6% of every output reservation is quota reserved and never spent — the median reply of 2,005 tokens leaves 2,091 of quota burned — while 27.6% of replies are longer than the cap, so enforcing it as max_tokens truncates better than one reply in four. Sweeping the cap does not fix it, it only moves the error: 1024 wastes just 13.9% but truncates 70.1%; 9200 (the published P90) truncates only 10.3% but wastes 66.2%; 32768 truncates 1.0% and wastes 88.1%. There is no constant that is right, because the two errors are monotone in opposite directions and the distribution's spread is the thing generating both. The fix is structural, not numerical: reserve small and top up during generation, or accept a post-hoc bill and stop calling it admission control.
    Did you have that?
  4. Cued recall

    A gateway's own hop is measured at 0.7 ms p99. A team argues that this proves the tier is pointless overhead a well-configured L7 load balancer could absorb. What does the 0.7 ms actually buy, and what is the ratio?

    How sure are you, before you look?
    It buys the choice of which replica serves the request, and on this lesson's cited numbers that choice is worth 3,700 ms — a vLLM instance answers a prompt whose prefix it already holds with a 0.6 s first token and the same prompt cold at 4.3 s, a 7.17x difference. So the leverage is about 5,286 to 1, and the hop itself is 0.0163% of a cache-blind request. The reason a generic L7 balancer cannot absorb this is precisely the boundary with api-gateway-and-bff: that lesson's arithmetic holds because every backend is interchangeable, so the routing decision is worth microseconds and round-robin is nearly optimal. Here the backends are NOT interchangeable — one card's HBM holds this prompt's KV blocks in 16-token pages and the others do not — so the decision needs live per-replica state (queue depth, KV utilisation, prefix overlap) that a connection-counting balancer does not have and cannot infer. llm-d measured the consequence at P90 TTFT of 0.542 s with precise KV-event-driven scheduling against 92.551 s with random placement: 170x.

  5. Near transfer

    A video-transcoding API charges and rate-limits per upload. Uploads range from a 4-second clip to a 3-hour film, and the platform keeps hitting capacity while its dashboard shows the request limit comfortably unmet. An engineer proposes limiting on file size at upload time instead. Where does that proposal work, and where does it hit the same wall this lesson's token limiter hits?

    How sure are you, before you look?
    It works on exactly the half this lesson's input tokens correspond to: file size, like prompt length, is countable before you admit the job, so the limiter can stop being blind to the dominant term. It hits the same wall on the OUTPUT half. Transcode cost is not a function of input bytes alone — it depends on resolution, codec, how many renditions are requested and how compressible the content turns out to be, none of which is known until the job runs. So the platform lands in the same reserve-then-reconcile shape: estimate from file size and the requested ladder, hold that estimate, replace it with measured encoder-seconds when the job finishes, and refund. And it inherits the same three consequences — the estimate needs a cap (whose constant is wrong in both directions, exactly like the 4096 case), concurrent admissions racing on a stale counter can overshoot by the whole in-flight batch, and the bill stops being linear in the countable quantity. The structural lesson transfers precisely: making the limiter's unit closer to the resource is a large win, and it does not remove the estimate.
    Did you have that?
  6. Far transfer

    The abstraction is: a control loop is enforcing a budget in a unit that is cheap to count but only loosely related to the resource actually being consumed, AND the true consumption is not observable until after the work has been committed — so the loop must reserve an estimate, act, and reconcile, and the interval between reservation and reconciliation is a window in which the budget is unenforced. Name an instance outside inference serving.

    How sure are you, before you look?
    A hospital operating-theatre schedule. The countable unit is the booked slot — one procedure, one hour — and it is trivially enforceable at admission. The resource is theatre-minutes plus surgeon-hours, and the true consumption of a given operation is not knowable until it is under way; a routine cholecystectomy can run 40 minutes or turn into four hours. So the scheduler reserves a nominal duration (the estimate, with its own constant that is wrong in both directions — over-book and lists collapse, under-book and theatres sit idle), commits, and reconciles against the actual when the patient leaves. The window between incision and closure is exactly this lesson's band: the schedule's remaining capacity is a guess for the whole of it, and every case admitted during that window is admitted against a number that is wrong. Other instances: a cloud provider's spot-capacity admission, which counts instance-launch requests while the resource is instance-hours-until-termination, unknowable at launch; and a law firm's matter intake, counting engagements while the resource is billable partner-hours, with the reconciliation arriving months later — which is why fixed-fee work reprices exactly the way a cached prefix does, breaking the assumption that the bill is linear in the countable unit.
    Did you have that?
