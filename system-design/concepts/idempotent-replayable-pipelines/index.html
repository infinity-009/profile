Tier 5 · Moving data around Idempotent, replayable pipelines

The same four-stage pipeline replayed three times costs $0 through a guarded stage and $194 through an unguarded one — the other three stages were never the risk

`idempotency.mjs` already prices what one non-idempotent operation costs when a retry duplicates it. `determinism-as-design-tool.mjs` already prices what one non-deterministic operation costs when a replica replays it. `queue-vs-log.mjs` already prices whether a source can hand back history at all. This lesson does not re-derive any of that — it composes the three into the one question every crash recovery, backfill, and deliberate replay actually asks: is this pipeline, as a whole, safe to run again? The answer is a conjunction, not an average: one stage that duplicates, one stage that reads the wall clock, or one source that cannot reach back far enough breaks the guarantee for the entire chain, regardless of how many other links are flawless. A $97 charge replayed three times through a bare balance increment costs exactly $194 of duplicate damage; the identical charge behind a fully-guarded idempotency key costs about three billionths of a cent — roughly sixty billion times less, and still never exactly zero.

01

The backfill fixed the bug. It also ran a $480,000 pipeline stage twice.

A billing pipeline undercharged a subset of customers for four months — a bug in how usage was metered, since fixed. The plan is the boring, safe-sounding one: replay four months of usage events through the corrected pipeline and let the numbers land where they should have the first time. Nothing new gets written for the backfill, because “just replay it” is supposed to be the choice that needs no new code.

Every stage downstream of the source runs exactly the same logic that ran the first time — including one line nobody thought to flag: balance_due += usage_charge. It ran once per event on the original pass. It runs again, on every one of the same events, during the replay — because that is what “replay the pipeline” means: run the same code on the same input, again.

node -e "import('./src/sim/idempotent-replayable-pipelines.mjs').then(m => {

  console.log(perRecord);
  console.log('for 40,000 records:', perRecord.costDollars * 40000);
})"

Forty thousand usage-charge records, each replayed exactly once extra, at an average $12 charge per record: $480,000 added to real balances that nobody asked to add. The backfill’s fix was correct. The replay mechanism was correct. The one line that read-modified-and-wrote instead of setting a value was never checked against either of those facts, because nobody had a name for the thing it was missing.

02

Assume three good stages out of four is basically a passing grade

The instinct: a pipeline with three naturally idempotent stages and a source that retains years of history is “mostly fine” — one weak spot among several strong ones, a B+ that a team can live with while they get around to fixing it. The gap: safety here is not graded on a curve. It is a conjunction across every stage and the source, and a conjunction has no partial credit — one broken link anywhere breaks the guarantee for the entire chain, exactly as completely as four broken links would.

Predict A bug-fix backfill re-runs four pipeline stages against two years of history: three stages are naturally idempotent, the fourth is a raw balance += amount. The source retains three years. Is this backfill safe to run end to end?
safeToReplay's weakest-link scan reports the source as fine (a 2-year lookback against 3 years of retention clears easily) and names exactly stage[2] (increment) as the sole broken link. Being non-idempotent anywhere in the chain breaks the WHOLE pipeline's guarantee — there is no partial credit and no averaging, the same way one non-atomic checkpoint or one non-replayable source breaks exactly-once-via-checkpoints-and-sinks's guarantee regardless of how good the other two pieces are.
Show it without answering

Four things the rig makes hard to miss. The verdict chip never averages — it is always exactly “safe” or “NOT safe,” and it always names which chip broke it. Toggling the source alone can flip a perfect chain of stages to unsafe, and toggling one stage alone can flip a perfectly retained source to unsafe — the two axes are genuinely independent causes of the identical failure. The determinism checkbox breaks things a different way: switch it off and the cost bars stop being bars at all, because a stage that reads the clock has no well-defined “duplicate cost” — it doesn’t repeat the old answer wrong, it invents a new one. The guarded bar barely moves as replay count climbs, while the unsafe bar climbs in a straight line with no ceiling — the same shape idempotency.mjs’s own guard ladder draws, one level up.

03

The intuition: payroll reruns last month's numbers after finding a tax bug

Payroll finds a bug in how overtime tax was withheld last month. The fix is right, and the plan is the same boring plan: recompute last month’s paychecks from the stored timesheets and issue the difference.

Recomputing gross pay from stored hours is safe to redo as many times as anyone likes. It is a SET gross_pay = hours * rate — the second computation lands in exactly the same place as the first, because it never reads what a previous run already wrote. Running it five times by accident during testing produces the identical number five times.

Recording “$50 bonus for every hour of overtime” as an appended running total is not. If that step is overtime_bonus_total += 50 * hours, recomputing it a second time on the same timesheet adds a second $50-per-hour bonus on top of the first one — not because anyone was careless, but because the operation itself carries no memory of having already run. The fix was right; the recompute mechanism was right; the one appended total was never checked against either fact.

And if last month’s timesheets were already purged after payroll closed the books, none of this matters anyway. A perfect recompute step run against timesheets that no longer exist recomputes nothing. This is the source half of the same requirement — payroll’s retention policy on timesheets is doing the identical job a topic’s retention window does for a kappa replay, and a department that never checks how long it keeps timesheets has no idea whether its own “just rerun it” plan is available to them at all.

A pipeline stage being idempotent answers “does running it twice hurt.” A pipeline stage being deterministic answers a different question: “does running it twice change the answer.” A source being replayable answers a third: “is the input still there to run it on.” All three have to hold, everywhere in the chain, or the plan to “just replay it” is a plan built on a fact nobody checked.

04

The mechanism: two axes per stage, one axis for the source, and a single broken link anywhere

Per stage, two independent axes. stageSafety checks both, and reports which one (if either) failed:

AxisReused fromWhat it promisesWhat breaks it
Idempotentidempotency.mjs’s OPERATIONS listRunning it twice never duplicates the effectA read-modify-write (increment), an append, a charge, an email — with no guard
Deterministicdeterminism-as-design-tool.mjs’s replay modelRunning it on the same record always gives the same answerReading the wall clock or unseeded randomness inside the stage

A stage guarded by an idempotency key is treated as idempotent for the purposes of this classifier — idempotency.mjs’s own analyse(), called with all three of its guards forced on, decides that — but it is never marked exact, because the third guard is a retention bet and a bet is not a guarantee.

Per source, one axis, reused unchanged from queue-vs-log.mjs. replayFeasible answers exactly one question: can this source hand back everything since lookbackSeconds ago, given its retentionSeconds? A classic delete-on-ack queue answers no, always. A log answers yes, provided the lookback fits inside retention — and a lookback that does not fit is not a smaller version of “replayable,” it is the identical failure a queue has, arrived at a different way.

The classifier is the conjunction, and it is the only new code in this file. safeToReplay checks every stage’s two axes and the source’s one axis, and reports every break it finds, not just the first — because “which one” is exactly what an operator needs to fix it, the same reason idempotency.mjs’s own analyse() reports all three of its failure modes rather than one.

06

The trade-off: a conjunction means paying every cost, everywhere

Determinism is a constraint on what code is allowed to do, and it is free at runtime and expensive at review time. No stage in the chain may read the wall clock or an unseeded random source, ever — not because it is hard, but because it is exactly the kind of thing a “just add a timestamp for logging” change slips in without anyone thinking of it as touching correctness.

A naturally idempotent stage costs nothing beyond writing it that way — the cheapest fix on this whole page. A SET instead of an INCREMENT, an INSERT … ON CONFLICT DO NOTHING keyed on the record’s own stable identity instead of a client-generated token: zero guard machinery, zero retention window, and it is exact rather than a bet. The reason it is not the default everywhere is the same reason idempotency.mjs names for its own key store: most people reach for the guard before asking whether the operation could have carried its own identity.

A guarded stage buys a number close to zero and charges a key store, forever, per idempotency.mjs’s own trade-off — the write, the unique index, the retention window that is a correctness parameter disguised as a cleanup setting. This lesson adds nothing to that bill; it only shows the bill applies identically whether the duplicate came from a network retry or a deliberate replay months later.

A replayable source buys “the input still exists” and charges retention-sized storage, per queue-vs-log.mjs’s own trade-off — and the one number every team underestimates is the LOOKBACK a source will eventually be asked for. A checkpoint-bounded crash gap is seconds. A kappa-style full-history replay for a new consumer, or a bug-fix backfill discovered a year later, can ask for far more than whatever retention window was sized against “how long until the last consumer group catches up.”

And because the whole thing is a conjunction, there is no cheap partial version. Guarding three stages out of four and leaving the fourth bare is not 75% safe — the numbers in slot 5 show it is exactly as unsafe as guarding none of them, just with a smaller, quieter bug. The honest instruction is the unglamorous one: check every stage’s two axes, check the source’s one axis, and write down which of the three this pipeline is actually relying on, rather than writing “replayable” as if it were a single yes.

07

In the wild

Temporal’s workflow-replay model is this lesson’s determinism axis, enforced by a runtime rather than left to review. Temporal reconstructs a running workflow’s state by replaying its event history through the same workflow code — which only works if that code is deterministic on every replay. Temporal’s own documentation states the constraint directly: workflow code must avoid non-deterministic operations (direct calls to the system clock, unseeded random numbers, unordered map iteration) and must route them through the platform’s own deterministic APIs instead — the identical rule determinism-as-design-tool.mjs already prices, enforced at the framework boundary rather than by a code reviewer’s memory.

DDIA’s chapter on streaming systems states this lesson’s whole thesis in one sentence, about derived data built from an event log: “Updating a derived data system based on an event log can often be made deterministic and idempotent… making it quite easy to recover from faults,” adding that “log-based systems achieve correctness through deterministic retry and idempotence” where a distributed-transaction approach would instead need an atomic commit protocol (Kleppmann & Riccomini, DDIA, 2nd ed., ch. 13 “A Philosophy of Streaming Systems,” “Reasoning about dataflows”/“Derived data versus distributed transactions,” p. 541). That is determinism and idempotence, named together, as the reason a log-based pipeline recovers cheaply — independently of this lesson, and a chapter away from where the individual pieces are usually cited.

The same chapter’s own cost-of-non-idempotency example is this lesson’s charge-a-card case, verbatim in spirit: “Processing twice is a form of data corruption: it is undesirable to charge a customer twice for the same service… or to increment a counter twice” (Kleppmann & Riccomini, DDIA, 2nd ed., ch. 13, “Aiming for Correctness,” “Exactly-once execution of an operation,” p. 562), followed by a worked SQL example transferring $11 between two accounts where a retry transfers $22 instead — “even though code like this is a standard example for transaction atomicity, it is not correct, and real banks do not work like this” (same section, p. 563).

Airflow and dbt’s backfill tooling exist because “just replay it” is the industry’s own default plan, not a strawman. Both tools are built around re-running a pipeline’s tasks over an arbitrary historical date range after a logic change — which is exactly the deliberate-replay trigger this lesson names, and neither tool’s documentation claims that re-running a task is automatically safe; task idempotence is left as the author’s own responsibility, the same weakest link this lesson’s classifier checks explicitly rather than assuming.

Now put the page away

Everything above this line was the Passive rung — necessary, and the weakest thing on offer. Testing yourself on it will feel worse than rereading it and will hold roughly twice as long. That gap between how it feels and what it does is the entire reason this section exists.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A pipeline stage is idempotent if running it twice on the same record gives the same result as running it once; a pipeline is replayable only if every stage is idempotent AND the upstream source can hand the input back again — a log with retention, not a delete-on-ack queue
  • The reasons a pipeline actually gets re-run — a crash recovering from a checkpoint, a failed batch task rerun from scratch, a deliberate backfill after fixing a transform bug, a new consumer replaying full history — are the SAME requirement checked at a different granularity and triggered by a different event, not four separate problems
  • Safety is a conjunction across every stage and the source, not an average: a single non-idempotent stage or a single non-replayable source anywhere in the chain breaks the WHOLE pipeline's guarantee, independent of how many other links are fine — the weakest-link model
  • Idempotence (repeating it doesn't duplicate the effect) and determinism (repeating it doesn't change the answer) are independent properties; a stage that reads the wall clock or unseeded randomness can be perfectly idempotent in the dedup sense and still unsafe to replay, because it returns a DIFFERENT plausible answer, not a caught duplicate
  • Re-running a non-idempotent, unguarded stage N times duplicates the effect on every run after the first, deterministically — a $97 charge replayed 3 times costs exactly $194 of duplicate damage. Applying idempotency.mjs's full three-guard key cuts that to about 3×10⁻⁹, a factor of roughly sixty billion, but never reaches exactly zero — the same retention-is-a-bet asymmetry idempotency.mjs already names, one layer up
  • Every specific mechanism this repo already teaches for safe re-running — a stream's checkpoint + replay + sink, MapReduce's redo-from-scratch, kappa's full-history replay — is this SAME classifier evaluated on a different pipeline shape; the trigger and the granularity change, the requirement does not
  • A source's retention window can break "safe to replay" even when every single stage is flawless — retention has to cover the LONGEST lookback anyone will ever ask for, including a kappa-style full-history replay or a bug-fix backfill from years back, not just a checkpoint-bounded crash gap

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

    Why does guarding a non-idempotent stage with a full idempotency key — all three of idempotency.mjs's guards — never make replaying it exactly as safe as a stage that was naturally idempotent to begin with?

    How sure are you, before you look?
    Because two of idempotency.mjs's three guards are exact but the third — retention — is a bet: no finite window covers every possible replay delay, and a deliberate backfill run years after the fact is exactly the kind of delay that tests it. This lesson's cost model reuses that residual rate directly, so a guarded $97 charge replayed three times costs about three billionths of a cent in expectation rather than $194 — sixty billion times better, and still never zero.
    Did you have that?
  4. Cued recall

    A kappa-style pipeline's every stage is a plain SET, individually perfect. A new consumer comes online and asks to replay the full 180-day topic history, but the topic only retains 90 days. Is the pipeline safe to replay for that consumer?

    How sure are you, before you look?
    No — and every single stage reports back as individually safe. The classifier names the SOURCE as the sole weakest link here, because a 180-day lookback against a 90-day retention window fails regardless of stage quality. This is the case that proves "idempotent stages" is necessary but not sufficient on its own: safety is stages AND source, and either one alone breaking is enough to break the whole guarantee.
    Did you have that?
  5. Near transfer

    exactly-once-via-checkpoints-and-sinks.mdx already composes a checkpoint, a replayable source, and a safe sink into one end-to-end guarantee. Doesn't that lesson already cover everything this one does?

    How sure are you, before you look?
    No — it covers ONE instance, at ONE granularity, triggered by ONE event: a stream operator recovering from a crash, replaying a checkpoint-bounded gap of seconds. This lesson is the general classifier underneath that instance. The same two requirements — every stage idempotent and deterministic, the source replayable far enough back — also explain why a failed MapReduce task can simply be rerun from scratch (a completely different mechanism: no checkpoint at all, a durable input block standing in for the source), why a kappa architecture's full-history replay can fail even when every stage is flawless (the source's retention, not any stage, is the weakest link), and why a deliberate bug-fix backfill months later is subject to the exact same idempotency-key retention bet idempotency.mjs already prices for an ordinary network retry. exactly-once-via-checkpoints-and-sinks.mdx prices ONE composition; this lesson names the requirement every one of those compositions is quietly checking.
    Did you have that?
  6. Far transfer

    The abstraction is: redoing an action safely, after the fact, requires BOTH that the action leaves the world in the same state no matter how many times it's applied, AND that whatever the action operates on is still available to operate on again — losing either one breaks the ability to redo it correctly, independent of how good the other one is. Name an instance outside computing.

    How sure are you, before you look?
    Pharmaceutical batch reprocessing. When a drug batch fails a quality check, the fix (re-filtering, re-crystallizing) is only safe to apply if it does no harm when applied to already-good product a second time — the idempotence side. But regulators also require manufacturers to keep retained samples of the original raw materials and in-process batches for a fixed period specifically so a failed batch CAN be traced and reprocessed at all — the replayable-source side, with an explicit retention window standing in for a log's. A flawless reprocessing procedure does nothing for a batch whose retained samples were already discarded past the retention period, the same way a flawless idempotent stage does nothing for a pipeline whose source has already aged the input out — one axis being perfect never substitutes for the other.
    Did you have that?
