Tier 1 · The network Connection pooling explained well nowhere else

Taking one connection out of each pool made the wait for a connection 6.6× longer, and the database never noticed

A pool is a queue with a server count you chose by hand, so its size is set by Little's Law and the wait in front of it is Erlang-C shaped. That makes both mistakes look identical from the outside — too few connections and callers wait while the backend idles, too many and the queue moves inside the backend where you cannot time it out — and it makes the number the database actually sees a product nobody configured.

01

Two changes, opposite directions, and the same graph

A service runs on 8 instances. Each one keeps its own pool of database connections. The workload is 800 requests a second, and each request holds a connection for 25 ms — a query, a row or two of results, back to the pool. The database has 32 CPU threads it can usefully run at once and max_connections = 200.

The pool is set to 4 per instance: 32 connections in the fleet. Callers wait 5.3 ms for one, the request takes 30 ms end to end, and nobody thinks about it.

Someone tightens the pool to 3 per instance to be careful with the database. That is 24 connections — still more than the 20 the workload needs, and the arithmetic for that is coming. The mean wait for a connection goes to 35 ms, the p99 wait to 213 ms, and the request that took 30 ms now takes 60 ms. The database’s own metrics are identical in both configurations: 20 of its 32 workers busy, 62.5% utilised, mean query time 25 ms. It is doing the same work at the same speed. The graph everybody looks at is flat.

So the pool goes the other way — 100 per instance, because connections are cheap and latency is not. Latency does drop back to 25 ms. Three other things happen:

  • The fleet now opens 800 connections against a cap of 200. Instance number 3 fails to start, with its own configuration unchanged.
  • At 9 MB of server-side memory per connection, those 800 sockets hold 7.03 GB of the database’s RAM to make 20 connections’ worth of progress.
  • The next traffic peak — 1,400 requests a second against a ceiling of 1,280 — no longer queues in the pool. Ten seconds in, the database is completing 98 requests a second: a cap of 800 does bind eventually, but only after throughput has fallen thirteen-fold, and with no cap at all the same moment reads 6. The same peak with the pool capped at 32 completes 1,280.

Three configurations, one workload, and every one of them presents as “the database is slow”. In the first the database is 62.5% busy and the queue is in the client. In the third the database is the queue, and the thing that used to bound it was the pool nobody wanted.

02

Give the pool one fewer connection than it is comfortable with

The mental model almost everyone starts with is that a pool is a cache of connections: bigger is warmer, smaller is thriftier, and the only cost of getting it wrong is a little memory. Pool size gets a round number, usually the library’s default, and it is revisited when something breaks.

A pool is not a cache. It is a queue with a hand-chosen server count. c connections, one waiting line, first come first served — the same object as the queueing lesson’s single-server hockey stick, with c servers instead of one. Which means it has a utilisation, ρ, and everything that follows from ρ follows here too.

Predict 800 requests a second, each holding a connection for 25 ms, across 8 instances with 4 connections each. Little's Law says 20 connections are busy at any instant, and callers wait 5.3 ms for one. You now remove a single connection from each instance: 24 in total, still four above the 20 the workload needs. What happens to the mean wait for a connection?
Per instance, ρ goes from 0.625 to 0.833, and the Erlang-C wait C/(c(1−ρ))·W moves on both terms at once: the probability of waiting at all rises from 0.32 to 0.70, and the drain rate c·μ − λ falls from 0.06 to 0.02 per ms. Multiply the two and the mean wait goes 5.33 ms → 35.11 ms, with the p99 at 213 ms. The second option is the belief this whole lesson is about: being above λW makes a steady state exist, and says nothing about how long the wait is. Computed in src/sim/pool.mjs and graded against a discrete-event simulation of the pool in pool.test.mjs.
Show it without answering

Four things to do with it, in this order:

  1. Read the valley. The curve is a cliff on the left, a flat floor in the middle, and nothing on the right. The flat floor is wide — 6 connections per instance and 128 per instance are within 0.34 ms of each other — which is exactly why oversizing survives code review. It is not visible in latency.
  2. Cross the amber line. Drag the pool below λW ÷ instances and the dot lifts off the curve into “no steady state”. That is not a large number. It is the absence of one: the queue grows for as long as the load lasts.
  3. Drag app instances from 8 to 40. Nothing in the top band moves much — each instance now sees a fifth of the traffic — but the middle bar quintuples. Nobody edited a pool setting. The deployment scaled.
  4. Press low-traffic outbound pool. 4 requests a second behind 160 connections. The bottom band says each connection serves 1.46 requests before the idle timeout reaps it, against a break-even of 26.7. That pool is cold, and every dashboard will tell you it is warm.
03

The intuition: a shelf of keys

Forget connections. You run a workshop with a machine room, and the rule is that you may not enter without a key. Keys live on a shelf by the door. Take one, work, hang it back.

How many keys do you need? Twelve people an hour want in, and each stays five minutes. Five minutes is a twelfth of an hour, so on average one key is in use — twelve × one twelfth. That is the whole calculation, and it is the same one that sizes a connection pool.

Now get it wrong in both directions.

Too few keys. One key, and the arrivals bunch up as arrivals do. Someone waits at the shelf while the machine room stands half empty, and the queue at the shelf grows fastest exactly when the room is busiest. From inside the machine room nothing looks wrong at all: the machines are running, the work is getting done at the usual speed. The queue is at the door, and the door is not instrumented.

Too many keys. Cut two hundred keys, because keys are cheap. Now everybody who turns up walks straight in, and on a busy afternoon two hundred people are in a room with thirty benches. Nobody waits at the shelf. Everybody is inside, in each other’s way, and the work per hour falls — which it never did when they were queueing at the door. You did not remove the queue. You moved it somewhere with no line, no order and nobody to say “come back in five minutes”.

Two more details from the same shelf, because they matter as much as the count:

  • Eight workshops, one machine room. Each has its own shelf and its own keys. The machine room sees the total, and no single shelf’s label says what that total is. Worse, a key hanging idle in workshop three is no use at all to the person waiting in workshop five.
  • Keys that dissolve if unused. If a key vanishes after fifteen minutes on the shelf and your workshop only needs the room every forty minutes, you are cutting a fresh key nearly every time — while the shelf, to anyone glancing at it, looks perfectly well stocked.

The number of keys is rate × duration. Fewer than that and the queue is at the door, where you can see it and turn people away. More than that and the queue is inside the room, where you can do neither.

04

The mechanism: one law for the size, one distribution for the wait

The size is Little’s Law, and it is not a preference

connections busy at any instant = arrival rate × holding time

L = λW, the identity from the queueing lesson, with W the time a connection is checked out. 800 requests per second × 0.025 s = 20. That is how many connections can be simultaneously useful; the 21st has nothing to do.

src/sim/pool.mjs computes this by calling the kernel’s littlesLaw rather than retyping the multiplication, so the sizing rule and the law cannot drift apart. Three consequences worth stating separately, because each one is a mistake in the wild:

W is the holding time, not the query time. Everything between checkout and return is in W. A transaction that makes an HTTP call while holding a connection has a holding time ten times its query time, and needs ten times the pool. This is the single most common reason a correctly-sized pool is too small: nobody measured what they thought they measured.

Only the product matters. 800 rps at 25 ms and 8 rps at 2.5 s need exactly the same 20 connections. So “we are a low-traffic service, we do not need many connections” is not an argument — it is half of one.

The pool is a concurrency cap, so it is also a throughput cap. c connections each completing one hold every W seconds is c/W requests per second, full stop. 16 connections at 25 ms is 640 rps, whatever the backend could have done.

The wait is Erlang-C shaped, which is why it does not warn you

With c connections and offered load a = λW erlangs, ρ = a/c, and three closed forms — all of them already in the kernel, because this is M/M/c and so is everything else in this repo that has a queue in front of workers:

mean wait = C(c, a) · W ÷ (c(1 − ρ))

C(c, a) is Erlang’s C formula (1917): the probability that an arriving caller finds every one of the c connections busy. Divide it by the rate at which the pool drains, c·μ − λ, and you have the mean time a caller spends waiting for a socket. Both factors are in the table below, because both of them move.

The reason a pool feels like it has no warning zone is that both factors move at once. Take one connection per instance out of the worked example:

From 4 to 3 the probability of waiting rises 2.2× and the drain rate falls 3×, so the wait moves 6.6×. And the whole distribution is closed-form, because the wait — conditional on waiting at all — is exponential with rate c·μ − λ:

P(wait more than t) = C · e^(−(c·μ − λ)·t)

One expression, three readings. Set it equal to 0.01 for the p99. Set t to your acquire timeout and it is the fraction of callers that fail. Integrate it and you get the mean back — which the test asserts as an identity at 1e-9, by Simpson’s rule, so the quantiles and the mean cannot disagree.

That exponential tail is the shape of the hazard here. At ρ = 0.833 the p99 wait is 6.06× the mean, and at a 250 ms acquire timeout 0.47% of callers fail — a number that looks like a rounding error right up until slot 6 does something with it.

Capacity is a minimum, so a big pool raises nothing

capacity = min(instances × poolSize, backend parallelism) ÷ holding time

32 connections ÷ 25 ms = 1,280 rps. So does 800 connections, because the backend’s 32 workers are the other term. Twenty-five times the sockets, identical capacity, identical latency.

This is the sentence that makes oversizing a specific mistake rather than a wasteful one. A pool above the backend’s parallelism has no steady-state cost at all — and no benefit. What it removes is the cap. Below the ceiling, a bounded pool and an unbounded one are indistinguishable; above it, they are different failures.

What “the queue moved to the backend” costs, exactly

A pool queues FIFO in front of c connections. A database does not: it time-slices everything admitted, so n in-flight requests share the workers and each takes n ÷ workers times as long, plus a contention term for the context switching, lock traffic and cache pressure that concurrency itself creates. Model that term as 1 + κ·(n − workers)/workers — κ is a knob in src/sim/pool.mjs, not a measurement of your database — and the throughput curve min(n, workers) ÷ (W · inflation) peaks at exactly n = workers and falls beyond it. The test finds that peak by scanning the curve rather than trusting the algebra.

Hold the work in flight constant at 100 requests and choose where to put it:

The honest bound on this claim is in the same test: at κ = 0 the two rows are identical. If extra concurrency were free, moving a queue would be free.

Above the ceiling the difference stops being a factor and becomes a kind. At 1,400 rps against a 1,280 rps ceiling — 9% over — a fluid model of the same station says:

The collapse happens between 32 and 800, so only a cap at or below the backend’s parallelism protects it — and the test asserts that too, the first version of that assertion having expected 1,280 rps from the 800-connection case before the model returned 98.

A pool is per process, so N of them are not one of them

Two separate penalties come out of sharding, and the first is the one people know about:

The backend sees instances × poolSize. Eight instances of 100 is 800. That product is in no configuration file. It changes when the deployment scales, when an autoscaler reacts to CPU, when someone runs a one-off job with the same library defaults.

And N private pools wait longer than one shared pool of the same total size. Same connections, same ρ, different wait, because an idle connection in instance three cannot serve a caller queued in instance five:

24 connections, 800 rps, 25 msMean wait

18.8×, from nothing but the arrangement. Matching the shared pool with private ones takes 5 each — 40 connections instead of 24, 67% more sockets for the same latency. This is why an external pooler helps without adding a single connection: it turns N small pools into one large one.

Keep-alive: the break-even, and the timeout that undoes it

Reusing a connection is only worth something if it is reused enough to spread the setup over. Setup S amortised over r requests is S/r per request, so requiring that to be at most a fraction f of the useful work gives the break-even directly:

break-even reuse = setup ÷ (target overhead × service time)

An 80 ms handshake — two round trips at 40 ms — on a 30 ms call, at a 10% overhead target: 80 ÷ (0.1 × 30) = 26.7 requests per connection. That is the number the pool has to deliver before keep-alive has paid for itself.

Now the delivery side, which is where the surprise is. A connection dies when it sits idle longer than the idle timeout T. If requests are spread evenly over the pool’s c connections, one connection sees a request every g = c/λ seconds, and with exponential gaps it survives to the next one with probability 1 − e^(−T/g). The number of requests it serves is geometric, so:

expected reuse = e^(T/g), where g = connections ÷ arrival rate

Not the traffic rate — the traffic rate per connection. Graded against a Monte Carlo that draws idle gaps and counts reaps, to within 1.5% at 200,000 trials.

Two things fall out of that exponent and neither is where intuition points:

A larger pool makes keep-alive worse. The same requests spread over more sockets means longer gaps and more reaping, and the required concurrency here is 4 × 0.03 = 0.12, so every one of those 160 connections beyond the first few is doing nothing except diluting the traffic that keeps the others alive. The fix is a smaller pool.

And T/g below ln 2 ≈ 0.69 means the median connection dies before its second request. At 160 connections the gap is 40 s, so any idle timeout under 27.7 s puts you there. The break-even would need 131 s — longer than nginx’s 75 s default, longer than a typical load balancer’s 60 s, and not yours to set if the far end is someone else’s API.

The acquire timeout and the retry policy are one control loop

A caller that waits T_acq for a connection, gives up, and retries has added an arrival at exactly the moment the pool had none to give. So the load is not λ but the solution of

λ′ = λ · (1 + q(λ′) + q(λ′)² + …)

q is the timeout rate at the inflated load — the same exponential tail as before, read at t = T_acq. Solved by iteration in the model, and graded by scanning for the sign change and bisecting, which is a different route to the same root.

At 1,050 rps against a pool of 32 with a 100 ms acquire timeout, the naive calculation says 3.6% of callers time out. Let each of them retry once and the equation has no solution: the retries alone push the load past the pool’s capacity.

Read the direction: a longer acquire timeout is safer, because a short one converts waiting callers into fresh arrivals sooner. That is the opposite of the fail-fast instinct, and it is why the acquire timeout is a system-level parameter dressed up as a client-level one.

There is a second root, and it is the reason a retry storm outlives its cause. At 900 rps the stable solution is 904 rps — a 0.4% amplification, invisible. The equation’s other root is at 1,204 rps, and between the two the residual is negative: any burst that lifts the arrival rate past 1,204 leaves the pool in a region where the retries alone sustain the overload. Load returning to normal does not bring it back.

05

The numbers: what to set it to, and when any of this binds

The sizing rule, in the order to apply it

  1. Measure the holding time, checkout to return, at the percentile you care about. Not the query time.
  2. λW is the floor. Below it there is no steady state.
  3. Add headroom for the tail, not for comfort. The Erlang-C table above is the price list: ρ = 0.83 costs 1.4 holding times of wait, ρ = 0.625 costs 0.21, ρ = 0.42 costs 0.014. Somewhere around 1.5–2× λW the wait stops being a term in your latency budget.
  4. The backend’s useful parallelism is the ceiling. Above it, more connections raise no throughput and remove your admission control. The HikariCP wiki’s formula — (core_count × 2) + effective_spindle_count — is an estimate of exactly this quantity.
  5. Then multiply by the instance count and compare with max_connections. If that fails, the answer is a shared pooler, not a smaller per-instance pool: sharding the pool is what made you need 67% more sockets in the first place.

When does this bind — 100 rps or 100k?

At low load the pool is always oversized and the failure mode is keep-alive, because oversizing dilutes traffic per connection until the idle timeout wins. In the middle band the defaults are accidentally reasonable. At high load the pool stops being the interesting number and the holding time is everything — halving W halves the connections you need, and no configuration change does that.

06

The trade-off: a bounded pool is admission control, and admission control means saying no

Everything above argues for a pool sized at λW with headroom, capped at the backend’s parallelism, shared across instances by a pooler. Here is what each of those costs, because all four have a real bill.

A cap converts latency into errors, and that is the point. Once the pool is a bound, an overload does not disappear — it queues, and past the acquire timeout it fails. At 1,400 rps against a 1,280 rps ceiling the capped configuration holds throughput at 1,280 and leaves 1,193 requests queued at ten seconds behind the 32 it is running; something has to shed them. The alternative was a database completing 6 requests a second. So you have chosen a known error rate over an unknown collapse, and you now need somewhere to put the rejected work: a shed response, a queue with a deadline, a degraded path. This is the same trade as load shedding, and it is the reason the pool is best understood as your outermost admission point rather than as a resource cache.

Which means the acquire timeout is a load-shedding parameter, not a client preference. A short one fails fast for the caller and amplifies for the system: 100 ms with one retry moves the collapse from 1,280 rps to 1,024, costing 20% of capacity. A long one preserves capacity and hides the failure inside your own latency, which is worse for anything with a deadline upstream. There is no setting that is good on both axes; what makes it survivable is bounding the retries rather than the wait — which is what a circuit breaker and a retry budget are for.

A shared pooler buys the 18.8× and charges for it. PgBouncer or RDS Proxy in front of the database turns N private pools into one, and the bill is specific: an extra network hop on every query, a new process to run and fail over, and — in transaction pooling mode, which is the mode that does the useful multiplexing — the loss of anything that assumes a session. Session-level SET, advisory locks, LISTEN/NOTIFY, temporary tables and some prepared-statement patterns stop working, because your next statement may land on a different server connection. That is not a tuning caveat; it is a change to what SQL means in your application.

Sizing to the holding time constrains what you may do while holding a connection. If W is the lever with the most leverage at scale, then the rule “never make a network call while holding a database connection” stops being style advice and becomes a capacity decision. The cost is real: you have to restructure work that was naturally interleaved — read, call, write becomes read, release, call, acquire, write — and you have given up the transactional guarantee that spanned the whole thing. Some of that work belongs in the saga lesson.

And the honest limit of the model. The closed forms here assume exponential holding times and Poisson arrivals. Real holding times are more variable than that, and Kingman’s approximation from the queueing lesson says the wait scales roughly with (ca² + cs²)/2 — so a workload with one slow query class mixed into a fast one waits considerably longer at the same ρ than this lesson’s tables show. The direction of every finding is unchanged and the magnitudes are optimistic. If your holding time has a fat tail, size for the tail: the connections a p99 request holds for 400 ms are not available to anyone during those 400 ms.

07

In the wild

The most widely-read pool-sizing document argues for a small pool, and derives it from these two quantities. HikariCP’s wiki page About Pool Sizing is the reference most Java services are tuned against, and its central claim is counter-intuitive enough that the page exists mainly to defend it: the right pool is small — a few dozen — and enlarging it past the backend’s parallelism makes things worse rather than better. Its formula, taken from the PostgreSQL wiki, is connections = ((core_count × 2) + effective_spindle_count): an estimate of the backend’s useful parallelism, which is the ceiling term in this lesson’s min(). The page also recounts a case from Oracle’s Real-World Performance group in which cutting a large connection pool by more than an order of magnitude improved throughput and response time simultaneously — the numbers are on that page and I have not reproduced them here, but the direction is the one slot 4’s throughput curve predicts: past n = workers, admitting more concurrency reduces the work done.

PostgreSQL’s own documentation puts the multiplication problem in its defaults. max_connections defaults to 100, and each connection is a separate server process with its own memory. So the fleet arithmetic bites early: 8 instances of a 10-connection default pool is 80, and the eleventh instance of an autoscaling deployment is refused — with nothing in any application’s configuration having changed. The PostgreSQL wiki’s Number Of Database Connections page is the community’s answer to exactly this and its recommendation is the pooler, for exactly the reason in slot 4: it is the only way to get one large pool out of many small processes.

PgBouncer is the 18.8× in production, and its documentation is the trade-off. In transaction pooling mode it multiplexes many client connections onto a few server connections, and the manual is explicit that this breaks session-scoped features — the list of unsupported operations is the price of the multiplexing, not a bug in it. AWS’s RDS Proxy and Google’s Cloud SQL Auth Proxy exist in the same role, and AWS’s own framing of the problem is the serverless version of the fleet multiplication: each concurrently-executing Lambda has its own pool, the concurrency is elastic, and so instances × poolSize has no ceiling at all until the database supplies one by refusing connections.

HTTP keep-alive has the same break-even and a worse timeout situation. RFC 9112 makes persistent connections the default for HTTP/1.1 and lets either end close an idle one, which means the reuse count is set by whichever side is more impatient — and it is usually not you. nginx’s keepalive_timeout defaults to 75 s, common load balancers use 60 s, and a partner API’s is whatever they chose. So the 131 s that slot 4’s pool would need is not available at any price, and the only remaining lever is the one the exponent says: fewer connections, so each one is used more often. This is also why many HTTP clients defaulting to an effectively unbounded socket pool is a worse default than it looks — it is optimising the thing that is never the constraint.

And the failure this lesson shares with the retry lesson has a name in every postmortem. “The database was slow” is the conclusion when the queue was in the client, in front of a database that was 62.5% busy. The specific tell, worth putting on a dashboard before you need it, is the pool’s acquire wait histogram next to the backend’s service time histogram. When the first moves and the second does not, no amount of database tuning is going to help, and the fix is a number in a configuration file that Little’s Law will tell you.

Now put the page away

Everything above this line was the Passive rung — necessary, and the weakest thing on offer. Testing yourself on it will feel worse than rereading it and will hold roughly twice as long. That gap between how it feels and what it does is the entire reason this section exists.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • The connections a workload needs is λW — arrival rate × holding time — and that is Little's Law, so a pool above it can never be busier and a pool below it converts a fast backend into an unbounded queue
  • The wait for a connection is Erlang-C shaped: P(wait) climbs towards 1 while the drain rate c·μ − λ collapses towards 0, so the wait does not degrade gracefully and one connection can be worth a factor of six
  • The pool's capacity is min(instances × poolSize, backend parallelism) ÷ holding time, so a pool wider than the backend raises no capacity and lowers no latency — what it removes is the admission cap
  • A pool is per process, so the backend sees instances × poolSize — a product in nobody's configuration file, which crosses max_connections when the deployment scales rather than when anyone edits anything
  • N private pools of c are strictly worse than one shared pool of N·c at the same total, because an idle connection in one process cannot serve a caller queued in another
  • Keep-alive pays only if reuse ≥ setup ÷ (target overhead × service time), and the reuse an idle timeout T delivers is e^(T/g) where g is the per-connection request gap — so a larger pool makes keep-alive worse
  • A caller that times out waiting for a connection and retries adds an arrival exactly when the pool had none to give, so the load at which the pool stops having an equilibrium is strictly below its capacity

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    800 requests a second each hold a connection for 25 ms, across 8 instances with 4 connections each. Callers wait 5.3 ms for a connection. You remove one connection from each instance — 24 in total, still above the 20 the workload needs. What happens, and why is the backend no help in diagnosing it?

    How sure are you, before you look?
    The mean wait goes to 35 ms, 6.6× worse and longer than the 25 ms query it is waiting for; the p99 wait goes from 58 ms to 213 ms. The cause is that ρ per instance went from 0.625 to 0.833 and the Erlang-C wait multiplier C/(c(1−ρ)) moves on both terms at once: the probability of waiting at all rises from 0.32 to 0.70 and the drain rate c·μ − λ halves. The backend is no help because it is doing exactly the same work either way — 20 of its 32 workers busy, 62.5% utilised, in both configurations. Nothing in its metrics distinguishes the good case from the bad one, because the queue is not in it.
    Did you have that?
  2. Cued recall

    A service runs 8 instances with a pool of 100 each against a database with max_connections = 200. At the current load nothing is queueing and latency is 25 ms. Name what is actually wrong, in the two units it is wrong in.

    How sure are you, before you look?
    800 connections for a required concurrency of 20. In sockets: 4× the database's cap, so instance number 3 is refused at startup with nobody having edited a configuration file, and at 9 MB of server-side memory per connection it is 7.03 GB of the database's RAM held to make 20 connections' worth of progress. In admission control: 800 is far above the backend's 32-way parallelism, so the pool caps nothing — and at 1,400 rps against a 1,280 rps ceiling, an uncapped station falls to 6 rps within ten seconds while one capped at 32 holds 1,280 rps and leaves the excess in a queue with a timeout on it.
    Did you have that?
  3. Cued recall

    A partner API is called 4 times a second through a pool of 160 connections, with a 15 s idle timeout, an 80 ms handshake and a 30 ms call. Keep-alive is on and every connection in the pool is healthy. How much of each request is setup, and what is the fix?

    How sure are you, before you look?
    Each connection sees a request every 160 ÷ 4 = 40 s, and a 15 s idle timeout kills it long before that: expected reuse is e^(15/40) = 1.46 requests per connection, so the amortised setup is 80 ÷ 1.46 = 55 ms on a 30 ms call — 183% overhead, on a pool every dashboard reports as warm. Break-even for a 10% overhead is 26.7 requests per connection, which at this pool size needs a 131 s idle timeout that no server will grant. The fix is to make the pool smaller: at 18 connections the same 15 s timeout reaches break-even, and at 20 the overhead is 13%. Shrinking costs nothing, because the required concurrency is 0.12.
    Did you have that?
  4. Cued recall

    The same 24 connections, arranged as 8 private pools of 3 or as one shared pool of 24. Same load, same ρ. Why is the wait not the same, and what is the production form of the fix?

    How sure are you, before you look?
    35.1 ms against 1.86 ms — 18.8×, from nothing but the arrangement. An idle connection in one process cannot serve a caller queued in another, and M/M/c is not N copies of M/M/(c/N): the shared pool has 24 chances to free a connection for the next waiting caller and each private pool has 3. Matching the shared pool's wait with private pools takes 5 each — 40 connections instead of 24, 67% more sockets for the same latency. The production form is an external pooler (PgBouncer, RDS Proxy) in front of the database, which is why it helps without adding a single connection: it converts N small pools into one large one.
    Did you have that?
  5. Cued recall

    A pool of 32 connections can serve 1,280 rps. At 1,050 rps offered, 3.6% of callers exceed a 100 ms acquire timeout and each of them retries once. What is the new timeout rate?

    How sure are you, before you look?
    There isn't one — the fixed point stops existing. Retries make the arrival rate a solution of λ′ = λ(1 + q(λ′)), and at 1,050 rps the retries alone push λ′ past the pool's capacity, so the equation has no root. The cliff is not at 100% of capacity: with a 100 ms acquire timeout and one retry it sits at 1,024 rps, 80% of the pool's 1,280. And the direction surprises people — a longer acquire timeout is safer (1 s moves the cliff to 96%), because a short one converts waiting callers into fresh arrivals sooner. Worse, the equation has two roots: below 1,204 rps the system sits on the stable one, and a burst past it never comes back on its own.
    Did you have that?
  6. Near transfer

    A thread pool of 200 fronts a service whose handlers each make one 40 ms downstream call at 300 requests per second. An engineer proposes raising the thread pool to 2,000 because "requests are queueing". What does the arithmetic say, what will actually change, and what is the real fix?

    How sure are you, before you look?
    The same law with threads for connections. Required concurrency is 300 × 0.04 = 12, so 200 threads is already 17× what the work needs and 2,000 is 167×. Raising it changes nothing about capacity — that is set by whatever the threads are waiting on, exactly as a connection pool's capacity is min(pool, backend parallelism) ÷ hold — and it removes the only admission control in the path, so an overload that used to queue in front of 200 threads now arrives all at once at the downstream service. If requests are queueing at 300 rps with a required concurrency of 12, the holding time is not 40 ms: something is holding a thread far longer than the call takes, and the number to measure is the holding time, not the call time. That is the same trap as a transaction that makes an HTTP request while holding a database connection.
    Did you have that?
  7. Far transfer

    The abstraction is: a shared resource is claimed for a duration, so the number of claim tokens you need is rate × duration — and issuing more tokens than that moves the contention downstream to a place with no queue discipline, while issuing fewer converts a fast resource into a slow queue. Name an instance outside computing.

    How sure are you, before you look?
    Operating-theatre slots in a hospital. Theatres needed = operations per day × hours each ÷ hours open, which is Little's Law; book fewer and surgeons queue while theatres stand empty, book more than the recovery ward can take and the queue moves into recovery, where patients cannot be told to come back later. Restaurant covers. Tables needed = parties per hour × dwell time; overbook and the queue moves from the door — where it is visible, orderly and can be turned away — into the kitchen, where every order slows down together. That is precisely the pool-versus-backend distinction, including the part where the kitchen's throughput falls as its concurrency rises. Library copies are copies = borrows per week × loan period, and the fix everyone reaches for is buying copies while the cheap one is shortening the loan. In every case the tell is the same: someone is tuning the token count when the number that matters is the duration a token is held.
    Did you have that?
