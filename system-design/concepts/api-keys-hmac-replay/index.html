Tier 7 · Security, privacy, compliance API keys & HMAC replay explained well nowhere else

Padding a replay window from a 4.6-minute floor to 15 minutes buys an attacker 3.3× the requests for zero extra false rejects, while the HMAC check underneath it costs 36× less than the signature it replaced

An API key is not a short-lived token with the serial numbers filed off — it is a different trust model, verified by recomputing a keyed hash instead of checking a signature or asking an identity tier anything. That changes which costs are real: HMAC verification is nearly free, so the actual trade-offs move to the replay window around a signed timestamp, and to the fact that a leaked key's exposure has no design ceiling the way a token's does.

Read first — jwt-revocationwebhooksfailure-detection

01

A signature that was never forged, on a key that never expired

An integration partner’s API key turns up pasted into a public bug report — copied into a support ticket along with the rest of a curl command, by someone debugging a webhook that wasn’t firing. It is an HMAC-signed key: every request carries a signature computed from a 512-bit secret only the vendor and this one customer hold, over a canonical string that includes the request body. Nobody downstream could have forged a request with it, and nobody did. The signature was never the weak point.

The key has no expiry. It is valid until someone disables it, and in this fleet the mean time from a leak like this one to rotation is 30 days — fast catches inside a day when a scanner trips, slow ones dragging past six months when the key sits in a low-traffic integration nobody audits. Modelled as a heavy tail rather than averaged away, that 30-day mean means the leaked key is still live a month after the leak with probability 25%, and still live a year later with probability 0.17% — never exactly zero, for the same reason a 15-minute OAuth access token is exactly zero after 15 minutes: only one of those two credentials was given a number that bounds it.

Three questions follow from that one difference, and this lesson prices each of them: what a receiver actually pays to check an HMAC on every request, what stops a captured signed request from being replayed, and what “the key leaked” costs when there is no lifetime to run out the clock on.

02

The signature stops forgery. It does nothing about replay.

The belief this has to break
Our requests are HMAC-signed, so nobody can replay them either.

A signature over a canonical request string — method, path, a timestamp, a hash of the body — proves the request was constructed by someone holding the shared secret, and that not one byte of it has changed since. It says nothing about whether this exact request has been seen before. Capture one valid, signed request off the wire — a compromised logging pipeline, a misconfigured proxy that echoes headers, a browser extension, anything that sees plaintext before or after TLS — and resending it byte-for-byte produces a second signature check that passes for exactly the same reason the first one did: nothing in an HMAC verification asks “have I processed this before.”

The fix is not a better signature. It is a freshness check: the signer includes a timestamp (so the signature covers it — an attacker can’t move the timestamp without invalidating the signature), and the receiver accepts only within a window around its own clock. That window is the entire replay-prevention mechanism, and it has to be sized, not just enabled.

Predict A receiver narrows its accept window from 15 minutes to 30 seconds, to 'reduce the replay attack surface.' A mobile client with a clock 40 seconds fast starts failing every call. What actually went wrong?
The window has a floor set by how far a legitimate request's timestamp can drift from the receiver's clock — clock skew plus one-way network delay — and 30 seconds is below it for this client. The window did not fail to protect anything; it started rejecting real traffic, which is the OTHER way to get this wrong, not evidence that narrower is safer. HMAC's own cost (Slot 4) is unrelated to the window's width.

Three things the rig is for.

The curve only has one interesting feature, and it is not a crossover. Unlike jwt-revocation’s two lines that trade off in both directions, this is a single curve with a floor: below it you are paying in false rejects, above it you are paying in exposure, and the floor itself is the only point paying for neither.

The floor is not a guess. It is failure-detection’s own accuracy/completeness inversion, reused unchanged: “the narrowest safety margin that keeps a target false-positive rate” is the exact same question whether the positive event is a live node declared dead or a live request declared a replay.

Nonce cache and replay budget are the same formula. Both are a population under Little’s Law — arrivals at a constant rate, living for the window’s duration — applied to two different populations: what the receiver must remember, and what the attacker gets to do.

03

The intuition: a wristband nobody has to radio anyone about

A door checks a paper wristband by looking at it — a printed pattern that is genuinely hard to reproduce without the printer. No radio, no lookup, no queue: this is the entire reason wristbands scale to a festival and ID checks against a guest list do not.

That is HMAC. The signature is the wristband’s print — cheap to verify, expensive to forge, checked locally by someone holding only the shared secret to recognise it (a printer template; an HMAC key), never by asking a central desk.

It is also exactly why a photograph of the wristband is a problem the print pattern cannot solve. The photo reproduces the pattern perfectly — it is the same bytes — so whoever printed a copy from it sails through the same check that was supposed to stop forgery, because forgery was never what that check was for. Two fixes exist and only one of them is what most doors actually do:

  • Stamp the entry time on it, and only honour it within a window of “now”. A photo taken and printed an hour later fails the stamp check even though the print is perfect. This is the timestamp-plus-window: cheap, and it degrades to “replayable for the length of the window” rather than “replayable forever”.
  • Tear off a stub, once. A wristband with a stub already torn is refused regardless of timestamp. This is a nonce: single-use, and it is why the window rig above also has to price a cache of stubs already torn — remembering them is not free either.

A shared-secret signature answers “was this constructed by someone who holds the key?” — never “have I seen this exact message before?” Those are different questions, and only a freshness check (a window, a nonce, usually both) answers the second one.

04

The mechanism: a cheap check, a floor, and a formula reused three times

Verification cost. HMAC-SHA256 is one keyed hash over the canonical string — no handshake, no certificate chain, no public-key operation. Measured via node:crypto the same way tlswire.mjs measures RSA and ECDSA: a fixed per-call cost plus a per-byte rate.

hmac(bytes) = 0.79 µs + 0.295 ns × bytes

At 500 bytes that is 0.94 µs — about 36× cheaper than an ECDSA-P256 verify and 11× cheaper than an RSA-2048 verify, both reused unchanged from tlswire.mjs’s own measured table. There is no connection state to amortise a cost into and none to pay for: the cost is purely per request.

The replay window’s floor. failure-detection’s detector.mjs already defines “the margin needed to hold a target false-positive rate, given a delay distribution’s mean” as a closed-form inversion of its survival function. Reused here unchanged, because “how late can a live node’s heartbeat be before it is wrongly declared dead” and “how late can a live request’s timestamp be before it is wrongly declared a replay” are the same question:

floor = marginFor(targetRate, meanDelay)

meanDelay is the mean of (clock skew + one-way network delay), and targetRate is the false-reject rate you are willing to accept for a legitimate but slow client. Nothing about signing, key length or algorithm appears in it — the floor is a property of the network and the clocks, not the credential.

Everything past the floor, priced by the same law twice. A nonce cache — the set of signatures a receiver must remember to catch a replay inside the window — is a population under Little’s Law: arrivals at the legitimate request rate, held for the window’s duration. An attacker’s budget with one captured signature is the identical formula with the attacker’s own request rate substituted in.

population = λ · W

Reused from kernel.mjs’s littlesLaw, the same function webhooks reuses for a sender’s retry-queue depth. Here it answers two questions with one formula: how many nonces a receiver holds, and how many requests a captured signature is worth.

At 150 ms — ordinary NTP-over-the-public-internet skew plus typical request latency, the range clocks calls “tens of milliseconds, occasionally far worse” plus transit time — the 4.6-minute floor lands within a factor of two of a real, published production default: Stripe’s webhook signatures use a 5-minute tolerance out of the box (Slot 7). That is not evidence Stripe derived their number this way; it is evidence the model’s floor is in the right neighbourhood for the traffic it claims to describe.

Padding that floor to a round 15 minutes “to be safe” is where the lesson’s headline number comes from:

Predict An OAuth access token (15-minute lifetime) and an API key (mean 30 days to detect-and-rotate a leak) both leak at the same moment. One day later, what is the probability each credential is still valid?
The token's exposure is a step function: dead with certainty at its 15-minute lifetime, so it is exactly 0% a day later, not approximately. The API key's exposure is a survival function with a 30-day mean and no ceiling — one day is short relative to a 30-day mean, so it is still valid with effectively 100% probability. The interesting divergence shows up at 30 days, not one, which the rig below plots directly.

The pareto-tail invariant is worth sitting with on its own: a credential with a 30-day mean detection time still has a one-in-four chance of being live at exactly 30 days. A mean is not a deadline. Only a lifetime is one, and an API key does not have one.

What to set.

  • Compute the floor before choosing a window. marginFor(targetRate, meanDelay) at your actual clock-skew-plus-network-delay is one function call; “15 minutes, rounded, because it sounded safe” is a guess with a real attacker-budget cost attached to it.
  • Do not pad past the floor for safety margin. Every extra minute buys the same false-reject rate you already had and multiplies the nonce cache and the replay budget for nothing — this is the one direction in this lesson with no offsetting benefit at all.
  • Bind the nonce, not just the timestamp, if the operation is not naturally idempotent. A window alone stops a replay from working forever; only remembering which signatures have already been used stops it working twice inside the window.
  • Treat “detect and rotate faster” as thinning a tail, not moving a wall. It is real and worth doing, and it will never turn an API key’s exposure into a step function — only scoping the key down (least privilege) or giving it a forced maximum age does that.
  • When the trust model is service-to-service and long-lived, price the credential’s blast radius, not its verification cost. HMAC’s own cost is a rounding error next to either of the other two numbers in this lesson.
06

The trade-off: cheap to check, priced somewhere else entirely

HMAC verification is nearly free, and that is not a minor footnote — it is why the other two costs are where the real design decisions live. If checking a signature cost even a tenth of a millisecond, at real gateway request rates that alone would be worth a lesson. It doesn’t, so it isn’t: the entire “is this credential cheap to check” question this lesson opened with resolves to “yes, trivially” in Slot 4, and the two axes that remain — the window and the blast radius — are where every real incident in Slot 7 actually happened.

The window has a floor, not a crossover. Unlike jwt-revocation’s stateless-versus-session trade-off, there is no argument for a window wider than the floor: nothing improves past it, and the nonce cache and replay budget only grow. The only genuine trade-off is at the floor — narrower rejects real traffic, and that is the one direction with an actual cost on both sides.

Blast radius is not a trade-off at all — it is a missing knob. An OAuth access token trades load against exposure because both ends of that trade are chosen at issue. An API key has nothing chosen at issue: its exposure is whatever a detection process happens to take, and “happens to take” is a survival function, not a decision. The fix is not a better window or a cheaper check — it is either a forced maximum age (turning the API key into a token with extra steps) or accepting that the blast radius is unbounded and scoping what a single key can reach.

07

In the wild

Stripe’s webhook signatures are the cleanest public illustration of the window itself. Each Stripe-Signature header carries a timestamp and an HMAC-SHA256 over timestamp + "." + payload, so the timestamp is inside what is signed and cannot be moved without invalidating the signature. Stripe’s own libraries default to a 5-minute tolerance, and their docs are explicit about why the check exists at all: “A replay attack is when an attacker intercepts a valid payload and its signature, then re-transmits them … If the signature is valid but the timestamp is too old, you can have your application reject the payload,” adding “Don’t use a tolerance value of 0. Using a tolerance value of 0 disables the recency check entirely.”

AWS Signature Version 4 signs every request with AWS4-HMAC-SHA256 and, per AWS’s own documentation, includes the request date specifically because “including the date and time in a request helps prevent third parties from intercepting your request and resubmitting it later” — the timestamp-in-the-signature mechanism this lesson’s window sits on top of, independently arrived at by a completely different API design.

RFC 2104, “HMAC: Keyed-Hashing for Message Authentication” is the base specification: “a mechanism for message authentication using cryptographic hash functions … in combination with a secret shared key.” Nothing about a replay window is in it — HMAC was never supposed to solve that problem, which is this lesson’s Slot 2 in one sentence.

AWS IAM’s own best-practices guidance names the exact gap a long-lived API key opens: for the use cases that still need one, AWS recommends teams “update the access keys when needed” using access-last-used data, rather than any automatic expiry — because for a long-term credential there isn’t one. The recommendation is a process, not a control.

GitHub’s secret scanning is the automated half of detection, and it is worth reading precisely because it stops short of automatic revocation: “When a partner secret is detected, we notify the provider so they can take action, such as revoking the credential” — GitHub tells the vendor, the vendor still has to act, and GitHub’s own guidance is to “rotate the affected credential immediately” rather than assume the notification alone closes the exposure.

Codecov’s 2021 Bash Uploader compromise is the real-world version of this lesson’s blast-radius table — and the source of its 60-day row, not a coincidence next to it. A Google Cloud Storage credential was used for “periodic, unauthorized access … beginning January 31, 2021,” modifying the uploader script to exfiltrate environment variables from every CI run that used it, until “Codecov secured and remediated the script April 1, 2021”: January 31 to April 1 is exactly 60 days. Codecov’s own account is that it surfaced because a customer noticed the published checksum didn’t match, not because of Codecov’s own monitoring — undetected access to a credential with no lifetime of its own, for exactly as long as this lesson’s least-monitored row assumes.

DDIA has no meaningful coverage of this lesson’s subject. Its only mention of API keys (2nd ed., p.185, in the Encoding and Evolution chapter) is about using one to select an API version for a client, unrelated to authentication, signing or replay — checked directly against the text rather than assumed absent.

Now put the page away

Everything above this line was the Passive rung — necessary, and the weakest thing on offer. Testing yourself on it will feel worse than rereading it and will hold roughly twice as long. That gap between how it feels and what it does is the entire reason this section exists.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • HMAC-SHA256 verification is a keyed hash, not an asymmetric signature — no chain, no handshake, one pass over the bytes — so at realistic request rates it costs a small fraction of one CPU core
  • A signature over a timestamp stops the timestamp being forged; it does nothing to stop the whole signed request being replayed verbatim unless the receiver also enforces an accept window around "now"
  • The window's floor is detector.mjs's own margin-for-a-target-rate inversion, reused unchanged: the narrowest window that keeps a chosen false-reject rate, given the mean clock-skew-plus-network-delay
  • Every millisecond of window above that floor rejects nothing extra and is pure replay opportunity — sized by Little's Law into both a receiver's nonce-cache population and an attacker's request budget
  • An OAuth access token's exposure is bounded by design, a step function that is exactly zero after its lifetime; an API key's exposure is a survival function of a detection-and-rotation delay that has no ceiling at all
  • A heavy-tailed detection delay is still substantially "live" long after its own mean — a power-law (k=2) tail predicts a leaked key has a 25% chance of still being valid at exactly its mean detection time
  • Speeding up detection thins the tail of a distribution that was never bounded; shortening an OAuth TTL moves a wall that was bounded from the start — the two credentials are not the same lever pulled by different amounts

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    At 150 ms of mean combined clock skew and network delay, the floor for a one-in-a-million false-reject rate is about 4.6 minutes. A team pads it to 15 minutes "to be safe". What did they actually buy?

    How sure are you, before you look?
    Nothing on the false-reject side — the rate at 15 minutes is already effectively at the target. What they bought is 10.4 extra minutes of pure replay opportunity: at 200,000 legitimate requests/second the nonce cache a receiver must hold grows from ~54.6M entries to 180M, and a captured signature is worth 3.3× more requests to a patient attacker (75 versus 23, at one request every 12 seconds) — for the exact same protection against a slow, real client.
    Did you have that?
  2. Cued recall

    An API gateway verifies a 500-byte canonical request string on every call, at 50,000 requests/second. What does HMAC-SHA256 cost in cores, and how does that compare to doing the same per-request check with an ECDSA-P256 signature instead?

    How sure are you, before you look?
    About 0.047 cores — under 5% of one CPU — because HMAC is a single keyed hash with no public-key math in it. The same check done as an ECDSA-P256 verify would cost 1.67 cores, 35.7× more, which is tlswire.mjs's own measured verify cost reused unchanged. Verification cost was never the reason to prefer one over the other; the trust model is.
    Did you have that?
  3. Near transfer

    A team already stores an idempotency key per request to make retries safe. They conclude this also stops replay attacks on their HMAC-signed API. Are they right?

    How sure are you, before you look?
    No. An idempotency key is metadata the caller supplies and the server trusts, built to make a benign client's own retries safe — it says nothing about who is allowed to make the request in the first place. A replay is a captured, validly-signed request being resent by someone who was never the caller; if the operation has no idempotency key at all (a GET, a read, anything with no side effect to dedupe), there is nothing for that store to catch, and the request still succeeds again. The nonce/timestamp window is authentication-layer freshness bound into the signature itself; the idempotency key is an application-layer convenience that happens to reuse the same "have I seen this before" shape for an unrelated reason.
    Did you have that?
  4. Far transfer

    The abstraction is: a proof that is cheap to verify locally is exactly as replayable as it is copyable, and only a freshness check bounds how many times a copy works. Name an instance outside computing.

    How sure are you, before you look?
    A paper concert wristband: the print pattern is hard to forge, so security checks it and waves you through without radioing anyone — which is exactly why a photographed and reprinted wristband also gets waved through, unless the wristband is also torn or stamped with a time nobody re-checks. Also: a subway single-ride ticket good until it is punched; a one-time verification code good for ten minutes; a wax seal on a letter, which proves who sent it and not that it hasn't been steamed open and resealed; a hotel key card cut with a validity window baked into its magnetic stripe. The tell is the same shape every time — the check is local and fast specifically because it does not ask a third party, and everything local and fast is exactly as reusable as it is easy to copy.
    Did you have that?

Graded items get a due date on an expanding ladder — 1, 3, 7, 16, 35, 90, 180 days — and land in review mixed with every other lesson's items. Mixed, not grouped: blocking one topic teaches you what its problems have in common, while interleaving forces you to tell them apart, which is the skill that actually fails in an interview and in production. Nothing is marked mastered today — same-day correctness measures how accessible a thing is right now, not how well you learned it.
