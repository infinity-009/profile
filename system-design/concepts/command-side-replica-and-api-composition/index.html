Tier 8 · Architecture and patterns Replica vs. API composition

A four-service composed read's p99 is 253ms — barely past the slowest dependency's own 250ms, not their 350ms sum — while a command-side replica answers the same read at a flat 2ms, until its projector falls behind and staleness reaches 4.3 seconds in 30

A product page needs Catalog's name, Pricing's price, Inventory's stock count and Reviews' rating — four services, four databases, no shared join. There are exactly two honest ways to answer that one read. API composition queries all four live, in parallel, and merges the answers at the gateway: always consistent with each service's current state, because there is no second copy of the data to go stale, but its latency is the MAXIMUM of four different services' own tails and a slow or down dependency means a partial answer, not a clean failure. A command-side replica pre-joins the same four services' data ahead of time, off the write path — `cqrs.mdx`'s read model, fed by four sources instead of one — into one queryable store: a read is a flat lookup regardless of how many services fed it, paid for with `cqrs.mdx`'s own staleness. This lesson prices both sides in the same units and reconciles them against one latency SLA and one staleness tolerance, including the state worth being able to name: neither pattern clears the bar, and the fix is fewer/faster dependencies or a faster projector, not a pattern choice.

01

One product page, four services, and no shared table to join

A product page needs Catalog’s name and description, Pricing’s current price, Inventory’s stock count, and Reviews’ rating. database-per-service.mdx already made the case for why those four live in four separate databases: a shared instance is one migration lockstep and one blast radius for everyone on it. Granted that split, one honest question is left over, and it is this lesson’s whole subject: how does the one page load that needs all four answers actually get them, now that there is no single database to run one join against?

There are exactly two honest answers. Query all four services live, right now, in parallel, and assemble the page from whatever comes back — API composition. Or maintain a separate store that already has all four answers pre-joined, kept current by watching each service’s own change stream — a command-side replica, the same read-model idea cqrs.mdx prices for one source, here fed by four. Neither is a workaround; they are the two structurally different ways to answer a cross-service read once the join itself is gone.

02

What each side actually costs, at query time

API composition’s latency is the MAXIMUM of four different tails, not their sum. Catalog, Pricing, Inventory and Reviews each have their own latency distribution — Inventory’s own p99 is calibrated to 250ms, the slowest of the four (Catalog 20ms, Pricing 50ms, Reviews 30ms). The composed request’s own p99 — the max of all four draws — is 253.41ms: just past Inventory’s own tail, nowhere near the naive 350ms sum of all four p99s. Most requests, Inventory alone is already the slowest leg; the composed number only rises above 250ms for the small chance another dependency is also deep in its own tail at the same instant. fanout.mjs already derived this exact identity — P(max ≤ x) = F(x)ⁿ — for N identical legs (N shards of one service); API composition calls N different services with N different distributions, so composedLatencySurvival generalizes it to P(max ≤ x) = Π F_i(x), reducing to fanout.mjs’s formula exactly when every leg happens to share one distribution.

And it carries a partial-failure risk the replica side has no analogue for. With each service’s own independent failure probability (Catalog 0.02%, Pricing 0.05%, Inventory 0.3%, Reviews 0.02%), the chance that at least one of the four fails or times out on a given composed read is 0.39% — atLeastOneDependencyFails, the same heterogeneous generalization applied to fanout.mjs’s shared-q pAnySlow. A command-side replica’s read is one lookup against one store; there is no dependency list to fail partway through.

03

The intuition: calling four shops live, or a caterer's pre-assembled tray

Ordering a platter from four different food stalls, live, means calling each stall as the order comes in and waiting for all four to finish before the tray goes out. It is always exactly right — whatever each stall has ready right now is what ends up on the tray — but the tray is only as fast as the slowest stall that morning, and if one stall doesn’t pick up, the tray goes out short one item rather than not going out at all.

A caterer who pre-assembles trays ahead of the lunch rush, restocking each section from the same four stalls on a running schedule, hands over a tray instantly regardless of how many stalls feed it — but if a stall delivered nothing since the last restock, that section of the tray is exactly as stale as the last restock, not as fresh as calling that stall would have been. Nothing about either arrangement is a mistake; they are the same two options this lesson prices, dressed as lunch instead of a page load.

04

The mechanism: two reused shapes, generalized once, and one reconciliation

API composition’s max is fanout.mjs’s max, generalized to heterogeneous legs. composedLatencySurvival builds the exact identity fanout.mjs uses for N identical shards — P(max ≤ x) = 1 − Π(1 − S_i(x)) — but does not assume the N legs share one distribution, because Catalog is not Inventory. Feed it four identical survivals and it collapses to fanout.mjs’s own formula exactly (verified directly in the test file); feed it four different services’ own calibrated tails and it prices the real product-page scenario. survivalQuantile, the generic bisection inverter, is reused completely unchanged on top of it — it never assumed identical legs to begin with. atLeastOneDependencyFails does the same generalization to fanout.mjs’s shared-failure-rate pAnySlow.

The replica’s staleness is cqrs.mjs’s staleness, fed by more sources. A command-side replica is the identical projector-falls-behind-its-source mechanism cqrs.mjs already prices for one service’s read model — projectionLagGrowthRate, projectionBacklogOverTime, projectionStalenessSeconds are imported and called unchanged. The only thing genuinely different here is the write-side load feeding the projector: cqrs.mjs fans out from one source into N read models, so this lesson’s replica fans in from N sources into one store — the write rate the projector has to keep up with is the SUM of all four services’ own event rates (2 + 50 + 200 + 5 = 257/s), a plain sum rather than a new mechanism, so it gets no function of its own.

queryTimeVerdict is the new part: a reconciliation, not a new cost. Modeled directly on traffic-shaping-and-hedging.mjs’s reconcile, it takes the two sides’ already-computed numbers — composition’s p99 against a latency SLA, the replica’s staleness against a tolerance — and returns which pattern (if either) actually clears its own bar. Composition never needs read-your-writes routing, because it has no second copy of the data to lag in the first place — needsReadYourWritesRouting called at staleness 0 states that as a fact rather than an assertion.

Two readings. The composed p99 barely moves as services join — it stays anchored near Inventory’s own 250ms tail, because Inventory alone is almost always the maximum — while the naive sum grows without bound, one more p99 added every time. That gap is the entire argument against “just sum every dependency’s p99”: it is not a slight overestimate, it is a fundamentally wrong shape.

That last row is the one worth sitting with: a 100ms SLA and a 50ms staleness tolerance together are not a request either pattern can satisfy as configured, and no amount of arguing about which pattern is “better” changes that — the read needs fewer/faster dependencies or a faster projector, not a different pattern.

06

The trade-off: consistent-and-slow, or fast-and-stale, priced against one read's actual bar

What API composition buys. It is never behind: every read sees each service’s current state, because there is no second copy to fall behind on — compositionNeedsRywRouting is false by construction. It also needs no extra infrastructure: no projector to run, no second store to keep schema-compatible with four upstream services. What it costs is structural, not tunable: the p99 is set by whichever dependency is slowest right now, and a partial dependency failure degrades the read rather than failing it cleanly — 0.39% of reads in this scenario carry that risk.

What a command-side replica buys. A read is one lookup, flat at 2ms here, regardless of how many services fed it — the join cost is paid once, on the write path, not on every read. What it costs is cqrs.mdx’s own bill, doubled up: staleness (the replica is only as fresh as its projector’s last pass) and a real piece of infrastructure to build, run, and keep in schema sync with four upstream sources, whose combined event rate (257/s here) the projector must sustain indefinitely or fall permanently behind.

When each one wins, concretely. A page load with a generous latency budget and a tight freshness requirement — a live trading blotter, an inventory check right before checkout — favors composition: staleness is unacceptable and the dependencies are fast enough to afford calling live. A page load with a tight latency budget and a tolerance for a few seconds of lag — a product page’s star rating, a dashboard’s aggregate count — favors a replica: nobody notices a rating that is 4 seconds old, and nobody tolerates a 253ms page load four times a second. Neither choice is free, and the honest move, queryTimeVerdict’s whole point, is pricing both against the read’s actual bar rather than picking the pattern that sounds more architecturally serious.

07

In the wild

Chris Richardson’s microservices.io pattern catalog names API composition directly as “API Composition” — the pattern of implementing a query that spans several services by invoking each one and combining the results at the composer (a gateway, a BFF, or the client), naming plainly the exact latency-bound-by-slowest-leg and partial-failure trade this lesson prices. Richardson’s catalog names the alternative this lesson’s replica side implements as “CQRS” — the same read-model idea cqrs.mdx already cites Greg Young for — applied here with a replica fed by several services rather than one.

DDIA’s social-network home-timeline case study is the clearest published statement of the replica side’s actual cost: “this process of precomputing and updating the results of a query is called materialization, and the timeline cache is an example of a materialized view… The materialized view speeds up reads, but in return we have to do more work on writes” (Kleppmann, Designing Data-Intensive Applications, 2nd ed., “Case Study: Social Network Home Timelines,” p. 35) — a materialized view fed by one source (a user’s followers) rather than four services, but the identical shape: reads get cheap, writes get expensive, and DDIA’s own term for what happens when one action fans out into many downstream updates — “fan-out” — is the fan-in this lesson’s replica runs in reverse, from four sources into one store.

cqrs.mdx is this lesson’s nearest sibling and does the staleness math this lesson reuses unchanged; the head-to-head against API composition, and the reconciliation against a stated latency SLA and staleness tolerance, are this lesson’s own addition. database-per-service.mdx is the lesson that removes the shared database this one assumes is already gone, and api-gateway-and-bff.mdx is where API composition usually physically runs — at the gateway or BFF layer, not inside the client.

  3. Near transfer

    A team checks that catalog, pricing, inventory and reviews each individually meet their own 100ms p99 SLA, and reasons: "since every one of the four legs is individually compliant, the composed request — which is just the max of the four — must also meet 100ms." Is that right?

    How sure are you, before you look?
    No, and the gap is not small. If all four services are independently calibrated so that each one's OWN p99 is exactly 100ms (each has a 1% chance of exceeding 100ms on any given call), the composed request's actual p99 is 245.8ms — nearly 2.5× the 100ms everyone checked. P(composed request ≤ 100ms) = P(all four ≤ 100ms) = 0.99⁴ ≈ 96.06%, not 99% — so the composed request exceeds 100ms about 3.94% of the time, not 1%. Checking each dependency's own SLA in isolation answers "is this ONE leg compliant," which is a different question from "is the MAXIMUM of all of them compliant" — the same reasoning error `fanout.mjs`'s original max-of-N identity already guards against for identical shards, generalized here to four services that are not even identical.
    Did you have that?
  4. Far transfer

    The abstraction is: answering a question that spans several independent sources either by asking all of them live every time (always current, but as slow as the slowest source and broken by any one source not answering) or by keeping one running answer assembled ahead of time from those same sources (instant to consult, but only as fresh as its last update). Name an instance outside computing.

    How sure are you, before you look?
    A real-estate closing coordinator's checklist, against calling the bank, the inspector and the title company fresh every time a buyer asks "are we ready to close?" Calling all three live is always exactly correct as of that moment — but the answer takes as long as whichever of the three is slowest to pick up, and if the title company's line is busy, the buyer gets a partial answer, not a clean yes-or-no, exactly the way API composition's latency is bounded by its slowest dependency and a down dependency degrades the whole read. The coordinator's running checklist — updated as each party reports in — answers instantly regardless of how many parties there are, at the cost that if the inspector called in an hour ago and nobody updated the sheet yet, the checklist is confidently wrong for that hour, the same staleness a command-side replica carries between projector runs.

    Other instances: a company's consolidated "account status" dashboard, updated periodically from billing, shipping and support systems rather than querying all three live on every page load; and a hospital's patient chart summary, assembled periodically from lab, pharmacy and imaging systems rather than a nurse phoning all three departments fresh before every round.
    Did you have that?
