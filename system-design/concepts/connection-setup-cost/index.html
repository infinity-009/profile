Tier 1 · The network Connection setup explained well nowhere else

Ten times the bandwidth made a 604 ms API call 0.3 milliseconds faster

A request is not one round trip. A cold HTTPS request is four, three of which carry no application data at all — so for a small response the answer arrives when distance says it can, and a wider link changes it by a rounding error. The number worth knowing is how big a response has to get before the bytes cost more than the introductions.

Read first — latency-numbersback-of-envelope

01

604 milliseconds for four kilobytes, and the bytes were 0.32 of them

An internal service in Amsterdam calls a pricing API in California. The endpoint returns a 4-kilobyte JSON document. The API’s own timing says the handler takes 4 milliseconds, and that dashboard has read 4 ms for a year.

The caller measures 604 milliseconds at p50.

Everyone reaches the same conclusion, and it is a reasonable one: the network between the two is too slow, so buy more of it. Both ends are upgraded from a 1 Gbit/s link to a 10 Gbit/s link.

p50 afterwards: 604 milliseconds. Not “a little better” — better by 0.3 milliseconds, which is smaller than the run-to-run variation of a single measurement, so nobody can tell from the graph whether the upgrade happened at all.

Here is where the time went, and none of it is a mystery once you count the right thing. One round trip on that path is about 150 ms — the last row of the latency table. The HTTP client in this service opens a fresh TLS connection for every call, because that is what the library does unless told otherwise. A fresh TLS 1.2 connection over TCP needs four round trips before the first byte of the response arrives:

  • one for TCP’s SYN and SYN-ACK,
  • two for TLS 1.2’s handshake,
  • one for the request and its answer.

Four times 150 is 600 ms. Add the handler’s 4 ms and you have 604. The 4 kilobytes of JSON, at 100 Mbit/s, take 0.32 milliseconds.

The response body was 0.05% of its own response time. The other 99.95% was two machines agreeing on how to talk to each other, and that cost is not made of bytes — it is made of round trips, and a round trip is distance. It has no bandwidth term in it at all, which is why buying bandwidth did not appear on the graph.

Two changes fix it, and neither touches a line of the handler. Enabling TLS 1.3 removes one round trip: 454 ms. Reusing the connection instead of opening a new one removes all three setup round trips: 154 ms. That is 3.9× on a service where nothing was slow.

02

The obvious fix, and why the graph does not move

The mental model almost everyone starts with is that a network is a pipe, that latency is what happens when the pipe is too narrow, and that both are therefore the same purchase. It is a good model for a video stream and a bad one for a request, and the reason is that it collapses two quantities that have different units:

  • Bandwidth is bytes per second. It divides into the size of a thing.
  • Latency is seconds per exchange. It multiplies by the number of exchanges.

A 4 kB response contains almost no size and quite a lot of exchanges, so it lives entirely in the second term. Nothing in setup round trips × RTT can be bought.

The rig below draws one request as a duration, one block per round trip. Before you touch it, commit to a number.

Predict A 4 kB response, on a fresh TCP + TLS 1.3 connection, 150 ms round trip, 100 Mbit/s link. You upgrade the link to 1 Gbit/s — ten times the bandwidth. How much faster does the response get?
Three round trips at 150 ms is 450 ms and contains no bandwidth term, so the upgrade cannot touch it. The only term it touches is the body: 4,000 bytes × 8 ÷ 100 Mbit/s = 0.32 ms, which becomes 0.032 ms. So the saving is 0.29 ms out of 450.32 — 0.064%. The first option is the pipe model, and it would be the right answer for a 100 MB file on the same path, where 10× the link really is worth about 85%. What decides which world you are in is the response size, and this lesson's headline is where the boundary sits. Computed in src/sim/handshake.mjs.
Show it without answering

Four things to do with it, in order:

  1. Drag the link rate from 1 Mbit/s to 10 Gbit/s. Four orders of magnitude. Time to first byte does not change by a single millisecond, because time to first byte has no bandwidth term. The readout for what a 10× upgrade buys reads 0.06%.
  2. Now drag the round trip. At 0.5 ms the 200 ms budget line is off the right-hand end of the axis and the footer tells you by how much — the whole cold request is about a hundredth of a budget. At 150 ms the same three blocks are two and a quarter budgets wide. Same code, same protocol, same bytes, same link.
  3. Walk down the stack list. TLS 1.2 to TLS 1.3 removes one block. resumption, no early data removes none — that is the row worth stopping on. TCP + TLS 1.3 early data removes one and not two. Only QUIC 0-RTT and warm get to a single block.
  4. Now drag the response size up. At 150 ms you have to reach 3.75 MB before the grey block is longer than the amber ones. Almost no API response is 3.75 MB. Set the round trip to 0.5 ms and the same threshold is 12.5 kB, which most responses clear easily — so the pipe model is not wrong, it is a model of the datacentre being applied to the internet.
03

The intuition: one envelope, and a building with an intercom

You have one envelope to deliver, to a flat on the second floor of a building with a locked front door and an intercom.

You press the buzzer. You wait. A voice says “hello?”. You say who you are and who the envelope is for. You wait. The voice says “second floor, come up” and the latch clicks. You climb. You hand over the envelope. It takes two grams of paper and about ninety seconds, and nearly all of the ninety seconds is the conversation.

Now improve it. Widen the letterbox — make it a hundred times wider. Nothing changes; the envelope already fitted. Make the envelope a hundred times heavier and, within reason, still nothing much changes: carrying it up is not what took the time.

Two things do change it. Someone gives you a key, so you skip the intercom entirely and walk straight up — you now deliver in twenty seconds instead of ninety, having changed nothing about the envelope. Or the flat moves to the ground floor of a building you are already standing in, and distance stops mattering.

The key is a connection you already have. Being closer is a CDN or a regional replica. And the letterbox is bandwidth — genuinely useless here, and genuinely the only thing that matters if what you are delivering is a wardrobe rather than an envelope. That switch, from envelope to wardrobe, is a specific size, and finding it is what the rest of this lesson does.

04

The mechanism: everything before the first byte is counted in round trips

Start with the question that makes the counting non-obvious: why does a handshake message cost a whole round trip rather than half of one?

Because each message is a function of the one before it. The client cannot compose its Finished until it has the server’s key share, and it cannot get the server’s key share until it has sent its own and waited. A negotiation cannot be pipelined with itself — that is what distinguishes it from sending data, where you can put the next packet on the wire without hearing about the last one. Each dependency in the chain costs one there-and-back.

So the whole of connection setup is an integer, and the response time follows from it:

time to first byte = (setup round trips + 1) × RTT

setup round trips — everything that must complete before the client may transmit application data. The +1 is the request going out and the first byte coming back, which every request pays, on the warmest connection you have. RTT — one round trip on that path, from the previous lesson. Server processing adds to this and is orthogonal to all of it.

One caution about halves, because this is where the counting usually goes wrong

You will see TCP’s handshake priced at 1.5 round trips: SYN, SYN-ACK, ACK, three one-way flights. That is double counting, and RFC 9293 §3.5 shows why. In its Figure 6 the client’s ACK is the third flight and the client’s first data segment is the fourth, at the same sequence number — and the section states plainly that synchronising the connection with data-carrying segments “is perfectly legitimate”. The ACK and the request leave the client at the same instant. So that third flight is the same flight the request needed anyway; charge it to the handshake and you have billed it twice.

Priced as delay compared with a connection that already existed — which is the only thing anyone can act on — every phase below is a whole number.

Four rows in that table are worth more than the others, because each one contradicts something that gets repeated.

TLS 1.3 resumption does not save a round trip. Figure 3 of RFC 8446 draws the “Subsequent Handshake” and it has the same shape as the full one in Figure 1: ClientHello out, server flight back, client’s Finished and first application data out. What resumption removes is the Certificate and CertificateVerify messages — a signature to verify and a few kilobytes to send. That is CPU and bytes, not latency. It was different in TLS 1.2, where the abbreviated handshake genuinely is one round trip cheaper than the full one, and that is where the belief comes from.

“0-RTT” over TCP is one round trip, not zero. Early data removes the TLS handshake and leaves TCP’s alone, so the request still departs one round trip after the SYN. Only QUIC reaches zero, and it reaches zero for a structural reason: its transport handshake is its crypto handshake, so a 0-RTT packet can be coalesced into the very first UDP datagram alongside the Initial packet. This is the row where treating each protocol as a single constant hides the answer, and adding phases up reveals it — Cloudflare’s own accounting agrees, pricing a resumed TCP connection at “3 RTT + DNS” and a 0-RTT one at “2 RTT + DNS”.

QUIC’s 1 has documented exceptions. RFC 9000 §8.1 forbids a server from sending more than three times as many bytes as it has received before it has validated the client’s address, and §8.1.2 lets it demand validation up front with a Retry packet — Figure 9 in that section draws the extra round trip. Separately, a client only knows to try QUIC if it has been told: the Alt-Svc header that advertises HTTP/3 arrives in an HTTP response, which means over a connection that is not HTTP/3 (RFC 9114 §3.1.1). The HTTPS DNS record exists to break that circularity.

DNS is not denominated in your RTT. It belongs in “before a byte of application data moves”, and it cannot be added to the round trip count, because its round trips go to different machines. One exchange with your resolver — usually near, so usually cheap — and then, on a cache miss, the resolver’s own walk down the delegation chain to servers wherever they happen to be. It is also the one term on this page that an origin’s own metrics cannot see at all.

Notice what the fourth arrow means for the client. TCP has been established since the second arrow; the socket is open, connect() has returned, and every metric that counts connections counts this one. It carries nothing for another two flights. “The connection is up” and “the connection can carry your request” are 300 milliseconds apart, and only one of them is instrumented by default.

05

The numbers: the size at which the bytes start to matter

Here is the 604 ms from the top of the page, decomposed. Three of the five contributions are round trips, and exactly one of those three is immovable.

Where the crossover is

Set transfer time equal to handshake time and solve. Both sides are simple, which is what makes the answer memorable:

crossover bytes = setup round trips × RTT (ms) × 125 × link rate (Mbit/s)

125 is bytes per millisecond per Mbit/s: one megabit per second is 1,000,000 ÷ 8 ÷ 1,000 = 125 bytes every millisecond. Decimal throughout, matching how link rates are quoted.

For a cold TCP + TLS 1.3 connection — two round trips of setup, the ordinary modern case:

Read the middle column. Across an ocean, on a fairly ordinary 100 Mbit/s link, a response has to reach 3.75 megabytes before the bytes cost as much as the handshake did. API responses are kilobytes. Web pages are hundreds of kilobytes. Almost nothing a request-response service returns is on the right side of that line, which is why “the network is slow, buy more network” is such a durable and such an expensive mistake.

Now read across a row instead of down a column, because that direction is the uncomfortable one. The crossover is proportional to the link rate: ten times the bandwidth pushes it ten times further out. Every upgrade you buy increases the range of responses for which the network is entirely round trips. Bandwidth cannot win this argument; it can only widen the region in which it loses.

And read down the first column, because the same arithmetic is what makes the pipe model reasonable inside a datacentre. At 0.5 ms the crossover is 12.5 kB, which an awful lot of responses clear. The pipe model is not a bad model — it is a model of the datacentre, applied at a distance where it stops holding.

Second, and more usefully: the same purchase is worth 15.8% inside a datacentre — 250 times more. This is a result about distance, not about bandwidth. The further away the caller, the less any amount of bandwidth can do for a small response, because the fixed term grows and the variable term does not.

And to be fair to the pipe: on a 100 MB transfer across that same ocean, 10× the link is worth about 85%. Bandwidth is not a bad purchase. It is a purchase that is right for exactly one of the two terms, and most services spend their time in the other one.

No protocol will ever remove the last round trip, because a request that is never answered is not a request. Ten years of transport engineering — TLS 1.3, QUIC, 0-RTT — was worth exactly the three removable round trips, and there is no fifth generation coming that will find a fourth.

Which also means: a warm connection and QUIC 0-RTT are the same number, 150 ms, and the last row achieves it without any of the trade-off in the next slot. Connection reuse is the first thing to check and the last thing to give up.

One number I expected to be different

I wrote the model expecting TLS 1.3 resumption and TLS 1.3 0-RTT to be the same row, and expecting 0-RTT to mean zero. Both were wrong, and the model caught both only because it sums a declared round trip count per phase rather than storing one constant per protocol. Resumption without early data is one round trip — the same as a full handshake — and early data over TCP is one round trip, not zero, because TCP’s handshake is still underneath it. The RFC figures say so plainly once you go and look: RFC 8446 §2.2 Figure 3 and §2.3 Figure 4 have the same number of flights above the client’s application data as Figure 1 does, minus one for the early-data case. A model that stored tls13-resume: 0 would have produced a page of plausible, wrong milliseconds.

Second, smaller surprise: I expected “bandwidth does nothing” to be a general result. It is not — it is 15.8% inside a rack. Stating it as a general law would have been the flattering version and would have been wrong in the one place a reader is most likely to test it.

06

The trade-off: zero round trips is a promise about your handlers

There are exactly three ways to get rid of a setup round trip, and each one bills you.

0-RTT is bought with replayability, and this is not a footnote. RFC 8446 §8 is blunt: “TLS does not provide inherent replay protections for 0-RTT data.” The server-side anti-replay mechanisms in §8.1–8.3 reduce the exposure without closing it, and §8 explains the hole it cannot close. An attacker sends one ClientHello with early data to two zones of the same service. Zone A has the ticket and accepts the data as 0-RTT. Zone B has never seen it, rejects 0-RTT and forces a full handshake. Block A’s ServerHello, the client completes with B, and — being a well-behaved client that retries on a network error — sends the request again. It has now run twice, and nothing at the TLS layer was violated.

So the requirement lands on the application, in normative language. Appendix E.5: “Replayable 0-RTT data presents a number of security threats to TLS-using applications, unless those applications are specifically engineered to be safe under replay (minimally, this means idempotent, but in many cases may also require other stronger conditions, such as constant-time response).” Note minimally. Idempotent is the floor, not the bar — §8 adds that “even operations normally considered idempotent could be exploited by a large number of replays”, meaning timing oracles and rate-limit exhaustion. E.5 also states the client-side rule, and it is a MUST NOT: clients “MUST NOT send messages in early data which are not safe to have replayed and which they would not be willing to retry across multiple 1-RTT connections.” And 0-RTT data is not forward secret, because it is encrypted under the pre-shared key alone.

The consequence is structural rather than cryptographic. Whether a request may go in early data is a fact about the handler at the other end, and no transport layer can look that up. Which is why HTTP had to grow a profile of its own: RFC 8470 permits safe methods only, adds an Early-Data: 1 header so an intermediary knows what it is forwarding, and defines the 425 (Too Early) status code so a server can decline and ask for the request again on the completed handshake. A status code is a large thing for a protocol to add, and it exists because this cannot be solved below the application.

Connection reuse is bought with state, and state has a footprint. A warm connection is a file descriptor, a socket buffer, a TLS session, an entry in every load balancer’s connection table and a timer on both ends. n clients × m upstreams of idle-but-open connections is a real number that runs out of something — usually ports or descriptors on the middle box, and usually at the worst moment. Worse for architecture: a pooled connection is pinned to whichever backend it first landed on, so a long-lived pool quietly defeats load balancing, and a newly deployed instance receives no traffic until connections churn. Reuse is still almost always right; it is not free.

QUIC is bought with a second implementation of everything. UDP is blocked, rate-limited or deprioritised on enough networks that a production client keeps a TCP path as well — so you are now running two transports, and the QUIC one is in userspace, where you pay more CPU per byte and lose the kernel and NIC offloads that TCP has accumulated over thirty years. The Alt-Svc bootstrap means the first connection to an origin is often not the one you optimised. And the anti-amplification limit in RFC 9000 §8.1 puts a real constraint on the server’s first flight: a large certificate chain against a 1,200-byte client Initial can exceed the three-times budget, which is why certificate compression matters more in QUIC than it did in TLS over TCP.

And the honest ceiling: none of this makes the last round trip smaller. Every technique here removes a count. When the count reaches one, the remaining number is distance ÷ (c/n) and the only move left is to change the distance — which is the CDN and edge-replica argument, and which costs a copy of your data and a consistency problem, exactly as the previous lesson said it would. This lesson buys you 4×. The next order of magnitude is not for sale here.

07

In the wild

HTTP had to add a status code for this. RFC 8470, Using Early Data in HTTP (Thomson, Nottingham & Tarreau, September 2018), exists because TLS 1.3’s 0-RTT pushed a security decision up into the application and there was no vocabulary for it. §4 sets the client rule — “clients MAY send requests with safe HTTP methods … in early data when it is available and MUST NOT send unsafe methods (or methods whose safety is not known) in early data” — and §5.2 defines 425 (Too Early): “the server is unwilling to risk processing a request that might be replayed.” If you want one piece of evidence that 0-RTT is not a transport flag, it is that HTTP needed a new status code to hold the consequences.

And here is what a large CDN actually did with it. Cloudflare shipped 0-RTT on 15 March 2017 (Nick Sullivan, Introducing Zero Round Trip Time Resumption). Their answer to the replay problem was not a cryptographic one: “only GET requests with no query parameters are answered over 0-RTT”, plus a size cap and a limit on how long a request can be replayed. A GET with no query string is about the largest set of requests anyone was willing to declare replay-safe by default — which is a useful calibration for how confident to be about your own endpoints.

QUIC’s 1 RTT has a bootstrap problem, and it was worth a DNS record type. Cloudflare’s post of 30 September 2020 on the HTTPS DNS record states the circularity exactly: “HTTP/3 is advertised using the Alt-Svc HTTP header, which is only returned after the browser has already contacted the origin using a different and potentially less performant HTTP version.” Publishing the endpoint in DNS instead — the HTTPS and SVCB record types, RFC 9460, November 2023 — is what lets a first-ever request be HTTP/3. The engineering lesson generalises past QUIC: a protocol that must be discovered over the protocol it replaces cannot be used on the first connection, and the first connection is exactly the one with no warm state to fall back on.

The exception rows in the QUIC spec are the interesting ones. RFC 9000 §8.1.2, Figure 9 draws the Retry exchange, which is a documented, standards-track case where QUIC’s “one round trip” is two — a server that will not spend state on an unvalidated source address makes the client come back first. If you are measuring a QUIC deployment and seeing two setup round trips, that is not a bug report; it is Figure 9.

Where the round trips went next. Two lessons pick up directly from here. Once data is flowing, the rate is not the link rate — it is a window divided by this same RTT, and that is bandwidth-delay-product. And the transfer term above deliberately ignores TCP slow start, which means every crossover size on this page is a lower bound: a real large transfer starts slower than the link and ramps, pushing the crossover further out still. The other direction — what happens when several requests share one connection and one of them stalls — is head-of-line-blocking.

Now put the page away

Everything above this line was the Passive rung — necessary, and the weakest thing on offer. Testing yourself on it will feel worse than rereading it and will hold roughly twice as long. That gap between how it feels and what it does is the entire reason this section exists.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • Time to the first byte of a response is (setup round trips + 1) × RTT — the +1 is the request and its answer, which every request pays, warm or cold
  • The round trip ladder: TCP 1, TLS 1.2 full 2, TLS 1.3 full 1, TLS 1.3 resumption without early data 1, TLS 1.3 early data 0, QUIC first flight 1, QUIC 0-RTT 0
  • A handshake message costs a whole round trip because each message is a function of the previous one, so a negotiation cannot be pipelined with itself
  • TLS "0-RTT" is zero at the TLS layer only — over TCP the SYN and SYN-ACK remain, so only QUIC 0-RTT is genuinely zero
  • Transfer time exceeds handshake time only above handshake-ms × 125 × Mbit/s bytes, which is 3.75 MB across an ocean at 100 Mbit/s
  • Session resumption saves the certificate and the signature, not a round trip — that is CPU, not latency
  • 0-RTT data is replayable and TLS provides no inherent protection, so RFC 8446 requires early data be safe under replay, of which idempotent is the minimum rather than the bar

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A service returns 4 kB of JSON in 4 ms of handler time, and callers 150 ms away measure 604 ms. The team buys ten times the link bandwidth at both ends and the number does not move. Where is the time, and why was the purchase irrelevant?

    How sure are you, before you look?
    Four round trips, of which three carry no application data: 1 for TCP's SYN/SYN-ACK, 2 for TLS 1.2's handshake, 1 for the request and its answer. Four × 150 ms = 600 ms, plus 4 ms of handler. The 4 kB itself is 4,000 × 8 ÷ 100 Mbit/s = 0.32 ms, which is 0.05% of the response — so ten times the link rate removes 0.29 ms of 604. Bandwidth is bytes per second and this cost is seconds per exchange; they are different quantities and only one of them is for sale. The two changes that do work remove round trips: TLS 1.3 takes it to 454 ms, connection reuse to 154 ms.
    Did you have that?
  2. Cued recall

    Two teams both want a round trip back. One migrates to TLS 1.3 and turns on session resumption; the other turns on HTTP keep-alive. Which one gained nothing, and what does the RFC figure show?

    How sure are you, before you look?
    Resumption gained nothing in round trips. RFC 8446 §2.2 Figure 3's "Subsequent Handshake" has exactly the shape of the full handshake in Figure 1: ClientHello, then the server's flight, then the client's Finished carrying its first application data. What resumption removes is the Certificate and CertificateVerify — a signature verification and a few kilobytes, so CPU and bytes, not latency. Keep-alive removes all the setup round trips, because there is no setup. Note the asymmetry with TLS 1.2, where the abbreviated handshake (§7.3 Figure 2) genuinely is one round trip cheaper than the full one — so "resumption saves a round trip" was true in 1.2 and stopped being true in 1.3, which is why the belief survives.
    Did you have that?
  3. Cued recall

    Someone proposes enabling TLS 1.3 0-RTT so the connection costs nothing. What does it actually cost over TCP, and what has the application just promised?

    How sure are you, before you look?
    Over TCP it costs one round trip, not zero: "0-RTT" names the TLS layer, and the SYN/SYN-ACK underneath is untouched. Only QUIC 0-RTT is genuinely zero, because QUIC's transport and crypto are the same handshake and the 0-RTT packet rides in the first UDP datagram. And the promise is large: RFC 8446 §8 states that "TLS does not provide inherent replay protections for 0-RTT data", so Appendix E.5 requires that applications using it be "specifically engineered to be safe under replay (minimally, this means idempotent, but in many cases may also require other stronger conditions, such as constant-time response)". That is a claim about your handlers, which no transport can check — which is why HTTP needed its own profile (RFC 8470: safe methods only, and a 425 (Too Early) status code for declining).
    Did you have that?
  4. Cued recall

    Why does buying a faster link make the handshake a larger share of a small response rather than a smaller one?

    How sure are you, before you look?
    Because bandwidth appears in only one of the two terms. Handshake time is setup × RTT and contains no bandwidth at all; transfer time is bytes ÷ rate and shrinks. So the crossover size — handshake-ms × 125 × Mbit/s bytes — moves up in proportion to the link rate: 3.75 MB across an ocean at 100 Mbit/s, 37.5 MB at a gigabit. Every upgrade widens the range of responses for which the network is entirely round trips.
    Did you have that?
  5. Near transfer

    A batch job copies 50,000 small files to an object store 40 ms away, opening a fresh HTTPS connection per file, and takes 5 hours. The proposal is to move the job to a machine with a 10 Gbit/s uplink. What is the actual bound, what does the arithmetic say, and what are the two fixes?

    How sure are you, before you look?
    The bound is round trips × files, not bytes. Cold TCP + TLS 1.3 is 3 round trips per file, so 50,000 × 3 × 40 ms = 6,000 seconds ≈ 1.7 hours of pure propagation with the files at zero size — and a 10 Gbit/s uplink removes none of it, because none of it is bytes. The two fixes are the same two as in the lesson: reuse the connection, which takes 3 round trips per file to 1 and the total to 33 minutes, and go concurrent, because sequential round trips add and parallel ones do not — 50 connections in flight turns 33 minutes into under a minute. Note which fix is not on the list: making each transfer faster. This is the same shape as the N+1 query problem one lesson back, one layer down: there the repeated cost was a query, here it is a handshake.
    Did you have that?
  6. Far transfer

    The abstraction is: a per-interaction fixed cost that is paid in exchanges rather than in volume, so it falls only by having fewer exchanges or by being closer — never by making the channel wider or each exchange bigger. Name instances outside networking.

    How sure are you, before you look?
    The disk seek. A spinning platter charges per I/O, not per byte, so 4 kB and 400 kB cost nearly the same and the fix was never faster arms — it was sequential writes and larger blocks, which is "fewer exchanges" exactly. Also: a short-haul flight, where check-in, security and boarding are three hours around a 55-minute flight, so a faster aircraft is worthless and people drive instead; warehouse picking, where travel dominates the pick and the answer is batch picking rather than faster trolleys; a surgical theatre, where turnover between cases can exceed the operation, so throughput comes from parallel induction rooms, not faster surgeons; and a doctor's appointment, where a six-minute consultation sits behind a two-week booking. The tell is always the same: the cost does not scale with the size of the thing being moved, so every optimisation aimed at the thing is aimed at the wrong term.
    Did you have that?
