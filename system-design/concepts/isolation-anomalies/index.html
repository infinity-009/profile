Tier 3 · Storage and state Isolation anomalies explained well nowhere else

Oracle's SERIALIZABLE and PostgreSQL's REPEATABLE READ are the same level, and neither name is right

The isolation levels you can name are not the levels you get. Locking REPEATABLE READ and snapshot isolation are incomparable — each prevents an anomaly the other permits — so "at least REPEATABLE READ" is not a safety requirement. And the anomaly snapshot isolation cannot see commits both transactions cleanly, raises no error, and moves no metric.

Read first — replication-lagbtree-vs-lsm

01

Two doctors went off call at the same moment and the rota was empty

An on-call rota with one rule: at least one doctor must be on call. The code enforcing it is four lines and obviously correct:

BEGIN;
SELECT count(*) FROM doctors WHERE on_call = true AND shift = 'friday';
-- if count >= 2, allow it
UPDATE doctors SET on_call = false WHERE name = 'alice' AND shift = 'friday';
COMMIT;

Alice and Bob both open the app at 16:59. Both transactions run that SELECT and both get 2. Both conclude that one other doctor is on call, so it is safe to go off call. Alice’s transaction updates the alice row. Bob’s updates the bob row.

Different rows. No write-write conflict. Nothing to detect.

Both commit. Zero doctors on call. No error was raised. No transaction was aborted, no lock was contended, no deadlock was logged, and no metric moved. The database was running PostgreSQL’s REPEATABLE READ, which is a name that suggests this cannot happen, and the database behaved exactly as documented.

The name is the problem. REPEATABLE READ on PostgreSQL is snapshot isolation, and snapshot isolation permits this. On SQL Server, where REPEATABLE READ is the lock-based level the standard actually describes, the same code is safe — and a different piece of code, one that counted rows in a range, would be unsafe there and safe on PostgreSQL.

02

Run all thirty-five combinations and read the one that says nothing

The belief this has to break
The isolation levels are a ladder: each one prevents everything the one below it prevents, plus more.

They are not a total order. Locking REPEATABLE READ and snapshot isolation are incomparable, which Berenson, Bernstein, Gray, Melton and O’Neil proved in 1995 and which is still absent from most treatments:

  • Locking RR holds a shared lock on every row it reads until the transaction ends. So it prevents write skew and lost update. It takes no range locks, so it permits phantoms.
  • Snapshot isolation reads from one fixed version. So it prevents phantoms and read skew. It has no read locks at all, so it permits write skew.

Neither set of permitted anomalies contains the other. That means “we use REPEATABLE READ or stronger” is not a safety claim — it names a keyword, and the keyword maps to different levels on different engines. Asserted as set non-containment in txn.test.mjs, both directions.

Predict Two transactions each read both doctors, each see 2 on call, and each set a different doctor off call. On PostgreSQL REPEATABLE READ (snapshot isolation), what happens?
Snapshot isolation detects write-write conflicts, and these two transactions wrote different rows. There is nothing to conflict on. Both commit, the invariant both of them checked is now false, and no error, abort, lock wait or metric records it. This is write skew, and it is the one anomaly snapshot isolation cannot see.
Show it without answering

Four things to take from it.

The staircase has a step missing. Every row prevents more than the row above it, until snapshot isolation, which prevents the phantom that locking RR allows and permits the write skew that locking RR prevents. That is the incomparability, visible as a shape.

The first column is empty at every level. Dirty write is impossible even at READ UNCOMMITTED, because write locks are long everywhere. It is the anomaly nobody has heard of precisely because no level permits it — and ANSI SQL left it out of its phenomena, which is the omission Berenson used to show the standard’s list was incomplete.

“Prevented” is three different mechanisms. Blocking, aborting, and a snapshot. Only the third is free. The second is only safe if your code has a retry loop, and code written against a blocking engine does not have one.

Snapshot isolation × write skew is the quietest cell in the table. Two commits, no abort, no block, no error. Every other failure in this repo announces itself somehow.

03

The intuition: both of you looked, and both of you were right

Two people share a car. The rule is that the tank must never be left below a quarter.

Both check the gauge on Friday morning. Both see half a tank. Both reason: there is enough for one trip, and if the other one drives too we would be under a quarter, but they have not driven yet, so I am fine. Both drive. The tank is at an eighth.

Neither of them made an error. Both checked. Both read the gauge correctly. Both drew a correct conclusion about the state they observed. The constraint broke because the state they observed was not the state they acted in, and nothing either of them could have done — looking more carefully, checking twice, checking later — would have caught it, because the other person’s decision had not happened yet at the moment of looking.

This is why the fix is never “check more carefully”. The three fixes that work are the three that change the structure of the situation:

  • Serialise the decision. One of you decides for both. (SERIALIZABLE.)
  • Invent something to contend on. A whiteboard slot for “who is driving today” that both of you must claim. (SELECT ... FOR UPDATE on a row that represents the constraint.)
  • Move the invariant outside both actors. A cut-off valve that physically will not dispense below a quarter. (A database constraint.)

Write skew is not a race to write the same thing. It is two correct reads of a shared condition followed by two writes that never meet. The database has nothing to detect because, at the level of rows, nothing conflicted — and that is why checking harder cannot be the fix.

04

The mechanism: what each level actually holds, and for how long

Every level in the table is a choice about two questions: which version of a row does a read see, and what is held until the transaction ends.

LevelA read seesHeld to end of transaction
READ UNCOMMITTEDthe newest value, committed or notwrite locks
READ COMMITTEDthe newest committed value, per statementwrite locks
REPEATABLE READ (locking)whatever its shared lock is pinningwrite locks + shared locks on rows read
SNAPSHOT ISOLATIONthe version as of transaction startwrite locks, plus first-committer-wins at commit
SERIALIZABLE (SSI)the version as of transaction startthe above, plus read-write dependency tracking

Everything in the anomaly matrix follows from that second column, and two rows of it explain the incomparability:

  • Locking RR’s shared locks on rows read are what stop write skew: the other transaction’s write to a row you read cannot proceed. They say nothing about rows that do not exist yet, which is why a range query can gain a row — the phantom.
  • Snapshot isolation has no read locks at all. A fixed version cannot gain a row, so phantoms are gone. And nothing stops a write to a row somebody else merely read, so write skew is wide open.

05

The numbers: what the keyword buys, per engine

The matrix is not the useful table. This one is, and no engine’s documentation contains it because it requires naming a competitor:

EngineDefaultREPEATABLE READ gives youSERIALIZABLE gives you

SQL ServerREAD COMMITTEDlocking REPEATABLE READtrue serializable

Three things in that table ship bugs.

Oracle’s SERIALIZABLE is snapshot isolation. It permits write skew. Code reviewed and approved on the grounds that it runs at SERIALIZABLE is not protected on Oracle, and the keyword is the strongest one the language has. Asserted directly in txn.test.mjs: permits(ENGINES.Oracle.map.SERIALIZABLE, 'writeSkew') is true.

PostgreSQL and SQL Server give opposite guarantees for the same keyword. REPEATABLE READ is snapshot isolation on one and locking RR on the other, and those are the two incomparable levels. Code correct on either can be wrong on the other, in different ways.

MySQL defaults to REPEATABLE READ, and PostgreSQL to READ COMMITTED. The same application, ported, changes which anomalies it is exposed to without a line of code changing — and it changes in both directions, because MySQL’s RR is snapshot isolation but its SELECT ... FOR UPDATE and UPDATE do a current read against the newest committed data rather than the snapshot, so a read-modify-write inside a REPEATABLE READ transaction can behave like READ COMMITTED.

The bottom two rows are why “just use SERIALIZABLE” is a complete answer only when it comes with “and wrap every transaction in a retry”. Without the retry, moving up a level converts a silent wrong answer into a visible error — which is better, and is not the same as correct.

06

The trade-off: three ways to fix write skew, and one that looks like a fix

SERIALIZABLE catches everything and charges retries. On PostgreSQL this is SSI, which tracks read-write dependencies and aborts a transaction that would create a cycle. Real, correct, and its cost is proportional to contention rather than to load — which means it is nearly free until the day it is not, and the day it is not looks like a spike in serialization failures rather than in latency. Every transaction needs a retry loop.

Materialising the conflict catches one invariant and charges a lock. Add a row representing the thing being constrained — the room-day, the shift, the shared budget — and SELECT ... FOR UPDATE it. Now the two transactions do collide, because you invented something for them to collide on. Precise and cheap. Its weakness is that it lives in code and the next caller can forget it, which is the same weakness as every convention.

A database constraint catches one invariant and cannot be forgotten. Where the invariant is expressible — a unique index, a check, PostgreSQL’s exclusion constraints for overlapping ranges — this is strictly the best answer, because it is enforced regardless of isolation level and regardless of which code path wrote. The limit is expressibility: “at least one doctor on call” is a constraint over a set with a minimum, which is not a check constraint and needs a trigger or a materialised counter.

And the one that looks like a fix: raising the isolation level without checking what that keyword means on your engine. Going from READ COMMITTED to REPEATABLE READ on PostgreSQL does not prevent write skew, and going to SERIALIZABLE on Oracle does not prevent write skew, because both of those are snapshot isolation. This is the failure this lesson exists for: an action that reads as a fix in the diff, in the review, and in the runbook, and changes nothing about the anomaly it was performed to prevent.

07

In the wild

Berenson, Bernstein, Gray, Melton and O’Neil, “A Critique of ANSI SQL Isolation Levels” (SIGMOD 1995) is the source of everything above, and it is thirty years old. It introduced P0 dirty write, showed ANSI’s phenomena are ambiguous under a locking reading and a phenomena reading, defined snapshot isolation, and proved it incomparable with locking REPEATABLE READ. Almost every modern treatment inherits its taxonomy and drops its central result.

PostgreSQL accepts READ UNCOMMITTED and silently gives READ COMMITTED — a documented, standard-permitted behaviour that means the weakest level is unreachable. Its REPEATABLE READ is snapshot isolation; its SERIALIZABLE is Serializable Snapshot Isolation (Cahill, Röhm, Fekete 2008), the first implementation to get serializability at close to snapshot-isolation cost. The docs are unusually honest about needing a retry loop.

Oracle has no REPEATABLE READ at all, and its SERIALIZABLE is snapshot isolation. DDIA singles this out: for years “SERIALIZABLE” in the most widely deployed enterprise database did not mean serializable, which is a large part of why the term is mistrusted.

MySQL / InnoDB defaults to REPEATABLE READ and is the reason the “current read” distinction matters: consistent reads use the snapshot, but UPDATE, DELETE and SELECT ... FOR UPDATE read the latest committed row and take next-key locks. So InnoDB’s RR prevents many phantoms via gap locks — a mechanism the standard does not describe — while its read-modify-write behaviour is closer to READ COMMITTED than its name suggests.

CockroachDB, FoundationDB and Spanner all offer serializable as the only level, on the argument that this table is a permanent source of bugs and the right fix is to delete the choice. They charge retries and, in Spanner’s case, a hardware clock. That is a defensible trade and it is worth noticing that the industry’s newest systems removed the knob rather than documenting it better.

DDIA chapter 7 is the best modern treatment: the on-call-doctors example above is its canonical write-skew case, and its framing — that these are not bugs but the specified behaviour, and the application must supply the guarantee or do without it — is the same position chapter 5 takes on replication lag. Same book, same argument, two chapters apart, which is not an accident: both are cases where a weaker-than-expected guarantee is correct, documented, and named something reassuring.

Model and matrix — the (level, anomaly) grid in this lesson is derived by src/sim/txn.mjs executing all thirty-five combinations, and src/sim/txn.test.mjs (14 tests) asserts the derived grid equals Berenson’s Table 4 cell for cell. The paper is the oracle and the executor is the thing under test — writing the matrix by hand and checking the code against it would let both be wrong together. That direction is what caught my own lost-update schedule being a disguised dirty write.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • Locking REPEATABLE READ and snapshot isolation are incomparable — RR prevents write skew and permits phantoms, SI is the reverse
  • Write skew is two transactions checking the same constraint and writing different rows, so nothing conflicts and the constraint breaks
  • Snapshot isolation permits write skew silently: both commit, nothing blocks, nothing aborts, no error is raised
  • Dirty write is excluded at every level including READ UNCOMMITTED, because write locks are held to end of transaction everywhere
  • PostgreSQL's REPEATABLE READ is snapshot isolation and Oracle's SERIALIZABLE is snapshot isolation
  • The same table cell can be enforced by blocking or by aborting, which is a deadlock strategy versus a mandatory retry loop
  • ANSI SQL's definitions were shown ambiguous and incomplete by Berenson et al. in 1995

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    Why is "we run at REPEATABLE READ or stronger" not a statement about which anomalies you are safe from?

    How sure are you, before you look?
    Because locking REPEATABLE READ and snapshot isolation are incomparable, and both are sold under that name or a stronger-sounding one. Locking RR holds long read locks, so it prevents write skew and lost update but takes no range locks and permits phantoms. Snapshot isolation reads from a fixed version, so it prevents phantoms and read skew but permits write skew. Neither set contains the other. SQL Server's REPEATABLE READ is the first; PostgreSQL's is the second. The phrase names a keyword, not a guarantee.
    Did you have that?
  2. Cued recall

    Describe write skew precisely enough that you could spot it in a code review.

    How sure are you, before you look?
    Two transactions read an overlapping set of rows, both check a constraint over that set, both find it satisfied, and each writes a different row. No two writes touch the same row, so there is no write-write conflict for the database to detect, and the constraint the pair validated is now false. The tell in review is a SELECT that counts or checks something followed by an UPDATE to a row that was not the one counted — booking the last seat, going off call, spending the last of a shared budget, claiming a unique username.
    Did you have that?
  3. Cued recall

    What makes write skew under snapshot isolation harder to find than a lost update?

    How sure are you, before you look?
    Nothing signals. Both transactions commit, neither blocks, neither aborts, no serialization failure is raised, no deadlock is logged, and no metric moves. A lost update under snapshot isolation aborts somebody, so it appears as an error rate you can graph. Write skew appears as data that is quietly wrong, discovered later by a human, with no trace connecting it to the transaction that did it.
    Did you have that?
  4. Cued recall

    Two levels both prevent lost update. Why does it matter which one you use?

    How sure are you, before you look?
    Because they prevent it by different mechanisms with different bills. Locking REPEATABLE READ blocks the second writer on a shared lock — so your code needs no retry logic and your throughput and deadlock rate pay. Snapshot isolation aborts the second committer with a write-write conflict — so your code must have a retry loop, and without one what was a wrong answer becomes a 500. Same cell in the matrix, opposite production incidents.
    Did you have that?
  5. Cued recall

    Which anomaly is impossible at every isolation level, and why has almost nobody heard of it?

    How sure are you, before you look?
    Dirty write — two transactions interleaving writes so the result matches neither. It is impossible everywhere, including READ UNCOMMITTED, because write locks are held to end of transaction at every level. Nobody has heard of it because it never happens, and ANSI SQL omitted it from its phenomena entirely even though excluding it is what every level's implementation already does. Berenson et al. named it P0 and used its absence to show the standard's list was incomplete.
    Did you have that?
  6. Cued recall

    A long analytical query reads a hundred tables under READ COMMITTED. What is wrong with the result, and what is the fix?

    How sure are you, before you look?
    Read skew: each statement sees a fresh committed state, so rows read at different moments can straddle other transactions' commits and the result satisfies no single state the database was ever in. A sum can be off by a transfer that was half visible. The fix is a snapshot — one version for the whole transaction — which is why pg_dump takes one and why long reads belong at REPEATABLE READ on PostgreSQL. Nothing about the query is wrong; the isolation level is.
    Did you have that?
  7. Near transfer

    A booking service checks "fewer than 10 bookings for this room today" then inserts a booking. It runs on PostgreSQL REPEATABLE READ. Two requests arrive at once with 9 bookings present. What happens, and what are the three fixes?

    How sure are you, before you look?
    Both snapshots see 9, both pass the check, both insert different rows, both commit. You have 11 bookings and no error was raised anywhere — this is write skew with a phantom flavour, and PostgreSQL's REPEATABLE READ is snapshot isolation, which permits it. The three fixes, in increasing order of how much they change: (1) SERIALIZABLE, which detects it and aborts one — and now needs a retry loop; (2) materialise the conflict — SELECT ... FOR UPDATE on a row representing the room-day, so the two transactions do collide on one row; (3) a database constraint, if the invariant can be expressed as one — an exclusion constraint here, which is the only fix that cannot be forgotten by the next caller. The trap answer is "add a unique index", which does not work: the rows are legitimately distinct.
    Did you have that?
  8. Far transfer

    The abstraction is: two actors independently verify a shared precondition, each acts on a different resource, and no conflict is detectable because they never touched the same thing. Where else?

    How sure are you, before you look?
    Two people each check the shared calendar, see the other is covering Friday, and both book leave. Two engineers each confirm the other has not deployed, and both deploy. Two threads each check that a pool has capacity and both allocate. Two countries each verify the other is holding reserves. The structural fix is always one of the same three: serialise the decision, invent a shared object to contend on, or make the invariant enforceable by something outside both actors. Checking harder never works, because both actors did check and both were right at the moment they looked.
    Did you have that?
