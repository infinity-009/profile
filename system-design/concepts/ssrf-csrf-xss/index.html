Tier 7 · Security, privacy, compliance SSRF, CSRF, XSS

SameSite=Lax still attaches a session cookie to a cross-site top-level GET, and three independent layers each missing 30% of the time compound down to 2.7%

`injection-at-trust-boundaries` (built alongside this lesson) owns the general principle: untrusted data crossing into a context that executes or interprets it. This lesson is the three specific, NAMED mechanisms that principle shows up as on the web, and each one breaks a DIFFERENT implicit trust assumption. SSRF: the server trusts that a URL it fetches on the user's behalf is safe to reach from the server's own network position. CSRF: the server trusts that a request carrying valid session cookies was actually initiated by the user, not by another site the user's browser also has open. XSS: the server trusts that content it renders back to OTHER users doesn't contain another user's executable script. Same shape — an implicit trust assumption, silently false — three different assumptions, three different fixes, and for each one a real architectural mitigation costed honestly rather than reduced to "add a check".

Read first — jwt-revocationoauth-flows

01

One 'edit profile' feature, three bug reports, three different broken assumptions

A social app ships a profile page with three unremarkable features. Set an avatar by pasting a URL — the server fetches it server-side and stores a resized copy, so it always has a stable copy even if the original disappears. Update a bio through a normal form POST. And the bio, once saved, renders on every visitor’s view of the profile.

Three weeks after launch, three reports land in the same sprint. A security scan shows the avatar-URL fetch can be pointed at the server’s own cloud metadata endpoint and comes back with temporary credentials. A customer’s display name changed after they clicked a link in an email from a site that has nothing to do with the app. Another user’s bio contains a <script> tag that runs in the browser of anyone who views their profile, and it has been live for two days.

Whoever triages this week’s tickets is tempted to file all three under “input validation” and hand them to one engineer. That engineer will spend most of two weeks proving the tickets are not the same bug, because each one is a violation of a different thing the server assumed without ever writing the assumption down:

  • The avatar fetch trusted that a URL is safe to request from wherever the server’s network access reaches — it never occurred to anyone that “fetch this image” and “make an arbitrary request from inside our production network” were the same feature.
  • The bio update trusted that a request carrying a valid session cookie was sent by the user sitting at the keyboard — the browser attaches cookies to a request regardless of which page built it.
  • The bio rendering trusted that stored text stays text — HTML rendered as HTML cannot tell the difference between a sentence a user typed and a script the browser will execute.

Three names for these exist — SSRF, CSRF, XSS — and each has a real, specific, load-bearing mechanism and a real mitigation with a real cost. None of them is “add a check.”

02

The one everybody gets wrong on paper: what SameSite=Lax actually still sends

Predict A state-changing action lives behind a GET endpoint, protected only by a session cookie set with SameSite=Lax — the modern browser default. An attacker's page links to it, and a victim clicks. Does the browser attach the cookie to that request?
`csrfCoverage('lax')` reports `leavesTopLevelGetOpen: true`. Lax withholds the cookie on a cross-site POST, on a cross-site XHR/fetch, and on a cross-site iframe load — 3 of the 4 cross-site contexts, 75% coverage — but a cross-site TOP-LEVEL navigation using a 'safe' method is the one context Lax was deliberately built to still allow, because a normal link click looks identical to an attack from the browser's point of view. CORS is irrelevant here: CORS governs whether a script can READ a cross-site response, not whether a top-level navigation carries a cookie. Only SameSite=Strict closes this — and it has its own cost, covered below.

03

The intuition: a courier, a pre-stamped form, and an announcer who reads everything aloud

SSRF is a courier who will fetch a package from any address you hand them, and bring it back inside the building — including the building’s own supply closet, if you give the courier that address instead. The courier doesn’t check WHERE the address is, only that you asked. Told to build one that refuses “obviously internal-looking” addresses, the courier can still be sent to one that starts outside the building and redirects them to the supply closet once they’re already walking — the courier follows directions given mid-errand exactly the same as directions given at the start.

CSRF is a pre-stamped order form that the company will act on as long as it bears your account number — because normally, only you write your account number on a form. The company never imagined a stranger could copy your account number onto their OWN form and mail it in from anywhere; the form doesn’t prove who filled it out, only that the right number appears on it, which is exactly the confusion a browser attaching a cookie to a request creates.

XSS is a community announcer who reads every posted note aloud, verbatim, to whoever walks up next. The announcer has no way to tell “a message for the next visitor” apart from “an instruction to the announcer” — both are just words on a card. Pin a note that says “and also, announcer, hand the next visitor’s wallet to me,” and the announcer, unable to parse content differently from instruction, does exactly what it says.

Three failures, and notice what’s constant: in every case, something downstream trusted a signal — a destination, a credential, a piece of text — that was never actually proof of what it was trusted to mean.

SSRF, CSRF, and XSS are not the same bug wearing three names. Each is a different implicit trust assumption breaking: a fetch destination’s safety, a cookie’s authenticity, stored content’s inertness. The fix for one says nothing about how to fix the other two.

04

The mechanism: three specific gaps, and the one law they all end at

SSRF redirect coverage = validated hops ÷ total hops

redirectChainExposure. The most common real mitigation mistake: validate the URL the user supplied, then hand it to an HTTP client that follows redirects on its own. Every hop after the first is a URL the validator never saw. At 1 of 5 hops checked, coverage is 20% and 4 hops are open — including whichever one an attacker points at an internal address. Three real fixes exist at different cost: a hostname denylist (cheap, blind to IP literals and to anything a redirect reveals later), resolve-then-check-then-fetch-again (two DNS resolutions, and an attacker who controls the DNS answer with a zero TTL can return a different IP to each one — DNS rebinding), or resolve once and connect to the pinned IP directly (one resolution, no gap to rebind through). ssrfStrategy encodes exactly these three, by resolution count and by what each blocks.

CSRF coverage = blocked cross-site contexts ÷ 4, per SameSite mode

csrfCoverage, built on SAMESITE_MATRIX — a direct encoding of the cookie spec’s own behaviour, not a simulation of it. None blocks nothing (0% coverage). Lax, the modern default since Chrome 80, blocks cross-site POST, XHR/fetch, and iframe loads but NOT a cross-site top-level GET (75% coverage, leavesTopLevelGetOpen: true). Strict blocks every cross-site context, including that one (100%) — at the cost of the FIRST cross-site navigation into a logged-in page arriving logged out, because Strict cannot distinguish “an attacker’s link” from “a bookmark” either. SameSite alone is a network-layer control; an anti-CSRF token adds an application-layer one that doesn’t depend on a cookie attribute at all, at the cost this lesson prices below.

Stored XSS exposure = views/hour × hours until removed

storedXssExposure, deliberately meaningless for reflected or DOM-based XSS. Reflected XSS needs one victim to follow a crafted link — nothing persists, so there is no window to accumulate views in. DOM-based XSS never reaches the server at all; a client script writes attacker-controlled data into innerHTML or a similar sink itself. Stored XSS writes the payload to the database ONCE and it is then served, unattended, to every later viewer — 500 views/hour for 48 hours is 24,000 exposed views from a single write, with zero further action from the attacker. That asymmetry, not just “which sink,” is why stored XSS is treated as categorically worse in every real triage process.

Layered bypass probability = the product of each independent layer’s own miss rate

layeredBypassProbability, reusing correlation.mjs’s parallelFailure UNCHANGED: an attacker gets through N independent layers only if EVERY one misses, which is the identical event to “every replica in a redundant set is down” — P(all miss) = q₁·q₂·⋯·qₙ, whether the qᵢ is a WAF rule or a disk. Three layers each missing 30% of the time compound to 2.7%, not 30%. The catch, priced in Slot 6: this is optimistic exactly when it matters, because it assumes independence.

06

The trade-off: three coverage/cost pairs, and one assumption none of them can skip

SSRF: pinning the resolved IP is the only strategy that removes the gap rather than shrinking it, and it costs the most engineering. A hostname denylist is a one-line check and blind to anything not on the list — an IP literal, an encoded IP, a hostname the list didn’t anticipate. Resolve-then-fetch is a bigger lift and still rebindable. Resolving once and connecting to the pinned IP directly closes the gap by construction, but it means writing (or adopting) an HTTP client that doesn’t do its own second resolution — most language standard libraries don’t expose this as a flag, so it is usually a custom transport, not a config option. The cheapest real addition, independent of any of this: network-level egress control that denies the metadata range and RFC 1918 addresses from wherever the fetch actually runs, so an application bug is not the only thing standing between a user-supplied URL and the internal network.

CSRF: SameSite and an anti-CSRF token protect DIFFERENT things, and most real designs need both. SameSite is free to add and costs nothing but the UX trade-off above (Strict logs out a freshly-arrived cross-site visitor). It does nothing for the one context that still needs a token: state-changing GET, or any request path a future refactor accidentally leaves reachable cross-site. A synchronizer token is real, ongoing storage — 320 MB at 10 million active sessions above — and a double-submit cookie needs none of that storage, at a narrower guarantee: it assumes an attacker cannot SET a cookie on your origin (defeated by a subdomain takeover or a misconfigured sibling app), which is strictly weaker than “cannot READ your cookies,” the guarantee the browser’s same-origin policy actually gives. oauth-flows.mdx already prices a sibling of this exact mechanism — the state parameter exists specifically to stop CSRF against an OAuth callback — and jwt-revocation.mdx’s bearer tokens are CSRF-immune for a structural reason worth naming: a bearer token in an Authorization header is attached by your own JavaScript, not by the browser automatically, so a cross-site form has nothing to forge it with. That’s not a reason to abandon cookies — it trades one class of attack for session-fixation and storage concerns bearer tokens bring instead.

XSS: output encoding is necessary and not sufficient, which is why CSP and Trusted Types exist as a second and third layer rather than a nicer version of the first. Context-aware encoding has to be correct for EVERY sink a value reaches — HTML body, an attribute, a URL, inline JavaScript — and getting even one sink wrong reopens the hole encoding was supposed to close. A strict CSP with per-response nonces blocks any inline <script> that doesn’t carry the nonce, which is real, load-bearing protection against a missed encoding call — but it does nothing for DOM-based XSS, where a client script hands attacker data straight to innerHTML without ever going through a <script> tag CSP would catch. Trusted Types closes exactly that remaining gap, by making the risky DOM sinks themselves refuse a raw string. Each layer is real. None of them is redundant with the others, because each closes a specific hole the others leave open — which is a stronger reason to stack them than “more is safer.”

And the one assumption everything above quietly makes: that the layers are independent. Slot 4’s law is optimistic exactly where teams lean on it hardest. An egress firewall and an app-level allowlist are independent if one team owns the network and a different team owns the code — but if both are generated from the same infrastructure-as-code template, a single bad commit can open both at once. Encoding and a CSP nonce are independent if they come from separate systems — but if the same broken templating library both renders the page and mints the nonce, a bug in it can defeat both simultaneously. correlation.mjs’s common-cause model, the same one correlated-failure.mdx uses for replica placement, prices exactly this: a shared root cause with probability c puts a floor of c·q under the compound bypass rate that no additional independent-looking layer gets below. Counting layers is not the same as counting protection.

07

In the wild

Capital One’s 2019 breach is the reference SSRF incident, and it is also the reason IMDSv2 exists. Per Capital One’s own 2019 disclosure and the U.S. Department of Justice’s criminal complaint against the perpetrator, an attacker exploited a misconfigured web application firewall in front of a Capital One-owned, AWS-hosted application to perform an SSRF request against the EC2 instance metadata service, retrieved temporary IAM credentials for a role with S3 access, and used them to exfiltrate data affecting roughly 100 million individuals in the United States and roughly 6 million in Canada. AWS’s response, announced in November 2019, was IMDSv2: a session-oriented metadata endpoint that requires a PUT request to fetch a token before any metadata GET will be honored — exactly the kind of interaction a typical SSRF (which can only induce a target server to issue a simple GET to an attacker-chosen URL) cannot perform on its own, which is why it’s this lesson’s third named SSRF layer rather than a generic “network firewall.”

SameSite=Lax became the web’s default cookie behaviour in Chrome 80 (February 2020), announced in advance by the Chromium team. Firefox and other major browsers followed with their own Lax-by-default rollouts. The behaviour this lesson’s SAMESITE_MATRIX encodes — Lax still attaching the cookie to a cross-site top-level navigation using a “safe” method — is the browser vendors’ own documented semantics (MDN’s SameSite cookies documentation), not a simulation of them, and is exactly why security guidance treats SameSite as a real, free improvement over no attribute at all and simultaneously insists it is not sufficient on its own.

OWASP’s Cheat Sheet series is the standard practitioner reference for all three, and keeps them as three separate documents on purpose: the SSRF Prevention Cheat Sheet’s core recommendation is network-layer allowlisting over hostname-string denylisting, precisely because encodings and redirects defeat the latter the way this lesson’s redirect-chain example does; the CSRF Prevention Cheat Sheet documents the synchronizer-token and double-submit patterns and their respective trade-offs, covered above; the Cross Site Scripting Prevention Cheat Sheet is built around exactly the sink-by-sink, context-aware encoding this lesson’s mechanism section describes.

DDIA covers the general principle underneath XSS specifically, and does not cover CSRF or SSRF by name — an honest gap, not a stretch. In the “Knowledge, Truth, and Lies” section of Chapter 9, Kleppmann and Riccomini write that “Web applications do need to expect arbitrary and malicious behavior from clients that are under end-user control, such as web browsers. This is why input validation, sanitization, and output escaping are so important: to prevent SQL injection and cross-site scripting, for example” (p. 378), and follow it with “A publicly accessible application must carefully sanitize any user input” (p. 379) — the server-as-authority framing this lesson’s standfirst leans on for why XSS specifically is a trust failure rather than a bug in one function. Searched directly: the book has no passage on CSRF, SSRF, the confused-deputy problem, or the SameSite attribute — those are this lesson’s territory, not DDIA’s.

  • SSRF, CSRF, and XSS are three DIFFERENT implicit trust assumptions failing, not one generic "input validation" bug: SSRF trusts a fetch destination is safe to reach, CSRF trusts a cookie-bearing request came from the user, XSS trusts rendered content stays inert in somebody else's browser
  • Validating the URL a user supplies and then handing it to an HTTP client that follows redirects on its own is a real, common SSRF bypass: at 1 of 5 hops validated, coverage is 20%, and the other 4 hops — including whichever one lands on an internal address — were never seen by the check
  • SameSite=Lax, the modern browser default since Chrome 80 (February 2020), still attaches the cookie to a cross-site TOP-LEVEL GET navigation — a state-changing endpoint reachable by GET is not protected by it at all; only Strict closes that context, at the cost of the first cross-site navigation into a logged-in page arriving logged out
  • Stored XSS is categorically worse than reflected or DOM-based XSS because it has an unattended exposure window — every view between the write and the takedown is exposed with no further action from the attacker, e.g. 500 views/hour for 48 hours is 24,000 exposed views from one payload
  • Independent defensive layers compound multiplicatively: an attacker only gets through if EVERY layer misses, so three layers each missing 30% of the time compound to 2.7%, not 30% — the identical mechanism as independent replicas in `correlation.mjs`'s `parallelFailure`, reused unchanged rather than re-derived
  • That compounding is optimistic: it assumes independence, and layers built on the same broken assumption — the same templating library, the same misconfigured proxy — are not independent; `correlation.mjs`'s common-cause floor (`correlated-failure.mdx`) prices exactly how little redundancy buys once that assumption breaks
  • `injection-at-trust-boundaries.mdx` prices a DIFFERENT mechanism — a request path's sequential boundary crossings, where missing even ONE breaks that hop's protection (a series/AND-of-successes chain); this lesson's layering is redundant defenses aimed at ONE choke point (a parallel/AND-of-misses stack) — same-looking multiplication, opposite architecture

  1. Cued recall

    A team validates a user-supplied avatar URL against a private-IP denylist, then hands it to an HTTP client configured to follow redirects automatically. The client follows 4 more hops and lands on the cloud metadata endpoint. Was the validation function wrong?

    How sure are you, before you look?
    No — the function itself is fine; the architecture around it is the bug. redirectChainExposure({ totalHops: 5, validatedHops: 1 }) returns 20% coverage and uncheckedHops: 4: the check saw hop 0 and nothing past it, because the client's own redirect-follow happens entirely INSIDE the fetch call, after the validation already returned. The attacker doesn't need to supply a bad URL — they supply an ALLOWED one that 302s somewhere the check never looked. Fixing this means either validating every hop's Location header before following it, or removing the gap a different way: resolve once and connect to the pinned IP, which is what ssrfStrategy('resolve-and-pin') does instead.
    Did you have that?
  2. Cued recall

    An app puts a "transfer $100 to this account" action behind a GET endpoint and relies on SameSite=Lax session cookies as its only CSRF defense. A victim clicks an attacker's link. Is the transfer protected?

    How sure are you, before you look?
    No. csrfCoverage('lax') returns leavesTopLevelGetOpen: true — Lax withholds the cookie on a cross-site POST, on a cross-site XHR/fetch, and on a cross-site iframe load (3 of 4 cross-site contexts, 75% coverage), but a cross-site TOP-LEVEL navigation using a "safe" method — which GET is defined as — is exactly the one context Lax was designed to still allow, because that is also what a normal link click or bookmark looks like. Putting a state-changing action behind GET converts "click a link" into "carry out the action", and no SameSite mode short of Strict — which has its own cost — closes that specific hole. The actual fix is architectural: state-changing actions do not go behind GET, full stop, independent of any cookie attribute.
    Did you have that?
  3. Near transfer

    SSRF's redirect-chain gap and CSRF's SameSite=Lax gap both have the same SHAPE — "the check covers less than the attacker can reach." Are they the same underlying bug, fixable the same way?

    How sure are you, before you look?
    No, and treating them as one bug is exactly the mistake that gets both patched wrong. They share a META-pattern — a boundary that looks closed but has an uncovered path around it — but the boundary itself is completely different machinery. SSRF's gap is about which NETWORK DESTINATION a request ends up reaching after the app's own logic has run; closing it means controlling what the server is allowed to CONNECT TO (an egress firewall, a pinned resolution), and no cookie attribute is involved anywhere. CSRF's gap is about whether the BROWSER attaches a credential to a request it didn't initiate from your site; closing it means changing what the COOKIE ATTACHES to (SameSite, a token), and no DNS resolution or redirect is involved anywhere. Recognizing the shared shape is useful for spotting where to LOOK for a coverage gap — it tells you nothing about how to CLOSE the one you find, and reaching for a redirect-chain fix on a cookie bug (or vice versa) is a category error, not a shortcut.
    Did you have that?
  4. Far transfer

    The abstraction is: independent defensive layers compound multiplicatively — a bad outcome needs every layer to miss — but layers that share a hidden common cause are not actually independent, so the compounding promise silently stops applying exactly when a shared design flaw is present in more than one of them. Name a non-computing instance.

    How sure are you, before you look?
    James Reason's "Swiss cheese" model of accident causation (1990). Draw each safety layer in a hazardous system — a pilot's checklist, a maintenance inspection, a warning light, a second pilot's cross-check — as a slice of Swiss cheese: mostly solid, with holes where that specific layer can fail. An accident happens only when the holes in EVERY slice line up at once, which independent, differently-shaped holes make rare — stack four slices and the odds of total alignment fall fast, the same multiplication this lesson runs on security layers. But the model's actual point, the part people forget, is that the holes are not static or independent by assumption: a single organizational failure — the same cost-cutting decision, the same training gap, the same rushed schedule — can drill a correlated hole through several slices at once, which is precisely the common-cause failure this lesson's ConceptMap routes to `correlated-failure.mdx`'s floor. Redundant layers are only as good as the assumption that nothing punches through more than one of them at a time, in security exactly as in aviation safety.
