Tier 0 · Why anything is hard at all Event loops & C10K explained well nowhere else

Ten thousand threads cost 781 MiB, and one blocking call in a hundred costs your event loop 91% of its clock

The two reasons everyone gives for choosing an event loop — threads eat memory, context switches eat CPU — are both off by two orders of magnitude on a modern machine. The reason that is real never gets stated: a loop's whole advantage is that it never blocks, and one synchronous call in one handler takes 11× the throughput off eight cores.

Read first — one-request-end-to-endlittles-lawqueueing

01

You moved to the event loop to hold more connections. Throughput fell by a factor of eleven.

A service does something small per request: parse a JSON body, look one thing up in a cache, write a JSON response. Measured, the handler needs about 200 microseconds of CPU. The box has eight cores, and running eight worker processes with one event loop each, it serves 40,000 requests per second. The arithmetic is exactly as simple as it looks: 200 µs of work, eight cores, 8 ÷ 200 µs = 40,000.

Then a feature ships. One code path — a large file upload, an admin export, a password hash on the signup route — makes a call that does not return for 200 milliseconds and does not yield while it waits. It is on one request in a hundred.

Nobody expects that to matter much. It is 1% of traffic, and the work is I/O, and I/O is what an event loop is supposed to be good at.

Throughput goes to 3,636 requests per second.

Not 39,600, which is what “we lost 1% of requests” would predict. 3,636 — an 11× collapse from a change that touches one request in a hundred. p99 latency goes from microseconds to hundreds of milliseconds. CPU utilisation on the box falls, because the cores are now mostly waiting. Every dashboard says there is spare capacity.

And the same workload, on the same eight cores, running a pool of ordinary operating-system threads instead, still serves 40,000 requests per second. The shape everyone left behind because it “does not scale” is, on this workload, eleven times faster.

That is the lesson. The reasons usually given for preferring an event loop are two, and on a modern machine both are quantitatively wrong. The reason that is real is never stated as the central one, and it is the one that just cost this service 91% of its throughput.

02

The obvious fix is more loops. There is a ceiling with no hardware in it.

The first instinct is that the box is out of loops. One loop is one thread, the machine has eight cores, so run more loops — and if eight is not enough, the collapse is a capacity problem and capacity is something you can buy.

Here is the arithmetic that instinct runs into. The loop has one thread. While a handler is inside a synchronous call, that thread is not available to any other connection. So the blocking duration is not a wait happening off to one side — it is service time, and the loop’s mean service time is:

mean service = s + f × B

s — the CPU your handler needs. f — the fraction of requests that hit the blocking call. B — how long that call blocks. One loop serves 1 ÷ (s + f·B) requests per second.

At s = 200 µs, f = 1% and B = 200 ms that is 200 µs + 2,000 µs = 2.20 ms, so one loop serves 454.5 rps where it used to serve 5,000. And the term that matters is what happens as B grows, because f · B contains no hardware at all:

ceiling per loop → 1 / (f × B) = 1 / (0.01 × 0.2) = 500 requests per second

Not per core. Per loop. Buying a faster CPU shrinks s, and s has already left the equation.

Predict Handler CPU is 200 µs. One request in a hundred makes a synchronous call taking 200 ms. Eight loops on eight cores served 40,000 rps before. What do they serve now?
Mean service is s + f·B = 200 µs + 0.01 × 200 ms = 2.20 ms, so one loop serves 1 ÷ 2.20 ms = 454.5 rps and eight serve 3,636. The last option has the right shape and the wrong number: 1/(f·B) = 500 rps per loop is a floor the ceiling approaches from above as B grows, and eight loops would be 4,000 — the real answer sits below it, because s is still in the denominator. The first option is the instinct this lesson exists to break: the 1% of requests do not cost you 1% of throughput, they cost you 90.91% of the loop's wall clock, because a loop has one thread and cannot do anything else during them.
Show it without answering

Three things to get out of it, in this order:

  • Set how long it blocks to 1 ms. The loop retains 80% of its clean ceiling at f = 0.1%, and there is nothing to see. Blocking is not a category error; it is a quantity, and the quantity is f · B.
  • Drag it to 200 ms. 1% of requests, 90.91% of the loop’s time. The strip labelled of loop time is nearly all crimson while the one labelled of requests is nearly all teal, and the two strips describe the identical population.
  • Now drag event loops from 8 down to 1 and back. The ratio between the loops’ bar and the pool’s bar does not change. Eight times the loops is eight times the ceiling, and eight times a number that is 11× too small is still 11× too small.
03

The intuition: a pharmacist who also answers the phone

One counter, one pharmacist, one queue. Almost every interaction takes about thirty seconds: hand over a prescription, take a bag, done. The pharmacist never stops moving, and the queue never builds, and this is a genuinely excellent way to run a counter — far better than four half-occupied counters, because there is no coordination and no idle staff.

Then the phone rings, and it is an insurance authorisation that takes twenty minutes of hold music.

The pharmacist cannot hand the phone to anyone. There is only one of them. So the queue of thirty-second interactions — each of which needed thirty seconds of actual work — waits twenty minutes. One customer in a hundred phoning does not slow the counter by one percent. It hands the counter over completely, for the duration, once every hundred customers.

An event loop is a single server that is fast precisely because it never waits. Its entire advantage is conditional on that, and the condition is not enforced anywhere. Any call in any handler — yours, your framework’s, a dependency’s, a dependency’s dependency’s — can take it away, and nothing in the type system, the tests or the dashboards will tell you which ones do.

Now notice what the supermarket does about the identical problem. It puts an express lane with a fifteen-item limit next to the normal ones. That is not a faster checkout; it is a bound on B, installed because a lane cannot interrupt a customer halfway through. And what the pharmacy does about it is hire a second person to take the phone — which is a thread pool, and it is why the runtime under Node.js ships with one.

04

The mechanism: three separate arithmetics, and only one of them still binds

“Can one machine hold ten thousand connections?” is three questions wearing one coat. They have different answers, they became untrue at different times, and almost every argument about concurrency models is two people answering different ones.

One: memory, where the famous number computes the wrong quantity

The canonical estimate is: the default thread stack is 8 MiB, ten thousand of those is 78 GiB, so thread-per-connection is absurd. Every number in that sentence is correct and the conclusion does not follow, because ulimit -s is a reservation. The kernel maps the range and charges nothing; physical pages are charged when a page is written. The machine pays for the stack the handler actually dirties.

So the resident cost is 80 KiB per threaded connection against 24 KiB for a loop — a factor of 3.33, not a factor of 340. The reservation is 103.05× the resident figure, and that ratio is the entire size of the mistake. In consequences:

Ten thousand threads is five percent of a laptop. The memory argument for event loops was decisively true in 1999 and stopped being the binding constraint some time in the 2000s, and it is still the first argument anyone reaches for.

What actually stopped people in 1999 was neither of these numbers. It was the 32-bit address space. A 3 GiB user split divided by an 8 MiB stack reservation is 383 threads — while the same machine’s RAM would have held 4,915. The reservation was not a memory limit; it was an address-space limit, and it bound at an eighth of the memory limit:

That last row is worth sitting with. pthread_attr_setstacksize to 64 KiB moves the address-space wall by 108× and makes RAM the limit again — a two-line change, available in 1999, that takes a 383-connection server to 4,915. It still does not reach ten thousand on that hardware, which is why the era’s answer was not simply “use smaller stacks”. But it means the memory story was never the clean argument it is remembered as.

Two: scheduling, where the cost scales with the request rate and not the connections

The second argument is that ten thousand threads means the scheduler thrashes. The load-bearing question is what quantity the switch bill actually scales with, and it is not the connection count.

A thread that is blocked on a socket is not runnable. The scheduler does not consider it, does not switch to it, and does not pay for it. Ten thousand idle connections are ten thousand entries that cost nothing to skip. What costs is crossing the CPU, and a request crosses it twice per blocking I/O point — once to give up the CPU, once to be woken:

switches per second = 2 × λ × (I/O waits per request)

λ — requests per second. The connection count does not appear. Ten thousand connections at one request per second and one thousand connections at ten cost the scheduler exactly the same.

The per-switch cost has two parts, and only the second is interesting. The direct part — register save, page-table switch, scheduler bookkeeping — is a hardware constant of about 3.00 µs. The indirect part is refetching whatever of the resumed thread’s working set was evicted while it was away, and it depends on one dimensionless number: how many times over the interleaved footprints overrun the last-level cache. Below that point it is exactly zero:

Two things follow. The threshold is at 1,024 threads sharing the cache — and by Little’s Law the threads sharing a cache are the ones in flight, not the ones that exist. A service at 10,000 rps whose requests spend 5.2 ms in the system has 52 in flight. It is nowhere near the threshold, and adding connections does not move it. And the ceiling is under 10 µs: even past the threshold the cost does not run away, it saturates, because you cannot refetch a footprint more than once.

The thread pool’s context switches — the thing the argument is about — cost one and a half percent of the machine. And the shape that is 20.83× more expensive per wait is the event loop, if it is using the wrong readiness call. Which brings us to the question that was actually hard.

Three: readiness, which is where C10K genuinely lived

An event loop iteration is two steps: ask the kernel which sockets are ready, then run a callback for each. The APIs differ in exactly one way, and it is a complexity class.

  • select() and poll() charge per watched descriptor, per call. The kernel copies the descriptor set in from user space, calls each file’s poll method, and copies results out — whether or not anything happened on it. Call it 100 ns each.
  • epoll (Linux 2.5.44, 2002) and kqueue (FreeBSD 4.1, 2000) charge per ready event. The interest set lives in the kernel and persists between calls, so the cost does not contain the number of registered descriptors at all. That single sentence is the whole of the fix.

The naive conclusion from this is that a poll loop’s CPU grows without bound and eventually the loop cannot keep up. That is not what happens, and the simulation that grades this model is blunt about it. What happens has two regimes with a real connection count between them.

Below the knee the loop finishes an iteration before the next socket is ready, so it goes back to sleep, wakes once per event, and pays the whole descriptor scan for that one event. Cost is linear in the connection count and the loop is genuinely idle part of the time.

Above the knee the scan alone outlasts the gap between events, so every call returns a batch — and the batch is whatever arrived during the iteration that the batch itself sized. That is a fixed point, and solving it gives the surprising half:

iteration = N × c_poll ÷ (1 − events per second × c_event)

The scan share is pinned at 1 − (events × c_event): the same at 10,000 connections and at 50,000. And the iteration length is linear in N.

An O(watched) readiness API does not take throughput away from you. It takes CPU that could have done work — 6.64× epoll’s, for the same 15% of useful work — and it takes delay, proportional to the connection count.

Which finally gives the C10K number as something derived rather than folklore. Hold a one millisecond budget on the delay the loop’s own iteration adds, and invert it:

Not out of memory, not out of CPU, not out of throughput — out of the latency budget it spends re-asking the kernel about sockets that did nothing. That is the C10K problem, and epoll and kqueue ended it in 2000–2002 by deleting the term.

05

The numbers: when each of the three actually matters

The three arithmetics bind at wildly different scales, and the practical value of separating them is knowing which question you are in.

And the rare-and-long corner is the dangerous one, because it is the one that does not show up in a load test: at 0.1% you need a thousand requests before you see it once, and the mean of your latency distribution barely moves while the tail becomes the whole story.

Which is the second cost, and it is worse than the ceiling. The blocking makes the service-time distribution violently uneven — a squared coefficient of variation of 81.82 at 1% and 200 ms, against 0 for a constant handler — and variance is a multiplier on queueing delay. This is queueing’s Kingman term with the variance supplied by your own handler, and it is why the symptom reaching you is almost always “p99 is terrible and the CPU graph is flat” rather than “throughput is capped”.

06

The trade-off: you bought a shape whose precondition nothing enforces

The event loop is not a mistake and this lesson is not an argument for threads. On the workload it was designed for it is the better shape, and the honest statement of what you traded is this: you moved the cost of concurrency from the operating system, where it is charged automatically, to your own discipline, where it is not charged until production.

The row that costs money is the last but one. A thread pool’s failure mode is legible: the queue grows, CPU rises, utilisation goes up, and every tool you own points at it. The loop’s failure mode is a flat CPU graph and a collapsed ceiling, which reads on a dashboard as we have plenty of headroom, and the number that would have told you is not one anybody graphs.

Four consequences worth carrying:

  • A blocked thread releases its core. This is the whole reason the pool wins here. The pool’s CPU bound is cores ÷ s = 40,000 and its thread bound is threads ÷ (s + f·B) = 232,727 at 512 threads, so it binds on cores, and waiting is free. By Little’s Law it only needs 40,000 × 2.20 ms = 88 threads in flight to reach that ceiling — so 512 is generous, and 64 would cap you at 29,091. Sizing a pool is a Little’s Law calculation, not one thread per connection.
  • With nothing blocking, the two shapes are numerically identical — the advantage factor is exactly 1.00×. Every number above is a statement about f · B, and if f · B is zero the comparison has no content. That is the honest half, and it is why the loop is not wrong.
  • f · B is not a property you can audit once. It lives in transitive dependencies: a synchronous fs call, a JSON body big enough that parsing it is 40 ms of CPU, a regex that backtracks, a crypto call, a DNS lookup that fell back to the blocking resolver, a zlib compression on a large response. Every one is one line, and every one is B.
  • The mitigation is a second server, which is a thread pool. This is not a compromise, it is the actual production architecture of every event-loop runtime in use: libuv runs a pool (four threads by default) precisely so that filesystem, DNS and crypto work does not enter the loop’s service time. The express lane needed the item limit.

And the honest ranking of the two arguments this lesson opened with: stop using memory as the reason. At 5% of a laptop for ten thousand threads it decides nothing. Use it when you are holding hundreds of thousands of mostly-idle connections, which is a real and specific architecture — a push gateway, a chat fanout, an MQTT broker — where 24 KiB against 80 KiB is a 3.33× difference in how many machines you buy, and where the connections are idle enough that f · B is near zero by construction.

07

In the wild

Dan Kegel’s C10K page (1999, revised through 2014) is the document that gave the problem its name, and it is worth reading for what it actually says: it is a survey of I/O readiness strategies — select, poll, /dev/poll, real-time signals, kqueue, and later epoll — and of per-thread stack sizing. It is a document about the third arithmetic on this page, not the first two. The framing that survived into folklore, “threads do not scale, use events”, is narrower than the source.

Banga, Mogul and Druschel, “A scalable and explicit event delivery mechanism for UNIX” (USENIX 1999) is the paper that states the complexity argument precisely: select() and poll() cost time proportional to the number of watched descriptors rather than the number of active ones, which is the wrong quantity for a server holding many mostly-idle connections. Their proposed declare_interest() / get_next_event() split — a kernel-resident interest set, plus a call that returns only what happened — is the design that kqueue (FreeBSD 4.1, 2000, Jonathan Lemon) and epoll (Linux 2.5.44, 2002, Davide Libenzi) both implement. The C10K problem has a paper, a fix, and a date.

The event-vs-thread argument has a matched pair of papers, and reading only one of them is how people end up certain. John Ousterhout’s “Why Threads Are A Bad Idea (For Most Purposes)” (USENIX 1996) is the case for events. Von Behren, Condit and Brewer’s “Why Events Are A Bad Idea (for High-Concurrency Servers)” (HotOS 2003) is the reply, and its argument is precisely the one the numbers on this page reproduce: the observed advantages of events came from implementation artefacts of the thread packages of the day rather than from anything intrinsic, and what remains is a control-flow question. Adya, Howell, Theimer, Bolosky and Douceur’s “Cooperative Task Management without Manual Stack Management” (USENIX 2002) is the third piece, and it is the one that names the axis these two were arguing past each other on: task management (cooperative vs preemptive) and stack management (manual vs automatic) are independent choices, and “events vs threads” conflates them.

libuv’s thread pool is the mitigation in production form. Node.js is the canonical single-loop runtime, and it ships a worker pool — four threads by default, UV_THREADPOOL_SIZE — used for filesystem operations, DNS resolution via getaddrinfo, and some zlib and crypto work. The reason is exactly the f · B term: those calls have no portable non-blocking form, so they are moved off the loop rather than allowed into its service time. Anything not on that list — a synchronous crypto call, a large JSON.parse, a backtracking regex — is still on the loop, which is why the practical advice in that ecosystem is phrased as “never block the event loop” rather than as a throughput number.

nginx versus apache is the same story with the roles that are usually quoted. nginx (2004) is an event-loop-per-worker design built directly on epoll and kqueue, and it beat apache’s prefork and worker MPMs decisively on exactly the workload where the third arithmetic binds: many concurrent, mostly-idle, keep-alive connections doing very little work each — static files and proxying, where s is small and f · B is close to zero by construction. That is the event loop’s home ground, and the outcome there is not evidence about a workload with a 200 ms synchronous call in it.

And the historical footnote that undoes the memory argument retroactively: the 1999 wall was the 32-bit address space, at 383 threads on a box whose RAM would have held 4,915. The Linux 2.6 scheduler (2003) removed the run-queue scan that made switch cost grow with thread count — on the 1999 model that term alone took a switch at 383 runnable threads from 3.00 µs to 10.64 µs. Both of the era’s real constraints were fixed by other people, in the kernel and in the hardware, within four years. The one that was never fixed is the one in your handler.

Everything above this line was the Passive rung — necessary, and the weakest thing on offer. Testing yourself on it will feel worse than rereading it and will hold roughly twice as long. That gap between how it feels and what it does is the entire reason this section exists.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A thread per connection costs about 80 KiB of resident memory, not the 8 MiB of reserved stack — the reservation is address space and only physical pages are charged
  • Context-switch cost is driven by the request rate and by how many threads share the cache, never by the connection count; idle connections cost nothing to schedule
  • select() and poll() charge per WATCHED descriptor per call and epoll/kqueue charge per READY event — that difference is the whole of the 2002 fix
  • An O(watched) readiness API does not cost throughput, because the batch grows until the scan amortises away; it costs CPU and it costs delay proportional to the connection count
  • One event loop's ceiling is 1/(s + f·B) where f is the fraction of requests that block and B is how long for, and 1/(f·B) is a floor no hardware removes
  • A blocked thread holds a thread and releases its core, so a pool is bound by cores while a loop is bound by wall-clock occupancy — which is why the pool wins on exactly this workload

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    Someone sizes a 10,000-connection server by multiplying the 8 MiB default stack by 10,000 and concludes they need 78 GiB. Which quantity did they compute, and what does the machine actually get charged?

    How sure are you, before you look?
    They computed address space, not memory. The default pthread stack is an mmap reservation: the virtual range is consumed at thread creation, physical pages only when a page is written. Charged: the pages the handler actually dirties (about 32 KiB), plus the kernel stack (16 KiB, always resident), task_struct and friends (8 KiB), and the socket side (24 KiB) — 80 KiB in total. The reservation is 103.05× the resident figure. Ten thousand threads is 781.25 MiB, which is 5.09% of a 15 GiB machine, and the same box holds 196,608 of them before RAM runs out.
    Did you have that?
  2. Cued recall

    A server holds 10,000 connections that are each idle 99% of the time. How much scheduler work do those connections cause, and what quantity does the switch bill actually scale with?

    How sure are you, before you look?
    The idle ones cause none. A thread that is not runnable is never picked; ten thousand blocked threads are ten thousand entries the scheduler skips. The bill is 2 × λ × (I/O waits per request) — two switches around each wait, one to give up the CPU and one to be woken — so it scales with the request rate, and the connection count does not appear in it. At 10,000 rps with two waits each that is 40,000 switches a second at 6.00 µs per request, which is 1.50% of eight cores. Raising the connection count tenfold to 100,000 changes that figure by nothing at all.
    Did you have that?
  3. Cued recall

    Both a thread pool and a poll loop pay something per blocking I/O point. Write down the two costs, and say at what connection count they cross.

    How sure are you, before you look?
    A thread pays two context switches: 2 × 3.00 µs = 6.00 µs, independent of connections. A poll loop pays the descriptor scan, N × 100 ns, divided by however many sockets that one call found ready. So they cross at N* = 60 × batch: at a batch of 1 the loop is already the more expensive shape at 60 connections, and at a batch of 8 at 480. At 10,000 connections and a batch of 8 the poll loop pays 125 µs per wait against the thread's 6 µs — 20.83× — and wants 250% of the single thread it has.
    Did you have that?
  4. Cued recall

    A poll loop is watching 10,000 mostly-idle connections and top shows it at 100% CPU. You add 40,000 more connections. Predict what happens to CPU, to throughput, and to latency.

    How sure are you, before you look?
    CPU: nothing — it was already 100% and stays there, with the same 85.0% of the thread spent scanning at 10,000 connections and at 50,000. Throughput: nothing, because the event-work ceiling has no scan term in it. Latency: it goes up fivefold, because the loop's iteration is linear in the watched set — 1.18 ms at 10,000 connections and 5.88 ms at 50,000 — and a socket that becomes ready waits about half an iteration before anyone looks at it. The lesson is that CPU utilisation stops being a saturation signal the moment the scan can expand to fill whatever the callbacks leave; the number to watch is the iteration length.
    Did you have that?
  5. Cued recall

    A handler needs 200 µs of CPU. One request in a hundred makes a synchronous call that takes 200 ms. What is the loop's mean service time, its ceiling, and the ceiling that no amount of hardware moves?

    How sure are you, before you look?
    Mean service is s + f·B = 200 µs + 0.01 × 200 ms = 2.20 ms, so one loop serves 454.5 rps and eight serve 3,636 rps against 40,000 with nothing blocking — 9.09% retained. The immovable one is 1/(f·B) = 500 rps per loop: as B grows the ceiling converges on it from above, and there is no hardware term in f·B to buy your way out of. The 1% of requests own 90.91% of the loop's wall clock, which is the whole mechanism — a loop has one thread, so a blocking call is not a wait happening off to one side, it is service time.
    Did you have that?
  6. Cued recall

    The same workload — 200 µs of CPU, 1% of requests blocking for 200 ms — on a pool of 512 threads across 8 cores. What does it serve, what binds, and how many threads are actually in flight?

    How sure are you, before you look?
    It serves 40,000 rps, 11.00× the eight loops, and it binds on cores, not threads: a blocked thread holds a thread and releases its core, so the CPU bound is 8 ÷ 200 µs = 40,000 and the thread bound is 512 ÷ 2.20 ms = 232,727. In flight at that ceiling, by Little's Law: 40,000 × 2.20 ms = 88 threads — so 512 is generous and 64 would not be, since 64 threads caps you at 29,091. And with nothing blocking the two shapes are identical, 1.00×, which is the honest half of the comparison.
    Did you have that?
  7. Near transfer

    A Go service holds 30,000 connections with one goroutine each and is fast. A colleague argues this proves goroutines beat threads because they are cheap — 2 KiB of stack instead of 8 MiB. Grade that argument, and name the property that is actually doing the work.

    How sure are you, before you look?
    The memory arithmetic is real but almost never the binding constraint, and the argument as stated would also predict that OS threads cannot do this, which is false: 30,000 OS threads is 30,000 × 80 KiB = 2,344 MiB resident, and a 15 GiB box holds 196,608 of them. The property doing the work is that the Go runtime turns a blocking call into a scheduling point: when a goroutine blocks on the network the runtime parks it and runs another on the same OS thread, and when it blocks on a syscall the runtime hands that thread to the syscall and brings up a replacement. So Go gets the event loop's "the thread is never idle" without the event loop's "one blocking call stalls everyone" — the property is the runtime's control over the blocking point, not the stack size. The test of that claim is the case where the runtime has no control: a cgo call into a C library that blocks does occupy an OS thread for its whole duration, and that is exactly the f·B term coming back.
    Did you have that?
  8. Far transfer

    The abstraction is: a shared server that handles many clients by never waiting is enormously efficient and completely undefended, because any one client's work can hold the single server for its entire duration and every other client's latency is that duration. Name an instance outside computing.

    How sure are you, before you look?
    The abstraction is cooperative multiplexing on a single non-preemptible server, and its signature failure is head-of-line blocking by an unbounded unit of work. A single-queue pharmacy counter where the pharmacist also takes phone calls: throughput is excellent while every interaction is thirty seconds, and one insurance-authorisation call holds the counter for twenty minutes while a queue of prescription pickups — each ten seconds of work — waits behind it. A supermarket express lane is the same system with the defence installed: the item limit is a bound on B, and it exists precisely because the lane cannot preempt. An operating theatre running a day list, where one complication cascades through every subsequent scheduled case. A single-track railway line with passing loops: capacity is set by the slowest train, not the average one. The structural fix is always one of three, and they are the same three here — bound the unit of work, preempt it, or move it to a second server so the shared one keeps turning. That last one is the thread pool, and it is why libuv has one.
    Did you have that?

Mixed, not grouped: blocking one topic teaches you what its problems have in common, while interleaving forces you to tell them apart, which is the skill that actually fails in an interview and in production. Nothing is marked mastered today — same-day correctness measures how accessible a thing is right now, not how well you learned it.
