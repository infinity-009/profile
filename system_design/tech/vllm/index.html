Tech D · AI-era inference server Apache-2.0 · PyTorch Foundation-hosted since 7 May 2025 — see slot 9

vLLM

A memory allocator with a model attached. Everything it is known for — the throughput, the batching, the prefix reuse — follows from treating the KV cache as pages rather than as one contiguous tensor per request, and everything it fails at follows from the same choice.

The default open serving engine, and the clearest example in this repo of a systems idea winning so completely that its own implementation was deleted. Read it as an allocator: what it hands out, what it refuses, and what it shares between strangers.

Concepts first — llm-inference-phaseskv-cachequeueingbackpressure

01

Why it exists

In 2023, serving a large language model meant one of two things: a research script that ran one request at a time, or a batching server that filled a fixed batch, ran it to completion, and started the next. Both wasted the accelerator, and they wasted it in ways that looked like different problems.

The batching server’s waste was easy to see and hard to fix: a batch finishes when its longest sequence finishes, so seven replies of twenty tokens waiting behind one reply of five hundred leave seven slots idle for 480 steps.

The waste underneath it was much larger and nobody was looking at it. A request’s output length is unknown when it arrives, and the KV cache — the keys and values every generated token must attend over — was allocated as one contiguous tensor sized for the longest reply the model could produce. For a chat workload averaging 400 tokens against a 4,096-token limit, 90% of the allocated cache never held a token. And because the allocation had to be contiguous, the leftovers between allocations were unusable: a server could refuse a request while reporting free memory.

vLLM came out of UC Berkeley with the observation that this is not an attention problem. It is an allocation problem, it was solved for physical memory in the early 1960s, and the solution is paging.

02

The mental model

A memory allocator with a model attached. If you hold one sentence about vLLM, hold that one, because almost every property people attribute to it is downstream of the allocator.

Concretely: the KV cache is a pool of fixed-size blocks (16 tokens is the usual size), and each sequence owns a block table — an ordered list of the physical blocks holding its tokens. A sequence grows by taking one more block when its current one fills. Nothing needs to be contiguous and nothing needs to be reserved in advance.

Read the consequences off that one structure:

  • Concurrency divides by actual length, not declared maximum. For the workload above, 8 GB of cache holds five sequences under contiguous reservation and sixty-one under paging. Same memory, same traffic, different allocator.
  • Continuous batching becomes possible, not just easier. Iteration-level scheduling requires admitting a new sequence between decode steps, which requires being able to hand out memory for it right then, which requires not having to find a contiguous run.
  • Prefix sharing becomes almost free. Two sequences beginning with the same tokens have byte-identical leading blocks, so both tables can point at the same physical blocks. Reference counting keeps that safe; copy-on-write handles divergence.
  • Preemption becomes a policy rather than a crisis. When the pool runs dry mid-generation the engine takes blocks back from a running sequence, either discarding them (re-prefill later) or swapping them to host memory.

And read the costs off it too. A stock attention kernel strides a contiguous tensor; a paged one must gather blocks through a table inside the innermost loop of the hottest kernel in the system. That kernel was the paper’s real engineering content, and the allocator was the easy half.

03

The core data structure

The block table, and the hash that makes blocks shareable.

A block holds block_size tokens’ worth of keys and values for every layer and every KV head. The table is an array of block ids. That is all.

Sharing is where the design gets interesting, because deciding that two blocks are interchangeable is a naming problem. vLLM hashes each block over three things:

IngredientWhy it must be in the hash
The parent hash — the hash of the block before itMakes the hash a name for the whole prefix, not just this block. Two blocks with identical tokens at different positions are not interchangeable.
The block’s tokensThe obvious part.
Extra hashes — LoRA id, multimodal input hash, cache saltEverything else that changes what these tokens mean. The same 16 tokens under a different LoRA adapter produce different keys and values.

Two details in that table carry real weight. The parent hash makes the structure a Merkle chain over the prompt, which is why a prefix match is a single hash lookup rather than a comparison. And the extra hashes are the mechanism by which a shared cache stays correct across tenants — the cache salt in particular exists so an operator can scope sharing, at the cost of the hit rate that made sharing worth having.

Only full blocks are hashed and cached. A prefix that ends part-way into a block cannot share that block, so the effective granularity of reuse is block_size, not one token. The documentation’s own example: two blocks of a three-block prefix hit, the third matches 2 of its 4 tokens and misses entirely — 8 of 12 tokens reused.

04

Production topologies

One process, one GPU. The default. The model’s weights must fit alongside a useful cache; the cache is what is left after weights and activations, and it is what sets your concurrency. --gpu-memory-utilization is the dial, and the honest way to set it is to compute the cache you need rather than to raise it until nothing crashes.

One process, several GPUs — tensor parallel. The weights are split across cards and every card participates in every layer, so there is an all-reduce per layer and the interconnect is on the critical path of every token. Inside one node over NVLink this is routine; across nodes over Ethernet it is usually a mistake.

Pipeline parallel splits by layer instead, which needs far less bandwidth and introduces bubbles. Reach for it when the model does not fit even split across a node’s cards, not as a first choice.

Several replicas behind a router. The scaling unit for real traffic. What makes this different from stateless web scaling is that each replica has its own prefix cache, so a router that balances by least-connections destroys hit rate that a router aware of prefixes would keep. This is the whole argument for a KV-locality-aware gateway, and it is the most commonly missed piece of an LLM serving deployment.

Prefill and decode on separate hardware. The two phases have opposite bottlenecks — prefill is compute-bound, decode is memory-bandwidth-bound — so running them on the same card means one of them is always mis-provisioned. vLLM supports splitting them, and marks it experimental: it provides the KV-transfer interface and depends on third-party connectors (NIXL over RDMA being the main one) for production. Budget for infrastructure work, not a configuration change.

05

The numbers

What runs out first: KV cache memory. Almost always, for a large model on one card. The paper’s own headline is 2–4× throughput at the same latency against FasterTransformer and Orca, and it attributes that to holding KV waste near zero where prior systems wasted the majority.

Work the arithmetic for your own deployment rather than taking a benchmark, because it is four lines and it decides your capacity:

KV bytes per token = 2 × layers × kv-heads × head-dim × bytes-per-element

For a 70B-class model with grouped-query attention — 80 layers, 8 KV heads, 128 head dim, BF16 — that is 320 KB per token. Then:

  • Cache available = card memory − weights − activations. On an 80 GB card with FP8 weights for a 70B model: 80 − 70 − ~2 = 8 GB.
  • Tokens of cache = 8 GB ÷ 320 KB = 24,414.
  • Concurrency = tokens ÷ mean sequence length. At 400 tokens, ~61 sequences. At 8,000 tokens, three.

That last line is the number people are surprised by, and it is why context length is a capacity decision rather than a feature flag. Long contexts are expensive not because the arithmetic is harder but because each request holds a slot for its whole life.

Two rules of thumb worth carrying, both from the arithmetic rather than a benchmark:

  • Block size barely matters. Its only effect is the last partly-filled block, B/2 tokens per sequence. Over 8 to 32 tokens that is 1–4% of a 400-token mean. The allocator is worth 12×; the block size is worth single digits.
  • Prefix reuse is worth what your traffic gives it. A shared system prompt or an agent scratchpad makes it the largest remaining lever; RAG, where retrieved context differs per request, makes it nearly a no-op. Measure mean shared prefix ÷ mean sequence length before believing either.
06

Capabilities — what you actually build with it

The matrix above is dense because vLLM’s surface is genuinely broad, so the useful reading is which entries are caveats and why.

Prefix caching is a caveat because of block alignment and key correctness, not because it is half-built. Aligning your prompts so the stable part comes first and ends on a block boundary is a real, cheap optimisation that most callers never make.

Speculative decoding is a caveat because of regime. It converts idle compute into tokens, and at high batch there is no idle compute — decode has become compute-bound. A drafter that improves single-user latency in staging can reduce throughput in production, with no code change between them.

Quantisation is native and the list is long, which is exactly where to be careful: accepting a format is not the same as having a fast kernel for it on your card, and neither is the same as your task tolerating the loss. Treat the list as “will load” and measure the rest.

Disaggregated prefill is a caveat because it is infrastructure. The interesting part is not vLLM’s side of it but the KV transport, and that is a third-party connector, an RDMA fabric and a router that knows which instance holds what.

07

How it fails

The prefix cache leaks through timing. A request whose prefix is cached skips prefill and returns its first token measurably sooner, so time-to-first-token is a channel for “has someone recently sent this text”. This is not hypothetical and it is not a vLLM defect specifically — Gu et al. (ICML 2025) audited production APIs and found cross-user cache sharing in seven providers. vLLM’s own docs state the sharper version for the hash: faster non-cryptographic hashing carries “increased risk of hash collisions, which can cause undefined behavior or even leak private information in multi-tenant environments.” SHA-256 has been the default since 0.11. If you serve multiple tenants, the salt is the control, and it costs you hit rate.

A shared block is pinned by its slowest reader. Reference counting is correct and it is also a retention mechanism. One long-lived agent session holding a 12,000-token prefix keeps ~750 blocks resident for its whole life, including while it is idle waiting on a tool call. Concurrency that looked available is held by whichever request is slowest to finish.

Preemption turns into a latency cliff, silently. When the pool runs dry the engine takes memory from a running sequence. Recompute costs a second prefill; swapping costs two PCIe transfers. Both are invisible in a throughput graph and both land squarely in the tail. If p99 time-per-output-token degrades under load while utilisation looks fine, look at the preemption counter before anything else.

Long contexts silently collapse concurrency. Nothing errors. The scheduler simply admits fewer sequences, throughput falls proportionally, and the cause is upstream in whatever started sending 16k-token prompts. Alert on admitted concurrency, not just on latency.

Every replica has its own cache, and a naive load balancer wastes it. Round-robin across four replicas turns a 90%-hit workload into roughly a 25%-hit workload. This is a routing bug that presents as a model-serving performance problem.

Version churn is real. Between v0.24.0 and v0.26.0 — under two months in mid-2026 — the default execution path changed to Model Runner V2 for all dense models and the legacy attention implementation was deleted. Pin the version and read release notes before upgrading; this is a fast- moving project with a small compatibility surface, not a database.

08

When not to use it

When you are calling an API. If a hosted provider serves the model you want at a price you accept, you are buying someone else’s answer to every problem on this page, and their prefix caching is already priced into your input tokens. Self-hosting is a decision about control, data residency, unit economics at scale, or a model nobody hosts — not about performance you cannot otherwise get.

When your model is small and your traffic is light. A 7B model at short context fits hundreds of sequences on one card; every waste described here is real and none of it binds, because compute becomes the limit first. A simpler server will not be measurably worse and will be much easier to operate.

When you need one request as fast as physically possible and nothing else. vLLM’s design optimises aggregate throughput under concurrency. For a single-stream latency target with no other traffic, an engine specialised for that — or the same model on a smaller, faster-per-token deployment — can win.

When you are running on hardware it does not target well. The optimised kernels and quantisation paths are strongest on recent NVIDIA parts. Support elsewhere exists and moves quickly; verify for your specific card rather than assuming the feature list applies uniformly.

When you need stability over a multi-year horizon without maintenance. See the version churn note above. This is an actively evolving system and running it means tracking it.

09

Versus the alternatives — including the governance, which matters here

Apache-2.0, and unusually for a project this central, that is not the whole governance story. vLLM was contributed by UC Berkeley and has been a PyTorch Foundation-hosted project since 7 May 2025, which means it is “officially governed and administered under the PyTorch Foundation’s neutral and transparent governance model.” That is a materially different risk profile from a permissive licence held by a single company — the licence tells you what you may do with the code, and the governance tells you how likely it is to change. Several systems in this repo’s tier A relicensed under commercial pressure; neutral foundation governance is the structural answer to that, and it is worth weighing when a serving engine is load-bearing in your architecture.

The two credible reasons to choose otherwise are a workload TensorRT-LLM’s compilation model suits exactly, and a prompt-reuse pattern SGLang handles better. Capabilities at a glance

CapabilitySupportNote
Paged KV cache ● native The original contribution. Fixed-size KV blocks plus a per-sequence block table, so a request occupies space proportional to its actual length rather than its declared maximum.
Prefix cache reuse ◐ with caveats Automatic, by hashing each block over (parent hash, block tokens, extra hashes). Two real limits: only *full* blocks are cached, so a prefix that ends mid-block misses the remainder — the docs' own example hits 8 of 12 tokens because the third block matches 2 of 4 — and the hash must include LoRA id, multimodal input and cache salt or the same tokens from different contexts collide.
Continuous batching ● native Iteration-level scheduling — a finished sequence is evicted and a waiting one admitted at each decode step, not at each request.
Speculative decoding ◐ with caveats n-gram, suffix, EAGLE and DFlash drafters. The caveat is regime, not support: it spends spare compute, and at high batch there is no spare compute, so the same config that helps a single user can cost throughput on a loaded server.
Quantised weights ● native FP8, MXFP8/MXFP4, NVFP4, INT8, INT4, GPTQ/AWQ, GGUF, compressed-tensors, ModelOpt, TorchAO. Which are *fast* rather than merely accepted depends on the card.
Multi-GPU sharding ● native Tensor, pipeline, data, expert and context parallelism. Tensor-parallel is the one you reach for first and the one that needs the fast interconnect.
Constrained output ● native Grammar- and schema-constrained decoding via xgrammar or guidance, enforced during sampling rather than validated afterwards.
Adapter hot-swap ● native Multi-LoRA against one set of base weights, for dense and MoE layers, selected per request. Note it changes the prefix-cache key — see slot 7.
Drop-in OpenAI API ● native OpenAI-compatible HTTP server, plus the Anthropic Messages API and gRPC. Switching a client is a base-URL change.
Multimodal input ● native Image and audio inputs through the same request path; the multimodal hash participates in the prefix-cache key.
Prefill/decode split ◐ with caveats Documented as **experimental**. vLLM provides the KV-transfer interface and relies on third-party connectors for production use — NixlConnector over NIXL/RDMA is the main one, with PyNccl, P2pNccl and AMD's MORI-IO alongside. Treat it as infrastructure work, not a flag.
Per-token accounting ◐ with caveats Usage is reported per request in the OpenAI-shaped response and aggregated in Prometheus metrics. There is no built-in per-tenant quota — that is the gateway's job.
