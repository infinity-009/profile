Tech A · In almost every design object storage Proprietary managed service. The S3 API itself is a de facto standard implemented by MinIO (AGPLv3), Ceph, Cloudflare R2, Backblaze B2 and GCS — so the interface is portable even though the service is not.

Amazon S3

An effectively unbounded, extremely durable key→bytes map that you may not append to — but which you *can* compare-and-swap. That last clause arrived in 2024 and turns object storage into a coordination primitive, which is a genuinely new thing.

The cheapest durable bytes available and the least interesting API, which is why it is under almost every large system. Two facts changed recently and invalidate most of what is written about it: reads have been strongly consistent since 2020, and conditional writes since 2024.

Concepts first — latency-numbersback-of-envelopequorums

01

Why it exists

S3 launched in March 2006 as Amazon’s first public web service, and the pitch was one number: storage at a price per gigabyte that made “keep everything” cheaper than deciding what to delete. The API was deliberately minimal — PUT, GET, DELETE, LIST — because the goal was durability and scale, not features.

The important thing about that minimalism is what it enabled. Because the API promises so little, the implementation is free to erasure-code data across availability zones, repair silently, and scale to exabytes without any of it being your problem. Every capability S3 lacks is a capability somebody else can build on top, and the ones that matter now have been: Athena for SQL, Iceberg and Delta for tables and transactions, and — since 2024 — conditional writes for coordination.

02

The mental model

An effectively unbounded, extremely durable key→bytes map that you may not append to — but which you can compare-and-swap.

Four clauses, and the last one is new enough that most published S3 advice predates it.

Key→bytes map. Not a filesystem. There are no directories; logs/2026/08/06/x.json is a single flat key that happens to contain slashes, and the console renders it as a tree because it is convenient. This is why LIST with a prefix is your only query and why key layout is the design decision.

Effectively unbounded, extremely durable. Eleven nines of designed annual durability, from erasure coding across three or more AZs. You cannot build this yourself at this price, and the correct posture is to treat “will the bytes still be there” as a solved problem and spend your attention elsewhere.

You may not append. An object is immutable. To change one byte you rewrite the whole object. This is the constraint that shapes everything: it is why log-structured formats write new files rather than modifying old ones, and why “small files” is the recurring performance problem in every data lake.

But you can compare-and-swap. In August 2024 S3 added If-None-Match: * (write only if the key does not exist) and later If-Match: <etag> (write only if unchanged). That is a genuine atomic compare-and-swap on a single key — which means S3 can implement a distributed lock, a leader election, and an append-only commit log. Object storage became a coordination primitive.

Both of the last two facts are recent, and this repo got one of them wrong. An earlier version of this page’s model read “a hash map you may not append to” and marked multi-key transactions and CAS as unsupported outright. That was accurate in 2023 and stale by 2024. The rule that came out of finding it: re-verify the mental model whenever the alternatives section changes, because a one-sentence model is memorable, and memorable claims outlive their expiry dates.

03

The core data structure

There is no public description of S3’s internals, so this is what is inferable from documented behaviour and Amazon’s own talks.

Objects are erasure-coded, not replicated. Reed–Solomon-style coding splits an object into data and parity shards spread across AZs, so it survives multiple device and facility failures while storing far less than 3× the bytes — which is how the price works. Contrast full replication, where 11 nines would cost several copies.

The key index is a partitioned, sorted, distributed store. The evidence is in the performance guidance: throughput limits are per prefix, they used to require random key prefixes to avoid hotspotting, and S3 now repartitions automatically as request rates rise. That is the signature of a range-partitioned index that splits under load — the hot partitions story, in a system you cannot see into.

Two design rules follow directly:

  • The prefix is the index. Layout keys so the queries you need are prefix scans: events/dt=2026-08-06/hour=11/…. Get this wrong and your only recourse is a full LIST of the bucket or a separate catalogue.
  • Randomness in key prefixes is no longer required for throughput, and the old advice to hash the first characters is obsolete. S3 partitions on demand. But partitioning takes time, so a cold bucket suddenly receiving 20,000 requests/s to one prefix will see 503 SlowDown responses until it adapts.

Two arithmetic exercises worth doing once.

Small files are a request-cost problem, not a storage problem. A terabyte in 10 million 100 KB objects costs $23/month to store and $50 in PUT requests just to write it once. The same terabyte in 1,000 objects of 1 GB costs $23 to store and $0.005 to write. This is why every data lake has a compaction job, and why “many small files” is the defining performance pathology of the format.

Egress dominates at scale. A petabyte stored is $23,000/month; a petabyte egressed is $90,000. Any design that reads data out repeatedly should be reading it from inside the same region, and a CDN in front of public objects pays for itself immediately.

06

Capabilities — what you actually build with it

Conditional writes are the interesting new capability and deserve their own paragraph. With If-None-Match: * you can implement create-if-absent — which is a mutual-exclusion primitive, so you can build a distributed lock or a leader election with nothing but a bucket. With If-Match: <etag> you get full compare-and-swap: read the current object and its ETag, compute a new value, write it conditionally, and retry on failure. That is an optimistic-concurrency loop and it is exactly how Apache Iceberg and Delta Lake now commit table metadata without a separate locking service — a dependency that used to require DynamoDB.

What it does not give you is multi-object atomicity. Two objects cannot be swapped together, which is why table formats put the whole commit in one metadata object and CAS that single pointer. The pattern is worth learning because it generalises: one CAS-able pointer to an immutable structure is enough to build a transactional system.

The claim-check pattern. S3 is where bytes go when they are too large for anything else — Kafka messages, database rows, API payloads. Store the object, pass the key. Every other entry in this matrix says “put it in S3” for blob, and this is the row where the matrix pays for itself.

Static hosting and CDN origin. Objects plus CloudFront is the cheapest way to serve static content that exists, and the request-cost arithmetic above is why the CDN is not optional.

Analytics substrate. Parquet in S3, queried by Athena, Spark, Trino or DuckDB, is the default data-lake architecture. The cost lever is entirely in layout: Athena bills per byte scanned, so partitioning and columnar formats are the difference between $0.05 and $50 for the same question.

07

How it fails

503 SlowDown during a traffic ramp. You exceed the per-prefix request rate before S3 has repartitioned. It is a throttle, not an outage, and the correct response is exponential backoff with jitter — but a client library that retries aggressively turns a throttle into a retry storm against a service that was about to accommodate you.

A hot prefix. All writes going to events/2026-08-06/ because the date is the first path component. One prefix, 3,500 PUT/s, and every writer in the fleet aimed at it. Add a higher-cardinality component earlier in the key.

Eventual consistency bugs that no longer exist. Since December 2020, S3 is strongly consistent for reads, writes and LIST. Code that polls for an object’s appearance, or maintains a DynamoDB index because “S3 LIST is eventually consistent”, is working around a behaviour that was removed — and its retry loops and staleness windows are now pure cost. This is worth actively hunting for in any codebase older than 2021.

The small-files pathology. Millions of tiny objects: LIST becomes thousands of paginated calls, Spark’s planning time exceeds its execution time, and request charges exceed storage charges. Compaction is the only fix and it should be designed in, not added after.

Silent deletion via lifecycle rules. A rule intended for tmp/ written with too broad a prefix expires production data on a schedule, days later, with no error. Versioning plus MFA delete is the protection, and lifecycle rules deserve the same review as a migration.

Accidental public access. Historically the most damaging S3 failure by a wide margin. Block Public Access is now on by default for new buckets and ACLs are disabled by default, which removes most of the risk — but a bucket policy can still open it, and pre-2023 buckets keep their old settings.

Cost surprises, in three flavours. Egress from a chatty cross-region reader. Requests from a small-files workload. And retrieval fees from a Glacier tier chosen for the storage price without reading the retrieval price — Deep Archive is 23× cheaper to store and expensive and slow to read, which is correct for backups and wrong for anything you might query.

08

When not to use it

As a database. 20–100 ms per GET with no secondary index. A read amplification of one object per lookup and a key that is your only index. DynamoDB costs more per byte and is the right tool.

As a filesystem. No atomic rename, no partial writes, no locking, no POSIX semantics. s3fs and its relatives make it look like one and the abstraction leaks under any real load. EFS or FSx if you need a filesystem.

For high-frequency small updates. An object is immutable, so a counter incremented a thousand times a second is a thousand full rewrites plus a CAS retry loop at ~50 ms each. Correct and absurd.

When you need sub-10 ms reads. S3 Express One Zone gets you single-digit milliseconds and gives up multi-AZ durability to do it. If you need both, you need a cache or a different store.

When egress economics do not work. Serving a petabyte a month directly from S3 to the internet is $90,000. A CDN, or Cloudflare R2 with zero egress fees, changes the answer.

On portability. S3 is proprietary, but the API has become a de facto standard implemented by MinIO, Ceph, R2, B2 and GCS’s compatibility layer. That makes the interface far more portable than the service, and it is a real architectural asset: code written against the S3 API has genuine exit options, which is not true of most managed services. Worth weighing against the licence churn elsewhere in this matrix — S3 cannot be relicensed against you, because you were never granted a licence in the first place; you are buying a service, and the risk is price and availability rather than terms.

Durable by default ● native Designed for 11 nines of annual durability via erasure coding across at least three AZs. A PUT is acknowledged only once that is done.
No ops burden ● native No capacity planning, no replication to configure, no upgrades. The single strongest argument for it.
Strongly consistent read ● native Read-after-write strong consistency for all operations since December 2020, including LIST. Every pre-2021 design that works around eventual consistency is now working around nothing.
Fast point lookup ● native GET by key. 20–100 ms first-byte, which is fine for objects and hopeless as a database read.
TTL expiry ● native Lifecycle rules expire or transition objects by age and prefix. Coarse — a daily-granularity batch process, not a per-key timer.
Point-in-time recovery ◐ with caveats Versioning keeps every version, so you can restore any object to any past state. There is no single cluster-wide "restore to 14:32" operation — you reconstruct it per key.
Multi-key transaction ○ no Conditional writes are single-key compare-and-swap. There is no atomic operation across two objects, which is why table formats build their own commit protocol on top.
Range scan ◐ with caveats LIST is lexicographic by key, paginated at 1,000. This is why S3 layouts encode hierarchy in the key — the prefix *is* the index.
Pub/sub fan-out ◐ with caveats Event notifications to SNS, SQS, Lambda or EventBridge on PUT/DELETE. At-least-once, and ordering is not guaranteed.
Large aggregation ◐ with caveats S3 Select and Athena scan objects with SQL, billed per byte scanned. Columnar formats plus partitioning are the difference between cheap and ruinous.
Flexible schema ◐ with caveats Bytes are bytes, so anything goes — and nothing validates it. Schema lives in your file format (Parquet, Avro) or nowhere.
Horizontal write scaling ● native 3,500 PUT/s and 5,500 GET/s per prefix, and prefixes are unlimited — so throughput is a function of how you name keys.
Atomic counter ◐ with caveats Possible since 2024 via If-Match compare-and-swap retry loops. Correct, and at ~50 ms per attempt under contention it is a coordination primitive, not a counter.
Secondary index ○ no The key is the only index. Any query by attribute needs a separate catalogue — which is what DynamoDB or a Glue/Iceberg catalogue is for.
Joins ○ no Athena, Spark, Trino or DuckDB do this over S3. S3 does not.
Full-text search ○ no No text analysis of any kind.
Geospatial query ○ no No spatial indexing.
Vector similarity ○ no S3 Vectors (2025) is a distinct service with its own API, not a capability of S3 buckets.
Ordered log ◐ with caveats Conditional PUT makes a genuine append-only log possible — that is exactly how Iceberg and Delta commit. Latency per append is tens of milliseconds, so it is a metadata log, not a data path.
