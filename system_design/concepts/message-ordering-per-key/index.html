Tier 4 · Distributed systems mechanics Per-key ordering

Kafka never promises one order for the whole topic — it promises 16 orders, one per partition, and calls that good enough

`total-order-broadcast.mdx` priced the expensive, general answer to "what order does everyone see messages in": serialize every message through one agreed sequence, and pay a throughput ceiling nothing about cluster size buys back. Almost no production queue actually does that. Kafka, Kinesis, SQS FIFO, and Pub/Sub ordering keys all make a narrower, cheaper promise — messages sharing a key arrive in order, full stop, with no promise at all across keys — and this lesson computes why that narrower promise is normally exactly enough, what it costs when it isn't, and what fixing that costs in the parallelism given up.

Read first — total-order-broadcast

01

Kafka's ordering guarantee is one sentence, and the sentence has a scope

Kafka’s documentation states its ordering guarantee in a single line: messages sent to the same partition are appended to that partition’s log in the order they were sent, and a consumer of that partition always reads them in that same order. That’s the whole guarantee. It says nothing about a message on partition 3 versus a message on partition 7 — not “usually the same order,” not “eventually consistent order” — genuinely nothing, by design.

total-order-broadcast.mdx computed what it costs to promise MORE than that: one shared sequence across every message, agreed by consensus, capped by a throughput ceiling nothing about cluster size buys back. Almost no production message queue pays that price by default. This lesson computes the compromise nearly all of them make instead, why it’s normally free, and exactly when it isn’t.

02

Assume 'my queue guarantees ordering' means one global order

The instinct, coming straight off total-order-broadcast.mdx: a message queue that “guarantees ordering” must mean every consumer sees every message in one identical sequence, the way that lesson defined it. That’s not what “Kafka guarantees ordering” means in practice, and the gap between the two readings is exactly where a real incident hides.

Predict A Kafka topic has 16 partitions, keyed on userId. User 42's events A then B are produced in that order. User 99's event C is produced between A and B, in real time. Which of these does Kafka's ordering guarantee promise?
Kafka's guarantee is scoped to a partition, not the topic. A and B share a key (userId 42), so they land on the same partition and Kafka guarantees A before B. C has a different key (userId 99) and can land on any partition, including a different one — Kafka makes literally no promise about C's arrival relative to A or B, regardless of when C was actually produced. Reading a per-partition guarantee as a per-topic one is the single most common misunderstanding this lesson exists to correct.
Show it without answering

At the rig’s defaults — 16 partitions, 5,000 msgs/s per partition — per-key ordering sustains 80,000 messages/second, computed by perKeyOrderingThroughput(16, 5000), against a 171.4 messages/second ceiling for a single global order at the same 5-node/10ms-RTT cluster total-order-broadcast.mjs already quantified — a 466.7× gap, for a guarantee that is narrower but, for most real workloads, exactly the one that was actually needed.

03

The hospital chart that never crossed departments

A hospital keeps one chronologically ordered chart per department per patient: cardiology’s chart for patient X is always in the order cardiology actually saw them, and the same is true, independently, for radiology and pharmacy. This is a genuine efficiency win — departments never wait on each other to update their own chart, exactly the way a Kafka partition never waits on any other partition to append a message.

It also means nothing links the charts to each other. If Tuesday’s cardiology finding is the reason Thursday’s radiology scan was ordered, and Thursday’s scan result is the reason Friday’s pharmacy prescription changed, nothing in “each department keeps its own chart in order” enforces that a clinician reading Friday’s prescription can trust Tuesday’s finding was already visible. The causal link crosses departments — crosses partitions — and per-department ordering was never designed to reach across that boundary.

04

Two questions per-key ordering answers, one it flatly does not

perKeyOrderingThroughput(N, perPartitionThroughput) = N × perPartitionThroughput

A direct pass-through to why-you-shard.mjs’s own throughputScaling — per-key ordering’s parallelism win is not a new mechanism, it’s why-you-shard.mdx’s sharding win, applied to ordered delivery specifically. N independent partitions, N times one partition’s throughput, because nothing about “ordered within a partition” forces any partition to wait on any other.

crossPartitionOrderingViolationProbability(N, keyAssignmentRandomness) = keyAssignmentRandomness × (N − 1) / N

The probability a causally-related pair of events — A must be ordered before B — lands on DIFFERENT partitions, and therefore loses the ordering guarantee outright. At keyAssignmentRandomness = 0 the pair always deliberately shares a key (ordering holds, by design). At keyAssignmentRandomness = 1 the two keys are chosen independently and uniformly among N partitions, giving the standard “not the same one of N” probability. This RISES toward 1 as N grows — the opposite of what “more partitions” intuitively sounds like it should buy.

sameKeyMitigationCost(N, perPartitionThroughput): before = throughputScaling(N, ·), after = throughputScaling(N−1, ·)

The fix for a cross-key causal link — force both streams onto ONE shared partition — costs exactly one partition’s worth of throughput, computed the same way the win was: why-you-shard.mjs’s throughputScaling at N partitions versus N−1. The absolute cost is constant (perPartitionThroughput, always); the cost AS A FRACTION of the whole fleet shrinks as N grows, because one partition is a smaller slice of a bigger pie.

06

The trade-off — a cheap default with one specific, computable blind spot

Per-key ordering is the right default precisely because most ordering requirements are already per-entity. “All of this user’s events in order,” “all of this order’s state transitions in order,” “all of this device’s telemetry in order” — pick that entity as the partition key and the ordering guarantee you actually needed falls out for free, at full linear-scaling throughput, with none of total order broadcast’s serialization tax.

The blind spot is exact, not vague: any requirement that spans two DIFFERENT keys gets zero help from per-key ordering, full stop. crossPartitionOrderingViolationProbability isn’t a tail risk that shrinks with careful engineering elsewhere — it is a direct, computable consequence of how many partitions exist and how independently the two keys were chosen, and it gets WORSE, not better, as the system scales out.

The mitigation is real but not free: sameKeyMitigationCost is a genuine, unavoidable trade, not a trick. Forcing two related streams onto one partition to guarantee their relative order costs exactly one partition’s worth of throughput, permanently, for as long as that merge lasts — cheap in relative terms at high N, but never actually zero. The only way to raise cross-key ordering back to total-order-broadcast.mdx’s full guarantee without merging anything is to pay that lesson’s serialization ceiling instead — there is no third option that is both free and general.

07

In the wild

Kafka’s own documentation states the partition-scoped guarantee directly, as the specific example this lesson is not the first to build on — a producer sends records to a topic partition in the order they are sent, and a consumer of a single partition reads them in that exact append order; the documentation is explicit that this says nothing about the relative order of records sent to different partitions, which is precisely the scope this lesson’s model treats as a hard boundary rather than a detail.

DDIA frames the same partition-scoped ordering guarantee as what removes the need for concurrency control in a log-based system — Martin Kleppmann and Chris Riccomini, Designing Data-Intensive Applications, 2nd ed., ch. 12, p. 511: “If the event log and the application state are sharded in the same way (e.g., processing an event for a customer in shard 3 requires updating only shard 3 of the application state), then a straightforward single-threaded log consumer needs no concurrency control for writes” — continuing on p. 512, “The log removes the nondeterminism of concurrency by defining a serial order of events in a shard.” This is exactly per-key ordering described from the consumer’s side: a consumer that never has to reconcile two shards’ relative order needs no coordination at all, which is the throughput win this lesson quantifies.

why-you-shard.mdx’s throughput-scaling law and total-order-broadcast.mdx’s throughput ceiling are both reused unchanged, not re-derived — every number in this lesson’s model comes from calling throughputScaling and totalOrderBroadcastThroughput directly, because the point of this lesson is that per-key ordering isn’t a third mechanism sitting alongside those two — it’s the first one, applied to the specific problem the second one already priced the expensive version of.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • Per-key (partition) ordering guarantees messages sharing the SAME key, or routed to the SAME partition, are delivered in the order they were produced — and makes NO promise whatsoever about the relative order of messages on DIFFERENT keys/partitions; this is a strictly weaker guarantee than `total-order-broadcast.mdx`'s single global order, chosen deliberately because it is far cheaper
  • The parallelism win is the exact mechanism `why-you-shard.mdx` already quantified for storage and throughput in general — N independent partitions run independently because nothing forces them to coordinate — `perKeyOrderingThroughput` is a direct pass-through to that lesson's own `throughputScaling`, not a new idea wearing new clothes
  • Per-key ordering is sufficient for most real ordering requirements because most ordering requirements are naturally per-entity already — "all events for user X must process in order" is satisfied exactly by keying on user X's id, at zero cost beyond picking that key
  • Per-key ordering gives you NOTHING when two events on DIFFERENT keys are causally related (event A for user X must precede event B for user Y) — the fix is either put both on the SAME key (giving up some parallelism) or fall back to a stronger, more expensive mechanism like total order broadcast
  • `crossPartitionOrderingViolationProbability(N, randomness)` quantifies the genuine risk: a causally-linked pair whose keys are chosen independently lands on different partitions with probability (N−1)/N at full randomness — RISING toward certainty as partition count grows, exactly backwards from what a naive "more partitions is safer" intuition would guess
  • `sameKeyMitigationCost` prices the fix — forcing two related streams onto one shared partition costs exactly one partition's worth of throughput, `why-you-shard.mdx`'s own `throughputScaling` at N versus N−1 partitions — a cost that SHRINKS as a fraction of the whole as N grows, because one partition is a smaller slice of a bigger pie
  • Per-key ordering's throughput and total order broadcast's ceiling are not two points on the same curve — one scales linearly with partition count, the other is FLAT regardless of partition count, because it serializes through one agreed sequence no matter how the data is sharded elsewhere; the gap between a rising line and a flat ceiling is why real systems default to per-key ordering

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A team keys their Kafka topic on `userId` so that "all events for a given user process in order." Their monitoring dashboard shows event A (for user 42) and event B (for user 99) arriving at the consumer in an order that doesn't match when they were actually produced. Is this a bug in Kafka's ordering guarantee?

    How sure are you, before you look?
    No — Kafka's guarantee was never about events for DIFFERENT users. Per-key ordering promises order WITHIN a partition (here, within one user's events), and says nothing at all about the relative order of two different keys' events, because they can land on two different partitions with no coordination between them. Event A and event B belong to different users, so nothing was ever promised about their relative order — the dashboard is observing the guarantee working exactly as specified, not failing.
    Did you have that?
  2. Cued recall

    A payments system needs "the refund event for order 500 must be processed after the charge event for order 500, always" and also needs "a fraud-flag event for user 7 must be processed before ANY of user 7's orders' events, across every order that user has." Can a single choice of partition key satisfy both requirements at once?

    How sure are you, before you look?
    The first requirement is satisfied for free by keying on order id — charge and refund for order 500 always share a key, so per-key ordering handles it with zero extra cost. The second requirement is NOT satisfiable by keying on order id, because a user's events are spread across as many different order-id partitions as they have orders — exactly the cross-key causal link `crossPartitionOrderingViolationProbability` prices. Satisfying it would require re-keying on user id instead (sacrificing the order-scoped parallelism) or accepting a stronger, more expensive ordering mechanism for that specific cross-cutting requirement — the two requirements pull toward two different, incompatible partition keys.
    Did you have that?
  3. Cued recall

    `total-order-broadcast.mdx` computed that Raft-style total order broadcast throughput DROPS as cluster size grows, because a bigger cluster needs a slower majority vote per agreed message. Does per-key ordering's throughput also drop as partition count grows?

    How sure are you, before you look?
    No — that is precisely the point of the trade. Total order broadcast's ceiling is set by how fast ONE shared sequence can be agreed on, and adding partitions elsewhere in the system does nothing to speed that single sequence up (or slow it down) — the ceiling stays flat regardless of N. Per-key ordering's throughput, by contrast, is `perKeyOrderingThroughput(N, perPartitionThroughput) = N × perPartitionThroughput` — it climbs linearly with N precisely because each partition is independently ordered and needs no coordination with any other, the same linear win `why-you-shard.mdx` already proved for storage and single-partition queries in general.
    Did you have that?
  4. Near transfer

    `why-you-shard.mdx` showed that a query with no partition key has to scatter-gather across every partition and pays a tail-latency cost that GROWS with partition count. This lesson's `crossPartitionOrderingViolationProbability` also grows with partition count, toward 1. Are these the same mechanism wearing two names?

    How sure are you, before you look?
    Same shape of arithmetic — a "does this land on all/different partitions" probability approaching certainty as N grows — but genuinely different mechanisms with different fixes. `why-you-shard.mdx`'s cost is a QUERY touching every partition on purpose (scatter-gather), and the fix is picking a partition key that makes more queries single-partition. This lesson's risk is two SEPARATE messages landing on different partitions by accident, when their causal relationship needed them on the same one — the fix is picking a partition key that deliberately correlates the two, or merging them onto one key. One is about how many partitions ONE operation has to visit; the other is about whether TWO operations end up on the same one at all. Both use "as N grows, a coincidence becomes a near-certainty" — the exact shape `scatter-gather.mdx` first quantified — but applied to different questions.
    Did you have that?
  5. Far transfer

    The abstraction is: a system promises order only within groups it defines (by some partitioning key), buys real parallelism by NOT coordinating across groups, and that compromise silently fails exactly when two things that mattered to each other ended up in different groups. Name an instance outside computing.

    How sure are you, before you look?
    A hospital's per-department patient record system. Each department (cardiology, radiology, pharmacy) keeps its own chronologically ordered chart for a patient's visits to THAT department — a genuine parallelism win, since departments update charts independently without waiting on each other. This works perfectly for "did this patient's three cardiology visits happen in the right order" — that's entirely within one department's chart. It completely fails to guarantee "the radiology scan ordered because of Tuesday's cardiology finding was actually read before Thursday's pharmacy prescription that depended on it" — that causal link crosses departments, and nothing about each department's own careful internal ordering says anything about the other's. The fix, exactly as in this lesson, is either forcing the related records into one shared chart (a merged summary, at the cost of losing per-department independence) or standing up a slower, more coordinated cross-department review process for exactly the cases where it matters.
    Did you have that?
