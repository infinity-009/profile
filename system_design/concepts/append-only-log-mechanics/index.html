Tier 5 · Moving data around Segments, offsets & compaction

A 1GB segment target turns 302GB of 7-day retention into 303 files, not one — and that granularity is why compaction has to exist at all

A log's defining property — append-only, read-by-position — says nothing about how it is stored, and "one growing file" is not the answer any real system uses. Kafka splits a partition into bounded-size segment files, each covering a contiguous range of monotonically increasing offsets; a consumer's "position" is simply the last offset it committed. This lesson computes three consequences of that segmented structure: how often a segment rolls over and how many stay live under a retention window, why deleting by segment age can never reclaim space for one expired key — which is the actual reason log compaction exists as a second, different mechanism — and why finding "everything after offset X" is a cheap lookup with a segment index instead of a scan of the whole log.

Read first — queue-vs-log

01

Retention was set to 7 days. Deleting one customer's data still took a rewrite.

A right-to-erasure request comes in for a customer whose event landed in a Kafka topic two days ago. Retention is configured at 7 days, so the team’s first instinct is to just delete that one record — the same way they’d DELETE FROM events WHERE id = ... in a database. It doesn’t work. The record sits inside a sealed file holding a few hundred thousand other records that all still need to exist, and there is no operation that edits one record out of a sealed file without rewriting the whole thing. Nothing is broken. The log is doing exactly what a log does. This lesson computes why that’s true, what it costs, and the second mechanism — compaction — that exists specifically because retention alone can’t reach inside a sealed file.

02

Assume a log is just one file that grows forever

The mental model most people start with: a log is an append-only sequence, so picture a single file, growing at one end, read sequentially from wherever you left off. That model gets the logical behavior right — append-only, read-by-position — and says nothing true about how it’s actually stored. No real log-based system keeps one infinite file.

queue-vs-log.mdx already establishes that a log’s whole value proposition is “append and retain,” with storage bounded by retention × throughput × message size rather than by unacked backlog the way a queue’s is. This lesson takes that retained-bytes number as given and goes one level deeper: how those bytes are actually laid out on disk, and what that layout costs and buys.

Predict A Kafka topic has 7 days of retention. A message written 2 days ago needs to be deleted right now, ahead of schedule (say, for a legal request). What actually has to happen?
Segments are immutable once sealed, and retention's only lever is deleting an entire segment once every message in it has aged past the window. A record 2 days old sits in a segment that also holds messages from around the same time, most of which have not aged out — so retention cannot touch it yet. Reaching that record before its segment ages out requires either rewriting the segment or running compaction with a tombstone for that key.
Show it without answering

At the rig’s default — 1,000 messages/second of 500-byte messages, a 1GB segment target, 7 days of retention — a new segment rolls over every 33.3 minutes, and the 7-day window holds 303 live segments, each an independently sealed file with its own index. At 1 day of retention that’s 44 segments; retention length and segment count scale together, linearly, because retention only ever deletes whole segments — it can’t shrink the size of what stays live, only how far back “live” reaches.

03

A tree ring, and why a forester never excises one cell

A tree doesn’t store a year of growth as one undifferentiated mass of wood — it lays down one bounded ring per year, a contiguous unit along the tree’s own natural axis (radial growth over time). Read “the last decade,” and a forester counts and reads whole rings; nobody examines individual wood cells. And when old growth needs to be excluded from a study — heartwood that’s decayed, or growth predating a fire nobody cares about for this analysis — it’s discarded ring by ring, wholesale. Nobody ever excises a handful of cells from the middle of one ring while leaving the rest of that ring intact, because a ring is the unit the tree’s own structure makes cheap to reason about, and a cell is not.

A log segment is that same trade, applied to a stream instead of a trunk. Bytes accumulate along one natural axis — offset order — and get bounded into rings (segments) so that “keep the last N days” and “look up everything after offset X” both operate on a manageable number of units instead of an unmanageable number of individual messages. The price is exactly the forester’s price: the unit of deletion is the whole ring, never a cell inside it.

04

Two different levers, two different jobs

SEGMENTS      A partition's offset range is split into bounded-size files. A size threshold
              triggers rollover: the active segment seals (becomes immutable), a new one opens.
              This is purely operational plumbing — file-handle count, per-segment index size.

RETENTION     Deletes WHOLE segments once every message in them ages past a time window (or
              the log exceeds a size cap). Granularity is the segment, because the segment is
              sealed and immutable — there's no cheap partial rewrite.

COMPACTION    A background pass that rewrites a segment keeping only the LATEST value per key,
              discarding older values for the same key. Reaches inside a segment retention
              can't touch yet — the fix for exactly retention's granularity limitation.

OFFSET INDEX  A sparse per-segment index (offset -> byte position) plus a base-offset list
              across segments. Turns "everything after offset X" into a binary search over
              segments, then a short scan inside one — not a scan of the whole log.

Segments are the storage unit everything else operates on. Retention and compaction are two different answers to “what gets kept,” suited to two different kinds of topic. The index is what makes reading any of it, at any point in the log, cheap regardless of how large the log has grown.

The saving is proportional to how often keys actually repeat, not to anything about compaction itself: at 10 average rewrites per key, compaction keeps exactly 1/10th; at 50, exactly 1/50th.

The unindexed cost is defined as the total log size — a full scan examines every retained message. The indexed cost grows by only about 6 messages examined across two full orders of magnitude of log growth, because it scales with log2(segment count) plus a fixed-size in-segment scan — segment count is the only term that grows with log size, and it grows inside a logarithm.

06

Neither lever is free — and picking the wrong one for the topic costs storage, not correctness

Smaller segments mean finer-grained retention and faster individual segment operations, at the cost of more open file handles and more separate per-segment indexes to maintain — this is a pure operational trade with no correctness angle: a 100MB segment target rolls over roughly 10× more often than a 1GB one for the same traffic, multiplying file-handle and index-metadata count by roughly the same factor.

Compaction is not free either — it is a background CPU and I/O cost, paid continuously, to buy back space time-based retention structurally cannot reach, and it only pays off when keys actually repeat. Running compaction on a genuine event-history topic (few or no repeated keys, the avgWritesPerKey = 1 row above) spends that CPU and I/O for approximately zero storage return — the topic needs time-based retention instead, because there’s nothing for compaction to collapse.

Running time-based retention on a genuine changelog topic is the mirror-image mistake: storage grows with total write volume forever, when the actual information content is bounded by the number of distinct keys — the 90-98% figures above are exactly the gap between “size the storage budget by how much gets written” and “size it by how much actually needs to be remembered.” Picking the right lever is a property of the topic’s own write pattern, not a global default either mechanism can be tuned around.

07

In the wild

Apache Kafka is the system this lesson’s terms are named after directly — its own “log.segment.bytes” (segment rollover), retention.ms/retention.bytes (time/size retention), and log.cleanup.policy=compact (compaction) are the three real knobs this lesson’s model computes against, and its offset-and-partition design is close to a direct implementation of what DDIA describes below.

DDIA describes partitions-as-shards, offsets, and consumer positioning directly, in the context of log-based message brokers: “a partition (shard) is append-only… [each] message is totally ordered,” and “consuming a shard sequentially makes it easy to tell which messages have already been processed… the broker does not need to track acknowledgments for every single message but only to periodically record the consumer offsets” (Kleppmann & Riccomini, Designing Data-Intensive Applications, 2nd ed., pp. 496–498) — the exact offset-as-position mechanism this lesson’s recall nodes state.

DDIA also describes log compaction directly, and traces it back to LSM-tree merge-compaction: “the storage engine periodically looks for log records with the same key, throws away any duplicates, and keeps only the most recent update for each key… [enabling] a new consumer from offset 0 of the log-compacted topic [to] sequentially scan over all messages… [and obtain] a full copy of the database contents without having to take another snapshot” (pp. 505–506) — the same keep-latest-value-per-key mechanism this lesson computes the storage savings for, first introduced in the same book as SSTable segment merging (pp. 120–121).

content-defined-chunking.mdx covers a different mechanism that shares only the word “chunk/segment,” not the concept: that lesson’s chunking is for deduplication of arbitrary byte content by hash identity, and its whole problem is that byte-level edits shift chunk boundaries. A log’s segments never face that problem, because a log forbids the operation (in-place edits) that causes it — see this lesson’s near-transfer question above for the full contrast.

  • Martin Kleppmann and Chris Riccomini, Designing Data-Intensive Applications, 2nd ed., O’Reilly, “Log Compaction,” pp. 505–506, referencing “Constructing and Merging SSTables,” pp. 120–121.

Now put the page away

Everything above this line was the Passive rung — necessary, and the weakest thing on offer. Testing yourself on it will feel worse than rereading it and will hold roughly twice as long. That gap between how it feels and what it does is the entire reason this section exists.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A log is not stored as one growing file — it is split into SEGMENTS, bounded-size files (Kafka's own default order of magnitude is roughly a gigabyte), each covering a contiguous range of the partition's OFFSETS. A new segment opens and the old one is sealed (becomes immutable) once the active segment crosses the size target — this is rollover, and it is purely a size trigger, not a time one.
  • An OFFSET is a per-partition monotonically increasing integer identifying a message's position. A consumer's "position" is nothing more than the last offset it committed — that single integer is sufficient to resume reading exactly where it left off after a restart, because the log itself never reorders or renumbers anything already written.
  • RETENTION deletes whole segments once every message in them ages past a configured window (or the log exceeds a size cap) — deletion happens at SEGMENT granularity, not per-message, because a segment file is immutable and sealed; there is no cheap way to remove one record from the middle of it without rewriting the whole file.
  • That segment-granularity limitation is exactly why COMPACTION exists as a second, different mechanism: instead of deleting by age, a compaction pass rewrites a segment keeping only the LATEST value for each key and discarding older values for the same key — it can reclaim space for an individual overwritten key that time-based retention structurally cannot touch until the segment holding it ages out entirely.
  • Retention and compaction answer different questions and suit different topics: an event-history topic (a payment happened, a click happened) has few or no repeated keys, so time-based retention is what actually bounds its storage — compaction on that topic saves almost nothing, because there is almost nothing to collapse. A changelog/current-state topic (this user's current address, this order's current status) has the same key rewritten constantly, and compaction can shrink its storage by an order of magnitude or more relative to keeping every version.
  • Finding "everything after offset X" does not require scanning the log from the start. A SEGMENT INDEX makes it a binary search over segment base-offsets (which segment could this offset be in — O(log segment-count)) followed by a short scan inside one segment's own sparse offset index, rather than an O(n) linear scan across every retained message — the gap between the two grows directly with how large the log has become, not with anything about the query itself.

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A team sets a Kafka topic's retention to 7 days and later needs to delete one customer's data (a right-to-erasure request) that was written 2 days ago. Retention alone won't do it for another 5 days. Why can't the broker just delete that one record now, the way a database would delete one row?

    How sure are you, before you look?
    Because the record sits inside a sealed, immutable segment file alongside potentially millions of other records that are not being deleted — retention operates by discarding WHOLE segments once every message in them has aged out, not by editing files in place. Removing one record early would mean rewriting the entire segment file, which is exactly the operation segments are designed to avoid doing routinely. The two real options are: wait for time-based retention to age that segment out naturally, or run compaction with a tombstone for that key so a background pass rewrites the segment without it.
    Did you have that?
  2. Cued recall

    A topic modeling "this user's current shipping address" (a changelog topic — the same user-id key gets rewritten every time the address changes) is configured with 7-day time-based retention instead of compaction. What goes wrong, concretely?

    How sure are you, before you look?
    Every past address for every user survives for the full 7 days, even though only the most recent one is ever meaningful — a changelog topic doesn't accumulate distinct events, it accumulates repeated writes to the same small set of keys. Time-based retention keeps ALL of them regardless of key, so storage is sized by total write volume, not by the number of distinct users — the same shape mistake as keeping every UPDATE statement a database ever ran instead of just the current row. Switching to compaction would keep exactly one row per user (the latest), typically an order-of-magnitude smaller for a topic with real key reuse.
    Did you have that?
  3. Near transfer

    `content-defined-chunking.mdx` computes that inserting one byte into a fixed-size-chunked file destroys nearly every downstream chunk's identity, because fixed-size chunk boundaries are set by POSITION rather than content. Someone argues log segmentation has the identical flaw: "a segment's contents are also set by position — the Nth gigabyte of the stream — so editing an old message should shift every later segment's contents, too." Is that the right transfer?

    How sure are you, before you look?
    No — it misidentifies what's mutable. Content-defined chunking exists because a file CAN be edited in the middle (an insert or delete shifts every later byte), which is exactly the failure mode fixed-size chunking can't survive. A log segment never has that problem because the log itself is append-only: nothing already written ever moves, shifts, or gets edited in place. A segment's boundary is set once, when rollover happens, and it never has to be recomputed afterward. Fixed-size chunking's flaw is a consequence of mutability it was never designed for; log segmentation is safe from that exact flaw precisely because logs forbid the operation (in-place edits) that causes it.
    Did you have that?
  4. Far transfer

    The abstraction is: a structure grows without bound, so it gets split into independently-manageable, bounded-size units along its own natural ordering — and the whole structure's lifecycle policy (what to keep, what to discard) then operates on those units, not on individual elements, because the units are cheap to manage wholesale and the elements are not. Name an instance outside computing.

    How sure are you, before you look?
    A tree ring, and how a forester reads fire and growth history from it. A tree doesn't store its growth as one undifferentiated mass of wood — it lays down one bounded ring per year, each ring a contiguous, dateable unit along the tree's own natural axis (radial growth over time), the same way a segment is a contiguous unit along a log's own natural axis (offset order over time). A forester who wants "everything from the last decade" doesn't examine individual wood cells — they count and read whole rings, exactly the way a segment index looks up whole segments rather than individual messages. And when old growth needs to be discounted or discarded from an analysis (heartwood that's decayed, or growth predating a fire the study doesn't care about), it's discarded ring by ring, wholesale — never by somehow excising individual cells from the middle of one ring while leaving the rest intact.
    Did you have that?
