Tier 3 · Storage and state Lock taxonomy & granularity

4,999 row locks block nobody; the 5,000th escalates and blocks 995,000 rows in one step

A database enforces "don't let two transactions touch the same data unsafely" at row, page, or table granularity — the same protection, three different price tags. This lesson computes those prices directly: the lock-object overhead and unrelated-row blocking at each granularity for one fixed workload, why a granularity hierarchy needs intent locks to stay cheap to check, why a plain row lock cannot stop a phantom insert into an empty gap, and the exact row-lock count at which an engine gives up on fine-grained locking and blocks a table's worth of transactions at once.

Read first — isolation-anomalies

01

One more lock, and 995,000 rows go dark

A cleanup job deletes 4,999 old rows from a 1,000,000-row table, one row lock at a time. No other transaction on that table notices — every one of the other 995,001 rows is still free to read and write. The job deletes one more row. Row lock number 5,000 crosses a threshold nobody on the team configured on purpose, the engine escalates to a single table lock, and every other transaction touching that table blocks — not gradually, not for the rows the job actually needed, but for all of it, instantly, because of exactly one extra row.

Nothing was misconfigured. This is the documented, intended behavior of lock escalation, and this lesson computes the cliff: what a lock actually is, what row/page/table granularity actually costs in objects and in blocked concurrency, why a hierarchy of granularities needs its own mechanism (intent locks) to stay cheap to check, why a row lock alone cannot stop a new row from being inserted where none existed, and exactly where the escalation cliff sits.

02

Assume more locks always means more safety, and finer-grained always means better

The instinct: locking is a safety mechanism, so more granular locking is strictly an upgrade — it protects the same data with a smaller blast radius, so why wouldn’t an engine always lock at the finest grain available? The gap in that instinct is the word “always”: finer-grained locking does buy concurrency, but every lock is an object the engine has to allocate, hash, and check for conflicts against every other lock — and at some row count, that bookkeeping cost is what an engine trades away, on purpose, by escalating.

Predict A transaction has taken 4,999 row locks on a 1,000,000-row table, with escalation set to trigger at 5,000. It takes one more row lock. Roughly how many OTHER rows, that this transaction never touched, go from freely accessible to blocked?
Escalation swaps every fine-grained lock the transaction holds for ONE table-level lock. A table lock blocks every row in the table except that transaction's own writes — so crossing the threshold doesn't add a proportional amount of blocking, it jumps straight to (total rows − rows already locked), which on a 1,000,000-row table at 5,000 locks is 995,000. One extra lock request, and the blocked-row count goes from 0 to essentially the whole table.
Show it without answering

At the rig’s default — touching 4,999 of 1,000,000 rows — row-level locking takes 4,999 lock objects (319.9 KB) and blocks 0 rows it didn’t touch; table-level locking takes 1 object (64 B) and blocks 995,001 rows it never touched either. At a 5,000-lock escalation threshold, 4,999 locks block 0 other rows and 5,000 locks block 995,000 — the entire jump happens on one additional lock, not gradually. Checking whether a table-level lock is safe to grant costs 1,000,000 row scans without an intent lock, or 1 counter read with one — a 1,000,000× gap. Protecting 5 existing rows in a range from phantom inserts needs 6 next-key locks, not 5 — the extra one closes the gap after the last row.

03

A library checkout desk, not a padlock

A lock is not a padlock on a physical object — it’s an entry in a table the lock manager keeps, and every entry has a byte cost and a lookup cost. Think of a library that lends by the shelf, the book, or the whole floor:

  • Book-level checkout (row lock): the desk tracks exactly which books are out. Maximum freedom for everyone else — every book not checked out is available — but the desk’s ledger grows one line per book, and checking “is anything on floor 3 checked out” means reading every line for floor 3.
  • Floor-level checkout (table lock): the desk tracks one line — “floor 3, out.” Trivial to check, but it also declares every book on that floor unavailable, including the ones nobody actually wanted.
  • Intent to check out (intent lock): the moment someone checks out a single book, the desk ALSO stamps “someone has a book out” on that floor’s own line — not instead of the book-level entry, in addition to it. Now “is anything on floor 3 checked out” is answered by reading one stamp, not scanning every book’s line, because every checkout already paid the cost of updating it on the way in.

Escalation is the desk, mid-day, realizing its book-level ledger for one patron has grown past what’s worth maintaining line by line, and just writing “floor 3, out” instead — correct, cheap to track from then on, and now nobody else on that floor can check out anything, including books that one patron never touched.

Every lock in this lesson is the same object — a compatibility rule (S/X) attached to something. What differs is only WHAT that something is (a row, a page, a table) and whether a summary of it is also recorded one level up (intent) or swapped for a coarser one entirely (escalation).

04

The mechanism: one primitive, a hierarchy, and one gap the hierarchy alone doesn't close

Everything above reduces to two questions asked of every lock: which mode (S or X), and at which granularity. The compatibility rule never changes; only what it’s attached to does.

Granularity is a separate axis. A row/page/table hierarchy only stays cheap to check because every fine-grained lock also registers an intent lock one level up on its way down — that’s the entire reason a table-level lock request doesn’t have to scan the table’s rows. And a plain row lock, at any granularity, only ever covers rows that exist — closing the gap between them (so a range query is safe from phantom inserts) needs a distinct mechanism, the gap/next-key lock, layered on top rather than implied by granularity at all.

06

The trade-off: every one of these is a bill, not a bug

Finer granularity is not a free upgrade. Row-level locking gives every unrelated row full concurrency, and it pays for that in lock-object count — 4,999 objects and 319.9 KB versus a table lock’s single 64-byte object, for the exact same 4,999-row workload. An engine that only ever locked at row granularity would eventually spend more memory and CPU tracking locks than doing work, which is the honest reason escalation exists at all, not a design flaw someone forgot to fix.

Intent locks are close to free and buy a mechanism, not a shortcut. Registering one intent lock per level on the way down costs a small constant amount of extra bookkeeping per fine-grained lock taken — and in exchange, a table-level lock request never has to scan rows at all, regardless of table size. This is the one piece of the taxonomy that is a genuinely dominant trade: more bookkeeping on the cheap operation (taking a row lock) in exchange for eliminating an expensive one (checking a table lock) that would otherwise scale with table size.

Escalation trades concurrency for lock-manager memory, and the trade is invisible until it fires. Below threshold, a bulk operation behaves exactly like row locking — full concurrency for everyone else. At threshold, that flips to table locking’s full blocking, in one step. The operational cost isn’t the memory saved (real) — it’s that the same query, run against a table with slightly more matching rows, silently changes from “harmless” to “blocks everyone,” with no warning in the query itself.

Gap/next-key locks are the one mechanism here that costs almost nothing and closes a real hole. One extra lock per range, regardless of range size, converts “row lock, phantom-vulnerable” into “next-key lock, phantom-safe.” Compared to escalation’s abrupt trade or granularity’s continuous one, this is close to a strict improvement — the cost is a single row’s worth, at any scale.

None of these mechanisms resolve what happens once two transactions’ locks actually collide — whether one blocks and waits, whether the wait is detected as a deadlock and broken by aborting someone, or whether an optimistic protocol skips locking and validates at commit instead. That’s deadlocks and 2pl-ssi-deterministic-execution’s territory, both later in this tier — this lesson only establishes what a lock IS and what holding one costs, not what happens when two of them meet.

07

In the wild

Intent locks are Gray, Lorie, Putzolu, and Traiger’s contribution, not folklore. Their 1976 paper on granular locking defined intent-shared, intent-exclusive, and shared-intent-exclusive modes specifically to make a multi-level lock hierarchy checkable without a full scan at the coarse level — the mechanism this lesson’s intentLockCheckCost numbers are computing the payoff of, fifty years after it was first specified.

MySQL/InnoDB’s next-key locking is the real, shipped instance of the gap-lock mechanism. Under REPEATABLE READ, InnoDB combines a record lock with a gap lock on the interval before it — isolation-anomalies.mdx already noted this is how InnoDB’s RR prevents many phantoms via a mechanism the SQL standard doesn’t describe at all. This lesson’s rangeLockCount model is that same mechanism reduced to the one number that matters: N existing rows need N+1 locks to be fully phantom-safe, not N.

Lock escalation with a fixed row-count threshold is SQL Server’s real, documented default — escalation is considered once a single statement holds on the order of 5,000 row or page locks on one table or partition, which is the illustrative default this lesson’s DEFAULT_ESCALATION_THRESHOLD uses. Not every engine escalates this way: PostgreSQL has no row-lock escalation at all (its MVCC design avoids the row-lock-count problem differently), and MySQL/InnoDB’s locking is per-transaction rather than escalation-based — the exact threshold, and whether escalation happens at all, is engine-specific, which is why this lesson treats the number as a parameter to the model rather than a universal constant.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • Shared (S) locks are mutually compatible — any number of transactions can hold S on the same resource at once — but S blocks any transaction wanting X, and X blocks everything, including another X. Only S-S is compatible; S-X, X-S, and X-X are all not.
  • The SAME protection (don't let two transactions corrupt overlapping data) can be enforced at row, page, or table granularity — finer grain buys more concurrency (fewer unrelated rows blocked) at the cost of more lock objects to track; coarser grain is the reverse. Quantified: touching 4,999 of 1,000,000 rows costs 319.9 KB of row locks and blocks 0 unrelated rows, or 64 B of table lock and blocks 995,001.
  • Intent locks make a row/page/table hierarchy cheap to check: before taking a row-level X lock, a transaction also takes an intent-exclusive lock at the page and table above it, so a transaction wanting a table-level lock reads one intent-lock counter instead of scanning every row for a conflict — for a 1,000,000-row table that's 1 check instead of 1,000,000.
  • A plain row lock only protects rows that already exist — it says nothing about the empty space between them, so a concurrent INSERT into that space is a phantom a row lock cannot see. A gap lock locks that space directly; a next-key lock is a row lock plus the gap immediately before it, which is InnoDB's actual mechanism under REPEATABLE READ.
  • Next-key locking N existing rows in a range takes N+1 locks, not N — the extra one closes the gap AFTER the last row, which is the one gap a per-row next-key lock would otherwise still leave open to a phantom insert.
  • Lock escalation swaps many fine-grained locks for one coarse one once a row-lock count crosses a threshold, to cut lock-management overhead — but the resulting concurrency loss is a step function, not a gradual cost: one lock below threshold blocks 0 other transactions' rows, one lock at threshold blocks nearly the whole table, at once.
  • This lesson stops at the mechanism (what a lock IS, and what it costs). What happens when two transactions' locks actually collide — ordering, detection, retry — is `deadlocks`'s territory, and which protocol decides who blocks versus who aborts is `2pl-ssi-deterministic-execution`'s.

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A code review says "we hold a shared lock while reading, so this is safe." Safe against what, specifically, and not safe against what?

    How sure are you, before you look?
    Safe against another transaction WRITING that resource — X is incompatible with S, so a writer blocks until every reader's S lock is released. Not safe against another reader — S is compatible with S, so any number of concurrent shared-lock holders can read the same resource at once, which is the entire point of a shared lock existing as a distinct mode from exclusive. "We hold S" answers "are we blocking other readers" (no) and "are we blocking writers" (yes) — two different, easily conflated claims.
    Did you have that?
  2. Cued recall

    Why can't a lock manager grant a table-level lock by directly asking "is any row in this table currently locked incompatibly," the obvious-sounding approach?

    How sure are you, before you look?
    Because answering that question directly means checking every row's lock status — for a 1,000,000-row table, 1,000,000 checks, on every single table-level lock request, regardless of how few rows are actually locked. Intent locks turn this into a physically different operation: every transaction that takes a row- or page-level lock ALSO takes an intent lock at every level above it on its way down, so the table-level check becomes "is there an incompatible intent lock recorded on this one table object" — one read, computed once as it's taken rather than scanned for on demand.
    Did you have that?
  3. Cued recall

    A range query `WHERE age BETWEEN 20 AND 30` matches 5 existing rows. Under plain row locking, a concurrent transaction inserts a new row with age=25. Why does the row locking not stop this, and what does?

    How sure are you, before you look?
    Row locks are locks ON rows — they protect the 5 rows that already exist and say nothing about the row that doesn't exist yet at age=25. The INSERT never touches any of the 5 locked rows, so nothing conflicts, and a transaction that re-runs the same range query now sees 6 rows where it saw 5 — a phantom. A GAP lock, locking the space between index entries rather than any row, stops it; InnoDB's next-key lock (row lock + the gap immediately before it) is the real mechanism, needing 5+1=6 locks to fully close a 5-row range rather than 5.
    Did you have that?
  4. Near transfer

    A nightly job runs `DELETE FROM orders WHERE created_at < '2020-01-01'`, matching 40,000 rows on a 1,000,000-row table with a 5,000-lock escalation threshold. A teammate proposes batching it into `DELETE ... LIMIT 4000` loops instead of one statement. What does this lesson's model say that change actually buys, and what doesn't it fix?

    How sure are you, before you look?
    One 40,000-row DELETE crosses the 5,000-lock threshold at row 5,000 of 40,000 and escalates to a table lock for the remaining 35,000 — blocking every other transaction on the table (roughly 960,000 unrelated rows' worth) for the statement's whole duration. Batching into 4,000-row transactions keeps each one under threshold, so each batch holds row locks only and blocks nobody else's unrelated rows — the concurrency win this lesson's model predicts directly. What it does NOT fix: total lock-object overhead across the whole job is unchanged (still roughly 40,000 row-lock-equivalents somewhere), and now there are 10 separate transactions instead of one, which is a different correctness shape — a crash mid-job leaves some batches committed and others not, a question this lesson doesn't answer and `long-transactions-and-bloat` and the ACID atomicity boundary do.
    Did you have that?
  5. Far transfer

    The abstraction is: checking a summary flag maintained at each level of a hierarchy is enough to answer "does anything below this point conflict," without visiting every leaf. Where else does this appear?

    How sure are you, before you look?
    A building's fire-alarm panel reading one zone indicator per floor instead of querying every room's individual sensor. Each room's sensor, on triggering, doesn't just alarm locally — it also sets its floor's zone indicator, the way a row lock also sets an intent lock on its page and table. A fire marshal at the panel asking "is anything wrong on floor 4" reads one zone light, not forty room sensors — cheap specifically because every room already pushed its state one level up as a side effect of triggering, not because the panel went and polled anything. Same shape in a filesystem's per-directory "dirty" bit that lets a sync tool skip untouched subtrees, or a build system's per-target hash that lets `make` skip a whole dependency chain without inspecting every source file in it.
    Did you have that?
