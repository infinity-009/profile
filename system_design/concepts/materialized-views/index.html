Tier 3 · Storage and state Materialized views

A materialized view lets 50,000 changed rows out of 10 million cost 200× less than the full refresh it replaces — until the change volume itself erases that advantage

A materialized view precomputes and stores a query's result so a read is a lookup instead of a re-run. The read speedup is never free — someone has to keep the stored result in sync with the base table, and how that maintenance is done changes its cost by two orders of magnitude. This lesson prices full refresh against incremental maintenance, shows exactly which aggregate shapes earn a cheap incremental update and which don't, and puts a number on the staleness a fixed refresh cadence leaves a reader exposed to.

Read first — reading-explain-plans

01

200× cheaper to update — until the change volume itself takes that away

A materialized SUM over a 10,000,000-row table, with 50,000 rows (0.5%) changed since the last refresh, costs 50,000 row-touches to bring up to date incrementally — against 10,000,000 to recompute it from scratch. A 200× saving, and it looks like a strictly better way to maintain any materialized result. Swap the SUM for a MAX over the identical table and the identical 0.5% change, and the incremental cost doubles to 100,000 — still a 100× saving, but for a structural reason that has nothing to do with how much changed: maintaining a running maximum sometimes has to throw away the shortcut entirely and rescan. Push either aggregate’s change fraction high enough, and the saving keeps shrinking until it’s gone — SUM’s at 100% changed, MAX’s at just 50%. Incremental maintenance is not “the cheap option” as a fixed fact. It’s cheap under conditions this lesson computes exactly, and those conditions run out at different points for different aggregates — and for a median, they never hold at all.

02

Assume a materialized view is just a cache with a fancier name

The instinct: a materialized view stores a precomputed result, a cache stores a precomputed result, so keeping either one fresh should be roughly the same problem — evict and recompute when stale, the details don’t matter much. That instinct misses the one design question a materialized view actually turns on: when the underlying data changes, does the query’s own STRUCTURE let you compute just the change to the stored result, or does keeping it correct require touching the whole thing again? A cache is usually keyed by a single lookup and just gets invalidated. A materialized view sits behind an aggregation or a join, and whether that aggregation decomposes into a cheap delta is a property of the aggregate function itself — SUM decomposes, a median does not — not a knob you can tune by trying harder.

Predict A 10,000,000-row table backs a materialized MAX. As the fraction of rows changed since the last refresh climbs from near-zero toward 100%, incremental maintenance's cost climbs too. At roughly what change fraction does it stop being cheaper than just running a full refresh?
MAX/MIN's incremental cost has two terms that both scale with the changed fraction f: the delta cost itself (f · fullRefreshCost) plus an expected rescan cost, because the row that changed might have been the current extreme (also f · fullRefreshCost, since the extreme is equally likely to be any row). Together that's 2f · fullRefreshCost, which equals a full refresh's cost at f = 0.5 — half the crossover fraction SUM/COUNT gets, because SUM/COUNT only ever pays the single f · fullRefreshCost delta term.
Show it without answering

At the rig’s default — a 10,000,000-row table, 0.5% changed, SUM — incremental maintenance costs 50,000 row-touches against the full refresh’s 10,000,000, a 200× saving, nowhere near its 100% crossover. Switch to MAX at the same 0.5%: incremental cost doubles to 100,000 (still 100× cheaper), because MAX/MIN’s crossover sits at 50%, not 100% — push the slider past half the table changed and the incremental bar turns crimson, now more expensive than just refreshing. Switch to MEDIAN and the incremental bar is replaced outright: there is no crossover to reach, because there is no cheap delta to begin with.

03

A YTD total nudges by one entry; a running median doesn't work that way

A company’s year-to-date revenue total is a materialized view over every sale this year — instead of re-summing every line item whenever someone asks for the total, the number sits in one cell, updated the instant a new sale posts: add this sale’s amount, done. That’s the whole incremental update, and it costs the same whether the ledger has a hundred entries or a hundred million, because a SUM’s structure guarantees a new value only ever touches the one running total.

Now imagine someone wants the median sale size tracked the same way. A single new sale can shift which existing transaction is “the middle one” by an amount that has nothing to do with the new sale’s own size — the update has to know where the new value ranks among every value near the middle of the whole set, which the running total never needed to know about anything. There is no one cell to nudge. That’s not a harder version of the SUM problem; it’s a different problem, and it needs a genuinely different piece of machinery (an order-statistics structure such as two balanced heaps) if it’s going to be incremental at all — or it settles for being refreshed the way SUM never has to be: recomputed from scratch, in full.

04

Data cubes: the same precompute-and-store trade, spread across every dimension at once

Everything above prices ONE materialized aggregate. A data cube (also called an OLAP cube) generalizes it: pre-aggregate a fact table along multiple dimensions at once — by day, by region, by product, and every combination of them — so a query cut along any one of those dimensions is a lookup instead of a scan. The full-refresh-vs-incremental question and the staleness question this lesson prices both still apply to a cube; they just apply once per cell the cube materializes, which is its own cost this lesson doesn’t total up. What a cube’s cells should actually contain, how they’re organized against fact and dimension tables, and when a cube is worth building versus querying raw data directly are dimensional-modelling’s and oltp-vs-olap’s territory — this lesson only sets up the vocabulary they need.

fullRefreshCost = baseTableRows × costPerRow

Proportional to the FULL table, every refresh, regardless of how little changed since the last one. This is the number incremental maintenance is trying to beat.

incrementalMaintenanceCost(SUM/COUNT) = changedRows × costPerRow

Proportional only to what changed. Crossover against a full refresh: f = 1 — cheaper right up until literally every row has turned over.

incrementalMaintenanceCost(MAX/MIN) = changedRows × costPerRow + rescanProbability × baseTableRows × costPerRow

rescanProbability = min(1, changedRows / baseTableRows) — the chance the extreme value itself was among the changed rows. Both terms scale with the changed fraction, which is why the crossover lands at f = 0.5, not f = 1.

06

The trade-off — cheap incremental maintenance is a property you have to check, not assume

Incremental maintenance isn’t free just because it’s usually cheaper. It’s cheaper under two conditions that both have to hold: the aggregate’s structure has to support a fixed-cost delta at all (SUM and COUNT always do; MAX and MIN do, with a rescan tax; MEDIAN doesn’t), and the change volume has to stay under that aggregate’s own crossover fraction. A team that picks incremental maintenance because “it’s the modern approach” without checking which side of the crossover their actual change rate sits on can end up paying MORE than a full refresh would have cost — the MAX/MIN row past 50% changed in the table above is exactly that trap.

A full refresh is not free either — it’s just simple. Its cost never changes regardless of change volume, which is a real advantage when change volume is unpredictable or near 100%: it has no crossover to overshoot, because it has no better case to lose. The trade a team is actually making by choosing incremental maintenance is code complexity and infrastructure (something has to watch every base-table write and compute the right delta) against a variable win that can turn into a variable loss.

Refresh cadence is the same “freshness costs maintenance overhead” shape this course has already priced twice, under different names. reading-explain-plans showed a query planner’s belief about selectivity lagging the table’s true selectivity between ANALYZE ticks, with a real cost to running on stale belief; wal-and-fsync showed a durability acknowledgment lagging the actual write until the next fsync. A materialized view’s refresh interval is the same family: staleness is bounded by how often you pay to refresh, and tightening that bound always costs more refreshes, never fewer, regardless of which of the three systems is doing the refreshing.

07

In the wild

“Materialized Views and Data Cubes” is Kleppmann and Riccomini’s own heading for exactly this territory — Designing Data-Intensive Applications, 2nd ed., ch. 4, pp. 144–145: a materialized aggregate “can be useful in data warehouses,” and “a data cube (also known as an OLAP cube) does this by creating a grid of aggregates grouped by different dimensions.” Their own honest caveat on the cube’s limits matches this lesson’s median stance in spirit: “the disadvantage is that a data cube doesn’t have the same flexibility as querying the raw data” — precomputing along fixed dimensions is exactly what makes some queries cheap and others (anything outside those dimensions) no cheaper than before.

“Incremental view maintenance” is their term too, not one this lesson invented — ch. 12, pp. 516–517: “many SQL queries can’t be easily or efficiently converted to incremental computation,” which is the book’s own version of this lesson’s median refusal, generalized to “many,” not just one named aggregate. Their fix for the queries that CAN be converted — “IVM algorithms recompute and update only data that has changed” — is incrementalMaintenanceCost’s whole premise, and they name Materialize, RisingWave, ClickHouse, and Feldera as production systems built around doing exactly that with a stream of base-table changes rather than a periodic batch refresh.

The staleness trade this lesson’s refreshFrequencyTradeoff prices is the same shape reading-explain-plans already walked through for query-planner statistics, reused here for a different clock (a view’s own refresh schedule) rather than re-derived — the two lessons agree on the pattern without either one needing the other’s specific numbers.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A materialized view is a query's result, PRECOMPUTED and STORED — a read becomes a lookup against that stored result instead of a re-run of the underlying (often aggregating or joining) query, which is what makes reads fast; the entire cost of that speedup shows up somewhere else, in keeping the stored result in sync with the base table
  • FULL REFRESH re-runs the whole query and replaces the whole stored result — its cost is `fullRefreshCost = baseTableRows * costPerRow`, proportional to the FULL table every single time, regardless of how much actually changed since the last refresh
  • INCREMENTAL VIEW MAINTENANCE (IVM) computes only the delta a base-table change makes to the stored result — cost proportional to `changedRows` alone — but ONLY when the aggregate's structure supports decomposing into a delta; whether it does depends entirely on which aggregate function is involved, not on how the query is written
  • SUM/COUNT decompose cleanly (a changed row only updates the bucket it belongs to), so `incrementalMaintenanceCost` for them is exactly `changedRows * costPerRow` and their crossover against a full refresh sits at f=1 — incremental stays cheaper right up until literally every row has changed
  • MAX/MIN mostly decompose but carry a probability-weighted rescan cost (if the row that changed WAS the current extreme, there's no shortcut — recompute by scanning what's left), which is why their crossover sits at f=0.5 rather than f=1: incremental maintenance for a running max/min stops being the clearly cheaper option once half the table has turned over, far short of "everything changed"
  • MEDIAN has no fixed-cost delta update at all — `incrementalMaintenanceCost` throws rather than assign it a cheap cost, because inserting or removing one value can shift which row is the middle one, and finding out requires knowing that value's rank among every other row; the model's honesty here is the point, not a limitation to work around
  • A DATA CUBE generalizes the same precompute-and-store idea across MULTIPLE dimensions at once (day × region × product × …), so a query along any one of those cut points is fast — the same full-refresh-vs-incremental and staleness trade-offs apply to it, at the cost of the cube's own cell count; the storage shape that makes a cube queryable this way is `dimensional-modelling`'s and `oltp-vs-olap`'s territory, not this lesson's

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A 10,000,000-row base table backs a materialized SUM aggregate. Since the last refresh, 50,000 rows (0.5%) have changed. Roughly how much cheaper is incremental maintenance than a full refresh here, and does that ratio hold as more rows change?

    How sure are you, before you look?
    At 0.5% changed, incremental maintenance costs 50,000 row-touches against the full refresh's 10,000,000 — a 200× saving. That ratio does NOT hold as a constant: incremental cost for SUM scales linearly with `changedRows`, so the saving shrinks as more of the table changes, reaching parity (no saving at all) only once 100% of rows have changed — SUM's crossover fraction is 1. Incremental is cheaper than full refresh at every point below that, just by a shrinking margin.
    Did you have that?
  2. Cued recall

    The same 10,000,000-row table backs a MAX aggregate instead of a SUM, with the same 0.5% of rows changed. Is the incremental-maintenance cost the same 50,000 row-touches?

    How sure are you, before you look?
    No — it's 100,000, twice the SUM/COUNT figure, because of the probability-weighted rescan term: with a 0.5% chance the row that changed happened to be the current max, the expected extra cost is 0.5% of the full table (50,000) added to the 50,000 baseline delta cost. This is also why MAX/MIN's crossover sits at f=0.5 rather than SUM/COUNT's f=1 — the rescan term grows with the SAME fraction as the delta term, so the two together reach full-refresh cost at half the change volume, not nearly all of it.
    Did you have that?
  3. Near transfer

    A team maintaining a materialized MEDIAN sees that their SUM-based materialized views update via a cheap per-row trigger, and reasons: "MAX/MIN already needed a bit of extra rescan logic beyond the simple SUM case — median is probably just a bigger version of that same pattern, a rescan that happens a bit more often." Is that the right way to think about it?

    How sure are you, before you look?
    No — it treats a difference in DEGREE as if it were the same as MAX/MIN's, when it's a difference in KIND. MAX/MIN's rescan is occasional and bounded: the ONLY row that ever forces one is the current extreme itself, and once you rescan you get a stable new extreme back that's cheap to maintain again until it, too, is removed. A median has no such stable structure to fall back on — every single insert or delete can, in principle, shift which element is "the middle one," and finding out requires knowing that value's rank among everything else, not just checking one distinguished row. There is no fixed-cost delta rule for a median the way there is for a sum, a count, or even a max; a running median needs a genuinely different data structure (e.g., two balanced heaps) built for that purpose, which is a different tool than "incremental view maintenance applied to an ordinary aggregate query." `incrementalMaintenanceCost` throws for median specifically to keep that distinction from getting hand-waved into "just add a rescan."
    Did you have that?
  4. Far transfer

    The abstraction is: precomputing and storing a derived result so that reading it is cheap, at the cost of someone doing work to keep it in sync with a source that keeps changing — and that sync work is cheap only when the derived result's structure allows a small change at the source to be translated into a small, localized update at the derived result. Name an instance outside computing.

    How sure are you, before you look?
    A company's running year-to-date financial total versus its published each-item ledger. The YTD total is a materialized view over every transaction: instead of re-adding every line item whenever someone asks "what's our total revenue this year," the total is kept as a single stored number, updated incrementally — one new sale just adds its amount to the running total, a cheap, localized update, exactly like SUM's `changedRows`-only cost. Now compare a *running median transaction size* someone wants tracked the same way: a single new sale can shift which transaction is "the middle one" by an amount that has nothing to do with the new sale's own size, and finding the new median in general means re-examining the sorted order of transactions near the middle — there's no single running number you can nudge the way YTD total is nudged. The finance team can keep a YTD total in a spreadsheet cell for free; keeping a live running median requires a genuinely different piece of machinery (a sorted structure), or accepting that it's only refreshed periodically, in full, from scratch.
    Did you have that?
