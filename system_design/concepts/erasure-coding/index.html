Tier 3 · Storage and state Erasure coding

A (10,4) erasure code stores data at 1.4x instead of the 5x a 4-failure-tolerant replica needs — and rebuilds one lost fragment by reading ten nodes instead of one

Split the data into K pieces, compute M extra parity pieces, and any K of the K+M survive-together. That single trick is why cold storage at Facebook, Azure, and every major object store runs erasure-coded instead of triple-replicated — the storage bill drops by multiples. The bill nobody puts next to that saving is what happens when a disk actually dies: the same K that shrank the storage cost is exactly what it now costs, in nodes touched and bytes moved, to get one fragment back.

Read first — replica-placement-failure-domainsquorums

01

Cutting the storage bill in half triggered a rebuild that saturated the rack

A storage team is paying for 3x replication on a multi-petabyte cold archive: every object written three times, on three different disks, so that losing any two disks still leaves the data readable. Someone runs the numbers on switching to a (10, 4) Reed-Solomon erasure code — split each object into 10 data fragments, compute 4 parity fragments, store all 14 — and finds it tolerates the same four simultaneous failures 3-way replication’s cousin (5-way replication) would need to promise, at a fraction of the storage. The migration ships. The storage bill drops by more than half.

Three weeks later a single disk dies — an ordinary, expected, Tuesday-afternoon disk death — and the rebuild saturates the rack’s network for the better part of twenty minutes, something the old replicated scheme never did for a single-disk failure. Nothing is broken. The storage math was exactly right, and it was never the whole story.

02

Assume the storage-overhead number is the whole comparison

The belief this has to break
Erasure coding is strictly better than replication because it needs less storage for the same fault tolerance.

It needs less storage. That part is real and it is large — this lesson computes exactly how large. What that comparison leaves out is what happens the moment a fragment is actually lost: erasure coding’s rebuild and its degraded reads get MORE expensive as the same K that shrank the storage bill grows, and nothing about the storage formula warns you about that, because the storage formula doesn’t mention rebuilds at all.

Replication’s rebuild is “copy one intact replica from one other node” — flat, and independent of how many replicas you keep. Erasure coding’s rebuild is “recompute the lost fragment from K surviving fragments, wherever they live” — and that K is the same K sitting in the storage-overhead denominator that just made the storage picture look so good.

Predict A (10, 4) erasure code and a 5-way replica both tolerate 4 simultaneous failures. One disk dies. Which scheme moves more network bytes to rebuild what that one disk held, at a matched fragment/replica size?
A fragment carries no complete information alone, so reconstructing the ONE that was lost needs K=10 surviving fragments read over the network — 10x the bytes (and, at matched per-fragment fetch cost, 10x the time) that replication needs to copy its ONE intact replica from ONE other node. The failure tolerance is identical; the rebuild cost is not.
Show it without answering

At the rig’s default — K=10, M=4, 256 MiB fragments, a 15 ms per-fragment fetch — erasure coding costs 1.4x the original size against replication’s 5x, a real and large saving. Rebuilding one lost fragment then costs 2.50 GiB moved in 150 ms, against replication’s 256 MiB in 15 ms — exactly 10x more, in both bytes and time, because K=10 is the number of survivors the decoder needs. A read served while a fragment is down waits for the slowest of those 10 parallel fetches and then decodes: 51.9 ms against replication’s plain 15 ms fetch from an intact replica — 3.5x slower, with no decode step on the replication side at all.

03

The intuition: a jigsaw puzzle piece versus a photocopy

Replication is a stack of identical photocopies of one picture. Lose one copy, and getting it back is trivial: photocopy any other copy in the stack. The cost you pay is up front — you had to make and store N-1 extra photocopies you hope never to need.

Erasure coding is a jigsaw puzzle cut into K pieces, plus M extra pieces cleverly drawn so that any K of the K+M pieces, put together in the right way, recreate the whole picture — not just the K you started with. That is genuinely more storage-efficient: you are not storing K complete copies of anything, only K+M pieces that together are barely bigger than the original. But now lose one piece, any piece, and there is no photocopy of that specific piece anywhere. The only way to know what it looked like is to lay out K of the other pieces and work out what’s missing — and that reconstruction touches every one of those K pieces, not just the one you lost.

Replication trades storage for a trivial repair: copy the one thing you still have. Erasure coding trades that trivial repair for storage efficiency: the price of a smaller original is that recovering any one piece needs K of the others, every time.

04

The mechanism: three formulas, and the same K in every denominator and every multiplier

storageOverhead(K, M) = (K + M) / K  ·  replicationOverhead(faults) = faults + 1

Both express the same thing — a multiplier on the original data size — for the SAME number of tolerated failures M. As K grows for a fixed M, (K+M)/K → 1: the marginal storage cost of one more failure of tolerance shrinks toward nothing. Replication’s cost per extra failure never shrinks; it is always one more whole copy. Asserted against a hand computation of (K+M)/K and faults+1 in erasure-coding.test.mjs.

rebuildCost: erasure bytesMoved = K × fragmentSize, time = K × perFragmentFetchMs replication bytesMoved = fragmentSize, time = perFragmentFetchMs

At a MATCHED per-unit size (the same fragmentSize stands for one fragment or one replica), the amplification is exactly K in both bytes and time — not a tendency, an identity, because the arithmetic is a direct multiple by K. M does not appear in this formula at all: it bounds how many simultaneous losses the code can still survive, but it never changes what a single rebuild costs.

degradedReadLatency: erasure = orderStatMean(K, K, meanFetchMs) + decodeMs replication = replicaFetchMs  ·  no decode term

Decoding needs every one of the K fragments it fetched, not just the fastest — so the read is gated on the SLOWEST of K parallel fetches, the K-th-of-K order statistic, reused unchanged from quorum.mjs (the exact formula that models waiting for the last of a write quorum). Replication’s degraded read is a single fetch from a different, intact replica: no waiting on multiple sources, no decode.

Three formulas, one shared variable. K sits in the denominator of the storage formula (bigger K, smaller overhead) and as a direct multiplier in the other two (bigger K, bigger rebuild and bigger degraded-read cost). There is no value of K that improves all three at once.

06

The trade-off: storage cost and repair cost are the same lever, pointed opposite ways

Raising K buys storage efficiency and sells rebuild speed and degraded-read latency. Every extra data fragment shrinks (K+M)/K a little further toward 1, and simultaneously adds one more survivor the decoder must fetch and one more source the degraded read must wait on. It is not a diminishing-returns trade like raising N in a quorum — it is a direct trade, K-for-K, on two different axes at once.

Raising M buys more simultaneous failures survived and sells storage, on both schemes, but erasure coding sells much less of it. Going from M=4 to M=8 at K=10 doubles replication’s overhead outright (5x → 9x) while erasure coding’s overhead only grows from 1.4x to 1.8x — the fixed K keeps amortizing the extra parity. M does not change either scheme’s per-rebuild cost at all; it only changes how many losses can happen before a rebuild becomes impossible.

What actually decides which scheme to run is which failure is common and which is rare. A system where disks die often and rebuilds are routine wants replication’s flat, cheap-per-event repair, even at higher steady-state storage cost. A system storing cold, rarely-accessed, rarely-failing data — the exact profile of an archival tier — wants erasure coding’s low steady-state storage cost, and can afford an occasional expensive rebuild because rebuilds there are genuinely rare. Production systems routinely run BOTH: hot, frequently-accessed, frequently- rebuilt data replicated; cold archival data erasure-coded. Picking one scheme for an entire storage system, rather than per tier, is the mistake this lesson’s slot 1 incident actually was.

07

In the wild

Reed and Solomon’s original construction is fifty years older than any of the systems that use it. I. S. Reed and G. Solomon, “Polynomial Codes over Certain Finite Fields,” Journal of the Society for Industrial and Applied Mathematics, 8(2), 1960, describes the code family this lesson calls (K, M) throughout — the property that any K of K+M encoded symbols determine the rest is a theorem about polynomials over a finite field, not a storage-system design choice.

DDIA states the comparison to replication directly, in the context of distributed filesystems: “Replication may mean simply keeping several copies of the same data on multiple machines… or using an erasure coding scheme such as Reed–Solomon codes, which allows lost data to be recovered with lower storage overhead than full replication. The techniques are similar to RAID, which provides redundancy across several disks attached to the same machine” (Kleppmann & Riccomini, Designing Data-Intensive Applications, 2nd ed., pp. 459–460, ch. 11 “Batch Processing”).

Azure Storage’s production erasure coding was redesigned specifically because of this lesson’s rebuild-cost trade-off. Huang et al., “Erasure Coding in Windows Azure Storage,” USENIX Annual Technical Conference, 2012, documents Local Reconstruction Codes (LRC) — a scheme built precisely because standard Reed-Solomon’s repair cost (reading K fragments to rebuild one) was measured as too expensive at their scale, trading a small amount of extra storage overhead for a smaller number of fragments read per repair.

Hadoop’s HDFS has shipped erasure coding as an alternative to 3x replication since Hadoop 3.0, documented in the Apache Hadoop project’s “HDFS Erasure Coding” guide, typically configured as a 6-of-9 or 10-of-14 (K, M) Reed-Solomon scheme for cold data specifically because that data is rarely rebuilt — the same “erasure-code the cold tier, replicate the hot tier” split this lesson’s slot 6 describes.

Model and numbers — every figure computed by src/sim/erasure-coding.mjs and asserted in src/sim/erasure-coding.test.mjs (14 tests): storage overhead and rebuild cost against hand computations of the defining formulas, and degraded-read latency against quorum.mjs’s own order-statistic formula, reused unchanged for the “wait on the slowest of K parallel fetches” step.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A Reed-Solomon (K, M) erasure code splits data into K fragments, computes M parity fragments, and guarantees ANY K of the resulting K+M reconstruct the original — the MDS (maximum distance separable) property is a mathematical guarantee of the code, not an engineering approximation
  • Storage overhead is (K+M)/K for erasure coding versus faultsTolerated+1 for replication, at the SAME fault tolerance — K=10, M=4 costs 1.4x against a 5-way replica's 5x, and the gap widens as the fault-tolerance target rises (at M=8 it is 1.8x versus 9x, a 5x saving)
  • The exact K that shrinks the storage bill is what inflates the rebuild bill: rebuilding ONE lost fragment requires fetching K surviving fragments — because a single fragment carries no complete information alone — versus replication's rebuild, which is copying ONE intact replica from ONE other node
  • At matched per-unit fetch cost, erasure coding's rebuild moves K times the bytes and takes K times as long as replication's rebuild — an amplification that is exactly K, not approximately K, because the arithmetic is a direct multiple
  • A degraded read (serving a read while a fragment is down) under erasure coding is gated on the slowest of K parallel fragment fetches — the K-th-of-K order statistic, reused unchanged from quorum.mjs — plus a real CPU decode step; replication's degraded read is one plain fetch from an intact replica, no decode
  • Storage cost and rebuild/degraded-read cost move in OPPOSITE directions as K grows: wider K (more, smaller fragments for the same M) makes erasure coding cheaper to store and slower to repair or read degraded — there is no K that wins on all three axes at once

  1. Cued recall

    A team needs to tolerate 4 node failures. Compare a (10, 4) Reed-Solomon erasure code against 5-way replication (which is what "tolerate 4 failures" costs in pure replication). What is the storage overhead of each, as a multiplier on the original data size?

    How sure are you, before you look?
    Erasure coding: (K+M)/K = (10+4)/10 = 1.4x. Replication: faultsTolerated+1 = 4+1 = 5x. Same fault tolerance, 3.6x less storage — computed by storageOverhead(10,4) and replicationOverhead(4), asserted against a hand computation in erasure-coding.test.mjs.
    Did you have that?
  2. Cued recall

    Why does rebuilding ONE lost fragment in a (K, M) erasure code require reading K surviving fragments, rather than just copying the lost one from wherever a spare might be?

    How sure are you, before you look?
    Because a fragment is not a copy of anything — it is one coordinate of an encoding where only the FULL set of any K coordinates carries complete information. There is no "spare" of a specific fragment anywhere in the system; the only way to produce it is to run the decoder, and the decoder's input requirement is K fragments, from wherever they happen to live. That K-fragment read, potentially from K different nodes over the network, is the entire rebuild cost — there is no cheaper path.
    Did you have that?
  3. Cued recall

    At fragment size 256 MiB and a 15 ms per-fragment network fetch, what does it cost — in bytes moved and in time — to rebuild one lost fragment in a (10, 4) scheme, against copying one lost 256 MiB replica?

    How sure are you, before you look?
    Erasure coding: 2.50 GiB moved, 150 ms (10 fragments × 256 MiB, 10 × 15 ms). Replication: 256 MiB moved, 15 ms (one copy). Both the bytes and the time are exactly 10x higher for erasure coding — computed by rebuildCost({ K: 10, M: 4, fragmentSizeBytes, perFragmentFetchMs: 15 }).
    Did you have that?
  4. Near transfer

    A team compares a (20, 4) erasure code against a (5, 4) erasure code — same M=4 failures tolerated either way — and picks K=20 because it drops storage overhead from 1.8x to 1.2x. What did that comparison leave out?

    How sure are you, before you look?
    The rebuild and degraded-read cost, which moved the OPPOSITE direction and by a lot. Rebuilding one lost fragment now reads 20 survivors instead of 5 — 4x more network bytes and 4x more time for the identical 4-failure tolerance the smaller K already provided. A degraded read is now gated on the slowest of 20 parallel fetches instead of 5, which is a real latency increase (the K-th-of-K order statistic grows with K) that has nothing to do with how many failures the scheme survives. This is the same shape as quorums.mdx's "raising N buys everything except money" — except here, raising K is NOT free on every axis: it trades one cost for two others, and a team that only checked the storage line would ship a rebuild that saturates the network every time a disk dies.
    Did you have that?
  5. Far transfer

    The abstraction is: encoding information by combining many parts together is compact to store, because any one part now depends on all the others — but recovering any single part after damage requires consulting MANY of the others. Keeping independent, complete copies instead is expensive to store, but recovering one damaged copy requires consulting only ONE other. Name an instance of this trade-off outside computing.

    How sure are you, before you look?
    A statically indeterminate structure (a continuous truss or moment frame) versus a set of independent redundant load paths (parallel, individually-rated cables). A continuous truss uses its material efficiently — every member shares load with its neighbors, which is the structural equivalent of "compact storage" — but if one member fails, the load does not have one clean substitute: it redistributes across MANY surrounding members, and an engineer must re-analyze the whole indeterminate structure to know it still holds (the truss's version of "reading K survivors to reconstruct one"). A design with N fully independent parallel cables, each individually rated to carry the whole load, is comparatively wasteful of material — the "replication" storage cost — but losing one cable has a trivial, local fix: the other cables were already carrying the design load alone, no system-wide recomputation required. Efficient, shared encodings are cheap until something breaks; independent, redundant copies are expensive but the failure mode stays local.
    Did you have that?
