Tier 5 · Moving data around Cache writing strategies start here

A cache and a database are two copies of the truth, and something has to say which one gets written first

Cache-aside, write-through, write-behind, refresh-ahead, write-around, read-through — six names, one axis. Every one of them is an answer to a single question: when a write happens, does the cache get touched before, after, instead of, or independent of the database — and what does that ordering cost in latency, data loss, and staleness.

01

Two copies of the truth, and somebody has to go first

A cache and a database are, at the moment of a write, two separate copies of the same fact. The database is the one you trust. The cache is the one you read from, because reading from it is cheap. The instant a write happens, those two copies can disagree — and every strategy in this lesson is a different answer to which one gets written first, and what happens to the other one in the meantime.

That is the whole taxonomy. Not “which cache library,” not “how big should the cache be” — this lesson already covered eviction and stampedes without touching this question once. This one is purely about ordering a write against the source of truth, and it has exactly six named answers.

02

Assume they're all roughly the same trade

The instinct, on first hearing six names for one idea: they must all cost about the same, and picking one is a matter of taste or which library you already have. The numbers below say otherwise — two of these six differ by an order of magnitude in write latency for the identical database, and one of them has a data-loss number the other five do not have at all.

The belief this has to break
Six names for the same idea means six roughly interchangeable choices.

They split into four genuinely different latency shapes and only one of the six carries a real crash-loss risk. Write-through and write-behind sit at opposite ends of the same 20 ms database write — one pays it every time, the other never makes the caller wait for it — and that is not a rounding difference, it is the entire point of choosing one over the other.

Predict A database write takes 20 ms. A cache write takes 2 ms. Under write-through, the cache writes synchronously to the database before acking. Under write-behind, the cache acks immediately and flushes later. What does each cost the caller, per write?
Write-through does not acknowledge the caller until the database write has completed, so it pays the cache hop AND the full database latency: 2 + 20 = 22 ms. Write-behind acknowledges the instant the cache holds the value — 2 ms — and the database write happens afterward, off the caller's clock entirely. The database's 20 ms did not vanish in the write-behind case. It still happens. Nobody is just waiting for it anymore.

03

Three shapes, not six

Six names collapse into three latency shapes and a fourth idea that is not about latency at all.

Cache in the write path, synchronously — write-through. The caller waits for both hops. Correctness is perfect: the cache is never ahead of or behind the database, because it can never acknowledge a write the database has not also confirmed.

Cache in the write path, asynchronously — write-behind. The caller waits for one hop. The database write still happens, on the cache’s own schedule, which means there is now a window where the cache and the database disagree and a crash inside that window is unrecoverable data.

Cache out of the write path entirely — cache-aside, write-around, refresh-ahead, read-through. The caller talks to the database directly; the cache write latency line does not exist for any of these four, because there is no cache write to wait on. They differ from each other only in what happens on the next read, not on this write at all:

  • Cache-aside (lazy loading). The application reads through the cache on a hit and falls back to the database on a miss, populating the cache as it goes. On a write, the application writes the database directly and then — as a second, separate step — invalidates or updates the cache entry. Those two operations are not atomic. Between them there is a real gap where a concurrent reader can see the old cached value even though the database already has the new one. cache-invalidation is the lesson devoted to making that second step actually safe; this one only names that it exists.
  • Write-around. Writes go straight to the database and the cache is not touched at all — not even an invalidation. The entry gets populated later, only if and when the key is read again and misses. This is the right shape for data that is written far more often than it is re-read, because cache-aside’s invalidation would just be busywork for a key nobody asks for next.
  • Refresh-ahead. This one is not really a write-path strategy at all, and the honest thing to do is say so rather than force a sixth latency number where none exists: refresh-ahead’s write path is identical to cache-aside’s. What is different is on the read side — before a hot entry’s TTL expires, the cache proactively recomputes it in the background, so a request that would otherwise arrive during a cold-miss latency spike instead finds a fresh value already sitting there. It is a bet that a currently-hot key stays hot long enough for the early refresh to pay off; cache-stampede’s probabilistic early-expiry fix is the same underlying mechanism, applied to the dogpile-on-expiry problem specifically.
  • Read-through. Also not distinguished by where a write goes — it is functionally identical to cache-aside there. The difference is architectural: the cache library itself owns the miss-then-populate logic instead of the application code owning it. A read-through cache is handed a loader function once and calls it on every miss internally; a cache-aside application writes that same “check cache, fall back to DB, populate cache” logic itself, every time it needs it. Same data flow, different party responsible for it.
04

What write-behind's speed actually costs

Write-behind is the only strategy on this page with a real data-loss number, and it is not a vague “there is some risk” — it is a computable expectation.

E[writes lost] = writeRate × (flushInterval / 2)

A crash lands at a uniformly random point in the flush cycle, so the expected elapsed time since the last flush is HALF the interval, not the full interval. The worst case — a crash one instant before the next scheduled flush — is exactly double the expectation, always.

At 100 writes/second and a 10-second flush interval, computed by the model:

node -e "import('./src/sim/cache-writing-strategies.mjs').then(m => {
  const r = m.writeBehindLossWindow({ flushIntervalMs: 10_000, writeRatePerSec: 100, avgBytes: 500 });
  console.log(r);
})"

that prints an expected loss of 500 writes (250,000 bytes) against a worst case of 1,000 writes (500,000 bytes) — the worst case is exactly double, because the expectation is taken over a uniform crash point across the interval and the worst case is the interval’s full length. This is the identical shape replication.mjs’s writesLostOnFailover already uses for an async replica’s lag — a write-behind flush buffer is, mechanically, the same “unflushed backlog times the write rate” exposure a replication lag is, and the model reuses that function unchanged rather than re-deriving it.

The lever is the flush interval, and it is linear. Doubling the flush interval from 10s to 20s doubles both numbers. Halving it to 5s halves them. There is no clever tuning here — only a direct trade of “how much database load do the flushes generate” against “how many writes can a crash take with it,” and the two move in exactly opposite directions.

06

The trade-off — the cache never leaves the write path for free

Write-through buys perfect consistency and charges every single write the full database latency, forever. There is no write that skips the line. If the database is slow, every caller of every write is slow, with no exceptions — this is the strategy to pick when the correctness guarantee is worth more than the latency, which is most of the time for anything touching money, inventory, or a permission.

Write-behind buys the lowest possible write latency and charges it in two currencies at once: a crash-loss window that is a genuine probability-weighted expectation, not a rare edge case, and a staleness window on any reader who can reach a database replica the flush has not caught up to yet. Neither of those costs shows up in a load test that never kills the cache process — which is exactly why write-behind’s failure mode tends to be discovered in production rather than in a demo.

Cache-aside and write-around buy simplicity — the cache is never a dependency of the write path, so a cache outage cannot block a write — and charge it as a second, non-atomic operation (cache-aside) or as a cold cache on every re-read of write-heavy data (write-around). Cache-aside’s charge is cache-invalidation’s subject in full; write-around’s charge is invisible until something that used to be a cache hit becomes a guaranteed miss because it was never invalidated in the first place — it was simply never written there.

Refresh-ahead and read-through do not appear in this trade-off table on their own terms, because neither one changes the write-side cost at all. Refresh-ahead trades a little unnecessary refresh work for avoiding a cold-miss latency spike on hot keys — a bet, priced the same way cache-stampede’s early-expiry fix is priced. Read-through trades nothing measurable; it moves code, not cost.

07

In the wild

Write-through and write-behind are exactly what CPU cache designers have called them for decades, and the vocabulary transferred to application caching unchanged — a CPU write-back cache defers the store to main memory the same way an application write-behind cache defers the store to its database, for the identical reason (the store is slow relative to the thing doing the writing) and with the identical risk (a power loss before write-back completes loses the dirty cache line).

Redis and most managed cache products do not implement any of these as a built-in mode — they are patterns the application (or a library sitting in front of Redis) implements, not a configuration flag Redis itself exposes. AWS’s own caching guidance documents all six under these exact names, which is the closest thing this taxonomy has to a canonical published source; it is an industry pattern vocabulary rather than a single paper’s contribution.

Write-behind shows up under the database’s own name in specific products — a database’s buffer pool that acknowledges a transaction once it is in the write-ahead log and flushes dirty pages to disk later is the same write-behind shape one storage layer down, which is why wal-and-fsync and this lesson describe the identical “ack fast now, flush durably later, bound the crash-loss window” trade at two different layers of the stack.

CDNs run write-around by default for anything they did not push themselves — an edge node never eagerly caches an object on a client’s PUT; it waits for the first subsequent GET to pull it in, for the same reason write-around exists in a key-value cache: most written objects are never immediately re-read from that same edge, so eager population would waste cache space on objects nobody asks for again. cdn covers this network-hop instance of the same idea directly.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • All six strategies answer one question: when does the cache get written or refreshed relative to the database, not "is caching good"
  • Write-through pays cache latency plus full database latency on every write; write-behind pays only cache latency because the database write happens off the caller's clock
  • Cache-aside and write-around both keep the cache out of the write path entirely — the difference between them is only what happens on the next read miss
  • Write-behind's low latency is a loan against a crash: the expected loss is exactly half the worst case, because a crash lands at a random point in the flush cycle
  • Refresh-ahead and read-through do not change where a write goes at all — they change who owns the read-side miss-then-populate decision, which a write-latency model cannot show

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A cache write-through layer adds 2 ms of its own latency in front of a 20 ms database write. A write-behind layer adds the same 2 ms cache hop but does not wait on the database at all. What does each one cost the caller, per write?

    How sure are you, before you look?
    Write-through costs 22 ms — the cache hop plus the full database write, because it does not acknowledge the caller until the database has confirmed. Write-behind costs 2 ms — only the cache hop — because it acknowledges the instant the cache holds the value and flushes to the database later, off the caller's clock. The database latency did not disappear in the write-behind case; it just moved to a point in time the caller is no longer waiting on.
    Did you have that?
  2. Cued recall

    A write-behind cache flushes to the database every 10 seconds and receives 100 writes per second. If the cache process crashes at a uniformly random point between flushes, what is the EXPECTED number of writes lost — not the worst case?

    How sure are you, before you look?
    500 writes (250,000 bytes at 500 bytes/write), not the worst-case 1,000. A crash at a random point in a 10-second cycle has an expected elapsed time since the last flush of 5 seconds — half the interval, because the crash is equally likely to land anywhere in it — and 5 seconds × 100 writes/s = 500. The worst case (a crash one instant before the next flush) is exactly double the expected case, always, for any flush interval and rate.
    Did you have that?
  3. Near transfer

    A team reads that write-behind has "lower write latency than write-through" and switches their session-store cache from write-through to write-behind, expecting a straightforward win. Reads from the session store sometimes hit a read replica of the database. What did they just introduce that write-through never had?

    How sure are you, before you look?
    A staleness window sized by however long the write-behind flush plus replica replication lag takes. Write-through never has this: the cache and database are updated inside the same synchronous operation, so a replica that has received the write at all has received the current value. Write-behind acknowledges before the database write even happens, so a read hitting a replica can see a session state older than what the cache already told the writer succeeded — the exact "leader-follower-replication" async staleness gap, just relocated behind a cache instead of a database leader.
    Did you have that?
  4. Far transfer

    The abstraction is: moving an operation off the critical path lowers the latency the caller experiences, but does not delete the work — it relocates the work's risk to whoever is waiting on it after the fact, for however long the relocation window is open. Name an instance outside caching.

    How sure are you, before you look?
    Asynchronous logging and buffered I/O. A process that writes to an in-memory log buffer and returns immediately is faster per call than one that fsyncs every line — exactly write-behind's trade — but a crash before the buffer flushes loses every line written since the last flush, which is why crash-safety documentation for buffered loggers always states an explicit flush interval or "at most N seconds of logs may be lost" bound. Airline overbooking is the same shape in the opposite domain: selling a seat before confirming a no-show "acks" the sale faster and relocates the risk to the gate agent who may have to un-sell it later.
    Did you have that?
