Tier 3 · Storage and state Graph query languages

A 2-hop query is a 2-way join. A traversal of unknown depth needs recursion — and by hop 10, that costs 93× more than a graph engine's own pointer-following

A relational join can express any FIXED number of hops — "friends of friends" is a 2-way self-join, "friends of friends of friends" is a 3-way one. What it cannot express is "however many hops it takes": a variable-depth traversal has no fixed arity, so no fixed number of JOIN clauses can write it. SQL's late answer is `WITH RECURSIVE`, which runs the same join once per hop and, naively, has to re-check every new row against everything already visited — a check that gets more expensive every additional hop. A purpose-built graph engine skips all of that: every node already stores direct pointers to its neighbors, so following an edge is one O(1) pointer read, full stop. This lesson computes both costs as depth grows and shows exactly why the gap between them widens rather than staying flat.

Read first — join-algorithms

01

60 operations, or 1,380 — same 3-hop traversal, same data

“Find everyone within 3 hops of Alice” and “find everyone Alice can reach, however many hops it takes” look like the same kind of question with a different number typed in. They are not. The first is a fixed-arity join — write 3 self-joins (or their union) and you’re done, the same way join-algorithms.mdx prices any join between tables of known size. The second has no fixed arity at all: the number of hops needed depends on the graph, not on the query text, and no fixed number of JOIN clauses can express “however many it turns out to be.” That gap is why SQL needed a genuinely new construct — WITH RECURSIVE — decades after the relational model itself, and why a purpose-built graph engine can still beat it by a widening margin even once that construct exists. At 3 hops and 20 nodes discovered per hop, this lesson’s model puts a naive recursive-SQL traversal at 1,380 operations against a graph engine’s 60 — and by 10 hops, 18,600 against 200. Same traversal. The gap is not fixed; it grows with depth, and this lesson computes exactly why.

02

Assume a graph query is just a join with extra syntax

The belief this has to break
A graph-shaped query is really just a join in disguise — Cypher and SPARQL are convenient syntax for something SQL could always express, and any performance difference is a rounding error or a vendor benchmark trick.

Rounding error is not the right size word for a difference that widens every additional hop. A fixed-depth graph query really is just a join in disguise — “friends of friends” is a 2-way self-join whichever language you write it in, and there’s no fundamental reason SQL should be slower at that. The claim only breaks for variable-depth traversal, which a fixed-arity join cannot express at all, at any performance, because it isn’t a join with a different cost — it’s a different computation (iterate until nothing new is found) bolted onto a language that didn’t have that primitive for decades. Once that iteration exists (WITH RECURSIVE), it still has to pay for re-deriving “have I visited this node” from scratch every pass, which a graph engine’s index-free adjacency was built to never need.

Predict A recursive-SQL traversal and a graph-engine traversal both start from the same node and reach the same 20 new nodes per hop. Going from 3 hops to 10 hops, what happens to the cost RATIO between them (SQL cost ÷ graph-engine cost)?
A naive recursive CTE checks every newly-found row against an already-visited working table that is bigger on every subsequent hop, so its per-hop cost keeps climbing. A graph engine's index-free adjacency check is an O(1) lookup that doesn't grow with depth, so its per-hop cost stays flat. Two costs where one grows and the other doesn't produce a ratio that keeps widening, not one that holds steady — this model puts it at roughly 23× at 3 hops and roughly 93× at 10 hops for the same branching factor.
Show it without answering

At the rig’s default — 6 hops, 20 nodes discovered per hop — recursive SQL costs 6,360 operations (360 re-joining the edge table, 6,000 re-scanning the growing visited set) against a graph engine’s 120, a 53× gap. Drag hop depth up and the crimson curve pulls away from the teal one faster the further right you go — that’s the widening this lesson’s numbers below make exact.

03

Climbing a family tree, one generation at a time

Ask a genealogy database “who are Alice’s grandparents” and you’re asking for exactly 2 hops up a parent-of-parent chain — a 2-way self-join, done. Ask it “who are ALL of Alice’s ancestors” and there’s no fixed number of hops to name: some branches of a family tree run out after 4 generations of missing records, others go back 12. A query language that only supports fixed-hop joins genuinely cannot answer the second question — not slowly, not expensively, not at all — no finite number of JOIN parents AS p2 ON ... JOIN parents AS p3 ON ... clauses covers every possible tree shape. The only way to answer it is to climb one generation, see who that reaches, climb again from there, and keep going until a generation adds nobody new. That’s not a implementation detail — it’s the only shape the question has.

04

Three answers to the same question, three cost shapes

FIXED-DEPTH JOIN     "exactly N hops" -- write N self-joins (or their union), done at query-write time
                      cost: join-algorithms.mjs's own shapes, unchanged -- this case was never the problem

RECURSIVE SQL         WITH RECURSIVE -- repeat the SAME join once per hop until nothing new turns up
(WITH RECURSIVE)      naive version also re-checks every new row against everything already visited
                      cost per hop: edge-join (flat) + dedup-scan (GROWS every hop) -- worse than linear

GRAPH ENGINE           every node already stores direct pointers to its neighbors -- index-free adjacency
(Cypher / SPARQL)      cost per hop: O(1) per pointer followed, flat, no re-derivation of "already visited"
                      Cypher = property graph pattern matching; SPARQL = the equivalent over RDF triples

recursiveSqlTraversalCost(hopDepth, avgNodesPerHop) = Σ [ edgeJoinCost(hop) + dedupScanCost(hop) ]

edgeJoinCost reuses join-algorithms.mjs’s own nestedLoopCost unchanged — each hop’s frontier is the outer side, the edge table is the inner side, an index on the edge table’s source column collapses the per-row cost to a B-tree lookup. dedupScanCost is the same nestedLoopCost function again, but against the accumulated visited-set, which is (hop-1) × avgNodesPerHop rows by the time hop hop runs — a term that grows every iteration, which is what turns a traversal that’s linear for a graph engine into one that’s worse than linear here.

graphEngineTraversalCost(hopDepth, avgNodesPerHop) = hopDepth  ·  avgNodesPerHop

Index-free adjacency: following one edge is one pointer read, O(1), and checking “have I visited this” is an O(1) hash/bitset lookup the engine already keeps in memory — neither term grows with how many hops have already happened, so the total is exactly linear in depth times branching factor, nothing more.

At hop depth 1 there is no visited set yet to rescan (dedupScanCost is exactly zero by definition), so recursive SQL’s cost is just one indexed edge-join — 60 operations against the graph engine’s 20, a 3× gap that’s really just “a join costs a constant factor more than a raw pointer,” not the recursion problem this lesson is about. 06

The trade-off — recursion in SQL is not free, and neither is a second database

WITH RECURSIVE genuinely closes the “can this be expressed at all” gap — it does not close the performance gap. A team that needs variable-depth traversal only occasionally, on data that already lives in a relational store, can reach for a recursive CTE and get a correct answer; this lesson’s numbers say that answer gets proportionally more expensive every additional hop the traversal actually needs, which matters a great deal for “how far can this spread” queries and far less for one that’s known to bottom out in 2 or 3 hops.

A dedicated graph engine’s O(1)-per-hop promise is conditional on the data actually fitting the model — index-free adjacency means every node’s neighbor pointers live where the engine can walk them directly, which is a real storage and ingestion commitment, not a free performance upgrade bolted onto an existing relational schema. Standing up and operating a second database purely for traversal-heavy queries is the real cost being traded against the widening gap in the tables above — worth it once traversals go deep or run often enough, not worth it for a query that only ever needs 2 or 3 hops.

Property graphs (Cypher/GQL) and RDF triple stores (SPARQL) trade the same axis against each other, separately from the SQL-vs-graph-engine question. Both are graph-native and both get index-free adjacency; the difference between them is data-modeling fit — arbitrary key-value properties on nodes and edges (property graph) versus everything reduced to uniform subject-predicate-object triples (RDF), which shows up in schema flexibility and interoperability with other semantic-web tooling, not in this lesson’s traversal-cost numbers.

07

In the wild

DDIA’s own worked example is exactly this lesson’s comparison, run on the same tiny dataset in four different languages, and it states the line-count gap in the authors’ own words: Kleppmann and Riccomini build a graph of people, locations, and a within relationship, then ask “find people who were born in the US and now live in Europe” — a query that needs to follow a within edge an unknown number of times (a location can be within a state, within a country, within a continent). They write it as a 4-line Cypher pattern match, then as SQL: “The fact that a 4-line Cypher query requires 31 lines in SQL shows how much of a difference the right choice of data model and query language can make.” They then write the same query a third way, in Datalog, whose recursive rules make the transitive “within” relationship a native primitive rather than an iterated join. And SPARQL gets the equivalent variable-length-path syntax stated directly: ?person :bornIn / :within* ?location. — the * is SPARQL’s own notation for “zero or more hops,” the same “however many it takes” this lesson’s cost functions price out. They also note that the Graph Query Language (GQL) ISO standard, based on Cypher, was published in 2024 — the property graph model converging on one standard query surface the way SQL did for relational stores decades earlier.

The reused per-hop join cost is not new here — join-algorithms.mdx’s nestedLoopCost is called unchanged for both the edge-join and the dedup-scan terms in this lesson’s model; what’s new is only that the dedup-scan term’s inner table (the accumulated visited set) grows every iteration instead of being a fixed size decided in advance, which that lesson never had reason to model because a single join has no notion of “state left over from a previous iteration.”

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A fixed number of hops IS a fixed-arity join — "2 hops" is a 2-way self-join, "3 hops" is a 3-way self-join — but a VARIABLE-depth traversal ("everyone reachable, however many hops it takes") has no fixed arity at all, so no number of JOIN clauses, written in advance, can express it. This is a structural gap in the relational model, not a missing optimization.
  • SQL's answer arrived late — `WITH RECURSIVE` (a recursive common table expression) — and even then it works by literally repeating the same join once per hop until it stops finding new rows, rather than by any new relational primitive
  • A naive recursive CTE has to check every newly-found row against everything already visited, to avoid re-expanding a node it has already reached (needed the moment there's a cycle, or two paths converging) — and that check is itself a join against a working table that grows every single iteration, which is the mechanical reason its total cost grows faster than linearly in hop depth
  • A graph engine's index-free adjacency means every node already stores direct pointers to its own neighbors — following an edge is one O(1) pointer read, no join, no index walk, no re-derivation of "have I seen this" from scratch each hop
  • Two graph data models exist with roughly equivalent expressive power and different query surfaces: the PROPERTY GRAPH model (nodes/edges with arbitrary key-value properties, queried with Cypher/openCypher/GQL's ASCII-art pattern syntax) and the RDF TRIPLE STORE model (every fact a subject-predicate-object triple, queried with SPARQL); DATALOG is a third, logic-programming-based language that is natively recursive rather than needing a recursion bolt-on
  • Quantified: at 3 hops and 20 nodes discovered per hop, a naive recursive-SQL traversal costs roughly 23× a graph engine's cost for the identical traversal; by 10 hops, roughly 93× — the gap keeps widening with depth because the SQL side's re-scan of already-visited state grows every hop while the graph engine's per-hop cost stays a flat constant

  1. Cued recall

    A social app wants "everyone within 3 hops of Alice" (a fixed depth) and, separately, "everyone reachable from Alice at all, however many hops it takes" (unbounded depth). Why can the first be written as an ordinary SQL query today, while the second genuinely cannot without `WITH RECURSIVE`?

    How sure are you, before you look?
    "Within 3 hops" is a fixed-arity question — the query text can name exactly 3 self-joins against a friendship table (or one for each of hops 1, 2, and 3, unioned together) because the number of joins needed is known when the query is WRITTEN. "Reachable at all" has no such bound: the number of hops needed depends on the shape of the data the query is run against, which isn't known until the query RUNS. SQL has no construct for "an unknown number of joins, run until nothing new turns up" outside of `WITH RECURSIVE` — that is precisely the gap the recursive CTE exists to close, decades after the relational model itself.
    Did you have that?
  2. Cued recall

    A `WITH RECURSIVE` traversal and a graph-engine traversal are, on paper, doing "the same thing" — following edges outward from a start node. This lesson's model puts the SQL version at roughly 23× the cost at 3 hops and roughly 93× at 10 hops. Where does that growing gap actually come from, mechanically?

    How sure are you, before you look?
    Both pay a cost for each hop's edge lookup — the SQL side's join against the edge table, the graph engine's pointer follow — and that part alone doesn't explain a WIDENING gap. What does is the naive SQL side's dedup check: before accepting a newly-found row, it has to confirm the row isn't already in the accumulated "visited" set, and that set is bigger on every subsequent hop, so each hop's check costs more than the last. A graph engine's equivalent check is an O(1) hash/bitset lookup that doesn't grow with depth the same way, so its per-hop cost stays flat while the SQL side's climbs — which is exactly why the RATIO between them keeps increasing rather than settling at a fixed multiple.
    Did you have that?
  3. Near transfer

    `join-algorithms.mdx` computes the cost of a SINGLE join between two tables of known, fixed size and shows which of three algorithms wins. A team building a recursive parts-explosion query (a bill of materials: parts containing sub-parts containing sub-parts, arbitrarily deep) reasons: "a recursive query is just several joins chained together, and we already know how to cost a join — so we'll pick nested-loop-with-index for every level, since that lesson showed indexed nested-loop wins when one side is small." Is that the right way to extend the earlier lesson's finding?

    How sure are you, before you look?
    It reuses the right primitive but skips the part that's actually new here. `join-algorithms.mdx`'s cost functions (including the very `nestedLoopCost` this lesson calls unchanged for each hop's edge lookup) assume BOTH sides are a known, fixed row count decided before the query runs. A recursive traversal's hop-by-hop frontier size is not fixed in advance — it depends on the data — and more importantly, each hop ALSO has to pay a dedup check against an "already visited" working table that is a different, larger size on every iteration, which `join-algorithms.mdx` never had a reason to model because a single join has no notion of "state accumulated by previous iterations." Costing "N joins chained together" as if it were N independent joins of predetermined size undercounts exactly the term that makes this lesson's gap widen with depth instead of staying flat.
    Did you have that?
  4. Far transfer

    The abstraction is: answering "how far can this spread, and through how many links" has no fixed number of steps decided in advance — each round has to expand outward from whatever was newly reached in the PREVIOUS round, and avoid re-processing anything already accounted for, until no new expansion happens. Name an instance outside computing.

    How sure are you, before you look?
    Contact tracing during a disease outbreak. Investigators don't ask "who are this person's contacts, their contacts' contacts, and their contacts' contacts' contacts" as three fixed, pre-planned interview rounds — an outbreak's reach isn't known in advance. Each round, they interview whoever was newly identified as a contact in the PREVIOUS round, and every round has to check newly named names against everyone already logged, or the same person gets re-interviewed and re-counted every time their name resurfaces through a different chain — exactly the recursive CTE's growing dedup check, done with case files instead of a working table. A region with a pre-built social-contact registry (who is directly linked to whom, already recorded) can answer "who's within reach of this case" by walking those existing links directly — the human equivalent of index-free adjacency — instead of re-deriving the whole contact graph one interview round at a time.
    Did you have that?
