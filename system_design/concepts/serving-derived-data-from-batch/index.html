Tier 5 · Moving data around Serving derived data from batch

A 30-minute nightly rebuild is never fresher than 30 minutes and never staler than 24.5 hours -- and keeping the one most recent old copy for a full day still isn't long enough if a bad build takes 25 hours to notice: recovery costs a fresh 1,800-second rebuild, 60x an instant swap

`mapreduce-and-its-legacy.mdx` already covers what happens INSIDE a batch job; `cqrs.mdx` already covers splitting a read model from a write model in general, kept in sync by an incremental projector that updates on every write. This lesson is the specific mechanism many batch jobs use instead: build the ENTIRE output somewhere nobody is reading yet, verify it, then flip a single pointer to make it live in one atomic step. Readers only ever see last cycle's complete output or this cycle's complete output, never a mix, because the swap itself is one operation, not a gradual cutover -- the same principle `deployment-strategies.mdx` applies to code, applied here to data. It prices what that buys and what it costs: staleness that sawtooths between the job's own build time and a full cycle beyond it, and a storage bill that doubles for as long as the previous version is kept around as a rollback option, sized against how long it actually takes to notice a bad build.

Read first — mapreduce-and-its-legacycqrs

01

Nobody is reading the new index until it's completely done

A nightly job rebuilds a search index, a recommendation model, or a reporting table from scratch against the day’s full dataset. Two things have to be true when it hands that output to the live system that actually serves reads: no query should ever see a half-written index (some documents reflecting today’s crawl, others still missing), and the serving system should never have to go offline while the handoff happens. The standard pattern that satisfies both: build the whole thing somewhere nobody is querying yet — a brand-new file, table, or directory the live system doesn’t know exists — and once it’s completely finished and checked, flip ONE pointer to make it live. This lesson prices what that buys, in staleness, and what keeping the option to undo it costs, in storage.

02

Assume that keeping any old version at all makes rollback safe

The instinct: once a team starts keeping “the previous version” around instead of deleting it immediately, rollback sounds solved — there’s a good copy sitting right there. The gap is that sitting right there has an expiration date, and that date is a policy choice (the retention window) racing against a fact nobody chooses directly (how long it actually takes to notice the new version is bad).

Predict A nightly batch job (30-minute build, swapped in every 24 hours) keeps exactly one old version around -- a full 24-hour cycle's worth of retention -- before reclaiming it. A subtle bug in the new version isn't caught by an automated data-quality check for 25 hours. Is keeping 'one full cycle' of the old version enough to guarantee an instant rollback?
rollbackOutcome({ retentionWindowSeconds: 86400, detectionSeconds: 90000, buildDurationSeconds: 1800, instantSwapSeconds: 30 }) gives canRollbackInstantly: false and recoverySeconds: 1800 -- a fresh 30-minute rebuild, a 60x cost multiplier over a 30-second instant swap. The safety margin is exactly -3600 seconds: the retention window closed a full hour before detection did. Keeping the SAME single old version for 1.5 cycles (129,600s) instead of 1 -- still only a 2x storage bill, not 3x -- would have covered it with room to spare.
Show it without answering

At the rig’s default — a 30-minute build, a 24-hour swap cycle, a 25-hour detection time, 50GB per version — staleness sawtooths between 30 minutes and 24.5 hours, and keeping just one old version (24 hours of retention, a flat 2x storage bill) is not enough: detection takes longer than that window stays open, so recovering means the full 30-minute rebuild, 60x an instant swap. Drag retention past 1.5 cycles and the same 2x-storage row turns safe.

03

A city's reservoir switchover

A municipal water utility building a new reservoir doesn’t drain the old one first. Engineers fill and fully treat the ENTIRE new reservoir off to the side, where no tap draws from it yet — there’s no risk of a half-treated batch reaching anyone’s kitchen while the work is still going on. Once independent testing confirms the whole reservoir meets standard, one valve switches, and every tap in the city draws from the new supply starting that instant — there’s no in-between state where some neighborhoods get old water and some get new depending on which pipe segment they’re on.

And critically, the utility does not drain the OLD reservoir the moment the valve switches. They hold it, untouched, for some standard window, because a contamination problem can take hours or days of downstream testing to actually surface. Switch the valve back inside that window and the city is drinking known-good water again within minutes. Drain the old reservoir too early, and the exact same problem instead means shutting off taps while an entirely new reservoir is filled and treated completely from scratch.

04

Two formulas: how stale the data can be, and how safe the rollback is

Staleness. A job takes buildDurationSeconds (B) to produce a complete output, and a swap recurs every cycleIntervalSeconds (C), with B strictly less than C or successive builds would overlap. Right after a swap, served data is exactly B seconds old — the freshest it is ever going to get. From there it climbs linearly, second for second, until the next swap resets it:

stalenessSecondsAtTime(t) = B + ((t - B) mod C)

A sawtooth with floor B and peak-to-trough amplitude C. Mean staleness over one full cycle is the midpoint of that ramp: B + C/2. Force B to 0 — a refill assumed to take no time at all — and this is exactly TTL caching’s familiar “staleness resets to 0” result, reached here as a limit of a more general formula rather than shared code with it.

node -e "import('./src/sim/serving-derived-data-from-batch.mjs').then(m => {
  console.log(m.stalenessBounds({ buildDurationSeconds: 1800, cycleIntervalSeconds: 86400 }));
  console.log(m.stalenessBounds({ buildDurationSeconds: 300, cycleIntervalSeconds: 3600 }));
})"

A 30-minute build swapped in nightly (B=1800s, C=86400s) never drops below 1,800s (30 min) and never exceeds 88,200s (24.5h), averaging 45,000s (12.5h). Rebuild hourly instead with a 5-minute build (B=300s, C=3600s) and the same shape shrinks to a 300s–3,900s range, averaging 2,100s (35 min) — cadence, not the model, is what makes staleness small.

Rollback safety. The old version is kept for retentionWindowSeconds (R) after being superseded. A bad new version is noticed after detectionSeconds (D) of real time, however that detection actually happens:

canRollbackInstantly = R >= D

If the retention window is still open when a bad version is detected, rollback is a near-instant pointer flip. If it already closed, the old version is gone, and recovery costs a full rebuild (buildDurationSeconds) instead — recoveryCostMultiplier is that rebuild’s cost divided by an instant swap’s, and it is not a small number.

06

Neither cost is optional, and neither is free to shrink

Staleness cannot be engineered to zero without also shrinking the build-swap-cycle itself. The floor is the job’s own build duration, full stop — there is no policy knob on the read side that gets served data fresher than however long it took to produce it. The only lever is cadence: rebuilding hourly instead of nightly cuts both the floor and the mean, at the cost of running the whole job, and paying its full resource bill, 24x more often.

A retention window is not “safety” in the abstract — it is safety against ONE specific number: how long detection takes. The rig’s default makes this concrete: doubling storage from 1x to 2x (keeping exactly one old version) sounds like the obvious safety margin, and it still isn’t enough if detection is slower than one cycle. The number that actually has to be checked in a real system isn’t “do we keep an old version” — it’s “does our retention window outlast our own detection time,” which is a fact about monitoring, not about storage.

Storage cost during the overlap is genuinely 2x, not a rounding error, and it compounds with every extra version kept. A team that responds to a near-miss by keeping three cycles “just in case” is paying 4x storage indefinitely for a margin the arithmetic above shows a single, well-timed cycle would have covered just as well. The right response to a detection gap is usually to shrink the detection time, not to keep buying more storage against it.

Where this model is honest about its own limits: it treats one batch job’s build duration as constant cycle to cycle (real jobs vary with input size and cluster load), it treats detectionSeconds as a given input rather than deriving it from a specific monitoring mechanism (unlike canary-analysis-and-rollback.mjs, which derives its own detection time from a live statistical test — there is no equivalent single formula for “how long does a human or an automated check take to flag a bad batch artifact”), and it models rolling back to exactly one prior good version rather than a deeper chain of historical backups. None of that changes the central result — a retention window either covers detection or it doesn’t — but the exact seconds this model prints are this lesson’s illustration of the shape, not a number to paste into a real retention policy.

07

In the wild

DDIA states the immutable-output-plus-rollback pattern directly, for exactly this reason: “Or, even simpler, you can keep the old output in a different directory and switch back to it. Most object stores and open table formats… support this feature, which is known as time travel” — and names the general property it buys as “human fault tolerance” (Kleppmann, Designing Data-Intensive Applications, 2nd ed., “Batch Processing,” p.452) — the exact rollback-by-keeping- the-old-output move this lesson prices against a real detection-time number.

DDIA’s own “Serving Derived Data” section is this lesson’s direct subject: “Batch jobs are often used to build precomputed or derived datasets such as product recommendations, user-facing reports, and features for ML models. These datasets are typically served from a production database, key-value store, or search engine… the precomputed data needs to make its way from the batch processor’s distributed filesystem or object store back into the database that’s serving live traffic” — and states the atomic-swap payoff by name: “Building databases in batch and bulk-importing the data is very fast and makes it easier for systems to atomically switch between dataset versions” (Kleppmann, DDIA, 2nd ed., “Serving Derived Data,” pp.479-481).

Google’s own web-search index is one of the earliest large-scale examples of this exact pattern — an entirely new index generation built offline from a fresh crawl, then switched into serving wholesale once complete, rather than mutating a live index record by record — named here generically, without a specific paper citation, since none is available locally to quote character-for-character.

mapreduce-and-its-legacy.mdx’s disposability is this lesson’s precondition, one level up: that lesson prices redoing a single failed TASK from immutable input; this lesson prices publishing an entire finished JOB’s output the same way — as a disposable, all-or-nothing unit that’s either fully live or not live at all, never half of one. cqrs.mdx’s read/write split is this lesson’s nearest sibling, not its foundation: CQRS’s query model is kept in sync continuously, by an async projector reacting to every write; this pattern instead rebuilds the whole thing on a fixed cadence and swaps it in wholesale — the same goal (serve reads off a precomputed store) reached by a structurally different maintenance mechanism. deployment-strategies.mdx already covers this exact all-or-nothing cutover for CODE (blue-green); this lesson is the identical principle applied to DATA, with a rollback window sized in bytes and seconds instead of instances and requests. The atomic pointer/manifest update itself is often mechanically the same conditional write object-storage-as-coordination-primitive.mdx already prices — a compare-and-swap on one object key — cross-referenced there, not re-derived here.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • The mechanism: a batch job writes its ENTIRE output to a brand-new, uniquely-named location nobody is reading yet, so there is no partial-read risk during the write itself. Once that write is fully complete and verified, ONE ATOMIC operation (a pointer, symlink, or manifest-entry update) makes it live. A reader mid-query always sees either the complete previous version or the complete new one -- never a mix -- because the swap is a single operation, not a gradual cutover the way a rolling deploy is.
  • STALENESS is a deterministic sawtooth, not a probability. Right after a swap, served data is exactly as old as the job's own BUILD DURATION -- the freshest it will ever be, and never zero, because building the whole output took real time no matter how instant the swap itself is. From there staleness climbs linearly until the next swap drops it straight back down to that same floor. Peak-to-trough amplitude equals the CYCLE INTERVAL; mean staleness is exactly floor + half the amplitude.
  • TTL cache staleness (`cache-invalidation.mjs`'s `ttlStalenessWindow`) is this shape's zero-build-time special case, not a shared formula: a cache refill is modeled as instantaneous, so its floor is exactly 0. A batch swap's floor can never reach 0, because the build itself is not instantaneous -- the two are the same SHAPE (a periodic ramp that resets) generated by mechanically different processes (a deterministic cycle vs. a probabilistic Poisson arrival of writes).
  • The old version is deliberately NOT deleted the instant the new one goes live -- it is kept for a RETENTION WINDOW specifically so a bad new version can be rolled back to instantly, by flipping the pointer straight back, instead of paying for a full rebuild. Every concurrently-retained version costs one more full copy's worth of storage: keeping exactly one old version around is a flat 2x storage bill for as long as that window stays open.
  • A retention window only buys a real rollback option if it OUTLASTS however long it actually takes to detect a bad version. If detection is slower than retention, the old version is already reclaimed by the time anyone notices, and "rollback" means paying the full build cost again -- not an instant flip. This is the same detection-then-recover shape `canary-analysis-and-rollback.mdx` prices for a live canary, but that lesson's detection is a statistical test on live traffic error rates; this one's is normally an offline data-quality check on a completed artifact, so nothing here reuses that lesson's formulas.
  • Because the ENTIRE output is regenerated from scratch, from immutable input, every cycle -- the same disposability `mapreduce-and-its-legacy.mdx` prices for a single task, one level up, for a whole job's output -- a corrupted or buggy build is fixed by simply not swapping it in, or swapping back, rather than needing to repair partial state. DDIA calls this general property of batch-produced output "human fault tolerance."

  3. Near transfer

    This file's `stalenessSecondsAtTime` produces a periodic ramp that resets -- structurally the same SHAPE as `cache-invalidation.mjs`'s `ttlStalenessWindow`, a periodic staleness measure that also resets. Is building `stalenessSecondsAtTime` as its own function, instead of calling into `ttlStalenessWindow`, a missed reuse opportunity?

    How sure are you, before you look?
    No -- the two functions answer different questions that happen to draw a similar-looking picture. `ttlStalenessWindow` asks "given writes arrive as a Poisson process, what fraction of a fixed TTL window is spent serving data that's already wrong because a write landed inside it" -- a PROBABILISTIC question, and its floor is exactly 0 because a cache refill is modeled as instantaneous. `stalenessSecondsAtTime` asks "given a batch job on a fixed schedule, how old is the data RIGHT NOW" -- a DETERMINISTIC question with no randomness in it at all, and its floor is bounded below by the job's own build duration, which never shrinks to 0 no matter how fast the swap is. Forcing them to share code would have to either inject fake randomness into a deterministic schedule or pretend a real build takes no time -- hiding the one structural difference (a nonzero floor) that this lesson's whole staleness story depends on.
    Did you have that?
