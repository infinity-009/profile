Tier 10 · AI-era systems KV cache explained well nowhere else

The cache had room for nine more replies and the server refused the request

Once memory rather than compute decides how many users a card serves, the serving engine is a memory allocator — and the obvious allocator throws away 90% of the cache without leaking a byte. Not a tuning problem: a consequence of reserving space for a length nobody knows yet. Ten times the memory buys 59 users. Changing the allocator buys 61 on the hardware you already have.

01

Five users, and 3,934 free tokens the server will not touch

A single H100 is serving a 70B chat model. The weights take 70 of its 80 GB at FP8; after activations and workspace, 8 GB is left for the KV cache. That model spends 320 KB of cache per token, so 8 GB is 24,414 tokens of conversation held at once — a number worth keeping, because everything below is division into it.

Replies average 400 tokens. Twenty-four thousand tokens divided by four hundred is sixty. The capacity plan says sixty concurrent users.

The server serves five, and refuses the sixth. Its own metrics say the cache is 84% allocated with 3,934 tokens free — room for nine more replies of average length. Nothing is leaking: restart it and the same thing happens. Nothing is misconfigured. Every number in that paragraph is true at the same time.

The reading almost everyone takes is the cache is too small, buy more memory. Doubling it to 16 GB takes you from five users to eleven. Ten times the cache — 80 GB of KV on top of 70 GB of weights, a card that does not exist — gets you 59, and by the end of this lesson the same 8 GB will hold 61.

02

The obvious knob, and how little it does

The engine allocates cache the only way that looks safe. A request arrives; its reply could run to the model’s context limit, 4,096 tokens; attention kernels read the cache as one contiguous tensor and a contiguous allocation cannot be grown once its neighbour is placed. So the engine reserves 4,096 tokens up front, for a reply that will average 400.

Five reservations of 4,096 is 20,480 tokens. That is where the 8 GB went, and it is why the sixth request fails: 3,934 tokens remain and no 4,096-token reservation fits in them.

The knob the team reaches for is the block size, because it is the parameter the config file exposes. Drag it in the rig below and watch what it buys. Then press paged blocks, which is not a parameter at all.

Predict 8 GB of KV cache holds 24,414 tokens for this model. Replies average 400 tokens, but the server must reserve for the 4,096-token maximum when the request arrives, because it cannot know the length yet. How many concurrent sequences fit?
24,414 ÷ 4,096 = 5.96, so five. The first option is the arithmetic everyone does, and it is the right arithmetic for the wrong allocator: dividing by the average is what paged allocation achieves, and it does get 61. Under reserve-to-maximum the average never enters the calculation — the pool divides by the declared maximum, which is why the answer is 12× lower and why buying memory moves it linearly and slowly. Show it without answering

Two things in that rig are worth saying out loud, because they are easy to watch and not notice.

The block size is the wrong knob, and measurably so. Over the range anyone uses — 8 to 32 tokens — it changes the sequence count by under 5%. Push it to 128 and it costs 23%, which is why nobody does. The allocator change is 1,120%. A week of tuning the first is worth less than an afternoon on the second, and the config file only offers the first.

The free tail is not rounding. Under reserve-to-maximum there is always a remainder smaller than one reservation, and it is invisible to every “cache utilisation” metric, which reports memory held rather than memory written. A dashboard showing 84% is a dashboard reporting that 84% has been handed out. Only 8% of it holds a token.

03

The intuition: books on a shelf, and the index card that fixes it

Imagine a library that shelves books by keeping each one in an unbroken run of shelf, and has to decide the run’s length when the book arrives as a single page — because the book is still being written, one page a day, and a page must go next to the page before it.

There is one safe choice: give every arriving book the longest run any book has ever reached. Most books stop at forty pages and every one of them holds a metre of shelf. The library fills up with five books and a metre and a half of gaps, and turns away the sixth while a visitor stands in front of visibly empty shelving.

Now change one thing. Let a book’s pages live anywhere there is a free slot, and keep an index card at the front listing, in order, which slot holds which page. Nothing about the shelf changed; the requirement that a book be contiguous is gone. A forty-page book takes forty slots. The librarian follows the card instead of walking a run.

That is the whole idea, and it is not new. Operating systems did exactly this to physical memory in the early 1960s and called it paging — fixed-size pages, plus a page table per process mapping logical addresses to physical ones. The KV cache is a fresh instance of a problem solved sixty years ago, and it got solved badly the first time because the people building it were solving an attention problem and did not recognise it as an allocation problem.

The cost of the index card is honest and small: the last slot of every book is part empty. You trade a whole metre of reserved shelf for half a slot. That is the trade, and it is the good side of it.

04

The mechanism: three wastes, and where each one comes from

“The cache is full” covers three separate failures with three separate causes and three very different sizes. Naming them separately is most of the work, because two have the same fix and the third is the price of that fix.

1. Over-reservation — memory held by a live request that will never be written.

waste = 1 − mean length ÷ declared maximum = 1 − 400 / 4096 = 90.2%

Look at what is absent from that expression. No model, no accelerator, no block size, no batching policy, no scheduler — nothing anyone tunes. It is the arithmetic consequence of not knowing the output length in advance and choosing to allocate as though you did. Declare a 32,768-token maximum instead and it is 98.8%.

2. External fragmentation — free memory that no allocation fits into. The 3,934-token tail, and in a long-running server also the holes left between allocations as requests of different declared sizes come and go. This is the one that makes a server refuse a request while reporting free memory, and it exists only because allocations must be contiguous.

3. Internal fragmentation — the last block of each sequence, partly filled.

waste = (B ÷ 2) ÷ mean length = 8 / 400 = 2%

Half a block per sequence on average, so a constant per sequence — which means its fraction shrinks as sequences get longer, and at 4,000 tokens it is 0.2%. This is the only one of the three that the block size controls, and this is why the block size is not an interesting parameter.

What paging actually changes

A block table per sequence: an array of physical block ids, in logical order. A sequence grows by taking one more block when the current one fills. Blocks need not be adjacent, so there is no run to reserve and no hole to fit into — wastes 1 and 2 both stop existing, not shrink.

The cost is that attention can no longer treat the cache as one contiguous tensor. A stock attention kernel indexes cache[seq][pos] with a stride; a paged one has to gather blocks through the table on every step, inside the innermost loop of the hottest kernel in the system. That is the real engineering content of the vLLM paper — PagedAttention is a kernel, and the allocator is the easy half.

Prefix sharing falls out of the block table almost for free, and it is the largest remaining lever. If two sequences begin with the same tokens — a system prompt, a few-shot preamble, an agent’s scratchpad, a retrieved document — their leading blocks are byte-identical, so both tables can point at the same physical blocks. Store once, read many. Two mechanisms make it safe:

  • Reference counting per block, so freeing one sequence does not pull blocks out from under another that is still reading them.
  • Copy-on-write at the point of divergence: the first sequence to write into a shared block gets a private copy of that block only. The shared prefix stays shared; the divergent tail does not.

Both are exactly what a filesystem does with a snapshot, and for the same reason.

05

The numbers: when this matters, and how much

Same model, same card, same 320 KB per token. Only the allocator and the traffic change.

Four readings, and the last two are the ones that change what you do on Monday.

Paging is worth between 2× and 12×, and it is worth most where the declared maximum is furthest above the mean. Chat is the extreme: short replies against a large context limit. The agent loop gains least from paging alone, because a 16k-token request against a 32k limit is only 50% over-reserved.

Prefix sharing is worth between 1.07× and 3.6×, and the multiplier is a property of the traffic. It does nothing for chat with no shared preamble and nearly nothing for RAG, where each request carries different retrieved text. It is the single largest lever on an agent loop, where the scratchpad is most of every request. One measurement predicts it: mean shared prefix ÷ mean sequence length. That number is zero in most published benchmarks, which is why the lever is under-reported relative to its value.

The two levers compose, and they are not the same lever. On the shared-system-prompt row, paging alone gives 26 and sharing takes it to 59 — sharing is worth more there than paging was. Neither is a block size.

Below about a gigabyte of cache none of this matters, and a small model is a different problem. An 8B model at 2k context fits hundreds of sequences on the same card; every waste above is real and none of it binds, because compute becomes the limit first. This lesson is about the regime where memory binds, which for a 70B-class model on one card is every regime.

And when it runs out anyway

Once memory rather than compute decides concurrency, the serving engine is an admission controller, and sooner or later it runs out mid-generation and must take memory back from a sequence already running. Two ways: discard the blocks and re-run prefill when the sequence is rescheduled, or copy the blocks to host memory over PCIe and back.

I expected the answer to depend on the sequence — recompute the short ones, swap the long ones. It does not, at any length. Both costs are linear in tokens, so the length cancels:

recompute ÷ swap = P · PCIe ÷ (compute · bytes-per-token)

For a 70B model on an H100 over 32 GB/s of PCIe that is 6.91, at 200 tokens and at 200,000. Swapping always wins for this deployment; for a small model over a narrow link recompute always wins. The choice is a property of the model, the accelerator and the interconnect — three things fixed when you deploy — so an engine can decide once and be right for all of its traffic. That is a more useful result than the one I expected, and the opposite of it.

06

The trade-off: an indirection in the hottest loop, and shared state between strangers

You pay in the attention kernel. Every step of decode now gathers KV through a block table instead of striding a contiguous tensor, in the innermost loop of the most performance-critical kernel in the system. The allocator is a hundred lines; the kernel is the paper. In practice this means paged allocation is not something you add to an inference stack — it is something the stack either has or does not, and it is why “just page the cache” is not a patch.

Prefix sharing turns your cache into shared state between unrelated requests, and shared state leaks through timing. A request whose prefix is already cached skips prefill and returns its first token measurably sooner. That difference is a side channel: by sending a candidate prefix and timing the response, someone can learn whether another user has recently sent it. Gu et al. (ICML 2025) audited production APIs and found global cross-user cache sharing in seven providers, including OpenAI — and demonstrated the sharper version of the point by inferring an architectural fact about a closed model from cache timing alone. The mitigation is to scope sharing to one tenant, which costs you exactly the hit rate that made it worth doing.

A shared block cannot be freed while anything references it. Reference counting is correct and it is also a pinning mechanism: one long-lived agent session holding a 12,000-token prefix keeps 750 blocks resident for its entire life, including while it is idle waiting on a tool call. The memory that made 25 sequences fit is held by whichever of them is slowest to finish.

Copy-on-write moves the cost, it does not remove it. A shared prefix that diverges early copies almost everything and shares almost nothing, while still paying the bookkeeping. Beam search and parallel sampling are the good case — they diverge late by construction. Multi-turn chat with a per-user preamble is the bad case, and it looks identical in a config file.

And the honest ceiling: none of this makes memory bigger. Every technique here divides the same pool more carefully. The things that actually change the pool are a lower KV precision, an attention shape with fewer key-value heads (grouped-query, multi-query), a shorter context, or more cards — and each of those is a quality or a cost decision rather than an allocation one. Paging takes you from wasting 90% to wasting 2%. There is no second 12× available.

07

In the wild

vLLM and PagedAttention. Kwon et al., Efficient Memory Management for Large Language Model Serving with PagedAttention, SOSP 2023 — the paper that named the problem and built the fix. It reports 2–4× throughput at the same latency against FasterTransformer and Orca, and describes its own result as “near-zero waste in KV cache memory.” Both halves matter: the throughput number is what gets quoted, and the waste number is what caused it.

And then the kernel disappeared, which is the better ending. vLLM’s v0.25.0 release notes (11 July 2026) record that “the legacy attention implementation is deleted now that V1/MRv2 backends are the standard path.” The PagedAttention kernel the paper is named after is gone from the codebase. What replaced it — FlashAttention, FlashInfer, FlashMLA, TRTLLM-GEN, Triton — all assume paged KV memory as a matter of course. The idea did not lose; it stopped being a feature. That is the normal fate of a good systems contribution and it is worth recognising when you see it, because “our custom component was deleted” and “our idea became the substrate” look identical in a changelog.

Prompt caching, priced. Every major provider now bills a cached input token at a fraction of an uncached one. That price difference is prefix sharing, exposed as an API: the provider is telling you which of your tokens it did not have to prefill because it still had their KV blocks. Structure your prompts so the stable part comes first and you move tokens across that price boundary — which is an application-level decision produced entirely by an allocator detail.

And the side channel, measured. Gu, Li, Kuditipudi, Liang & Hashimoto, Auditing Prompt Caching in Language Model APIs (ICML 2025), tested production APIs for cross-user cache sharing and found it in seven providers. They also inferred that OpenAI’s embedding model is a decoder-only Transformer — a fact that was not public — from cache timing alone. It is a clean demonstration that a cache shared for throughput is an information channel whether or not anyone designed one.

Now put the page away

Everything above this line was the Passive rung — necessary, and the weakest thing on offer. Testing yourself on it will feel worse than rereading it and will hold roughly twice as long. That gap between how it feels and what it does is the entire reason this section exists.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • Over-reservation waste is 1 − mean length ÷ declared maximum, which depends on no tunable parameter at all
  • Paged allocation raises concurrency by removing an assumption (contiguity), not by tuning a number
  • The three wastes are over-reservation, external fragmentation between allocations, and the last partly-filled block — in that order of size
  • Internal fragmentation is B/2 tokens per sequence, so its fraction is B ÷ 2·mean-length and falls as sequences lengthen
  • Prefix sharing needs reference counting and copy-on-write, and its value is a property of the traffic rather than of the engine
  • Whether to recompute or swap a preempted sequence is independent of its length, because both costs are linear in tokens and the length cancels

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A server has 8 GB of KV cache, which is 24,414 tokens for this model. Replies average 400 tokens. It serves five concurrent users and refuses the sixth while reporting 3,934 tokens free. Nothing is leaking. What is happening?

    How sure are you, before you look?
    The allocator reserved the declared maximum — 4,096 tokens — for each request, because the output length is unknown when the request arrives and a contiguous allocation cannot be grown later. Five reservations of 4,096 is 20,480 tokens, so 90.2% of what is held will never be written, and the 3,934-token remainder is real free memory that no 4,096-token reservation fits into. It would hold nine more 400-token replies. Both statements in the report are true at once: the cache is nearly full and nearly empty, because "full" is measured in reservations and "empty" in tokens.
    Did you have that?
  2. Cued recall

    Why does doubling the KV cache from 8 GB to 16 GB take you from five concurrent users to eleven rather than to sixty-one?

    How sure are you, before you look?
    Because reserve-to-maximum waste is a fraction, not a fixed cost: 1 − mean/max is 90.2% at any pool size, so doubling the pool doubles the waste alongside the useful part. Concurrency under this allocator is pool ÷ maximum, which is linear in memory — so ten times the cache, 80 GB of KV on top of 70 GB of weights, reaches only 59, and is not a card you can buy anyway. Paged allocation reaches 61 on the original 8 GB, because it changes the denominator from the declared maximum to the actual length. Buying memory moves you along a line; changing the allocator moves you to a different line.
    Did you have that?
  3. Cued recall

    Two teams both switch to paged allocation. One spends a week tuning the block size and gains 4%; the other turns on prefix sharing and gains 3.6×. What determined the difference, and what would have told them in advance?

    How sure are you, before you look?
    The workload, not the engine. Internal fragmentation is B/2 tokens per sequence — a constant per sequence — so over the block sizes anyone actually uses (8 to 32 tokens) it costs between 1% and 4% of a 400-token mean and there is no more than a few percent available to win. Prefix sharing removes prefix ÷ mean of every sequence's cost, so it is worth 3.6× on an agent loop with a 12,000-token shared scratchpad, 2.3× on a shared system prompt, and 1.07× on RAG where the retrieved context differs per request. The advance warning is one measurement: the mean shared prefix length as a fraction of the mean sequence length. It is zero in most published benchmarks, which is why the lever is under-reported.
    Did you have that?
  4. Cued recall

    A serving engine runs out of KV memory mid-generation and must take memory back from a running sequence. It can discard the blocks and re-run prefill later, or copy them to host RAM over PCIe. Should it decide per request, based on how long the sequence is?

    How sure are you, before you look?
    No — and this is the surprise. Recompute costs 2·P·tokens ÷ compute and swapping costs 2·tokens·bytes-per-token ÷ PCIe. Both are linear in tokens, so the token count cancels out of the ratio, which is P · PCIe ÷ (compute · bytes-per-token) — a property of the model, the accelerator and the interconnect, all three fixed at deploy time. For a 70B model on an H100 over 32 GB/s of PCIe the ratio is 6.91 at every sequence length, so swapping always wins there; on a small model over a narrow link recompute always wins. The engine can decide once, statically, and be right for all of its traffic. Asserted across four orders of magnitude of length in src/sim/kvcache.test.mjs.
    Did you have that?
  5. Near transfer

    A photo service stores every uploaded image in a fixed 12 MB slot because a camera RAW file can reach 12 MB, while the median upload is 2.1 MB. Disk usage grows six times faster than the photo count, and the team's proposal is tiered storage. What is the actual defect, and what is the equivalent of the fix in this lesson?

    How sure are you, before you look?
    The defect is reserve-to-maximum, and the waste is 1 − 2.1/12 = 82.5% — the same formula, in a different unit. Tiered storage moves the wasted bytes to a cheaper disk instead of not writing them, so it reduces the price of the waste and not the waste. The equivalent fix is the same one: allocate in small fixed-size extents with a per-object map from logical offset to extent, so an object occupies space proportional to its actual size and pays only the last partly-filled extent. That is what every log-structured filesystem, every object store and ext4's extent tree already do, which is the real point — the KV cache is not a novel allocation problem, it is a well-solved one that got re-solved badly because the people building it were solving an attention problem.
    Did you have that?
  6. Far transfer

    The abstraction is: a resource is committed for the largest amount a request could need, because the amount it will actually need is unknowable at commit time — and the fix is to hand out small fixed-size units plus an index that says which units belong to which request. Name an instance outside computing.

    How sure are you, before you look?
    The shipping container. Break-bulk cargo was loaded piece by piece into whatever contiguous run of hold it fitted, so a ship's capacity was set by how awkwardly its cargo packed and a partly-loaded hold could refuse a crate it had room for. Containerisation replaced that with fixed-size units and a manifest — an index from container number to position — and the waste moved to the same place it moves in a paged cache: the part-empty last container. Port throughput rose by more than an order of magnitude, and nobody achieved it by tuning the size of the container. Other instances: hospital beds booked for the worst-case length of stay versus discharge-driven allocation with a bed-management system; airline seat blocking, where a group booking holds a whole row against a party that may not materialise; and parking, where an unmarked kerb is contiguous allocation with external fragmentation and painted bays are pages — bays waste the tail of each space and fit far more cars.
    Did you have that?
