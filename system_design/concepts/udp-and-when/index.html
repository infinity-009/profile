Tier 1 · The network UDP, and when you want it explained well nowhere else

A 200ms jitter buffer can never be saved by TCP's own retransmission timer

This isn't "TCP is sometimes too slow for real-time media" — it's categorical. RFC 6298 floors TCP's retransmission timer at a full second no matter how fast the network is, and no real-time jitter buffer can afford to hold a second of audio or video waiting to find out if a packet is coming. UDP drops the late packet and moves on; the gap gets concealed, not fixed. And the same protocol that can't wait for anyone has a second unrelated superpower: multicast delivers the identical stream to any number of receivers for the cost of one send, where unicast — TCP's only option — costs exactly proportional to how many are watching.

01

A video call engineer asks for 'more reliable' delivery, and gets a worse call

A team building a video calling product notices occasional glitches when packets are lost, and someone proposes running the media path over TCP instead of UDP — “TCP retransmits lost packets, so we’ll stop losing frames.” They ship it. Call quality gets worse. Not marginally — noticeably, with visible freezes where there used to be brief, barely-noticed glitches.

Nothing about the implementation was wrong. TCP did exactly what TCP promises: it retransmitted the lost data, reliably, in order. The problem is that “reliably” and “in time” are different guarantees, and the previous lesson already computed exactly how different.

02

Assume 'more reliable' is strictly better, and find the deadline it can't meet

The instinct is that TCP’s reliability is a strict improvement UDP simply lacks — more guarantees can only help. That instinct misses that a real-time stream isn’t asking “will this data arrive eventually,” it’s asking “will this data arrive before a specific, short deadline” — and a guarantee that ignores the deadline isn’t a weaker version of the right answer, it’s a different question entirely.

Predict A live audio jitter buffer holds 100ms of audio before it must play out. If a packet is lost, TCP-style reliable delivery retransmits it after the RTO fires — floored at 1 second by RFC 6298 regardless of network speed. Does the retransmitted packet make the deadline?
The RFC 6298 floor is exactly that — a floor, not a function of RTT once the computed value falls below it, which it does on any network faster than roughly a quarter-second round trip. A 1-second minimum wait against a 100ms deadline misses by 900ms, unconditionally. This is the same rto() computation from the previous lesson, reused with no changes: the floor doesn't know or care that this packet belongs to a real-time stream with a hard deadline.
Show it without answering

At the rig’s default — a 95ms jitter buffer — the floored RTO of 1.0 second misses the deadline by 905 milliseconds, a factor of over 10×. And at roughly 11,000 receivers, the same stream’s unicast egress costs 11,220× what multicast would cost for identical bytes delivered.

03

A broadcast that freezes a frame rather than waiting for a perfect one

A live television broadcast’s satellite feed drops a single frame. The engineering team could, in principle, request the missing frame be re-sent — but by the time any request-and-response round trip completes, the broadcast has moved seconds further along, and the “reliably recovered” frame would depict a moment that has already aired. Live broadcast systems don’t wait. They freeze or repeat the last good frame for an instant and press on, visibly imperfect but synchronized with the one thing that actually matters: real time.

That’s not a compromise TV engineers settled for reluctantly — it’s the correct answer to a deadline that a “wait for the right data” strategy cannot, structurally, meet. UDP’s drop-and-move-on behavior is the same answer, computed the same way, for the same reason.

04

The mechanism — a floor that doesn't know your deadline, and a fan-out that doesn't scale

TCP’s reliability path has a fixed, non-negotiable floor. Reused directly from packet-loss-and-retransmit:

RTO  =  max( SRTT + 4×RTTVAR ,  1 second )      (RFC 6298 §2.4)

Below the floor, RTO doesn’t depend on how fast your network actually is — it’s exactly 1,000ms, full stop. A jitter buffer of jitterBufferMs misses the deadline whenever:

missesDeadline  =  RTO > jitterBufferMs

For any realistic real-time jitter buffer — tens to a few hundred milliseconds — this is true unconditionally, not “usually” or “on slow networks.” That’s the whole argument for UDP in real-time media: not that TCP is slow, but that TCP’s specific recovery mechanism cannot mathematically fit inside the deadline that matters, on any network, ever, below the floor.

Multicast’s advantage is a different mechanism, and just as structural. A unicast sender pays for every receiver individually:

unicastEgress    =  bytesPerMessage × messagesPerSecond × receivers
multicastEgress  =  bytesPerMessage × messagesPerSecond            (independent of receivers)

TCP requires a dedicated connection per receiver — unicast is its only option. UDP datagrams can be addressed to a multicast group instead, letting the network’s own routers replicate the packet only where subscribers actually are, so the sender’s cost never grows with audience size.

06

The trade-off — UDP's honesty about loss is also its whole cost

UDP doesn’t remove loss — it removes the illusion that recovering it is free. Every dropped or late packet under UDP is a real, visible-to-the-application event: a frame repeats, an audio sample is concealed, a game character’s position is momentarily stale. Choosing UDP over TCP for real-time media doesn’t fix packet loss; it changes what a loss costs from “guaranteed multi-hundred-millisecond stall, structurally” to “possibly a small glitch, application-dependent” — genuinely better for this use case, but not free, and an application that does nothing with UDP’s raw drops (no interpolation, no concealment, no forward error correction) gets a worse experience than either extreme.

Multicast’s beautiful math comes with a deployment cost the math doesn’t show. IP multicast requires every router between a sender and every receiver to support and correctly configure it — a coordination problem the public internet has never solved at scale, which is why almost no internet-facing live streaming platform uses true IP multicast despite the numbers in slot 5 being completely real. What production systems do instead is approximate multicast’s benefit with a CDN: fan out once to edge nodes (a multicast-shaped step, at much smaller scale, inside networks the CDN operator controls) and unicast from each edge to nearby viewers — most of multicast’s saving, none of the internet-wide deployment problem.

And “use UDP” is not itself the fix — it’s the starting point for building exactly the reliability an application needs, no more. QUIC is the fullest expression of this: UDP underneath, with application-controlled retransmission, per-stream ordering (fixing TCP’s head-of-line blocking directly), and congestion control rebuilt in user space rather than inherited wholesale from a kernel TCP stack. “Use UDP” without that follow-through is just “accept unlimited, uncontrolled loss” — rarely the actual goal.

07

In the wild

RTP — the protocol underneath nearly every live audio and video stream on the internet — is built on UDP specifically because of this lesson’s mechanism. Schulzrinne, Casner, Frederick and Jacobson, RFC 3550: RTP: A Transport Protocol for Real-Time Applications (IETF, 2003), defines the packet format and the jitter-buffer-driven playout model this lesson’s missesDeadline() is a simplified version of — RTP carries timestamps specifically so a receiver can decide, per packet, whether it arrived usefully or should be treated as lost regardless of whether it technically showed up.

The RTO floor RTP’s timing model is racing against is the same RFC 6298 floor from the previous lesson — Paxson, Allman, Chu and Sargent, RFC 6298: Computing TCP’s Retransmission Timer (IETF, 2011). No new citation is needed here because no new mechanism was introduced; this lesson’s entire first half is the direct consequence of that RFC’s §2.4 meeting real-time media’s actual deadlines.

QUIC’s design documents are explicit that UDP was chosen to escape TCP’s specific reliability implementation, not reliability itself. Iyengar and Thomson (eds.), RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport (IETF, 2021), states directly that QUIC provides reliable, ordered delivery per stream while avoiding head-of-line blocking across streams — the “build only the reliability you need” principle this lesson’s trade-off section names, formalized as an IETF standard rather than a folk rule of thumb.

IP multicast’s deployment gap is documented, not folklore. Diot, Levine, Lyles, Kassem and Balensiefen, Deployment Issues for the IP Multicast Service and Architecture (IEEE Network, 2000), catalogued exactly the inter-domain coordination problems — inconsistent router support, difficult inter-provider peering agreements for multicast traffic — that kept true IP multicast from becoming the internet-wide default its egress-cost math would otherwise clearly justify.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • UDP has no retransmission, ordering, or congestion control — every one of those is a choice TCP makes for you that UDP leaves you free not to make
  • A real-time stream has a playout deadline, not just a latency preference: a jitter buffer discards anything arriving after its window, so lateness and loss have the same practical effect
  • RFC 6298 floors TCP's retransmission timer at 1 full second regardless of measured RTT, and no realistic real-time jitter buffer (tens to a few hundred milliseconds) can survive waiting that long
  • This makes "TCP is too slow for real-time media" a categorical fact rather than a tuning problem — the floor exceeds the deadline by 5x to 50x at any jitter buffer size an application can actually afford
  • UDP's answer to loss is to drop the late data and conceal the gap (interpolation, frame repeat, packet loss concealment) rather than to recover it — worse per-event, but available instantly, unlike a recovery that structurally cannot arrive on time
  • Multicast delivers one stream to any number of receivers by replicating packets in the network, so a sender's egress cost under multicast does not depend on receiver count at all
  • Unicast — TCP's only option — costs a sender exactly proportional to receiver count, so the SAME stream to 10 receivers and to 100,000 differs by exactly 10,000x in sender-side bandwidth
  • Choosing UDP is not "give up reliability" — it's "build only the reliability the application actually needs," which is what QUIC does explicitly: UDP underneath, application-controlled retransmission and ordering on top

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A video call engineer says "we should switch our real-time audio path from UDP to TCP for better reliability." What's wrong with that framing?

    How sure are you, before you look?
    TCP's reliability mechanism is structurally incompatible with a playout deadline, not just "more reliable but slower." A live audio jitter buffer typically holds somewhere between 20 and 200 milliseconds of audio; TCP's retransmission timer, per RFC 6298, is floored at a full 1,000 milliseconds regardless of how fast the actual network is. A lost packet recovered via TCP retransmission arrives 5 to 50 times later than the jitter buffer can wait — the "reliable" copy shows up long after it would have been useful, guaranteeing a stall where UDP would have produced a brief, concealable glitch instead. This isn't a configuration mistake to tune away; it's what "reliable" costs, structurally, and that cost is wrong for this use case regardless of tuning.
    Did you have that?
  2. Cued recall

    If TCP's retransmission is that slow, why does video buffering on a streaming service (not a live call) work fine over TCP?

    How sure are you, before you look?
    Because on-demand streaming isn't real-time — it can afford a jitter buffer measured in seconds, not milliseconds, precisely because there's no live human on the other end waiting synchronously. A 5-10 second client-side buffer comfortably absorbs a 1-second RTO-bound retransmission with room to spare, which flips the earlier inequality: now the deadline is longer than the floor, not shorter. The distinguishing question is never "is this video," it's "does a human need this data before some short, fixed deadline that a network can't guarantee it'll beat" — live calls and competitive gaming say yes; on-demand playback says no.
    Did you have that?
  3. Cued recall

    A CDN operator is building live sports streaming to 500,000 concurrent viewers and is deciding between per-viewer unicast connections and IP multicast. What does the math actually say, independent of any implementation difficulty?

    How sure are you, before you look?
    At 500,000 receivers, unicast egress costs exactly 500,000× what multicast costs for the identical stream — multicast's server-side cost is completely independent of receiver count, because replication happens in the network rather than at the sender. This is the entire reason multicast exists as a technology, and it's also exactly why almost nobody uses IP multicast for internet-scale streaming despite the math being this favorable: real-world multicast requires every router between sender and receiver to support and correctly configure it, which the public internet's ISP topology largely does not, uniformly, at internet scale. The math says multicast wins by five orders of magnitude; the deployment reality says most large streaming services use unicast plus CDN edge fan-out to approximate multicast's benefit within networks they control.
    Did you have that?
  4. Cued recall

    QUIC runs over UDP and is often described as "TCP's reliability rebuilt from scratch." If UDP is chosen specifically because it doesn't force reliability, why did QUIC choose UDP and then add reliability back?

    How sure are you, before you look?
    Because "UDP has no reliability" and "you can't build reliability on UDP" are different statements, and QUIC exploits the gap between them. TCP's reliability, ordering, and congestion control are baked into the kernel and the wire protocol, non-negotiable and hard to evolve — a genuine problem `head-of-line-blocking` and `tls13-and-0rtt` both describe from different angles. QUIC uses UDP as a bare, permissionless transport and reimplements reliability, ordering (per-stream, not per-connection — solving head-of-line blocking directly), and congestion control in user-space, where it can evolve without an OS kernel update. It didn't choose UDP to avoid reliability; it chose UDP to control reliability rather than accept TCP's specific, inflexible implementation of it.
    Did you have that?
  5. Cued recall

    Why does DNS use UDP for most queries but fall back to TCP for large responses, rather than picking one protocol for everything?

    How sure are you, before you look?
    Because the two protocols solve different problems and a DNS query mostly needs UDP's problem solved. A typical query is one datagram, one round trip, with no ordering or multi-packet reassembly to coordinate — UDP's lack of a handshake means a query gets answered in one round trip instead of the extra round trip a TCP handshake would add first, and that's a real, measurable latency win multiplied across billions of daily queries. But a small fraction of responses (many records, DNSSEC signatures) exceed what fits safely in one UDP datagram, and reassembling a large answer from multiple UDP packets, in order, with loss recovery, means re-implementing exactly what TCP already does — at which point falling back to TCP for that specific case is cheaper than reinventing it. This is the same lesson's actual rule: use UDP for what UDP is for, and don't rebuild TCP by hand when TCP already fits.
    Did you have that?
  6. Near transfer

    A gaming company's real-time multiplayer engine currently sends all game-state updates over UDP with no acknowledgment or retransmission at all — pure fire-and-forget. Players on poor connections report that their character occasionally "teleports" or actions feel unresponsive after any packet loss. Someone proposes "just switch to TCP for reliability." Evaluate that proposal and suggest a better one.

    How sure are you, before you look?
    The proposal has correctly identified a real problem (unacknowledged loss causes visible glitches) and reached for the wrong tool, for the exact mechanism this lesson describes.

    Why plain TCP is the wrong fix: game-state updates have the same playout-deadline shape as audio or video — a player needs the CURRENT state to render the next frame, not last frame's state, however reliably delivered. If TCP retransmits a lost state update, that update is not just late, it's stale — the game has already moved past the state it describes, and TCP's ordering guarantee makes it worse: TCP will hold every update AFTER the lost one, in a queue, until the lost one's retransmission arrives, which at the RFC 6298 floor is at least 1 full second. A single lost packet would freeze every subsequent update behind it for up to a second — head-of-line blocking on top of the RTO floor, compounding rather than fixing the "teleport" symptom into something far worse (a visible freeze, not just one skipped frame).

    What the "teleports" symptom actually indicates: pure fire-and-forget UDP with zero recovery means the client has no way to distinguish "nothing changed" from "an update was lost," so when a large or discontinuous state change finally arrives, it looks like a jump. This isn't an argument for reliability in TCP's sense — it's an argument for the client interpolating or extrapolating between the last known state and new arrivals, so a loss produces smooth motion toward stale-but-plausible positions rather than a freeze followed by a snap.

    A better fix, in order of effort: (1) send state as a snapshot of current truth on every tick rather than a delta requiring all prior updates — this alone means a lost packet is superseded by the next one arriving on schedule, with no retransmission needed at all; (2) add client-side dead reckoning/interpolation to smooth the visible gap when a snapshot is late or lost; (3) for the subset of events that genuinely can't be dropped (a critical hit, a death, an item pickup) — not movement — layer a lightweight application-level acknowledgment and resend only for those specific messages, exactly the "build only the reliability you need" principle QUIC applies at the transport layer. None of this requires TCP, and none of it inherits TCP's head-of-line blocking.
    Did you have that?
  7. Far transfer

    The abstraction is: a general-purpose recovery mechanism has a fixed minimum cost that exists to protect against a DIFFERENT failure mode than the one you're worried about, and that fixed cost can categorically exceed what your actual situation can tolerate — at which point the fix is not to wait faster, it's to accept the loss and move on visibly. Name an instance outside computing.

    How sure are you, before you look?
    A live TV broadcast's response to a dropped satellite feed frame. A broadcast engineer could, in principle, request a re-send of a missing frame from the source — but by the time any request-and-resend round trip completes, the broadcast has moved seconds ahead, so a "reliable" recovered frame would already show a moment that's aired and gone. Live broadcast systems instead freeze or repeat the last good frame for an instant and press on — visibly imperfect, but synchronized with real time, which is the actual requirement. Waiting for a perfect frame is not slower-but-correct; it's a category error, exactly like waiting out a 1-second TCP RTO for an audio sample due 100ms from now.

    Other instances: a surgeon's response to a dropped instrument mid-procedure — the protocol isn't "wait for the exact same instrument to be re-sterilized and returned" (the equivalent of a guaranteed, ordered retransmission), it's "grab the next-best available instrument and continue," because the patient's timeline has a deadline no cleaning cycle can meet. And a courtroom stenographer who mishears one word — the fixed, general-purpose "verify with the speaker before continuing" process exists for genuine ambiguity, but for one missed word among thousands, the stenographer marks it inaudible and continues rather than halting the entire proceeding to guarantee zero loss, because the meeting's own deadline (finishing the hearing) categorically outweighs recovering one word with certainty.
    Did you have that?
