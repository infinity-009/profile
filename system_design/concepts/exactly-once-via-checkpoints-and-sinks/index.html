Tier 5 · Moving data around Checkpoint + replay + sink

A 1-second checkpoint interval still hands an unsafe sink 1,000 duplicates; a 900-second interval hands an idempotent sink zero

`stateful-operators-and-checkpointing.mdx` prices what a checkpoint recovers: operator state consistent as of the last checkpoint, bounded by an interval you control. `exactly-once-and- delivery-semantics.mdx` proves true exactly-once delivery is impossible and prices what idempotent processing buys against a wire-level duplicate. Neither one, alone, is exactly-once stream processing — this lesson is the composition: a checkpoint plus a source that can replay from it plus a sink that survives a replay, and what breaks if exactly one of those three is missing. The concrete payoff: checkpoint interval controls how MANY events get reprocessed after a crash; sink idempotency controls whether that reprocessing duplicates anything at all. They are separate knobs, and this lesson computes both so the difference stops being a slogan.

01

Both celebrated pieces worked. The bug was in the piece nobody named.

A team runs a Flink-style job: checkpoints every 30 seconds, reads from Kafka, writes running account balances to Postgres. A worker crashes. Recovery looks textbook — the checkpoint loads cleanly, the consumer resumes from exactly the offset the checkpoint named, the last 30 seconds of events replay without a single gap or a single skip. Everyone involved would, reasonably, call this a success: the checkpoint did its job, Kafka did its job.

A week later, balances are off. Not everywhere — only for accounts that had an event land inside that one 30-second replay window. The checkpoint was never broken. The replay was never broken. The sink — balance = balance + amount, applied a second time to every event recovery legitimately reprocessed — was the one piece nobody had checkpointed, replayed, or in any other way protected, because neither of the other two pieces was ever designed to protect it.

02

Assume checkpointing (already priced) plus a replayable source (already available) IS exactly-once

The instinct: stateful-operators-and-checkpointing.mdx already prices exactly what a checkpoint recovers, Kafka is famously replayable, so surely the two together already are the guarantee. They are not, and the gap is precise rather than vague: a checkpoint’s actual claim is “operator state consistent as of the last checkpoint.” That sentence has nothing to say about output the operator already emitted before the crash — a row written downstream, a message published, an email sent. Replay does exactly what it is supposed to do to the input side of that gap: it hands the operator the same events again. What happens on the OUTPUT side of that replay is decided by a third thing this lesson hasn’t named yet, and it is decided independently of how good the first two are.

Predict A stream job reads from Kafka (fully replayable), checkpoints state and offset atomically every 30s, and writes to a sink via `balance = balance + amount` for every event — a raw, unguarded increment. After a crash, recovery correctly reprocesses 1,000 events since the last checkpoint. What happens to `balance`?
sinkDuplicateOutcome({ eventsReprocessed: 1000, sinkMode: 'unsafe' }) returns exactly 1,000 duplicate side effects -- one per reprocessed event, full stop. The checkpoint and the replay both did their job perfectly: state recovered correctly, the source handed back precisely the right 1,000 events. Nothing about EITHER of those two pieces was ever responsible for noticing that an event had already been applied once -- that is what a sink guard is for, and this sink has none. Shortening the checkpoint interval would shrink the 1,000 to something smaller, never to zero: it changes how much gets reprocessed, not whether reprocessing is safe.
Show it without answering

At the rig’s opening default — a 30-second interval, 1,000 events/s, an unsafe sink — recovery reprocesses 30,000 events and every single one of them duplicates its side effect. Switch the sink to idempotent without touching anything else and that second number drops to exactly zero — the 30,000 didn’t shrink, replaying them simply stopped mattering.

03

A real system names all three pieces by their real names

Kafka Streams’ “exactly-once semantics” is not a fourth mechanism bolted onto checkpointing — it is this lesson’s three pieces, each with a name in that system:

  • Checkpoint, piece 1: Kafka Streams checkpoints operator state by writing state changes to a dedicated, log-compacted Kafka topic (a changelog topic) — the state commit and the consumer offset commit are made to participate in the same Kafka transaction, which is precisely piece 1’s atomicity requirement, engineered rather than assumed.
  • Replayable source, piece 2: the input is Kafka itself — a log, not a queue, per queue-vs-log.mjs — so “resume from offset X” is a request the broker can always satisfy within retention.
  • Sink, piece 3: Kafka’s transactional producer writes output records and advances the consumer’s input offset inside one atomic transaction, so a downstream read-committed consumer never observes a half-replayed batch — this is the transactional/2PC route through piece 3, not the naturally-idempotent route.

Three pieces, three concrete mechanisms, one framework. The moment output leaves for a system that isn’t inside that transaction boundary — a different database, a different message broker, an email API — piece 3’s transactional guarantee stops applying, and whatever receives that output is back to needing its own guard, exactly the way idempotency.mdx’s own “in the wild” section already makes true of Kafka’s producer-side idempotence.

The numbers

Piece 1, checkpoint atomicity — checkpointAtomicityOutcome, a 37-event drift either direction:

Offset committed 37 events ahead of state comes back kind: 'lost', lostEvents: 37. State committed 37 events ahead of offset comes back kind: 'double-counted', doubleCountedEvents: 37. Same 37-event drift, opposite failure — which one you get depends only on which commit reached durable storage first.

Piece 2, replayable vs. not — 30s interval, 2,000 events/s, reprocessingBoundFromThroughput + sourceRecoveryOutcome:

node -e "import('./src/sim/exactly-once-via-checkpoints-and-sinks.mjs').then(m => {
  const gap = m.reprocessingBoundFromThroughput({ checkpointIntervalSeconds: 30, throughputEventsPerSec: 2000 });
  console.log('gap', gap);

The gap is 60,000 events either way — that number is set entirely by the interval and the throughput. A replayable source turns it into recoveredEvents: 60000, permanentlyLostEvents: 0. A non-replayable source turns the identical 60,000 into recoveredEvents: 0, permanentlyLostEvents: 60000 — same gap, opposite outcome, decided by a property of the source that the checkpoint’s own math never touches.

Read this table by column, not by row. Down the “events reprocessed” column, the interval is doing all the work — 900× the interval, 900× the reprocessed count, exactly linear. Across any one row, the sink mode is doing all the work — idempotent and unsafe start from the identical reprocessed count and land at 0 and “all of it” respectively, and the ratio between those two never depends on which row you’re looking at. Guarded sits in between, closer to idempotent by eleven orders of magnitude, and rises with the interval for the same reason unsafe does — it’s still eventsReprocessed × (1 − effectiveness), and effectiveness alone doesn’t erase the multiplication.

All three pieces, composed — endToEndGuarantee over the four SCENARIOS:

all-good → effectively-once results. nonatomic-checkpoint → broken. non-replayable-source → at-most-once. unsafe-sink → at-least-once, duplicated side effects. Four scenarios, one piece changed at a time from the same “all-good” baseline, four different named guarantees — not four degrees of the same guarantee.

06

Remove any one piece and you don't get a smaller guarantee — you get a different one

Remove piece 1 (checkpoint atomicity) and the failure is silent and structural. A non-atomic checkpoint doesn’t announce itself — the job keeps running, keeps checkpointing, keeps looking healthy. What it produces on recovery is either quietly missing events (if the offset commit won) or quietly double-counting them into the operator’s own aggregated state (if the state commit won) — and a double-counted running total doesn’t look like a bug, it looks like a number, which is worse than an obviously duplicated row in a log, because nothing points at it.

Remove piece 2 (replayability) and pieces 1 and 3 keep working perfectly, for nothing. The checkpoint still loads. It still says “resume from offset X.” The source has no offset X anymore — it deleted that event the moment a consumer acked it, the way queue-vs-log.mjs’s classic-queue model always has. The sink never even gets a chance to prove whether it’s safe, because there is nothing left to send it. This is the one failure mode that has nothing to do with either checkpointing or sinks — it’s a property of the source, decided long before either of the other two pieces is designed.

Remove piece 3 (sink safety) and the other two pieces did their job perfectly, and it didn’t matter. This is the failure this lesson opened with, and the numbers above make it exact: a 30,000-event reprocessing window through an idempotent sink is 0 duplicated side effects; the identical 30,000-event window through a raw increment is 30,000. Same checkpoint, same replay, same events — the only variable that moved was a property of the sink, and it moved the outcome from “correct” to “every single one of them” with nothing in between.

None of the three is a substitute for either of the others, and none of them is free: checkpointing costs whatever stateful-operators-and-checkpointing.mdx already priced (write throughput, interval-vs-recovery trade), a replayable source costs the retention-sized disk bill queue-vs-log.mdx already priced, and a safe sink costs either an idempotency-key store’s guard apparatus (idempotency.mdx) or a transaction protocol’s overhead (exactly-once-and- delivery-semantics.mdx’s “effectively-once” is this exact composition one layer down, at the message-delivery boundary instead of the stream-operator boundary).

07

In the wild

DDIA’s own chapter on stream processing ends on exactly this composition, in a section literally titled “Fault Tolerance”: batch jobs get exactly-once cheaply because failed output is simply discarded and the task retried from nothing — “the output of the failed task is discarded” — but “waiting until a task is finished before making its output visible is not an option” for a stream, “because a stream is infinite” (Kleppmann, DDIA, 2nd ed., “Fault Tolerance,” p. 526). Checkpointing (pieces 1–2 of this lesson) is DDIA’s answer to that first half. The second half gets its own two named subsections, and this lesson is built directly on top of them.

“Atomic commit revisited” is piece 3’s transactional route, named precisely: “To give the appearance of exactly-once processing in the presence of faults, we need to ensure that all outputs and side effects of processing an event persist if and only if the processing is successful… These actions must all happen atomically” (Kleppmann, DDIA, 2nd ed., “Atomic commit revisited,” pp. 527–528) — DDIA cross-references its own ch. 8 discussion of distributed transactions and two-phase commit (“Exactly-once message processing,” p. 329) as the general mechanism this section applies to the stream-processing boundary specifically.

“Idempotence” is piece 3’s other route, and it states piece 2’s requirement as an explicit precondition of piece 3 working at all: “An idempotent operation is one that you can perform multiple times, and it has the same effect as if you performed it only once… Relying on idempotence implies several assumptions: restarting a failed task must replay the same messages in the same order (a log-based message broker does this), the processing must be deterministic, and no other node may concurrently update the same value” (Kleppmann, DDIA, 2nd ed., “Idempotence,” p. 528). That parenthetical is piece 2 named from inside piece 3’s own section — idempotence is not a standalone fix, it is a fix that only works once a replayable source has already guaranteed the replay is identical every time.

Apache Kafka’s KIP-98, “Exactly Once Delivery and Transactional Messaging,” is the design document behind the transactional producer this lesson’s Slot 3 describes — idempotent producer IDs plus sequence numbers, and transactions spanning a state changelog write and an input-offset commit as one unit. idempotency.mdx’s and exactly-once-and-delivery-semantics.mdx’s own “in the wild” sections already name Kafka’s producer-side guarantee; this is the source document behind it, not a different mechanism.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • Exactly-once stream processing is not one mechanism — it is three independent pieces composed: (1) an ATOMIC checkpoint of operator state and source offset together, (2) a REPLAYABLE source that can resume from that checkpointed offset, and (3) a sink that either ignores or absorbs the output a replay re-emits (naturally idempotent, or transactional with the checkpoint)
  • A checkpoint's own guarantee, from `stateful-operators-and-checkpointing.mjs`, is narrower than it sounds: "operator state consistent as of the last checkpoint." It says nothing about output already emitted before the crash — that output gets re-emitted the instant the gap since the checkpoint is replayed, which is exactly what recovery is supposed to do
  • Piece 1's failure mode (checkpoint atomicity): if state and offset commit separately, a crash between the two commits leaves them disagreeing. Offset committed AHEAD of state loses the gap silently; state committed AHEAD of offset folds those events into the operator's own memory a SECOND time — corrupting every number the operator computes from then on, which is worse than a duplicated output
  • Piece 2's failure mode (replayable source): a consistent checkpoint's "resume from offset X" is a promise only the source can keep. A log-based source keeps it trivially (`queue-vs-log.mjs`); a delete-on-ack queue cannot keep it at all, and the guarantee collapses straight to at-most-once no matter how good the checkpoint or the sink is
  • Piece 3's failure mode (sink safety): even with a perfect checkpoint and a perfectly replayable source, a sink with no guard — a raw increment, an email send — duplicates every single reprocessed event's side effect. Checkpoint and replay both did their job; the sink is what leaks
  • The orthogonality this lesson makes numeric: checkpoint interval (and throughput) controls HOW MANY events get reprocessed on a crash — `reprocessingBoundFromThroughput`. Sink idempotency controls WHETHER that reprocessing duplicates a side effect at all — `sinkDuplicateOutcome`. Shrinking the interval to nearly zero does not make an unsafe sink safe; making the sink safe does not make a huge interval's reprocessing free
  • `idempotency.mjs`'s own asymmetry inherits into the sink piece unchanged: a naturally idempotent or transactional sink is exact — zero duplicated side effects, always. A sink protected only by an idempotency-key store gets arbitrarily close to zero but never reaches it exactly, because retention is a bet, not a proof — this lesson's "guarded" sink mode is that same bet, one layer up

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A team checkpoints operator state to durable storage every 30 seconds and separately commits the consumer's Kafka offset every 30 seconds, in two unsynchronized writes. A crash lands between the two. Is this exactly-once processing?

    How sure are you, before you look?
    No, and neither the source's replayability nor the sink's safety can rescue it. `checkpointAtomicityOutcome` names the two ways this specific failure resolves: if the offset commit landed and the state commit did not, the gap between them is LOST — nothing will ever ask for those events again. If the state commit landed first, those events get folded into the state a SECOND time on recovery — DOUBLE-COUNTED, corrupting the operator's own memory rather than merely duplicating output. `endToEndGuarantee` checks checkpoint atomicity first, before it even looks at the other two pieces, because a broken checkpoint makes their quality irrelevant.
    Did you have that?
  2. Cued recall

    A stream job reads from Kafka (replayable), checkpoints correctly, and writes to Postgres via UPDATE accounts SET balance = balance + amount WHERE id = ? for every event. After a crash and a clean recovery that reprocesses 1,000 events since the last checkpoint, what does balance look like?

    How sure are you, before you look?
    Wrong, by exactly the reprocessed events' worth of amount. sinkDuplicateOutcome({'{'} eventsReprocessed: 1000, sinkMode: 'unsafe' {'}'}) returns 1,000 duplicate side effects — one for every reprocessed event, independent of the checkpoint interval that produced that count. Checkpoint and replay both worked exactly as designed: the state recovered correctly and the source handed back the right 1,000 events. The sink is a read-modify-write, and nothing in the checkpoint or the replay mechanism can tell it "this one already happened" — that was never either of their jobs.
    Did you have that?
  3. Near transfer

    A sink writes INSERT INTO events (id, payload) VALUES (?, ?) ON CONFLICT (id) DO NOTHING, using the source's own offset as id. Is that this lesson's "idempotent" sink mode, or its "guarded" sink mode?

    How sure are you, before you look?
    Idempotent — structurally, not by a guard's mercy. `idempotency.mjs`'s own OPERATIONS list already calls "INSERT … ON CONFLICT DO NOTHING" naturally idempotent, and the reason it applies exactly here is that the key isn't invented by a client and retained for a configurable window — it's the offset, which a replay reproduces IDENTICALLY every time by definition, and the database's uniqueness constraint rejects the second write unconditionally. Compare that to this lesson's "guarded" mode, which is `idempotency.mjs`'s key-STORE approach: a key that has to be looked up within a retention window that can expire, which is exactly why guarded's duplicate rate in this lesson's numbers is never exactly zero. Same shape (a uniqueness check before the write), different guarantee (unconditional vs. retention-bounded) — the offset-as-key trick buys the exact version for free because the "key" was never something that could go stale.
    Did you have that?
  4. Far transfer

    The abstraction is: a recovery mechanism that correctly reconstructs internal memory after a failure does not, by itself, prevent an action already taken before the failure from being taken again — a second, unrelated mechanism has to make repeating the action either impossible or harmless, and how good the first mechanism is has no bearing on whether the second one exists. Name an instance outside stream processing.

    How sure are you, before you look?
    An ATM recovering from a power flicker mid-withdrawal. The ATM's own internal recovery — its transaction log, its record of which dispense command was in flight — can correctly tell it, on reboot, exactly what it had started doing before power dropped: that's the checkpoint, working perfectly. But whether the customer walks away with $400 instead of $200 depends entirely on a SEPARATE system: does the bank's core ledger treat "debit $200 for transaction #4471" as a repeatable, idempotent operation checked against that transaction id before it posts, or does it just apply "debit $200" again on any retry? A flawless ATM reboot does not make the ledger update safe to repeat, the same way a flawless checkpoint does not make a raw increment safe to replay — one system is recovering memory, the other is deciding whether an action may happen twice, and they are answerable to completely different engineering questions.
    Did you have that?
