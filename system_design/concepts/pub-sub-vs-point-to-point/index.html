Tier 5 · Moving data around Pub/sub vs. point-to-point

Point-to-point delivers a message once no matter how many consumers compete for it; pub/sub delivers it once PER subscriber — a 50× delivery-cost gap at 50 subscribers, and why Kafka's hybrid pays for the groups, not the members

`queue-vs-log.mdx` asked what a broker is obliged to KEEP — delete-on-ack or append-and-retain. This lesson asks an orthogonal question: for a given message, how many consumers actually RECEIVE it? Point-to-point delivers each message to exactly one consumer of a competing set, so total delivery work never grows no matter how many consumers are added — they only split who does it. Pub/sub delivers each message to every subscriber independently, so N subscribers means N full, separate deliveries of the same bytes. This lesson computes that delivery-cost gap exactly, classifies which topology a scenario actually needs with a real scoring function rather than an assertion, and prices the hybrid model most real systems actually run — Kafka's consumer-group topic — where cost scales with the number of independent groups and not at all with how many members split the work inside one.

Read first — queue-vs-logconsumer-groups-and-rebalancing

01

Fifty subscribers, fifty full copies of the same message

A team migrates a work queue to a pub/sub topic so that a second team can “just subscribe” to the same event stream, expecting the change to be free — same messages, same broker, just one more listener. Delivery bandwidth quietly rises by a factor matching the subscriber count, because pub/sub was never delivering the message once; it was delivering it once per subscriber, from the very first one. Point-to-point hands a message to exactly one consumer out of a competing pool. Pub/sub hands it, independently, to every single subscriber. That’s not an overhead someone forgot to optimize away — it’s the entire mechanism, and this lesson prices it exactly.

02

Assume 'more consumers' always means 'more parallelism, same total work'

The instinct carried over from point-to-point queues: adding a consumer to something reading a message stream should split the load further, so total delivery work never changes — it’s the same messages, just more hands processing them. That’s exactly right for point-to-point. It is exactly backwards for pub/sub, where “consumer” means “subscriber,” and every subscriber added is a whole new, independent recipient of every message — not a new hand helping process the existing pile.

Point-to-point’s contract: each message goes to exactly one consumer of a competing set. The broker’s total delivery work is messageCount x avgBytes — full stop. Adding consumers changes which one gets each message, never how many times a message is delivered.

Pub/sub’s contract: each message goes to every subscriber, independently. The broker’s total delivery work is messageCount x avgBytes x subscriberCount — every subscriber is a full, separate delivery of the same underlying bytes.

This is a different axis entirely from queue-vs-log.mdx’s delete-on-ack versus append-and-retain — that lesson priced what the broker is obliged to keep; this one prices how many consumers each message is obliged to reach. A system picks a storage model and a delivery topology independently: a classic queue is (delete-on-ack, point-to-point); Kafka’s per-partition read is (append-and-retain, and — as Slot 4 below computes — able to run either topology, or both at once).

Predict 100,000 messages at 2,000 bytes average go out to 50 independent pub/sub subscribers. How does that delivery cost compare to point-to-point delivery of the same 100,000 messages?
pointToPointCost({messageCount:100000, avgBytes:2000}) = 200,000,000 bytes (200 MB), full stop -- consumer count never enters that formula. pubSubCost({messageCount:100000, avgBytes:2000, subscriberCount:50}) = 10,000,000,000 bytes (10 GB) -- exactly 50x, because each of the 50 subscribers is an independent, full delivery of every message. The gap is exactly the subscriber count, by construction, not an estimate.
Show it without answering

At the rig’s default — 100,000 messages, 2,000 bytes average — point-to-point costs 200 MB, flat. Pub/sub at 4 subscribers costs 800 MB — exactly 4x. Push subscriber count to 50 and pub/sub costs 10 GB — exactly 50x the point-to-point figure, for the identical underlying traffic.

03

The deli ticket and the PA announcement

A deli counter’s ticket dispenser hands out one number per customer; whichever clerk is free calls the next number and serves that one customer. Adding a fourth clerk to a three-clerk counter speeds up the line, but the deli still slices exactly one order’s worth of meat per ticket — the total amount of meat sliced is set by how many tickets were issued, not by how many clerks are working. That’s point-to-point: one unit of work, one taker from a pool, and pool size never changes the total work.

A store’s overhead PA system works differently. “Cleanup on aisle 5” is heard, independently, by every employee wearing an earpiece. Wire up 10 earpieces instead of 3 and the announcement doesn’t get more efficient — it’s effectively repeated into 10 ears instead of 3, at the cost of however much broadcasting to 10 recipients actually costs over broadcasting to 3. That’s pub/sub: one event, N independent listeners, and total delivery work scales with N.

04

The hybrid: Kafka's consumer groups pay for the groups, not the members

Real systems rarely pick one topology and stop. Kafka’s own topic/consumer-group model combines both, and DDIA names the combination directly: “the two patterns can be combined — for example, using Kafka’s consumer groups feature. When a consumer group subscribes to a topic, each message in the topic is sent to one of the consumers in the group (balancing load across the consumers in the group). If two separate consumer groups subscribe to the same topic, each message is sent to one consumer in each group (providing fan-out across consumer groups)” (DDIA, 2nd ed., p. 492).

That’s exactly the mechanism consumer-groups-and-rebalancing.mdx already built the within-group half of: inside one group, partitions are owned by exactly one member at a time — point-to-point, full stop, the same competing-consumers mechanism as any classic queue. What’s new here is the across-groups half: K independent consumer groups each get their own full, independent read of the topic — pub/sub, one full copy per group.

K INDEPENDENT GROUPS, G MEMBERS EACH

  group 1 (G members, competing for group 1's copy)  <- full copy #1
  group 2 (G members, competing for group 2's copy)  <- full copy #2
  ...
  group K (G members, competing for group K's copy)  <- full copy #K

  delivery cost = messageCount x avgBytes x K   -- scales with K, the group COUNT
  delivery cost is UNCHANGED by G                -- splitting one copy across G members is free

hybridCost makes that a checkable claim rather than a description: it takes groupCount and membersPerGroup as separate inputs, and membersPerGroup never appears in the arithmetic at all. At 100,000 messages of 2,000 bytes and 3 groups, the cost is 600 MB whether each group has 1 member, 10 members, or 100 — identical every time, because load distribution within a group is free: it only decides which member does the work, exactly the way point-to-point never changes total delivery work with pool size. Only the number of independent groups (K) adds delivery cost — which is the concrete reason the hybrid model is the default most real systems reach for: it buys pub/sub’s “many independent interested parties” property without paying pub/sub’s full per-consumer cost, because every extra member inside an existing group is free parallelism, not an extra full copy.

06

The trade-off — point-to-point can't notify everyone, pub/sub can't share the load for free

Point-to-point naturally supports work distribution and nothing else. Competing consumers split a fixed pile of work, and total work stays constant no matter how many consumers join the pool — exactly what a task queue needs. It does not support “notify everyone interested” at all: a second team wanting to see the same stream gets nothing from subscribing to a point-to-point queue except a coin-flip chance of seeing any given message, because the mechanism hands each message to one consumer, not many. Getting “notify everyone” out of a point-to-point system needs extra machinery bolted on — N separate queues, or a fan-out stage duplicating every message, which is exactly the “N separate copies, storage multiplies by N” cost queue-vs-log.mdx already prices from the storage side of this same seam.

Pub/sub naturally supports “notify everyone interested” and nothing else, for free. Any number of independent downstream systems can each react to the same event without coordinating with one another — no extra machinery needed, no fan-out stage to build. What it does not do for free is share load within one subscriber’s own consumption: a single subscriber that itself needs multiple workers to keep up gets nothing extra from being a pub/sub subscriber — the topology delivers that subscriber a full copy regardless of how many internal workers it has, so pub/sub alone never turns one slow subscriber into many parallel ones.

The hybrid is the real-world answer most systems reach for precisely because it removes both gaps at once, at a cost that only scales with the axis that actually needs it. Every consumer group gets pub/sub’s independent full-copy property; every member inside a group gets point-to-point’s free internal parallelism. The price is exactly K, the group count — never G, the member count — which is why teams add workers inside an existing consumer group liberally (free) but think twice before standing up a brand-new consumer group for a stream that already has several (linear cost, same as adding a pub/sub subscriber).

07

In the wild

DDIA names both patterns, and their combination, in exactly the terms this lesson computes — Kleppmann & Riccomini, Designing Data-Intensive Applications, 2nd ed., O’Reilly, Chapter 12 “Stream Processing,” “Multiple Consumers,” pp. 492–493: “Load balancing: Each message is delivered to one of the consumers, so the consumers can share the work of processing the messages… Fan-out: Each message is delivered to all the consumers.” The book’s “load balancing” is this lesson’s point-to-point; its “fan-out” is this lesson’s pub/sub. The book’s own worked instance of the hybrid — “two separate consumer groups subscribe to the same topic, each message is sent to one consumer in each group” (p. 492) — is exactly hybridCost’s model, generalized to K groups.

consumer-groups-and-rebalancing.mdx already built the within-group mechanics this lesson’s hybrid reuses unchanged — partition ownership, one consumer per partition at a time within a group, and what happens when that assignment changes. This lesson adds the across-group axis on top: how many independent groups exist, and why that count is the only thing hybrid delivery cost tracks.

queue-vs-log.mdx already priced the “N independent readers” cost from the storage side, for a delete-on-ack queue — its fanoutStorageCost computed N separate physical copies as a storage problem; this lesson’s pubSubCost computes the structurally identical multiplication as a delivery-bandwidth problem, on a topology axis that applies regardless of whether the underlying broker deletes on ack or retains forever.

fanout-write-vs-read-time.mdx (sibling, not yet built) asks a different question about the same word — not how many recipients receive an event, but WHEN the per-recipient work of assembling their view happens, given that a pub/sub-shaped “many independent readers” relationship already exists.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • Point-to-point delivers each message to exactly ONE consumer of a competing set — total delivery work stays constant as consumer count changes, because adding consumers only changes WHO processes each message, never how many times it's delivered
  • Pub/sub delivers each message to EVERY subscriber independently — N subscribers means N separate, full deliveries of the same message, so delivery cost scales linearly with subscriber count, not with message count alone
  • This is an orthogonal axis to `queue-vs-log.mdx`'s delete-on-ack vs. append-and-retain — that lesson is about what the broker is obliged to STORE, this one is about how many consumers RECEIVE each message; a system can combine either storage model with either delivery topology
  • The hybrid topic/consumer-group model (Kafka) combines both: K independent consumer groups each get their own full copy of the topic (pub/sub across groups), but WITHIN a group the G members compete for that one copy's messages (point-to-point/load-balancing within the group) — this is `consumer-groups-and-rebalancing.mdx`'s within-group mechanism, reused unchanged as the point-to-point half of the hybrid
  • Hybrid delivery cost scales with K (the number of independent groups) and is completely flat against G (members per group) — splitting an already-delivered copy across G competing consumers is free, it changes who does the work inside a group, not how many times the message crosses the broker-to-consumer boundary
  • Choosing a topology is a real classification, not a taste call: it's driven by whether every interested party needs its OWN full copy (favors pub/sub) and whether any one party needs to split ITS OWN work across workers (favors point-to-point) — both properties at once is exactly when the hybrid wins

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A team runs an image-processing task queue: any of 20 workers may pick up any job, and each job should be processed exactly once. They're told "pub/sub scales better with more consumers, so let's make this a pub/sub topic instead of a point-to-point queue." What happens to the total processing work if they do?

    How sure are you, before you look?
    It goes up by a factor of 20, not down. Pub/sub delivers each job to EVERY subscriber independently — 20 workers subscribed to the same topic would each independently receive and process every single job, turning "process each image once" into "process each image 20 times." `pubSubCost` at 20 subscribers is exactly 20x `pointToPointCost` for the same message traffic. What this team actually wants is more competing consumers on the SAME queue — point-to-point's whole mechanism — which keeps total delivery work constant while letting the 20 workers split it.
    Did you have that?
  2. Cued recall

    A "user signed up" event needs to independently trigger a welcome email, an analytics pipeline update, and a fraud-check scan. A developer proposes a single point-to-point queue with three consumers so "the load balances across the three tasks." Will that work?

    How sure are you, before you look?
    No — point-to-point's mechanism guarantees each event goes to exactly ONE of the three consumers, competing for the same messages. Whichever consumer happens to receive a given signup event is the only one that acts on it — the other two never see it. `classifyTopology` scores this scenario correctly: `needsEveryReaderToSeeEveryMessage: true` (all three need every event) with `independentInterestedPartyCount: 3` classifies as `pub-sub`, not point-to-point — each of the three needs its OWN full, independent copy of every signup event, which is exactly what pub/sub delivers and point-to-point structurally cannot.
    Did you have that?
  3. Near transfer

    `fanout-write-vs-read-time.mdx` (a sibling lesson) asks WHEN fan-out work happens — at write time (push a copy to every follower's timeline as each post is made) versus at read time (compute the union on demand when a follower asks). A reader argues that's "the same question" as this lesson's point-to-point-vs-pub/sub axis, since both involve "fanning out to many recipients." Is that the right transfer?

    How sure are you, before you look?
    No — it's the same word ("fan-out") attached to two different axes. This lesson's axis is HOW MANY consumers receive a given message: point-to-point picks one out of a competing set, pub/sub delivers to all of them. `fanout-write-vs-read-time`'s axis is WHEN the work of assembling each recipient's view happens, GIVEN that a pub/sub-style "many recipients need to see this" relationship already exists — write-time fan-out precomputes each recipient's copy eagerly, read-time fan-out defers that computation until someone asks. A social-media post going out to a million followers is a pub/sub delivery problem either way; write-time versus read-time is a decision about WHEN to pay the cost this lesson's `pubSubCost` already prices, not a competing description of how many followers receive it.
    Did you have that?
  4. Far transfer

    The abstraction is: one delivery mechanism hands a single unit of work to exactly one taker from a pool, so the total work stays fixed regardless of pool size; a second mechanism broadcasts the same unit to every registered party independently, so the total work multiplies by however many parties are registered. Name an instance outside computing.

    How sure are you, before you look?
    A ticket dispenser at a deli counter versus a store's overhead PA announcement. A ticket dispenser hands out one number per customer, and any one of the counter's clerks calls the next number and serves that customer — adding more clerks changes how fast the line moves, but the deli still slices exactly one order's worth of meat per ticket, regardless of how many clerks are working the counter. A PA announcement ("cleanup on aisle 5") is heard by every employee wearing an earpiece independently — page 10 employees instead of 3 and the announcement doesn't get any cheaper or more efficient to make, it is simply repeated, in effect, into 10 ears instead of 3. The dispenser is point-to-point: one ticket, one taker, cost fixed by ticket count. The PA system is pub/sub: one announcement, N independent listeners, cost scaling with N — exactly the mechanical gap `pointToPointCost` and `pubSubCost` compute.
    Did you have that?
