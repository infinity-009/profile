Tier 6 · Running it in production Config as Deploy Risk

A config push changes fleet-wide behaviour exactly like a code deploy, but a typical config pipeline skips the canary stage entirely — so an equally-bad change exposed at 500 rps totals 300,199 requests reverted in 10 minutes flat, versus 1,699 for the identical bug run through an ordinary 5% code canary

`canary-analysis-and-rollback.mdx` prices what a CODE change costs once it's live: a fixed detection floor plus whatever a rollback mechanism's own delay adds. A config push (a feature flag, a rate limit, a routing rule, anything read from a dynamic-config system) changes runtime behaviour across the fleet the same way — `rollbackBlastRadius` applies unchanged, because the formula never asked whether "the bad behaviour" arrived as a binary or a config value. What changes is the pipeline around it: config systems are built to propagate near-instantly (that's their whole job), so they're usually run at canaryFraction=1 from the first millisecond, with no staged ramp and often no pre-push validation either — the two cheapest gates in this course, skipped together, for exactly the reason that makes each one look unnecessary on its own.

Read first — canary-analysis-and-rollback

01

The same bug, the same formula, a pipeline that skips the canary stage

Run the identical bug — 2% errors against a 0.5% baseline, at 500 requests/second — through two different pipelines. A code deploy goes out behind a 5% canary with a 60-second automated rollback: rollbackBlastRadius says it totals 1,699 requests by full recovery. A config push carrying the exact same bug goes out to 100% of the fleet from the first millisecond, because that is what a config-distribution system is built to do, and nobody notices until a human checks a dashboard 10 minutes later: the identical formula, canaryFraction: 1, rollbackDelaySeconds: 600, totals 300,199 — 177x more.

Nothing about the arithmetic changed. rollbackBlastRadius doesn’t know or care whether the bad behaviour arrived as a binary or a config value — it only asks what fraction of traffic was exposed and for how long. What changed is which two numbers a real config pipeline plugs into a formula this course already has: a much bigger canaryFraction (because config propagation is fast and usually unstaged) and a much bigger rollbackDelaySeconds (because there is often no automated statistical gate watching a config push at all — someone has to notice first).

02

Assume 'it's just a config, not a deploy' means it's lower-risk

The instinct: a deploy pipeline exists because code is risky — it has bugs, it needs review, it needs a canary. A config change feels like flipping a switch: no compilation, no artifact, no review gate most teams bother enforcing, so it feels cheap and safe to skip the ceremony. The switch it flips is read by every server in the fleet, though, and it flips for all of them at once — the ceremony a config path skips is the exact ceremony that would have caught the failure mode this rig prices.

Predict A code deploy runs behind a 5% canary with a 60-second automated rollback. An equally bad config push goes straight to 100% of the fleet and takes 600 seconds (10 minutes) for a human to notice and revert, at the same 500 rps and the same bug. Using rollbackBlastRadius for both, roughly how much MORE total exposure does the config push cause?
Both need the identical 199 exposures to cross the detection threshold — that part never changes. But the config push starts at canaryFraction=1 immediately (500 x 1.0 x 600 = 300,000 extra requests during its revert delay) while the code canary was only ever exposing 5% of traffic during a much shorter delay (500 x 0.05 x 60 = 1,500 extra). Total: 300,199 versus 1,699, a 177x gap — from BOTH numbers moving against the config push at once, not from either alone.
Show it without answering

At the rig’s default — a 5% bad-config rate, an 80%-effective validator, a 600-second revert delay, and a 5% staged-traffic option — instant propagation totals 300,199 requests per bad push against 15,199 for the staged alternative, a 19.8x gap that exists purely because config systems propagate near-instantly by design. Weighted by how often a bad config actually happens and slips past validation, skipping both gates costs 15,010 expected requests per push; doing both costs 152 — a 98.8x reduction from the two cheapest gates in this course.

03

The intuition: an overnight price update with a decimal point wrong

A grocery chain updates every store’s shelf-tag prices overnight through one central system — fast, uniform, exactly what the system exists for. If one price upload has a decimal point in the wrong place, it shows up at every single store the next morning, simultaneously, because the distribution system has no concept of “this one looks wrong” — it only knows how to push a value everywhere, reliably and fast. A sanity check before upload (is this price within 50% of last week’s number) catches the typo before a single shelf tag prints it. A staged rollout (push to five pilot stores, check for complaints, then push everywhere) catches it a few hours later instead of overnight, at the cost of those few hours. Skipping both is the fastest way to discover a decimal-point bug: from every register in every store, all reporting the same wrong price by opening time.

04

The mechanism: one formula, two new gates

Reused unchanged: exposure is exposure, whatever changed

rollbackBlastRadius from canary-analysis-and-rollback.mjs needs nothing new for the propagation side of this lesson — a config push at 100% instant rollout and a code deploy at 5% staged rollout are both just calls to it with different arguments:

totalExposed = nrequired + canaryFraction · totalRequestRate · rollbackDelaySeconds

The identical formula this course already derived. A config push plugs in canaryFraction≈1 (fast, usually unstaged propagation) and a typically LARGER rollbackDelaySeconds (no automated statistical gate watching it — a human notices first), which is why it lands so much further right on the same axis a code canary sits on, without the formula itself changing at all.

New: a gate that never reaches a single reader

validationCatchOutcome prices the one mitigation a config path can have that a code path typically already gets from review and CI before a canary ever sees the change — a schema/sanity check run before push:

escapedRate = badConfigRate · (1 − validationCatchRate)

The fraction of ALL config pushes that are both bad AND get past validation — the only ones that ever reach rollbackBlastRadius’s exposure math at all. A validator that catches nothing (validationCatchRate=0) leaves escapedRate equal to the raw bad-config rate; one that catches everything drives it to zero, at effectively zero propagation cost either way, because a rejected config is rejected before a single reader sees it.

New: combining the two into one expected cost

configRiskPolicy weights rollbackBlastRadius’s total by how likely a bad config is to reach production at all under each of four policies, so all four land on one comparable number:

expectedExposure = P(bad config reaches production) · totalExposedRequests

compareConfigPolicies computes this four ways: skip both gates (P = badConfigRate, exposure = instant total), validate only (P = escapedRate, exposure = instant total), stage only (P = badConfigRate, exposure = staged total), and both (P = escapedRate, exposure = staged total). Validation shrinks the PROBABILITY term; staging shrinks the EXPOSURE term — which is why stacking them multiplies the reduction rather than adding it.

06

Two cheap gates, multiplied, and the ceiling on each

Validation and staged rollout are not substitutes — they shrink different terms of the same expression. A validator that never lets a single bad config through still doesn’t help once one does, because it says nothing about how far that config gets before anyone notices. A staged rollout that catches every bad config eventually still lets 100% of PUSHES with obviously malformed values (a string where a number belongs, a rate limit of -1) reach a reader for however briefly the first stage runs, when a one-line schema check would have rejected it before push, for free.

Neither gate is free of a ceiling. validationCatchOutcome’s catch rate is only as good as what the validator was built to check — a syntactically valid, semantically wrong value (a rate limit of 5 instead of 5,000) sails through any schema check that doesn’t also know what “reasonable” means for that field. rollbackBlastRadius’s staged-rollout term still costs the same wall-clock propagation delay a code canary already accepts — the honest trade a config team is making by staging isn’t “no cost,” it’s “the same cost a deploy pipeline already pays.”

The revert delay is where config paths usually lose the most, and it’s the cheapest one to fix. Nothing about a config system prevents wiring the same automated statistical gate this course’s canary lessons already model onto a config rollout — the reason rollbackDelaySeconds is so much bigger for config in this lesson’s default isn’t a property of config values, it’s a property of which pipelines teams have actually built. minCanaryFractionForWindow, reused from canary-analysis-and-rollback.mjs unchanged, answers the same sizing question for a config canary that it answers for a code one.

“It’s just a config” is the sentence that skips both gates at once, and that’s exactly the scenario this lesson prices as worst. Nobody proposes skipping validation AND staging as a considered trade-off — each individually looks unnecessary for a small, “obviously fine” change, and the 98.8x gap between skipping both and doing both is what that pair of individually-reasonable shortcuts actually costs once they’re stacked.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A config push is the SAME `rollbackBlastRadius` formula as a code canary, evaluated at canaryFraction=1 from t=0 — nothing new needs deriving, because the formula never distinguished "bad code" from "bad config" in the first place. What differs is which canaryFraction and which rollbackDelaySeconds a real config pipeline actually uses.
  • Config systems are engineered to propagate FAST — that is explicitly their job, so a reader anywhere in the fleet sees a new value within milliseconds to seconds. The same property that makes them useful is exactly what removes the staged-rollout stage a code deploy pipeline takes for granted, unless a team deliberately re-adds it.
  • `validationCatchOutcome` is the ONE mitigation with no code-deploy equivalent modelled in this course, because code already passes through review and CI before a canary ever sees it — a schema/sanity check run before a config is ever pushed catches some fraction of bad configs at zero propagation cost, since a rejected config never reaches a single reader.
  • Validation and staged rollout attack DIFFERENT terms of the same expression: validation shrinks how often a bad config reaches production at all (the probability term), staged rollout shrinks how much damage it does once it's there (the exposure term) — which is why `compareConfigPolicies` shows stacking them multiplies the reduction rather than just adding it.
  • Skipping both gates is not merely "a bit worse" than skipping one — in the worked scenario it is a 98.8x jump in expected exposure per bad push over doing both, versus only a 5x or 20x jump from skipping either gate alone, which is the shape "the highest-severity outages come from the shortcut that skips everything" actually has.
  • None of this changes HOW exposure accrues once a bad change is live — that mechanism, and `rollbackBlastRadius`'s own arithmetic, stay exactly `canary-analysis-and-rollback.mjs`'s. This lesson only changes which canaryFraction and which rollbackDelaySeconds a real config pipeline plugs into it, and adds the one pre-push gate a config path can have that a code path already gets elsewhere.

    A team ships a bad code change behind a 5% canary with a 60-second automated rollback, and separately pushes an equally bad config change (same bug, same 500 rps) straight to 100% of the fleet, catching and reverting it in 10 minutes because nothing was watching it automatically. Two things compound here that a single canary-size comparison doesn't show together: a bigger fraction from the start, AND a slower revert delay because nothing automated was watching.

  2. Cued recall

    A validator that catches 80% of bad configs before push, applied to a 5% bad-config rate, still lets some bad configs through. If a team ALSO stages every config rollout at 5% traffic (same revert delay either way), does adding staging on top of validation help, or is validation alone already "enough" since it catches most bad configs?

    How sure are you, before you look?
    Adding staging still helps, substantially — the two gates aren't redundant because they act on different terms. Validation cuts the escaped-bad-config rate from 5% to 1% (`validationCatchOutcome`), but the 1% that gets through still propagates instantly and exposes 300,199 requests if unstaged. Staging on top cuts THAT number to 15,199 regardless of validation. Combined expected exposure per push: validation alone leaves 3,002 expected requests, staging alone leaves 760, and both together leave 152 — validation alone is not "enough" because it does nothing about the size of the blast once a bad config still gets through, which is the term staging exists to shrink.

  3. Near transfer

    `correlated-failure.mdx` already lists "same config or feature-flag push" as one of the failure causes that zone diversity does nothing against, calling it "faster than a deploy, usually unversioned, and applied to every replica at once by design." Does that lesson's point and this one say the same thing?

    How sure are you, before you look?
    They're adjacent, not identical. `correlated-failure.mdx` is making a placement argument: spreading replicas across racks and zones buys independence against physical/environmental faults, and a config push defeats that independence because it reaches every replica regardless of placement — the point is WHY diversity doesn't help here. This lesson is making a pipeline argument: GIVEN that a config push reaches the whole fleet at once, what does that cost in actual exposed requests, and what two specific gates (pre-push validation, staged rollout) bring that cost back down to what a code deploy already accepts. One names the blind spot; the other prices it and fixes it.

  4. Far transfer

    The abstraction is: a distribution mechanism engineered to propagate a value fast, to everyone, is functioning exactly as designed right up until the value it's distributing is wrong — at which point the same speed that was the feature becomes the entire blast radius, because nothing about "fast" implies "checked" or "staged." Name an instance outside computing.

    How sure are you, before you look?
    A product recall versus a live product update. A grocery chain's price-update system pushes new shelf-tag prices to every store overnight — fast, uniform, exactly what the system is for. If one bad price is uploaded (a decimal point off), it appears at every store simultaneously by the next morning, because the distribution mechanism doesn't distinguish "correct new price" from "typo" — that distinction has to be caught before upload (a sanity check: is this price within 50% of last week's) or the rollout has to be staged (push to five pilot stores first, watch for complaints, then push everywhere) for the speed to stop being a liability. A slower, region-by-region price rollout is strictly less efficient in the ordinary case and strictly safer in the bad one — the identical trade-off this lesson's `stagedFraction` dials.
