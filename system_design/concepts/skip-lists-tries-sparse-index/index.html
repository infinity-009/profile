Tier 3 · Storage and state Skip lists, tries, sparse index

A skip list's height is only "expected" — one build in 2,000 needs 76% more levels than that

A B-tree's height is a formula: plug in the row count and the page size, get one deterministic number, every time. Three other structures give that up on purpose, each trading the guarantee away for something else — a skip list trades it for no rebalancing logic at all, a trie trades per-key memory for a lookup cost that never depends on how many keys exist, and an LSM's sparse index trades index completeness for a footprint 1/K the size. This lesson puts a number on each trade, reusing `btree-vs-lsm`'s own cost model rather than re-deriving the B-tree side of it.

Read first — btree-vs-lsm

01

Three structures that give up the B-tree's guarantee, each for a different reason

btree-vs-lsm.mdx computed a B-tree’s height with a formula: log_fanout(rows) + 1. Plug in a million rows, an 8 KB page, a 16-byte key, and the answer is 3, every single time — not “about 3,” not “usually 3.” Three other structures this course hasn’t covered yet give that determinism up on purpose, and each one is trading it for something specific rather than for nothing:

A skip list trades a guaranteed shape for the complete absence of rebalancing logic — no rotations, no split/merge bookkeeping, just a coin flip per node at insert time. A trie trades per-key memory for a lookup cost that never depends on how many keys exist at all, only on how long the key is. An LSM’s sparse index — already half-built by btree-vs-lsm’s own model — trades index completeness for a footprint a fraction of the size, at the cost of a bounded scan. None of these are free lunches. This lesson computes exactly what each one costs.

02

Assume 'expected O(log n)' means the same thing as 'guaranteed O(log n)'

The belief this has to break
A skip list is O(log n), a B-tree is O(log n) — same bound, so it barely matters which one you pick.

They are not the same claim, and the gap between them is the entire subject of Pugh’s original paper. A B-tree’s height is a deterministic function of its inputs: same row count, same page size, same key size, same height, forever. A skip list’s height is the outcome of n independent random experiments — one coin-flip sequence per inserted node — and “expected O(log n)” describes the average of that random process, not a ceiling on any one run of it.

Run the same skip-list construction twice, with two different random seeds, at the exact same n and p, and you can get two different heights. Run the equivalent B-tree build twice and you cannot — there is no randomness in it to disagree with itself. That difference is measurable, and it is what the first rig tab shows directly rather than asserting.

Predict A skip list holds 1,000,000 keys with promotion probability p=0.5, giving an expected height of about 19.9. Across many independent builds at these exact same parameters, what is the most accurate description of the actual heights you'll see?
Height is the maximum of a million independent geometric draws, so it clusters tightly around the expected value by a law-of-large-numbers effect — but the maximum of that many draws has some spread, and the probability of a much taller build shrinks doubly-exponentially rather than hitting zero at some fixed ceiling. Across 2,000 seeded builds at these parameters, this lesson's model finds a mean of 21.3, a p95 of 25, and a tallest build of 35 — taller than expected, never impossible, never bounded by a formula the way a B-tree's height is.
Show it without answering

At the rig’s defaults, a skip list over a million keys has an expected height of 19.9 — 400 seeded builds land with a mean of about 21, a p95 of 25, and the tallest build in the batch at 35, next to a B-tree’s height for the same million rows, which is 3, unmoving, on every one of those same 400 draws. A naive 256-symbol trie over 100,000 twenty-character keys costs 1,024× a B-tree’s memory with no shared prefix and needs the entire key shared before it wins at all. An LSM SSTable’s sparse index at K=100 over ten million keys is 100× smaller than a dense index — 2.4 MB against 240 MB — for an average lookup that touches about 67 keys instead of 1.

03

A subway map, a filing-cabinet hallway, and a phone book's edge tabs

A skip list is an express-versus-local subway map, the analogy Pugh himself used. The bottom level is a local train stopping at every station (every key, in order). Above it, an express line skips most stations; above that, a line so express it only stops a handful of times across the whole route. Searching means riding the fastest line you can until you’re about to overshoot, then dropping to a slower one — and which stations get express service isn’t planned by a timetable committee, it’s decided by a coin flip when each station opens. Most of the time that produces a sensible, well-spread set of express stops. Occasionally, by chance, a stretch gets under-served and a search through it takes a little longer than usual.

A trie is a hallway of filing-cabinet drawers labelled one letter at a time. To file “handbag” you open drawer H, then inside it drawer A, then N, then D — and “handsome” shares the same first three drawers before diverging. The shared hallway is free: you only walk it once regardless of how many words start that way. What isn’t free is that every drawer you open has to have a slot for every possible next letter, whether or not anything is filed there — an empty slot for Q under H-A-N still takes up cabinet space.

A sparse index is a phone book with tabs only every hundred pages, not one per name. Looking up “Kowalski” means finding the tab labelled closest-before it, flipping to that page, and reading forward a hundred or so names until you hit it. The tabs are cheap because there are few of them; the price is that one lookup, done cover-to-cover if the tabs weren’t there, now costs a short manual scan instead of an instant jump.

04

The mechanism: three formulas, and the one thing each has that a B-tree's does not

skip list: E[height] = log_(1/p)(n)  ·  P(height ≥ k) = 1 − (1 − p^(k−1))^n

The first term is Pugh’s result: with each node promoted a level at probability p, a level stays populated as long as n·p^k ≥ 1, which happens up to about log_(1/p)(n) levels. The second term is what the B-tree’s formula doesn’t need one of: an exact, closed-form probability that a real build overshoots that expectation by any given margin, because the height is a random variable and a B-tree’s is not.

trie bytes = sharedPrefix × nodeBytes + numKeys × (keyLength − sharedPrefix) × nodeBytes

nodeBytes for a naive array-per-node trie is alphabetSize × pointerBytes — every node pays for a slot per possible next symbol, used or not. The shared prefix is walked by every key but stored once; everything past it is unique per key and multiplies by numKeys. A B-tree’s memory cost (storage.mjs’s btreeSpaceAmp, reused unchanged here) has no such split, because a B-tree’s nodes don’t represent shared prefixes at all — they represent sorted ranges of whole keys.

sparse index entries = totalKeys ÷ K  ·  lookup cost ≈ log₂(entries) + K/2

The index only needs one entry per K-key block, so its size falls linearly in K. The lookup adds a binary search over that shrunken index (cheap, log-scaled) to an average scan of half a block forward on disk (linear in K) — the two halves of the trade-off pulling in opposite directions as K moves, composed here with storage.mjs’s own lsmPointReadAmp for the cross-run half of the story btree-vs-lsm.mdx already covers.

06

The trade-off — three different bets, none of them free

The skip list’s bet: simplicity is worth an unbounded (if vanishingly unlikely) tail. No rotations, no split/merge bookkeeping, no invariants to prove after every insert — a skip list is genuinely easier to implement correctly than a balanced tree, which is a real engineering cost saved. What’s given up is the word “guaranteed”: a pathological run of unlucky coin flips can, in principle, produce a bad structure, and no amount of code review catches that the way a correctness proof for tree rotations does. In practice the probability is small enough that this bet has paid off for decades of production use (Redis’s sorted sets, among others) — but it is a bet, not a proof.

The trie’s bet: O(key length) lookups are worth the per-node alphabet tax, IF the keys cooperate. A trie’s lookup cost never grows as more keys are added — a property nothing comparison-based can offer — which is why it’s the default for autocomplete and prefix search regardless of the memory question. But the naive version’s memory bet only pays off when real keys actually share long prefixes (URLs under a common domain, words in one language, IP addresses in one block); point it at keys that don’t cooperate — hashes, UUIDs, anything high-entropy — and the per-node alphabet cost dominates with nothing to amortise it against. This is precisely why production tries are compressed, not naive.

The sparse index’s bet: K is a dial, not a decision made once. Every unit smaller the index gets, the scan gets proportionally longer — there is no value of K that shrinks both, because the total information (which key is where) has to live somewhere, and K only decides whether it lives in RAM or gets rediscovered by scanning disk each time. This is the same “container versus payload” shape btree-vs-lsm.mdx closed on, aimed at a different container.

07

In the wild

Redis’s sorted-set implementation is a skip list, chosen explicitly over a balanced tree for implementation simplicity — the source comments cite ease of implementation and comparable practical performance to balanced-tree alternatives as the deciding factors, which is exactly the bet this lesson computes rather than takes on faith.

Router longest-prefix-match tables are binary tries for the same reason the alphabet-2 example above crosses over so much earlier than the 256-symbol one: an IP address is a fixed-width bit string, so a bitwise trie’s per-node cost is tiny (two children) and its shared-prefix structure maps directly onto CIDR blocks, which are shared address prefixes by definition.

An SSTable’s own sparse index is described exactly this way in Kleppmann’s Designing Data-Intensive Applications: “you do not need to keep all the keys in memory… group the key-value pairs within an SSTable into blocks… and then store the first key of each block in the index. This kind of index, which stores only some of the keys, is called sparse” — and the same passage names a trie as one of the data structures that index itself can be built from, which is the connective tissue between this lesson’s second and third sections.

Now put the page away

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A skip list's height is a random variable — the maximum level assigned across n independent coin-flip promotions — not a computed shape, so Pugh's O(log n) bound is an EXPECTED cost. A B-tree's height is a deterministic function of rows, page size and key size: identical on every build with the same inputs, which a skip list's height is not.
  • The probability a skip list's actual height exceeds k shrinks doubly-exponentially in k (P(height ≥ k) ≈ n·p^(k−1)), so a build twice the expected height is astronomically unlikely but never structurally impossible — that gap between "vanishingly small" and "zero" is the entire difference between expected and guaranteed.
  • A naive array-per-node trie's memory is dominated by the alphabet-sized pointer array at EVERY node, not by the keys themselves, so it only beats a B-tree on memory once keys share almost their entire length as a common prefix — the per-node tax, not the sharing, is what a compressed (radix/Patricia) trie exists to remove.
  • A trie's lookup cost is O(key length), independent of how many keys are stored — a property no comparison-based structure (B-tree, skip list) can offer, because their cost is a function of N. That is why tries are the default for prefix queries and autocomplete regardless of how the memory question resolves.
  • An LSM's sparse index is `btree-vs-lsm`'s Bloom-filter read-amplification story with one added layer: WITHIN one SSTable, an index entry every K keys makes the in-memory index 1/K the size of a dense one, paid for with a bounded K-key scan on disk per lookup.
  • All three structures trade away one of the B-tree's defaults from a different angle — a guaranteed shape, per-key memory, or index completeness — and none of them make that default's value disappear; they each bet that, for a specific workload, it isn't worth paying for.

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    At n = 1,000,000 keys and p = 0.5, a skip list's theoretical expected height is about 19.9. Across 2,000 independently seeded constructions, the tallest one reached height 35. Is that construction a bug?

    How sure are you, before you look?
    No. Height 35 against an expected 19.9 is 76% taller, and it is exactly the kind of draw the model predicts will occasionally happen — P(height ≥ 35) for these parameters is a specific, computable, very small number, not zero. A B-tree given the same million rows produces the same height — 3 levels — on every single run, with no distribution to draw from at all. The skip list's promise was never "always this tall or shorter"; it was "usually about this tall, with a quantifiable, rapidly shrinking chance of much taller."
    Did you have that?
  2. Cued recall

    A colleague says "the expected-height formula guarantees a skip list search stays fast."

    How sure are you, before you look?
    The formula describes an average outcome, not a bound on any one outcome, and confusing the two is exactly the "expected but not guaranteed" gap this lesson computes. The probability of a bad draw shrinks doubly-exponentially with how far "bad" is defined, so in practice a skip list behaves extremely predictably — but "extremely predictable" and "guaranteed" are different claims, and only a B-tree's height formula supports the second.
    Did you have that?
  3. Cued recall

    A naive trie over 100,000 twenty-character keys, one array-per-node with a 256-symbol alphabet, costs about 4,096 MB with zero shared prefix and 4 GB — no, wait: recompute — why does the SAME trie cost only about 40 KB once the keys share all 20 characters?

    How sure are you, before you look?
    Because the model's cost is `(shared-prefix nodes stored once) + numKeys × (unshared nodes stored per key)`. At zero sharing every one of the 100,000 keys pays for all 20 of its own nodes, each a 256×8-byte pointer array (2,048 bytes) — 100,000 × 20 × 2,048 ≈ 4.10 GB. At full sharing there are only 20 nodes total, walked by every key and stored once — 20 × 2,048 = 40,960 bytes. The 100,000× swing is entirely the shared-versus-unique split; nothing about the keys' actual content changed, only how much of their prefix they have in common.
    Did you have that?
  4. Cued recall

    An SSTable's sparse index goes from K = 10 to K = 1,000 (a 100× coarser interval). What happens to the in-memory index size and to a lookup's disk-scan cost, roughly?

    How sure are you, before you look?
    The index shrinks by roughly the same 100× — 1/K entries means 1/K the memory footprint, which is the entire reason a sparse index exists. The scan cost moves in the opposite direction by close to that same factor: a lookup now has to scan up to 1,000 keys forward from the nearest index entry instead of up to 10. Nothing about the total amount of I/O work vanished; it moved from "held in RAM permanently" to "read from disk per lookup," and K is the one knob that decides where that line sits.
    Did you have that?
  5. Near transfer

    A junior engineer, having just read that a hash table degrades to O(n) lookups under a pathological hash function, says a skip list's unbounded worst case is "the same kind of risk." Is that the right comparison?

    How sure are you, before you look?
    No — the two unbounded worst cases come from different sources, and that difference is the whole point. A hash table's bad case is triggered by the KEYS: an adversary (or unlucky real-world data) that collides under the specific hash function in use can force every lookup toward O(n), and that risk does not shrink no matter how many times you run it with the same keys and function — it is a property of the input, not a random draw. A skip list's bad case is triggered by its OWN independent coin flips at insert time, unrelated to the keys' values; running the exact same key set again with a different seed gives a different height, and the probability of a meaningfully bad one shrinks doubly-exponentially with how bad "bad" means. One risk is adversarial and persistent; the other is random and evaporates almost as fast as you ask it to get worse.
    Did you have that?
  6. Far transfer

    The abstraction is: a system's AVERAGE behavior is provably good, and independent randomness makes real outcomes cluster tightly around that average — but no amount of clustering turns "extremely unlikely" into "impossible," so the guarantee that actually holds is statistical, not structural. Name an instance outside computing.

    How sure are you, before you look?
    Insurance underwriting. An insurer's expected payout per policy is a stable, almost boringly predictable number, because the law of large numbers averages thousands of independent policyholders' outcomes into a tight distribution around the mean — which is the entire business model. But "independent" is the load-bearing word, exactly as it is for a skip list's coin flips: a pandemic, a single catastrophic storm, or a financial crisis correlates many policies' losses at once, breaking the independence the averaging relied on, and the insurer's actual payout can land far outside the range the expected-value math ever suggested. The formula was never wrong; it just answered a question about the average case, and the tail event it couldn't rule out eventually arrived anyway.
    Did you have that?
