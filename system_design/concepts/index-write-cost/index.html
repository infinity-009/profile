Tier 3 · Storage and state Index write cost

A 5-indexed table's insert costs 6 writes. Updating one of those indexed columns costs 11 — not 6.

`what-is-an-index.mdx` stated the basic rule and stopped there on purpose: N indexes roughly multiply a write by (1 + N). This lesson is the part it deferred — the honest mechanics that make the real number worse than that flat multiplier in one direction and better than it in another, depending on which column actually changed, and depending on whether each index's own write lands as a cheap sequential append or an expensive random one.

Read first — what-is-an-indexbtree-vs-lsm

01

6 writes, or 11, or 1 — same table, same five indexes, three different single-row writes

A table carries 5 secondary indexes. Someone inserts one row.

Every index needs a new entry pointing back to that row, on top of the row itself landing in the base table — 1 base-table write plus 5 index writes, 6 writes total. That is exactly what-is-an-index.mdx’s writeAmplificationFactor(5), and for an insert it is exactly right: 6.

Now someone UPDATEs a column on that same row — a column that happens to be part of the key for all 5 of those indexes. Same table, same index count, one row touched. The cost is not 6. It is 11: the base table write, plus each of the 5 indexes paying a delete of its old entry and an insert of a new one, because the column that changed is exactly the column each index is sorted by.

Now someone updates a different column on that same row — one none of the 5 indexes cover at all. The cost is not 6 either. It is 1: the base table write, and nothing else, because not one of the 5 indexes has anything in it that needs to move.

Same table. Same 5 indexes. Three single-row writes, three totals: 6, 11, 1. The flat 1 + N multiplier what-is-an-index.mdx gave you was the honest basic version — this lesson is the part it said it was deferring.

02

Assume every write to an N-indexed table costs the same (1 + N)×

The belief this has to break
A table with N indexes multiplies every write by (1 + N), full stop — that's what the earlier lesson said, and it's the number to budget against.

what-is-an-index.mdx was careful to say that 1 + N was the basic relationship and that per-index nuance was later work — but “basic” reads as “close enough” until production shows a table whose write cost swings between roughly a fifth of the naive number and almost double it, on the exact same schema. What actually decides the multiplier is not N alone: it’s which operation, and for an UPDATE, which specific column changed relative to each index’s own key. An INSERT or DELETE really is flat — every index gets touched exactly once, so 1 + N is not an approximation there, it’s the number. An UPDATE is where the flat model breaks, in both directions at once, because an index whose key wasn’t touched costs nothing and an index whose key WAS touched costs double.

Predict A table has 6 secondary indexes. An UPDATE changes a column that is not part of ANY of those 6 indexes' keys. How many total write ops does this UPDATE cost?
Each of the 6 indexes is sorted by its own key. If the changed column isn't part of that key, the index's entry for this row is byte-for-byte identical before and after the update — same key, same pointer, same position in the tree. There is nothing to write. The base table still gets its one in-place write, so the total is 1, not the naive 1+6=7 an insert or delete on the same table would cost.
Show it without answering

At the rig’s defaults — 5 indexes, insert — the naive model and the actual cost agree at 6. Switch to “update, indexed col” and the same 5 indexes push the total to 11 — 5 more than naive, exactly one delete-plus-insert’s worth of extra cost per index. Switch to “update, other col” and the total falls to 1 — 5 fewer than naive, because none of those 5 indexes had anything to move. Every one of these N+1 writes is also still subject to the same write()-then-fsync durability mechanics wal-and-fsync.mdx already derived — an index’s write isn’t “durable” any more automatically than the base table row’s is, and this lesson doesn’t re-derive that gate, it just notes each touched structure pays it independently.

03

A card catalog, and a second box of cards sorted by something else entirely

A library’s card catalog is one alphabetized drawer, filed by author surname. Next to it sits a second box — a duplicate card for every patron, filed by library-card number instead of surname, kept purely so the front desk can look someone up fast when all they have is the card number. Two boxes. Two different sort keys. Same underlying people.

A patron updates their phone number. The clerk finds their card in BOTH boxes — already sitting exactly where it always sat, because a phone number is part of neither box’s sort key — crosses out the old number, writes the new one, and puts each card straight back. Two in-place edits. Cheap.

A patron legally changes their surname. The surname-sorted drawer now has a card in the wrong place: it has to be pulled from its old alphabetical slot and physically re-filed under the new letter. The card-number box doesn’t care at all — a surname change touches nothing about card-number order, so that box’s copy gets the same cheap in-place edit as the phone number did. The exact same real-world change costs a full pull-and-refile in one box and a two-second edit in the other, purely because of which field each box happens to be sorted by. A table with several indexes is exactly N of these boxes, each with its own sort key, and a single UPDATE prices out differently against every one of them.

04

totalWriteIOs(insert|delete) = writeAmplificationFactor(numIndexes) = 1 + N  ·  totalWriteIOs(update) = 1 + 2·k, k = indexes whose key the update changed

writeAmplificationFactor is what-is-an-index.mjs’s own function, imported and reused completely unchanged for the insert/delete case — it is not re-derived here because it is already exactly right for that case. The update case is this lesson’s addition: k ranges from 0 (no indexed column touched, cost collapses to 1) to numIndexes (every index’s key touched, cost rises to 1 + 2N) — the honest, per-index accounting the naive model folds into one number.

A B-tree entry’s position IN THE TREE is a deterministic function of its key

That’s what makes the tree sorted and therefore searchable in O(log n) at all (what-is-an-index.mdx, btree-vs-lsm.mdx). Change the key and the entry’s correct position changes with it — there is no “move it two slots over” primitive on a sorted tree, only remove-then-insert. This is exactly why an indexed-column UPDATE cannot be priced as one op: two DIFFERENT positions in the tree are involved, one being vacated and one being filled.

indexWriteThroughput(structure, device) reuses storage.mjs’s btreeWriteAmp / lsmLeveledWriteAmp / writeThroughput unchanged

Whether one of the N+1 (or 1+2k) ops above is cheap or expensive is a question this lesson answers by reusing btree-vs-lsm.mdx’s own device pricing, not a new assumption. One wrinkle that pricing surfaces honestly: an index entry (just a key + a pointer, ~24 bytes) is SMALLER than the ~128-byte base-table row btree-vs-lsm.mdx defaults to, and B-tree write amplification is page ÷ entry — so the same 8 KB page makes a small index entry amplify WORSE, not better, than the row it points back to. Every random B-tree page write above also carries the split-driven fill-factor cost btree-vs-lsm.mdx already priced as ~1.43× space amplification (pages settle near 70% full under random insertion) — a symptom of the same cascading-split mechanism, not a separate cost this lesson invents.

06

The trade-off: write-heavy tables pay for every index on every write; read-heavy tables barely notice

A write-heavy OLTP table should be stingy with indexes, because the tax is unconditional and per-write. Every index defined on a table adds its own op to every insert, its own delete-plus-insert to every update that touches its key, whether or not a single query ever reads through it that hour. The scenario table above makes this concrete: at 2,000 writes/second on spinning media, going from 0 to 5 indexes doesn’t just add “some” load — it takes the storage layer from 2,000 required IOPS to 12,000, a 6× jump the application never asked for directly. A schema with 8 “nice to have” indexes on a table that also needs to sustain a high insert rate is, mechanically, a promise to pay that multiplier on every single row, forever, regardless of how often any one of those 8 indexes actually gets used.

A read-heavy or analytical table can afford far more indexes, because writes are rare and indexes are exactly what reads are paying for. A reporting table that ingests a batch once a night and serves thousands of ad-hoc filtered queries during the day inverts the whole calculation: the N+1 write cost is paid once, off the critical path, while every one of those N indexes turns a query that would otherwise be a full scan (what-is-an-index.mdx’s own O(n) case) into a tree walk. The identical schema decision — “add this index” — is nearly free in one workload and a standing tax in the other; there is no context-free answer to “should this column be indexed,” only “given this table’s write rate versus its query mix, is the multiplier worth it.”

The backing structure is a lever the workload doesn’t have to accept passively. The 10 ms-budget table above is the sharpest version of this: the same set of secondary indexes that a spinning disk cannot afford at all as B-tree structures, it can afford in the thousands as LSM-backed ones — which is exactly why write-heavy, many-secondary-index systems (wide-column stores, search-oriented storage) lean LSM, and why that choice is a storage-engine decision made once, not a per-index one made five separate times.

07

In the wild

“A B-tree index must write every piece of data at least twice… write amplification” is Kleppmann and Riccomini’s own framing, not a house paraphrase. “A B-tree index must write every piece of data at least twice: once to the write-ahead log, and once to the tree page itself. In addition, writing out an entire page is sometimes necessary, even if only a few bytes in that page changed… If you take the total number of bytes written to disk in a workload and divide that by the number of bytes you would have to write if you simply wrote an append-only log with no index, you get the write amplification.” This lesson’s indexWriteThroughput/indexWriteLatencyMs price exactly that quantity, per index, per device — the book states the definition, storage.mjs (via btree-vs-lsm.mdx) already turned it into a formula, and this lesson applies it to the index’s own write rather than only the base table’s.

The book’s own next line is this lesson’s read/write-heavy trade-off, stated plainly: “In write-heavy applications, the bottleneck might be the rate at which the database can write to disk. In this case, the higher the write amplification, the fewer writes per second it can handle within the available disk bandwidth.” Slot 6’s IOPS scenario is that sentence made numeric.

what-is-an-index.mdx already cited this same book’s slot-6 line — “every index consumes additional disk space and slows down writes, sometimes substantially” — and explicitly deferred the per-index mechanics to this lesson. Nothing here contradicts that earlier page; it’s the same claim, worked out to the level where “sometimes substantially” becomes a number you can compute for a specific table.

Now put the page away

Everything above this line was the Passive rung — necessary, and the weakest thing on offer. Testing yourself on it will feel worse than rereading it and will hold roughly twice as long. That gap between how it feels and what it does is the entire reason this section exists.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • Insert and delete really do cost exactly (1 + N) writes — one per index, no more, no less — which is why `what-is-an-index.mjs`'s `writeAmplificationFactor` is reused unchanged here as the baseline for those two operations, not replaced
  • An UPDATE that changes a column an index's key covers cannot be an in-place edit: a B-tree entry's location in the tree IS a function of its key, so a changed key means the entry belongs on a different leaf entirely — the index pays a DELETE of the old entry plus an INSERT of the new one, two structural writes, not one
  • An UPDATE that changes a column NONE of the indexes cover costs LESS than the naive model says: each such index's key is untouched, so its position in the tree is untouched, so there is nothing to write there at all — zero, not one
  • Whether one of those N+1 writes is cheap or expensive is a property of the index's own backing structure, not of how many indexes exist — a B-tree-backed index write is a random page write, an LSM-backed one is a sequential append, exactly the random-vs-sequential distinction `btree-vs-lsm.mdx` already priced against real devices
  • A secondary index's entries are SMALLER than the base table's own rows (just a key plus a pointer), and B-tree write amplification is page ÷ entry — so at the same page size, a small index entry amplifies WORSE than the wider row it points back to, not better
  • The design consequence: write-heavy OLTP tables should be stingy with indexes, because every index taxes every write whether or not any query ever uses it; read-heavy or analytical tables can afford far more indexes, because writes are rare and reads are exactly what those indexes are for

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A table has 5 secondary indexes. An UPDATE changes a `status` column that 2 of those 5 indexes are built on; the other 3 index different columns entirely. How many total write ops does this single UPDATE cost, and why isn't it the naive 1+5=6?

    How sure are you, before you look?
    5 total: 1 base-table write, plus the 2 indexes whose key includes `status` each paying a delete-and-insert (2 ops apiece = 4), plus the 3 unrelated indexes paying 0 — their key never changed, so their position in the tree never changed. It isn't the flat 6 the naive `1 + N` model predicts because that model assumes every index pays exactly one touch regardless of which column changed; the honest model prices each index against whether ITS OWN key was in the set of columns this particular write touched.
    Did you have that?
  2. Cued recall

    Why does changing an indexed column's value cost a delete-then-insert instead of a cheaper in-place key edit?

    How sure are you, before you look?
    Because a B-tree entry's location in the tree is entirely a function of its key — that ordering is the entire reason the structure is searchable in O(log n) at all. Change the key and the entry belongs somewhere else in the tree, potentially on a completely different leaf page. There is no operation that "slides" an entry to a new sorted position in place; the engine has to remove it from its old spot and insert it fresh at the new one — two structural writes, not a patch to one.
    Did you have that?
  3. Cued recall

    A table with 5 B-tree secondary indexes and an otherwise-identical table with 5 LSM-backed secondary indexes both insert one row. Do they pay the same op count? Do they cost the same actual time?

    How sure are you, before you look?
    Same op count — both pay exactly 6 structural writes, because `writeAmplificationFactor` counts OPERATIONS, not their price. The time is very different: each B-tree write is a random page write (and, per `wal-and-fsync.mdx`, typically a full-page WAL image on top of that, before it's even durable), while each LSM write is a cheap sequential append whose real cost is deferred to a later compaction — `btree-vs-lsm.mdx`'s own argument, just applied to an index's write instead of the base table's.
    Did you have that?
  4. Near transfer

    `what-is-an-index.mdx` states "N indexes roughly multiplies single-row write cost by (1 + N)." A team reads that, budgets for a flat 6× write-cost increase after adding 5 indexes, and is confused in production when the actual multiplier is sometimes 11× and sometimes 1× depending on which column a given UPDATE touches. Did the earlier lesson get it wrong?

    How sure are you, before you look?
    No — it stated the multiplier for INSERT and DELETE, where it really is flat, and it said explicitly that the per-index nuance for UPDATE was later work, not its own. The team over-generalized a correct statement about two operations to a third one that behaves differently. An UPDATE splits into two very different cases depending on whether the changed column belongs to a given index's key: touching it costs 2 ops per such index, not touching it costs 0 — so the SAME table's effective write multiplier legitimately swings below 1+N or above it, purely depending on which columns a specific write happens to touch. There is no single number "the write multiplier" for a table; there is one per (table, which-columns-changed) pair.
    Did you have that?
  5. Far transfer

    The abstraction is: the exact same structure charges a completely different price for two edits of similar size, because one of them happens to move the thing to a new SORTED position and the other leaves its position untouched. Name an instance outside computing.

    How sure are you, before you look?
    A library card catalog, when a patron's library card records their phone number versus their legal name. The catalog is alphabetized by surname. Updating the phone number is an in-place edit — the card is already sitting in the correct alphabetical slot, and nothing about that slot depends on a phone number, so the clerk just crosses it out and writes the new one. Updating the surname changes the very field the whole drawer is organized by: the card has to be pulled from its old alphabetical position and re-filed at the new one, a physical remove-and-refile, not an edit. Two changes to "the same card," wildly different cost, for a reason that has nothing to do with how big the change is and everything to do with whether it touched the sort key.
    Did you have that?
