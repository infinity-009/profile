Tier 7 · Security, privacy, compliance JWT revocation explained well nowhere else

Cutting the token lifetime to 60 seconds cost 5× the identity-tier load of the sessions it replaced, and still left a 60-second window

A signed token is a cached authorization decision, and the lifetime you set is a cache TTL. That makes revocation cache invalidation, which is the hard part everywhere else too. The arithmetic nobody publishes: the stateless design only reduces load while the token outlives the gap between one user's requests, and shortening it past that point costs more than the sessions it replaced while still leaving a window.

Read first — back-of-envelopethundering-herd

01

Support pressed revoke, and the API kept answering for fifteen minutes

A contractor’s laptop was stolen. Within four minutes their account was disabled, every session was revoked in the admin console, and the console said it had worked — because it had. The authorization server had marked the token revoked and would not issue another.

The API served that token for another eleven minutes. Access-token lifetime was fifteen minutes, the token had been issued four minutes earlier, and no service on the request path asks the authorization server anything: they verify a signature and read an exp claim. The stolen laptop had a valid credential, and the correct number of things had been done about it.

So the fix went in: cut the lifetime to 60 seconds. Two million active clients, each making a request about every five minutes. Refresh traffic went from 2M/900 = 2.2k/s to 2M/60 = 33k/s, and the token endpoint — sized for the old number — started shedding. The server-side sessions this architecture had removed two years earlier would have cost 2M/300 = 6.7k/s, one store read per request, with no window at all.

The 60-second design was 5× more expensive than the stateful design it was chosen to avoid, and it still left a 60-second window.

02

Call the revocation endpoint and watch nothing happen

The belief this has to break
Calling the revocation endpoint logs the user out.

It invalidates the refresh token and the grant behind it, which is a real and useful thing: no new access token will be minted. RFC 7009 defines exactly this and returns 200 to say it worked.

What it cannot do is reach the access token already in the client’s hands. That token is a signed statement — the resource server checks the signature and exp locally, which is the entire reason a JWT is used instead of a session id, and the reason it scales. Local verification and remote revocation are the same property viewed from two sides. You do not get to keep one and drop the other.

So the credential stays live for the rest of its lifetime, and “log out everywhere” means “stop renewing, everywhere”.

Predict A 15-minute access token, one request a minute, revoked 4.5 minutes in. The revocation call returns 200. How many of that client's requests does the API serve after it?
Nothing on the request path consults the revocation, so every request left in the lifetime succeeds. 15 − 4.5 = 10.5 minutes of life remaining at one request a minute, so the requests at 5, 6, … 15 minutes all return 200: 11 of them. The last option is wrong for the opposite reason — the revocation did work, on the next token.
Show it without answering

Three things the rig is for.

The revocation succeeded. Both boxes are telling the truth at once. That combination is the whole topic, and it is why “did the revoke call fail?” is the wrong first question in an incident.

Nothing you do after issue changes the band. Revoking earlier shortens the exposure only because there is less lifetime left, which is the same lever seen from the other end.

The exposure is a duration, so it has a mean. Over revocations landing anywhere in a token’s life, the average access you hand an attacker is T/2. On a 15-minute token that is seven and a half minutes, every time.

03

The intuition: you cannot recall a photocopy

A building has a security desk. Every time someone wants into a room, the desk looks them up in a register and says yes or no. Revoking access is one edit to the register, and it takes effect on the next request — but every entry costs a walk to the desk, and at ten thousand people the queue is the building’s throughput problem.

So the desk starts issuing signed slips: bearer may enter rooms 3 and 7, valid until 14:30, signed by the desk. Now the door guard needs no register and no walk — check the signature, check the clock, done. This is a JWT, and the speedup is real.

Then someone’s slip is stolen at 14:05. You can tell the desk to stop issuing slips to that person, and it will. You cannot get the slip out of the thief’s pocket, and the door guard has no reason to phone the desk — checking the signature is precisely what the guard was relieved of phoning about.

Everything follows from that:

  • The “valid until” time is the only bound on the damage. Not your reaction time.
  • Shortening it means more trips to the desk, because slips expire more often. You are back in the queue you left.
  • Telling the guard to phone the desk about a list of cancelled slips works perfectly, and puts the walk back in.

A signed token is a cached authorization decision. The lifetime is a cache TTL, the revocation window is staleness, and revocation is cache invalidation — which is the hard part in every other tier of this curriculum for the same reason it is hard here.

04

The mechanism: two lines and where they cross

Three designs, one population: N active clients each making r requests per second, tokens living T seconds.

stateless: identity-tier load = N / T  ·  window = T

One refresh per lifetime per active client, and nothing else reaches the identity tier. The window is the whole remaining lifetime because no request consults anything.

per-request check (session, or denylist): load = N · r  ·  window = replication lag

One store read per request, forever. T does not appear — the lifetime is not part of this mechanism, which is exactly why the two lines can cross.

crossover: N/T = N·r  ⟹  T = 1/r

The population cancels. The crossover is the mean gap between one client’s requests, and it is a property of the client, not of the token, the algorithm or the provider. Asserted exactly in tokens.test.mjs.

Read that third law as an instruction and it is short: a stateless token saves work only while it outlives the gap between the requests it is used for.

The same 60-second lifetime is 30× on the right side of the crossover for the polling tab and 5× on the wrong side for the mobile client. One number cannot serve both, and it is the quiet clients — background apps, devices, integrations — that make a short lifetime expensive, because a short lifetime forces a refresh from a client that had nothing to say.

There is a second load term, and it is not the mean.

peak refresh = N / (login window + jitter × T), capped at N/T

Tokens issued together expire together. After an incident, a deploy that invalidated sessions, or a regional failover, the login window is small and the same total refresh work arrives as a spike.

Full jitter reaches exactly steady state, which is the invariant the test asserts rather than a fitted improvement: spreading arrivals over one whole lifetime is the steady state. This is thundering herd with token expiry as the synchronising clock, and it is why the capacity number to plan for is the peak, not N/T.

What to set.

  • Compute 1/r per client type before choosing a lifetime. It is the only number that decides whether stateless is saving you anything, and almost nobody computes it.
  • Do not go below the crossover for security reasons. You are paying more than the stateful design and still leaving a window. If the window is the problem, buy a per-request check deliberately, priced.
  • Jitter the lifetime at issue, ±10–25%. It costs nothing, and it is the difference between 1.1k/s and 16.7k/s on the worst day you will have.
  • Revoke the refresh token on every offboard and every credential-theft report. It does not close the current window and it closes every one after it, which is most of the exposure.
  • Give quiet clients long lifetimes and chatty clients short ones. The crossover says these are different problems; one global TTL is a decision not to notice.
06

The trade-off: a staleness bound, priced two ways, plus the one that is not on this axis

Raising T buys load and sells exposure, and the exchange rate is linear in both directions. Doubling the lifetime halves refresh traffic and doubles the mean access a stolen token gives away. There is no setting at which both improve, which is what makes this a genuine trade-off rather than a tuning exercise.

Lowering T stops buying anything below 1/r. Past the crossover you are paying more than the stateful design and still shipping a window. This is the failure the lesson exists for, and it is invisible in every discussion framed as “stateless versus stateful”, because that framing has no r in it.

Adding a denylist buys a real window and re-couples the request path. Cost is N/T + N·r, the highest of the three. What survives is smaller than it sounds but not nothing: the authorization decision is still local, so the per-request read is one key lookup against a small hot set — revocations are rare and short-lived, since an entry can be dropped once the token would have expired anyway. That last detail is the design’s one piece of good news: the denylist is bounded by T, so a short lifetime makes the expensive design cheaper to operate. The two levers finally point the same way, and only here.

Introspection is not a fourth option. RFC 7662 asks the authorization server per request, so it is a per-request check with a network hop instead of a store read — and the moment you cache introspection responses to make it affordable, the cache TTL becomes the revocation window and every formula above applies with T set to the cache TTL. Caching a decision is what creates this problem; the wire format never mattered.

And the option that is not on this axis at all: stop trying to shorten the window and shrink what a leaked token can do. These are the levers the dashed edge stands for, and they are the ones that survive a window you cannot close:

  • Narrow the audience and scope. A token that only works against one API, for one tenant, with one scope, is a smaller loss for the same window. RFC 9068 exists to make aud and scope meaningful in an access token.
  • Sender-constrain it. A bearer token is anyone’s; a token bound to a client key is not. RFC 9449 (DPoP) and RFC 8705 (mTLS-bound tokens) both make a stolen token useless without the private key, which is a stronger property than any lifetime.
  • Bind to a revocable identity. Kubernetes bound service-account tokens carry the ServiceAccount’s UID, so deleting the object invalidates outstanding tokens without a denylist — the check is does this subject still exist, which every request already does.
  • Re-check for the operations that matter. Reading a dashboard on a stale token is not the same risk as changing a payout account. Step-up authentication on the few dangerous operations costs a per-request check only where it is worth paying for.

The honest summary: you can bound how long a copy is honoured, or you can ask every time. What you cannot do is recall the copy — so the remaining engineering is in how much a single copy is allowed to do.

07

In the wild

AWS has no way to recall an STS session token, so it implemented revocation as a predicate on issue time. The console’s Revoke active sessions action attaches an inline policy to the role denying all actions when aws:TokenIssueTime is earlier than the moment you clicked. The credentials remain cryptographically valid and are refused at authorization time instead. It is the cleanest illustration of the whole lesson: the issuer could not reach the copies, so it changed what the copies are allowed to do. STS session lifetimes start at a 15-minute minimum, which is the same T/2 exposure arithmetic as above.

Kubernetes bound service-account tokens are the pattern done deliberately: default lifetime one hour, the kubelet refreshing each token before it expires, and the token bound to the ServiceAccount and Pod by UID. There is no revocation list — the documented way to invalidate outstanding tokens is to delete the ServiceAccount, which makes the existence check that every request already performs fail. The legacy alternative it replaced was a never-expiring Secret, which is T = ∞ and the reason the change was made.

Okta’s October 2023 support-system compromise turned on stolen session tokens found in customer-uploaded HAR files, and the response — invalidate the sessions — worked, because a session token is a reference that the server resolves on every use. Had those been self-contained bearer JWTs, the same response would have bought only “no new tokens”. The contrast is worth carrying: the incident response you want to be able to run is a property of the credential format you chose long before.

Chrome’s Device Bound Session Credentials proposal is the “shrink what a copy can do” branch taken seriously for cookies: a short-lived session cookie plus a device-bound private key, with the browser periodically proving possession to refresh it. The lifetime stays short — which by the arithmetic here means frequent refreshes — and the refresh is cheap and automatic, which is how you pay for a short window without a denylist.

OWASP’s JSON Web Token cheat sheet states the constraint plainly and recommends the same two mitigations everyone converges on: keep lifetimes short, and keep a denylist for the cases that cannot wait. It is worth reading precisely because it does not pretend there is a third answer.

Now put the page away

Everything above this line was the Passive rung — necessary, and the weakest thing on offer. Testing yourself on it will feel worse than rereading it and will hold roughly twice as long. That gap between how it feels and what it does is the entire reason this section exists.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A signed token is a cached authorization decision, so its lifetime is a cache TTL and revocation is cache invalidation
  • Revoking at the authorization server invalidates the refresh token, not the access token already issued, because nothing on the request path consults it
  • Stateless identity-tier load is N/T; a per-request check is N·r; they cross at T = 1/r
  • The crossover is a property of the client's request rate, not of the token, so one lifetime cannot be right for a chatty browser tab and a background mobile app at once
  • The stateless revocation window is the whole remaining lifetime, worst case T and mean T/2, and no call to the identity tier shortens it
  • Tokens issued in a burst expire in a burst: peak refresh load is N divided by the login window, not N/T, and jittering the lifetime at issue is what spreads it
  • A denylist costs N/T + N·r, the highest of the three, and buys the only thing the other two cannot: a window bounded by replication lag instead of by the lifetime

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    The revocation endpoint returned 200 and the API is still serving the token. What exactly did the 200 mean?

    How sure are you, before you look?
    That the authorization server recorded the token as revoked and will refuse to mint another one from that grant. The resource server verifies a signature and an exp claim locally — that is the entire reason a JWT is used instead of a session id — so it never learns of the revocation. What you actually killed is the next lifetime, not this one.
    Did you have that?
  2. Cued recall

    Derive the lifetime below which a stateless token costs the identity tier more than server-side sessions, and say what it depends on.

    How sure are you, before you look?
    Refresh load is one call per lifetime per active user, N/T. A session read is one call per request, N·r. Setting them equal gives T = 1/r — the mean gap between one user's requests. It depends only on the client's behaviour: nothing about the signing algorithm, the user count, or the identity provider appears in it.
    Did you have that?
  3. Cued recall

    2M active users, one request each five minutes, and a security review has moved the access-token lifetime from 15 minutes to 60 seconds. What happened to the identity tier, in numbers?

    How sure are you, before you look?
    Refreshes went from 2M/900 = 2.2k/s to 2M/60 = 33k/s, a 15× rise. The sessions that design replaced would have cost 2M/300 = 6.7k/s, so it is now 5× more expensive than the stateful design it was chosen to avoid — and the window it bought is 60 seconds, not zero. The ratio is exactly (1/r)/T = 300/60.
    Did you have that?
  4. Cued recall

    Every client reauthenticated inside a minute after an incident. Why is steady-state refresh load the wrong number to have planned for, and what is the fix?

    How sure are you, before you look?
    Because tokens issued together expire together. 1M clients on a 15-minute lifetime is 1.1k/s in steady state and 16.7k/s if they all acquired their tokens in the same minute — the same total work arriving as a 15× spike, which is thundering herd with token expiry as the synchronising clock. The fix is to jitter the lifetime at issue: ±25% of a 15-minute token spreads arrivals over 285 seconds and drops the peak to 3.5k/s.
    Did you have that?
  5. Cued recall

    A team adds a denylist check to every request so revocation is immediate. What did they just give up, and what is the JWT still doing for them?

    How sure are you, before you look?
    They gave up the property they adopted the JWT for: the request path is coupled to a store again, at N/T + N·r — the highest load of the three designs. The signature is still saving them the authorization round trip (claims, scopes and expiry are read locally), so the denylist read can be a single key lookup against a small hot set rather than a session join. That is a real saving; it is just much smaller than "no lookup at all".
    Did you have that?
  6. Near transfer

    A team replaces JWT verification with RFC 7662 token introspection so that revocation takes effect immediately, then caches introspection responses for 30 seconds to keep the load down. What have they built?

    How sure are you, before you look?
    A JWT with a 30-second lifetime, with extra steps. The cached introspection response is a local copy of an authorization decision trusted without asking, so the revocation window is now the cache TTL — 30 seconds — and the identity-tier load is N/30 per user rather than N·r. The lesson's arithmetic applies unchanged with T = 30. This is worth spotting because introspection is usually sold as the design that "does not have the revocation problem", and caching it re-buys the problem at whatever TTL was chosen.
    Did you have that?
  7. Far transfer

    The abstraction is: you cannot recall a copy, only stop making new ones — so the damage is bounded by how long a copy is honoured, not by how fast you react. Name an instance outside computing.

    How sure are you, before you look?
    A physical door key: changing the lock stops new copies working but you cannot reach the one in someone's pocket, so buildings use time-limited badges instead. Also: a certificate revocation list that clients refresh daily; a printed boarding pass after a cancelled booking; a paper prescription already dispensed; a signed purchase order honoured on its face by a supplier who does not call to confirm; a press embargo. The tell is always the same shape — the holder can act on the copy without contacting the issuer, so the issuer's only levers are the expiry printed on it and how much a single copy is allowed to do.
    Did you have that?

Graded items get a due date on an expanding ladder — 1, 3, 7, 16, 35, 90, 180 days — and land in review mixed with every other lesson's items. Mixed, not grouped: blocking one topic teaches you what its problems have in common, while interleaving forces you to tell them apart, which is the skill that actually fails in an interview and in production. Nothing is marked mastered today — same-day correctness measures how accessible a thing is right now, not how well you learned it.
