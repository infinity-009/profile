Tier 1 · The network Service mesh

A 20-service mesh needs 380 directed call paths, and its two sidecar hops turn a 0.1% failure rate into 0.2%

A service mesh's sidecar is nothing new — it's the forward-proxy/reverse-proxy box this course already costed, doing the mTLS this course already costed. What's actually new is what happens once there are N services instead of one proxy in front of one backend: an all-pairs topology to maintain, two extra hops that compound on every single call, and a control plane whose pushed configuration can be stale by a number this lesson computes exactly the way a DNS TTL already is.

Read first — proxies-forward-vs-reversemtlsconnection-setup-cost

01

The sidecar isn't new. The mesh is 20 of them, and that's the part nobody costed

A platform team introduces a service mesh across 20 services, expecting “just a proxy in front of each one” to be a small, mostly-invisible change. Three things show up that a single proxy never would have: the routing config is twice as large as anyone estimated, a backend’s measured success rate quietly drops a tenth of a percent for no code reason anyone can find, and a canary rollout takes longer to actually take effect everywhere than the deploy pipeline reports as “done.” None of these are bugs. All three are exactly what N-to-N topology, two compounding hops, and a config-push control plane predict — and this lesson computes all three numbers.

02

Assume a mesh is just N independent proxies, and watch two numbers refuse to match

The instinct: a service mesh is “add a sidecar to each service” — N services, N sidecars, N times the cost of one proxy, linear and simple. That’s true for the CPU (this course already showed concentration doesn’t change total termination cost). It is NOT true for the two numbers that actually define what a MESH costs beyond N separate proxies: how many distinct relationships it has to track, and what its extra hops do to reliability.

Predict A mesh has 20 services, and every service can call every other service. The team counts 190 unordered trust pairs (N(N-1)/2) and assumes that's also how many routing-rule entries the mesh config needs. How many does it actually need?
A trust relationship (do A and B need to talk to each other at all) is unordered — it's the same fact whether stated from A's side or B's. A routing rule, retry policy, or circuit-breaker threshold is typically DIRECTIONAL — A calling B can be configured differently from B calling A even between the same two services, so the count that predicts config size is directed call paths, N(N-1), exactly double the unordered count.
Show it without answering

At the rig’s default — 20 services — the mesh needs 190 unordered trust pairs but 380 directed call paths, exactly double. Each call now makes 2 sidecar hops at 0.5 ms each — 1 ms added latency — and a single hop’s 0.1% unavailability compounds to 0.1999% across both, essentially double at this small a rate. Running mTLS at every sidecar costs 0.134 added cores mesh-wide at 50 handshakes/second per service. And because the control plane pushes configuration rather than serving it live, a sidecar’s view can lag by up to 37.0 s in the worst case (a 30-second push interval plus a 7-second distribution-and-apply delay, stacked) or 18.5 s on average.

03

The intake system nobody asked to route through

A company used to let Engineering email Finance directly — one handoff, simple, and if it fails, it fails once. Someone introduces a shared intake system: now a request goes through intake before Finance ever sees it, and Finance’s reply goes back through intake before Engineering sees it. Two new handoffs, and the chance any ONE request gets lost doesn’t just add up — it compounds, because the request now has to survive both. Meanwhile, the company-wide policy that intake follows is set centrally and pushed out at the next quarterly review; an individual team’s actual behavior can lag the official policy by the review interval PLUS however long it takes them to notice and adopt it — the delays stacking, not whichever one is bigger.

A service mesh’s sidecar is that intake system, for every single service-to-service call in the building at once. The two extra hops aren’t a implementation detail — they’re the whole reason a mesh’s reliability math is different from a single proxy’s.

04

The mechanism — three costs, none of them the sidecar itself

TOPOLOGY        N services, all-pairs capable -> N(N-1)/2 unordered trust relationships,
                but N(N-1) DIRECTED call paths -- routing config tracks direction, trust doesn't

HOP COMPOUNDING every call now crosses 2 sidecar hops (egress + ingress), by architecture --
                latency ADDS (2 x per-hop ms), unavailability COMPOUNDS (1-(1-q)^2, not 2q)

CONFIG PUSH     control plane is out of the request path -- it pushes config ahead of time, so
                staleness = push interval + distribution/apply delay, STACKED like DNS TTLs,
                not bounded by whichever one is larger

Each of these reuses machinery this course already built for a different problem — coupling.mjs’s team-coordination pair count, composition.mjs’s serial-availability chain, dns.mjs’s cache-layer staleness — because the mesh’s costs are not mesh-specific mathematics. They’re the same shapes, arriving from a different direction.

06

The trade-off — a mesh trades per-call cost for whole-fleet uniformity

Every one of these three costs is the price of NOT hand-configuring N services individually. Without a mesh, each service would implement its own retries, its own mTLS, its own circuit breaking — inconsistently, because that’s what N independent implementations always produce. A mesh makes all of it uniform and centrally auditable, and that’s a real, large win. It does not make the underlying arithmetic go away: two hops still compound unavailability whether the compounding logic lives in a sidecar or nowhere at all, and pushing config to N sidecars is still slower than a single process reading its own config file, whether or not anyone built a mesh to do the pushing.

The honest comparison is not “mesh vs. free” — it’s “mesh’s uniform, auditable cost vs. N services’ inconsistent, hidden cost.” A service that today has NO retry logic, NO mTLS, and NO circuit breaker isn’t paying zero for those properties — it’s paying an invisible cost in outages that don’t have a name yet. The mesh’s costs are visible specifically because they’re computed instead of discovered during an incident.

07

In the wild

The sidecar-per-service architecture this lesson costs is Istio’s and Linkerd’s literal deployment model — every pod gets a second container running the data-plane proxy (Envoy for Istio, a custom Rust proxy for Linkerd), which is precisely the “two extra hops, by architecture, not by configuration” fact SIDECAR_HOPS_PER_CALL encodes as a constant rather than a tunable parameter in this lesson’s model.

The control-plane/data-plane split this lesson’s config-propagation lag depends on is the same split RFC 1035 already drew for DNS — a resolver (data plane, answers queries) versus the authoritative source of truth it periodically re-syncs from (control plane, pushes updates on its own schedule) — which is exactly why dns.mjs’s TTL-stacking arithmetic transfers to xDS config-propagation lag without modification: it’s the identical push-and-cache relationship, forty years later, with different names.

Serial reliability compounding across added hops is not a mesh-specific insight — it’s the same law guarantees.mdx and composition.mjs already established for any chain of dependent components, cited here rather than re-derived, because a sidecar hop is a component in a chain like any other, not a special case.

  • RFC 1035: Domain Names — Implementation and Specification, IETF, 1987 — the control-plane-push, data-plane-cache split this lesson’s config-propagation numbers reuse unchanged from dns.mjs.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A sidecar is not a new mechanism — it's the same forward-proxy/reverse-proxy box `proxies-forward-vs-reverse.mdx` already costed, sitting in front of and behind the same application, doing the mTLS `mtls.mdx` already costed. What's new about a MESH is what happens with N of them, not what any one of them does
  • A mesh of N services needs `N(N-1)/2` unordered trust relationships (reusing `coupling.mjs`'s `coordinationPairs` unchanged — the identical all-pairs shape team coordination already used) but `N(N-1)` DIRECTED call paths, exactly double, because a call from A to B is configured separately from a call from B to A even when both trust relationships exist
  • Putting a sidecar in front of and behind every service adds exactly 2 hops to every call (egress + ingress) — that's architectural, not a tunable setting. Those 2 hops don't just ADD latency, they COMPOUND unavailability: reusing `composition.mjs`'s `serialUnavailability` unchanged, a 0.1% single-hop failure rate becomes ~0.2% across both hops, not 0.1% twice
  • The mesh-wide mTLS CPU tax scales with the SUM of every service's handshake rate, because every one of N services' sidecars does mTLS at both ends of every call — reusing `mtlsServerLoad`'s own `addedCores` unchanged, the number that already isolates exactly the CPU mTLS adds on top of plain TLS
  • A mesh's control plane never sits in the request path — it pushes config to every sidecar ahead of time, so how stale a sidecar's view can get is the exact same arithmetic as DNS TTL staleness: delays STACK, worst case is the SUM of the push interval and the distribution/apply delay, not the max of them, reusing `dns.mjs`'s `worstCaseStaleness`/`meanStaleness` unchanged

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A team migrating 20 services onto a mesh estimates the config complexity by counting "how many pairs of services might need to trust each other" and gets 190. Six months later, the mesh's routing rules file has 380 entries. Did something go wrong?

    How sure are you, before you look?
    No — 380 is the right number for a different, equally real question. 190 is `coordinationPairs(20)`, the count of UNORDERED pairs (A-and-B, not caring which direction) — useful for "how many trust relationships exist." But a routing rule, a retry policy, or a circuit-breaker threshold is typically configured PER DIRECTION — A calling B can have different retry behavior than B calling A, even between the same two services. That's `directedCallPaths(20) = 380`, exactly double, and it's the number that actually predicts config file size, not the trust-pair count.
    Did you have that?
  2. Cued recall

    A service has a well-tested 99.9% per-call success rate (0.1% failure) measured before the mesh was introduced. After migrating to a mesh, the SAME backend, measured the SAME way, now shows roughly 99.8% success end-to-end. An engineer suspects the mesh introduced a bug. Is that the right read?

    How sure are you, before you look?
    Not necessarily — this is close to exactly what `serialUnavailability` predicts with no bug at all. If the original 0.1% failure rate was measured on the direct app-to-app call, and the mesh now inserts 2 additional hops (egress sidecar, ingress sidecar) each with their OWN small failure rate, those hops compound: `1-(1-q)^k` for k=2 hops at a similar per-hop q roughly doubles the failure rate, not adds a fixed amount. The engineer should check whether the sidecars' OWN failure rate matches what was budgeted for before assuming application code regressed — the compounding itself is the mesh working as specified, not a symptom of it being broken.
    Did you have that?
  3. Near transfer

    `proxies-forward-vs-reverse.mdx` computes that concentrating TLS termination at ONE reverse proxy costs the SAME total CPU as splitting it across N servers — concentration doesn't save compute, only keys. A service mesh does the OPPOSITE of concentration: it puts a separate sidecar next to EVERY one of N services rather than one shared proxy. Does the mesh-wide mTLS CPU tax computed in this lesson contradict that earlier finding?

    How sure are you, before you look?
    No — they're the same linear-in-rate law, applied to different topologies, which is exactly why `mtlsServerLoad` is reused unchanged rather than rewritten for the mesh case. Whether mTLS is terminated by 1 concentrated proxy, N servers each on their own, or N sidecars each paired with their own service, the total added CPU is `(added microseconds per handshake) × (total handshake rate)` — the same product either way. What changed is not the FORMULA, it's that a mesh's sidecars don't replace each service's own compute the way a reverse proxy replaces a server's own termination — they sit ALONGSIDE it, so the mesh's mTLS tax is additional CPU on top of N services' existing footprint, not a redistribution of CPU that already existed.
    Did you have that?
  4. Far transfer

    The abstraction is: inserting a uniform intermediary between every pair of communicating parties turns what was a simple bilateral relationship into a compounding one — extra steps in the path multiply the chance any single handoff fails, and a centrally-pushed rulebook can lag behind what's actually true at the edges by the sum of every delay in the distribution chain, not the largest one. Name an instance outside computing.

    How sure are you, before you look?
    A large company inserting a formal approval workflow between every two departments that used to just email each other directly. Before: Engineering asks Finance a question directly, one handoff, one chance to drop it. After a "process improvement" inserts a shared intake system in front of AND behind every department (submit a ticket, wait for the intake team to route it, wait for the receiving department to pick it up) — now every cross-department request has two additional handoffs, and the chance any ONE request gets lost or delayed compounds across both, not just adds a fixed delay. Meanwhile, the company-wide policy manual (the "control plane") is updated centrally and pushed out at the next quarterly review — an individual team's actual practice can lag the official policy by up to the review interval PLUS however long it takes a team to actually read and adopt the update, the two delays stacking rather than whichever is larger.
    Did you have that?
