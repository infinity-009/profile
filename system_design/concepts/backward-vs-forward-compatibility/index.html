Tier 3 · Storage and state Backward vs forward compatibility start here

A live table holds every schema version it has ever written — 16 of them still material at 20% growth per migration, and a strict parser breaks on 5 of 6 real schema changes

Backward compatibility means new code can read old data; forward compatibility means old code can read new data — two independent properties, not two names for the same caution. Both matter at once because of one fact neither direction alone explains: data outlives code. A live database holds records from every schema version it has ever written, in shrinking-but-nonzero proportion, while the code reading it is at most one or two versions at a time. This lesson computes how many historical versions a single reader actually has to tolerate, classifies six real schema changes against both properties, and quantifies what a strict "unknown field is an error" parser costs versus a lenient one.

01

One record fails going forward. A different record fails going backward. Same table.

Two incidents, same week, same table. First: a node still running last week’s code reads a record written thirty seconds ago by this week’s deploy, and crashes on a field it has never heard of. Second: this week’s new code reads a record written three years ago, and returns null where a number was supposed to be. Nobody shipped a broken migration. Nobody skipped a code review. Both failures are the same table being read in opposite directions by code that isn’t the same age as the data — and “we tested that new code reads new data” never once exercises either failure, because that test only checks one (code, data) pairing out of the several that exist in production at any moment.

02

Assume the direction that matters is 'new code, new data' — the one you actually tested

The instinct: ship the migration, deploy the new code, test that the new code reads what the new code just wrote. That pairing works by construction — the person who wrote the reader also wrote the writer, minutes apart, on the same laptop. The two pairings that actually break in production are the other two: old code meeting new data, and new code meeting old data. Both have names.

Backward compatibility means newer code can read data written by older code. Forward compatibility means older code can read data written by newer code. They are not two phrasings of the same caution — a single schema change routinely satisfies one and violates the other, which is exactly what the six changes further down in this lesson classify.

Predict A table has been through 16 schema migrations, each one shipped while the system's write volume was 20% higher than at the previous migration, and no row has ever been rewritten. Roughly what fraction of ALL live rows are still sitting in the very first (oldest) schema version?
Nothing is ever rewritten, so every version's rows are still there — the only thing that changes is the SHARE. With volume growing 20% per migration, version k's rows are proportional to 1.2^k relative to version 0, so the oldest version's share is 1 divided by the sum of 1.2^0 through 1.2^15 — a geometric series dominated by the newest, biggest versions. That works out to roughly 1.1% of all live rows: small enough to be easy to forget, never small enough to be zero.
Show it without answering

At the rig’s default — 16 schema versions, write volume growing 20% per migration, nothing ever deleted — the oldest version still holds 1.1% of all live rows, and all 16 versions clear a 0.1% materiality bar. Push growth to 50% and the oldest version’s share collapses to roughly 0.076% — negligible, but the rig’s own “never deleted” retention line makes the point concrete: negligible is not the same number as zero, and a reader that crashes on that one row in thirteen hundred still crashes.

03

Deployed code turns over in minutes; a live table does not turn over at all

A rolling deploy replaces every instance of a service within minutes: old code and new code overlap for the length of the rollout, then the old code is gone. A database does not have an equivalent step. DDIA states this plainly (p.179): “the five-year-old data will still be there, in the original encoding, unless you have explicitly rewritten it since then” — and rewriting a large table is expensive enough that most systems defer it indefinitely rather than pay for it up front. The result is a structural asymmetry this lesson’s whole first half is built on: code is at most one or two versions wide at any moment; data is every version anyone has ever shipped, weighted toward the newest but never fully rid of the oldest. A reader has to handle a much longer history than a writer ever runs concurrently with — which is why “does new code read new data correctly” is necessary and nowhere near sufficient.

04

Three mechanisms, one job each

FIELD TAGS       Every field is identified by a number, not a position or a name. As long as a tag
                 number is NEVER reused for a different field, its meaning never changes — a
                 decoder can always find the byte boundaries of a tag it recognizes. Reusing a tag
                 breaks both directions unconditionally, even when the new field happens to share a
                 type with the old one, because typeof alone can't tell "same slot, same meaning"
                 from "same slot, different meaning by coincidence."

DEFAULT VALUES   Backward compatibility's actual mechanism. When new code looks for a field an old
                 record never wrote, a default value (empty string, zero, an explicit sentinel)
                 stands in for the missing data, so a genuinely absent field never becomes a
                 required-but-missing crash.

IGNORE UNKNOWN   Forward compatibility's actual mechanism — and it is a PARSER DISCIPLINE, not a
FIELDS           schema property. A schema change can be structurally forward compatible and still
                 fail in production, if the parser reading it treats "I don't recognize this field"
                 as an error instead of a skip. That single design choice is the entire gap between
                 a strict and a lenient parser this lesson quantifies below.

Backward compatibility is “normally not hard to achieve,” as DDIA puts it (p.162) — the author of the newer code already knows what the old format looks like and can code around it directly. Forward compatibility is the harder direction precisely because it asks OLD code, already written and already deployed, to correctly do nothing with data it was never designed to see.

The strict parser fails on every additive change too — the two that are, by construction, perfectly safe to skip. Leniency is not a weaker check; it is the specific design choice that lets a forward-compatible schema change actually behave like one in production.

06

The trade-off — leniency and 'never reuse a tag' both cost something

A lenient parser trades validation strictness for compatibility, and that trade is not free: an attacker or a buggy writer can smuggle an extra field into a record and a lenient reader will silently ignore it rather than flag it, which is a real cost when the unknown field should have triggered an alert. The fix isn’t reverting to strict — it’s validating deliberately, at a boundary that knows it’s validating, rather than making every downstream reader do it by accident.

“Never reuse a tag number” costs allocation discipline forever, not compute: every team that ever removed a field has to remember that field’s tag is retired permanently, not free for reuse, which means the tag space only grows monotonically even as the schema itself shrinks. Skipping this discipline once — reusing tag 7 because “nothing uses it anymore” — reintroduces the exact double-meaning collision this lesson’s rig marks as a break in both directions at once, silently, because nothing about a byte stream announces which meaning a decoder should apply.

Defaults are a design decision with a wrong-answer cost, not a free unlock: choosing 0 as a missing-field default for a “discount percentage” field is silently wrong for every historical row that had no discount concept at all — the field materializes as “0% discount,” a specific claim, rather than “no data,” an absence. Backward compatibility being achievable via a default does not mean any default is a safe one to pick.

07

In the wild

Real binary schema formats implement exactly the tag/default/ignore-unknown mechanics this lesson models abstractly — grpc-and-protobuf.mdx already shows the concrete wire-level version of “ignore unknown fields”: every protobuf field’s length is computable from its wire type alone, which is precisely what lets an old decoder skip a field it has never heard of without knowing anything else about it. A future binary-schema-encodings lesson (once written) is where Avro’s writer’s-schema/reader’s-schema resolution and Thrift’s own tag discipline would sit side by side with protobuf’s — this lesson is the property both are built to satisfy, not the wire format itself.

A live migration’s phase ordering is a direct consequence of these two properties, not a separate concern — a future schema-migration-expand-contract lesson (once written) would cover the mechanics of when to add a column, dual-write, backfill, and only then drop the old column; that ordering exists specifically because each phase boundary has to stay backward AND forward compatible with whatever code is still running on the other side of a rolling deploy at that moment. Expand-contract is a rollout choreography built on top of the guarantee this lesson defines — not a substitute for it.

“Data outlives code” is Kleppmann and Riccomini’s own name for the asymmetry, not a metaphor invented for this lesson — DDIA states it as a direct consequence of how database writes actually work: “A database generally allows any value to be updated at any time… the five-year-old data will still be there, in the original encoding, unless you have explicitly rewritten it since then” (p.179).

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • Backward compatibility means newer code can read data written by older code; forward compatibility means older code can read data written by newer code — these are two independent properties of a (reader, writer) pair, and a schema change can satisfy one, both, or neither
  • "Data outlives code" (DDIA p.179): a live database holds records from every historical schema version it has ever written, in shrinking-but-nonzero proportion, because rewriting old rows is expensive and most systems defer it indefinitely — while the CODE reading that table is at most one or two versions at a time (a rolling deploy overlaps old and new for minutes, not years), so a reader tolerates far more historical versions than any writer ever runs concurrently
  • Field tags/numbers are the mechanism that makes either direction possible at all: as long as a tag number is never reused for a different field, its meaning never changes, so a decoder can always find the byte boundaries of a tag it recognizes and skip past ones it doesn't — reusing a tag breaks both directions unconditionally, even if the new field happens to share a type with the old one
  • Backward compatibility is achieved by a DEFAULT VALUE standing in for a field absent from an old record; forward compatibility is achieved by "ignore unknown fields," which is a PARSER DISCIPLINE, not a property of the schema itself — a strict parser that errors on any unrecognized field can turn a structurally forward-compatible change into a hard failure
  • Concretely: adding an optional field is compatible both directions; removing a field that was required breaks forward compatibility only; adding a required field with no default breaks backward compatibility only; changing a field's type or reusing its tag number breaks both directions unconditionally, regardless of parser leniency
  • Over a realistic 6-change schema history (2 additive changes, 1 harmless removal, 3 true structural breaks), a strict "unknown field = error" parser fails on 5 of 6 changes — including the harmless ones — while a lenient "ignore unknown fields" parser fails only on the 3 that are genuine incompatibilities

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A table has been migrated through schema v1 through v9. v9 removes a field that was REQUIRED in v8 and had no default. A node still running v8's reader code (mid-rollout) reads a record freshly written under v9. What happens, and which compatibility direction is this?

    How sure are you, before you look?
    The v8 reader fails to decode the record: it requires that field, the v9 writer never wrote it, and there is no default to fall back on. This is a forward-compatibility failure — older code (v8) trying to read data written by newer code (v9). Backward compatibility is untouched by this change; a v9 reader can still read every old v8 record just fine, since it simply no longer looks for the field it dropped.
    Did you have that?
  2. Cued recall

    Two schema changes both "add a field." One is compatible in both directions; the other breaks backward compatibility. What's the actual difference, and why does it have nothing to do with the field's type?

    How sure are you, before you look?
    The difference is whether the new field is optional-with-a-default or required-with-none. An optional field with a default is fine both ways: new code reading old records without it just uses the default, and old code reading new records ignores it. A REQUIRED field with no default breaks backward compatibility specifically, because new code now demands a value that old records structurally never wrote — there is nothing to fall back on. The field's type (string, int, whatever) never enters into it; the break is about whether an old record can satisfy the new reader's requirement, not what shape the value takes.
    Did you have that?
  3. Near transfer

    A team stores records as loosely-typed JSON in a schema-on-read ("schemaless") document store and argues "we don't need to worry about backward/forward compatibility — there's no fixed schema to be incompatible with." Is that right?

    How sure are you, before you look?
    No — schema-on-read doesn't remove the need, it just relocates where it's enforced. DDIA draws exactly this distinction (p.161): a schema-on-read store lets old- and new-format documents coexist without a database-level ALTER, but whatever application code reads that mixed pile of documents still has to fill in a default for a field an old document never had, and still has to tolerate a field a newer document has that it's never seen — the same two properties, just checked by hand in application code instead of by a schema definition. The "no schema" framing makes the discipline invisible, which is worse than absent, because nothing forces anyone to notice when it's missing.
    Did you have that?
  4. Far transfer

    The abstraction is: two independent parties exchange encoded messages across time, and either party might be running strictly older or strictly newer logic than the other at the moment of exchange — so compatibility has to hold in both directions at once, because neither party can force the other to upgrade simultaneously. Name an instance outside computing.

    How sure are you, before you look?
    An orthographic spelling reform, such as Portugal and Brazil's 1990 Orthographic Agreement. The reform changed how thousands of words are spelled going forward. Readers educated entirely under the OLD spelling still need to read text written under the NEW rules — forward compatibility, an "older reader" parsing "newer-written" text, achieved because the new spelling changes are mostly regularizations an old reader can still sound out. Readers educated entirely under the NEW spelling still need to read the country's entire existing literature, written under the OLD rules — backward compatibility, a "newer reader" parsing "older-written" text, which is why reforms are phased in over years rather than flipping overnight: exactly the rolling-deploy overlap this lesson computes, just measured in decades of print instead of minutes of container restarts.
    Did you have that?
