Tier 3 · Storage and state Partial & functional indexes

A partial index over 2% of rows is 480 KB against a 24 MB full index, and one wrong predicate turns 3 page reads into 1,000,000

Every index so far in this subsection has covered the whole column, for every row, exactly as written. This lesson is about two refinements that make an index cheaper by covering LESS — deliberately, precisely — rather than more: a partial index that only indexes the rows a WHERE clause names, and a functional index that indexes the result of an expression instead of the raw column. Both buy a smaller, cheaper-to-write index. Both also come with a sharp edge: stray one predicate or one expression off the index's own definition and the database gives that query nothing at all, not partial credit.

Read first — what-is-an-indexindex-write-cost

01

The same column, the same table, an index that's either 480 KB or 24 MB

An orders table holds 1,000,000 rows. 2% of them have status = 'pending'. A dashboard query runs constantly against exactly that slice: WHERE status = 'pending' AND customer_id = ?.

A plain index on customer_id, covering every row, costs 24 MB. An index declared with WHERE status = 'pending' right in its own definition — a partial index — covers only the 20,000 rows that actually match, and costs 480 KB: exactly 2% the size, because that is exactly the fraction of rows it bothered to index at all. Nothing about customer_id changed. What changed is that the index stopped pretending it needs to know about the other 980,000 rows, because this query never asks about them.

02

Assume a more specific index just does less of the same thing, a little worse

The instinct: an index that only covers part of a table must be a compromise — smaller, sure, but also a weaker version of the full index, helping a little less on every query. That is not what happens. A partial index is not a diluted full index; it is a full-strength index over a smaller table that happens to be a slice of a bigger one. On the query it was built for, it is exactly as fast as any other sorted index. The cost only shows up as an all-or-nothing gate on every OTHER query: a partial index either provably contains what a query needs, or it contributes nothing whatsoever — never something in between.

A functional index carries the identical trap in a different shape. CREATE INDEX ON users(LOWER(email)) does not make email queries faster in general — it makes exactly one expression, LOWER(email), fast to look up. A query that filters on the raw column, or on any other expression, gets nothing from it.

Predict A 1,000,000-row orders table has CREATE INDEX ON orders(customer_id) WHERE status = 'pending'. A query runs WHERE status = 'shipped' AND customer_id = ?. About how many rows does the database read?
The database can only use a partial index when it can PROVE the index's own predicate covers the query's predicate. status = 'shipped' is not status = 'pending' — there is no subset relationship, so the planner cannot trust the index to contain every shipped row (it may contain none). It falls back to reading the whole table, exactly the fullScanCost(1,000,000) = 1,000,000 rows a query would pay with no index defined on this table at all. The index isn't a little bit useful here; it is completely irrelevant to this query, the same lesson what-is-an-index.mdx already drew about an unindexed column.
Show it without answering

At the rig’s default — 1,000,000 rows, 2% matching, 5,000 writes/s — the partial index is 480 KB against the full index’s 24 MB (2.0% of the size), and only 100 writes/s touch it instead of all 5,000, saving 22.94 ms of index-maintenance work every second. On the functional-index side, WHERE LOWER(email) = ? costs 3 page reads through INDEX(LOWER(email)); the moment the query drops the LOWER() and asks WHERE email = ? instead, that same index gives nothing, and the cost jumps to 1,000,000 — a 333,333× collapse back to a full scan.

03

A locksmith who only stocks one manufacturer's blanks

A general locksmith keeps shelves of blank keys for every lock shape ever sold, plus a general-purpose cutting jig that can be reconfigured for any of them. That inventory is expensive to keep, and most of it sits unused most days — but it means walking in with any lock gets served.

A specialty locksmith who only stocks one manufacturer’s blanks and one jig calibrated specifically for them runs a far cheaper operation: less stock, one jig, nothing to reconfigure. Cutting a key for THAT manufacturer’s lock is exactly as fast as at the general shop — the narrow setup loses nothing on the case it targets. But a customer who shows up with a different manufacturer’s lock gets no partial service. The shop doesn’t cut a slightly-wrong key or charge less for a rough attempt — it simply cannot help, and the customer has to find a shop stocked for that specific lock. A partial index is that specialty shop for a slice of rows; a functional index is that specialty shop for one specific transformation of a column. Cheap to run, perfect on the one case it was built for, and silent on everything else.

04

Two refinements, one shared move: cover less, on purpose

PLAIN INDEX             every row, raw column value          — helps any query on that column
PARTIAL INDEX           only rows matching a predicate        — helps only a query PROVABLY
                         declared at CREATE INDEX time          covered by that same predicate

PLAIN INDEX             every row, raw column value          — helps an exact-match query on
                                                                 the raw column
FUNCTIONAL INDEX        every row, f(column) instead          — helps only a query using THAT
                         of the raw column                      exact expression, f(column)

Both refinements answer the same question — “does this index need to cover everything the raw column could be asked about?” — with the same answer, no. A partial index narrows which rows get an entry. A functional index narrows what value gets stored as the key. Neither one makes the underlying B-tree slower or faster to walk once it is entered — sortedIndexLookupCost (reused unchanged from what-is-an-index.mjs) is identical whether the tree holds every row’s raw value or 2% of rows’ precomputed expression result. What changes is which queries are allowed to walk it at all.

partialIndexSize(N, matchFrac) = N · matchFrac · bytesPerEntry

A partial index’s size scales directly with the fraction of rows matching its predicate, not with the table’s total row count — at matchFrac = 1 this is exactly fullIndexSize, the same formula what-is-an-index.mjs already uses for a full index, reused unchanged rather than re-derived.

writesTouching(partial) = writesPerSecond · matchFrac   vs.   writesTouching(full) = writesPerSecond

A write to a non-matching row costs the partial index nothing — not a discount, an outright skip. The per-op cost each MATCHING write still pays is index-write-cost.mjs’s own indexWriteLatencyMs, reused unchanged; this file only adds which fraction of writes pay it at all.

nonSargablePredicateCost(N) = fullScanCost(N) · functionEvalCostPerRow   vs.   functionalIndexLookupCost(N) = sortedIndexLookupCost(N)

When a query’s expression doesn’t match a functional index’s own expression, the database can’t seek by anything — it re-derives fullScanCost (reused unchanged from what-is-an-index.mjs) and pays one function evaluation per row on top. When the expression DOES match, the cost is sortedIndexLookupCost, exactly as if the expression’s result were an ordinary column.

06

The trade-off: narrower coverage is not free to choose correctly

A partial index’s saving is a bet that its predicate matches how the table is actually queried — get the predicate wrong and there is no partial credit. Choosing WHERE status = 'pending' because pending orders are rare and heavily queried is a specific claim about query patterns, not a general optimization. If a second, equally common query pattern filters on status = 'cancelled' instead, this exact index does nothing for it — a second partial index, at its own size and write cost, would be needed. A partial index is not a smaller version of “an index on this column”; it is an index on one particular slice of this column’s queries.

A functional index’s saving is the identical bet, aimed at an expression instead of a predicate. INDEX(LOWER(email)) is a claim that every relevant query will lowercase email before comparing — a claim that’s often true for login lookups and often false for admin tooling written against the raw column. Both indexes fail the exact same way when the bet is wrong: not degraded performance, but the complete absence of any benefit, silently, with no error raised — the query just runs as if the index were never created.

The functional index’s write side pays one extra cost the partial index doesn’t: computing the expression. Maintaining INDEX(LOWER(email)) means running LOWER() on every write before the key can even be produced, on top of the ordinary per-op index-write cost. In this lesson’s own NVMe/B-tree numbers that is 0.00468 ms of write cost becoming 0.00568 ms — about 21% more, small in absolute terms but never zero, because the database cannot store a value it hasn’t computed yet.

07

In the wild

Both features are ordinary, named parts of the SQL surface, not exotic tricks. PostgreSQL’s own documentation describes partial indexes (chapter 11, “Partial Indexes”) as indexes built with a WHERE clause restricting which rows are indexed, recommending them specifically for columns with a common value that’s rarely the target of a search — precisely the “2% pending, 98% completed” shape this lesson’s numbers are built on — and expression indexes (the same chapter, “Indexes on Expressions”) as indexes built on the result of a function or scalar expression rather than a plain column, with the caveat that a query must use a form that is textually identical, or provably equivalent, to the indexed expression for the planner to consider it.

The underlying B-tree machinery is unchanged from what-is-an-index.mdx and btree-vs-lsm.mdx — nothing here invents a new data structure. A partial index is a B-tree over fewer keys; a functional index is a B-tree whose keys happen to be function outputs instead of raw column bytes. Everything this lesson computes is the same sortedIndexLookupCost/fullScanCost pair those two lessons already derived, applied to a narrower input.

The per-write cost a matching row still pays is index-write-cost’s own figure, not a new one. This lesson’s write-savings numbers price only which fraction of writes touch the index at all; how expensive each one of those touches is remains exactly the device- and structure-specific cost that lesson works out in full.

Now put the page away

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A partial index is declared with a WHERE-like predicate at CREATE INDEX time (`WHERE status = 'pending'`) and holds an entry ONLY for rows matching it — at 2% of rows matching, the index is 2% the size of a full index over the same column, and writes to the other 98% of rows never touch it at all
  • A partial index can serve a query only if the query's own predicate is provably covered by the index's predicate — an exact-value mismatch (querying `status = 'shipped'` against a `WHERE status = 'pending'` index) gets none of the index's benefit and falls back to a full table scan, identical to the index not existing
  • A functional (expression) index is built on the RESULT of an expression applied to a column, not the raw column itself (`INDEX(LOWER(email))`) — a B-tree keyed on an expression's output is structurally identical to one keyed on a column, so a query using that exact expression gets the same handful of page reads any sorted index gives
  • The non-sargable-predicate trap runs in both directions: `WHERE LOWER(email) = ?` cannot use a plain `INDEX(email)`, and `WHERE email = ?` cannot use `INDEX(LOWER(email))` either — either mismatch forces the database to evaluate the function on every row and compare, collapsing an O(log n) lookup back to an O(n) scan
  • Both refinements trade the identical direction: narrower coverage (fewer rows, or one specific expression) buys a smaller and cheaper-to-write index, in exchange for that index being usable by a correspondingly narrower set of queries — the win and the catch are the same fact seen from two sides
  • A functional index's write cost is the ordinary per-op index-write cost PLUS one function evaluation per write — small in absolute terms (here, about 21% more than the write alone), but never zero, because the expression's value has to be computed before it can be stored

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A 1,000,000-row `orders` table has `CREATE INDEX ON orders(customer_id) WHERE status = 'pending'`, and 2% of rows are pending. How much smaller is this index than a plain index on `customer_id` over the whole table, and what happens to writes on the other 98% of rows?

    How sure are you, before you look?
    The partial index is 480 KB against the full index's 24 MB — exactly 2% the size, because it holds an entry only for the 2% of rows matching its predicate. Writes to the other 98% of rows do not pay a discounted cost against this index — they pay zero, because a row that never matches the predicate never gets an entry to maintain in the first place.
    Did you have that?
  2. Cued recall

    The same table now runs `SELECT * FROM orders WHERE status = 'shipped' AND customer_id = ?`. Does the partial index above help this query at all?

    How sure are you, before you look?
    No — not partially, not a little. The query's predicate (`status = 'shipped'`) is not covered by the index's own predicate (`status = 'pending'`), so the database cannot prove the index even contains the rows this query needs. It falls back to a full 1,000,000-row scan, identical in cost to the table having no index on this pattern at all.
    Did you have that?
  3. Cued recall

    A table has `INDEX(email)`. A query runs `WHERE LOWER(email) = ?`. Why doesn't the existing index help, and what does the database do instead?

    How sure are you, before you look?
    `INDEX(email)` is sorted by the RAW value of `email`, not by `LOWER(email)` — two rows with emails differing only in case sort far apart in that index, so there is no way to seek by the lowercased form using it. The database evaluates `LOWER()` on every row and compares by hand: at 1,000,000 rows that is 1,000,000 cost units, against 3 page reads if a functional index on `LOWER(email)` existed and the query used that exact expression.
    Did you have that?
  4. Near transfer

    A team builds `INDEX(LOWER(email))` specifically to speed up case-insensitive login lookups. Satisfied, they assume it also speeds up an existing admin report that runs `WHERE email = ?` (exact case, no `LOWER()`). Does it?

    How sure are you, before you look?
    No — and this is the same rule as the cued question above, run in the opposite direction. `INDEX(LOWER(email))` is sorted by the LOWERCASED value, not the raw one, so a query filtering on the raw column cannot seek through it any more than `INDEX(email)` could seek through a `LOWER(email)` filter. A functional index doesn't make the raw column faster to query and a plain index doesn't make the expression faster either — each index serves exactly the one form it was built on, and "close" doesn't count.
    Did you have that?
  5. Far transfer

    The abstraction is: a structure that deliberately covers a narrower slice of what it could — a subset of cases, or one specific transformed view of the input — costs less to build and keep current than a structure covering everything, but only helps the exact slice or view it was built around; anything else gets zero benefit, not degraded benefit. Name an instance outside computing.

    How sure are you, before you look?
    A locksmith who stocks blanks and cutting jigs for only one lock manufacturer. Carrying one manufacturer's blank stock and one calibrated jig is far cheaper to keep ready than a general locksmith's shelves of every blank shape in existence, and cutting one of THAT manufacturer's keys is exactly as fast as at a full-service shop — the narrow setup loses nothing on the case it was built for. But a customer who arrives with a different manufacturer's lock gets no partial help from that narrow setup: it doesn't cut a slightly-wrong key, it simply cannot cut one at all, and the customer has to find a shop stocked for that specific lock instead — the same all-or-nothing snap a partial index's predicate mismatch or a functional index's expression mismatch produces.
    Did you have that?
