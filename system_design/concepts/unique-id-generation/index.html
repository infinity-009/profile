Tier 3 · Storage and state Unique ID generation

A random primary key costs 1.43× the pages a time-ordered one needs, for the same million rows

Generating a value that has never been used before sounds like it should be free — call a function, get a number. But that number becomes a primary key, and a primary key's VALUE decides where every insert lands in a B-tree, not just whether it's unique. This lesson prices four real ID schemes — UUIDv4, UUIDv7, ULID, Snowflake — on the two axes that actually differ: how many bytes each one costs to store, and what its value layout does to insert locality, reusing the page-split model this course already built rather than re-deriving it.

Read first — heap-files-and-page-layout

01

Same table, same rows, same page geometry — one primary key costs 1.43× more pages

Two tables. Identical row size, identical 8 KB pages, identical million rows inserted at the same rate. The only difference is what the primary key column looks like: one table uses a UUIDv4, the other a UUIDv7. Both are 128-bit values — same size on disk, same index structure, same everything an ORM’s column definition would show you. One of these tables’ primary-key B-tree ends up needing 23,420 pages. The other needs 16,394. Nothing about “uniqueness” explains the gap — both ids are equally unique. What differs is where each new id lands.

Generating a value that’s never been used before feels like it should be a solved, free problem — call a function, get a number back. It is solved. It is not free, and the cost isn’t in the generation call at all; it’s in what the VALUE does once it becomes a primary key that a B-tree has to insert somewhere.

02

Assume any sufficiently random, sufficiently long ID is 'good enough'

The belief this has to break
A UUID is a UUID — as long as it's long enough to avoid collisions, which scheme you pick is a style choice.

True for the collision question and false for almost everything else a real system cares about. Collision probability is dominated by bit width, and at 122 bits of actual randomness (UUIDv4) that risk is not a practical concern at any volume this course discusses. But an id isn’t only a collision-avoidance token — the moment it becomes a primary key, its bit pattern also decides where in a B-tree every insert lands, and that property has nothing to do with how many random bits the scheme uses. A UUIDv4 and a UUIDv7 are both 128 bits, both practically collision-free, and produce a 1.43× difference in index size purely from how those bits are arranged.

03

A UUIDv4 is a dart thrown at the whole board; a UUIDv7 is a dart thrown at the edge

Picture a B-tree’s primary-key index as a long shelf of pages, sorted by key value. A UUIDv4 is 122 bits of uniform randomness — throwing a new id at this shelf is like throwing a dart at a dartboard the size of the entire shelf: it can land anywhere, with equal probability, forever. Every page, no matter how old, stays a live target for some future dart.

A UUIDv7 or a ULID replaces the leading bits with a millisecond timestamp, then fills the rest with randomness just for uniqueness within that millisecond. Now the dart is thrown at a target that moves steadily rightward over time — almost every throw lands at (or very near) the current rightmost edge of the shelf, because “now” is always later than every id generated before it. Pages that fall behind the moving edge are done being written to forever.

A Snowflake id does the same trick with a timestamp in its leading bits, plus a machine/worker id and a per-machine counter packed into the rest — same rightward-moving-target shape, at 64 bits total instead of 128, but generating one requires knowing your own machine’s assigned id, which some coordinating system has to hand out. A UUIDv7 generator needs nothing from anyone else; it just reads the clock.

Predict 1,000,000 rows, 128-byte rows, 8 KB pages, 61 rows/page (the same numbers heap-files-and-page-layout.mdx already uses). Roughly how many more pages does a UUIDv4-keyed primary index need than a UUIDv7-keyed one, for the identical rows?

At the rig’s defaults — 1,000,000 rows, 128-byte rows, 8 KB pages — the random-scheme primary key costs 23,420 pages and the time-ordered scheme costs 16,394, a 1.43× gap that grows in absolute page count as insert volume grows, because it’s a fixed multiplier on a number that keeps getting bigger.

The only fact this lesson adds to heap-files-and-page-layout.mjs’s existing two-pattern model: which named pattern each ID scheme’s bit layout actually produces. Everything downstream — avgFillFactor, pagesNeeded, splitCount, splitComparison — is reused unchanged from that lesson; nothing about page splits is re-derived here.

idBytes(scheme) = rawBytes, stringBytes

UUIDv4/UUIDv7: 16 raw bytes, 36-character canonical text (32 hex digits + 4 hyphens). ULID: the same 16 raw bytes, but a 26-character Crockford base32 text encoding — shorter as text for identical bit width, because base32 packs more bits per character than hex. Snowflake: 8 raw bytes, up to 20 decimal digits as text (a 64-bit unsigned integer’s maximum value has 20 digits). This is a genuinely separate cost from insertion pattern — it multiplies by every column that stores a copy of the id, most commonly a foreign key.

06

The trade-off: locality, size, and coordination pull in different directions

Fixing locality (UUIDv4 → UUIDv7) costs nothing in size and nothing in coordination. Both are 128-bit, 16-byte values; a UUIDv7 generator needs only an accurate clock, not a registry of machine ids. This is close to a free upgrade for any system already paying UUIDv4’s storage cost, which is why RFC 9562 standardized it rather than leaving time-ordered UUIDs as an ad-hoc convention.

Fixing size (UUID → Snowflake) costs coordination. Halving the raw byte width from 16 to 8 requires packing a machine/worker id into the value, and that id has to be assigned by something — a coordination service, a config file, a Zookeeper-style registry — so that two machines never reuse the same id concurrently and collide. UUIDv7 and ULID sidestep this entirely by relying on randomness plus a timestamp instead of a coordinated identity; the price is a value roughly twice Snowflake’s raw size.

Fixing size a different way (UUID → ULID) costs nothing but a different text encoding. ULID keeps UUIDv7’s full 128 bits and its coordination-free generation, and only changes how those bits are written as text — base32 instead of hex — for a real but smaller storage win than Snowflake’s. A team that wants no coordination and some storage savings, but not Snowflake’s full 64-bit cut, sits here.

None of these three axes — locality, byte size, coordination — moves together. A scheme can fix any one without touching the others, which is exactly why “just use UUIDs” and “just use Snowflake” are both incomplete answers: each optimizes one axis at a cost on a different one, and the right pick depends on which axis the actual workload is paying for.

07

In the wild

UUIDv7 is a ratified IETF standard, not a convention some framework invented. RFC 9562: Universally Unique IDentifiers (UUIDs), published in 2024, formally defines the version-7 layout this lesson uses — a Unix millisecond timestamp in the leading 48 bits, followed by version/variant marker bits and then random bits — specifically to give UUIDs the sortable, insert-friendly property this lesson quantifies, without deprecating version 4’s fully-random layout for cases where that property isn’t wanted.

Twitter’s Snowflake scheme is a widely-adopted, publicly documented design, not an academic paper: a 64-bit id built from a timestamp, a datacenter/worker id, and a per-worker sequence counter, built to generate roughly-sortable unique ids at high throughput across many machines without a shared counter service. Numerous systems since (Discord, Instagram, Mastodon) publish their own variants of the same three-part layout.

The insertion-pattern cost this lesson quantifies is not new arithmetic — it is heap-files-and-page-layout.mdx’s own trade-off slot, already naming “a random key (a UUIDv4)” as the random-pattern example, applied here to the specific question of which ID GENERATION SCHEME produces which pattern, and adding the storage-size axis that lesson does not cover.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A UUIDv4 is 122 bits of pure randomness (6 bits are fixed version/variant markers), so every new value is uniform across the ENTIRE key space — an insert targets a random existing page in a B-tree-indexed primary key, not the newest edge
  • UUIDv7 and ULID both put a millisecond timestamp in the LEADING bits, followed by random bits for uniqueness within that millisecond — IDs generated close in time sort close in value, so inserts are (almost) always at the rightmost page, independently of any other node
  • Snowflake packs a timestamp, a machine/worker id, and a per-machine sequence counter into 64 bits — also insert-friendly like UUIDv7, but it needs distinct machine ids assigned somewhere, which UUIDv7's fully independent generation does not
  • The insert-locality difference is exactly `heap-files-and-page-layout.mdx`'s own monotonic-vs-random split-cost model, reused unchanged: at 1,000,000 rows, 128-byte rows, 8 KB pages, a UUIDv4-style random key needs 23,420 pages against 16,394 for a UUIDv7/Snowflake-style ordered key — 1.43× more, from the insertion pattern alone
  • ID byte size is a real, separate cost from locality: a UUID (v4 or v7) is 16 raw bytes / 36 text characters, a ULID is the same 16 raw bytes but only 26 text characters (base32 instead of hex), and a Snowflake id is 8 raw bytes / up to 20 text characters — a gap that multiplies every time the id is copied into a foreign key column
  • Locality and size are independent levers: UUIDv7 fixes the locality problem UUIDv4 has while staying the same 16/36-byte size; only switching to Snowflake or ULID changes the size, and only switching away from UUIDv4 changes the locality

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    Two tables use identical page geometry and the same 1,000,000-row insert volume. One keys rows with a UUIDv4, the other with a UUIDv7. Both values are the same byte width — 16 bytes. Why does the UUIDv4 table's primary-key index end up needing more pages?

    How sure are you, before you look?
    Because the difference isn't about how many bytes each value takes — it's about WHERE each new value lands relative to the ones already in the tree. UUIDv4 is uniformly random over the full 128-bit space, so a new id is equally likely to insert anywhere in the existing key range, and every page stays a live insertion target forever (the classic ~70% post-split average fill). UUIDv7 puts a millisecond timestamp in the leading bits, so a new id almost always sorts after every existing one — inserts concentrate at the single rightmost page, which fills to ~100% and is then never touched again. At 1,000,000 rows and 8 KB pages that is 23,420 pages against 16,394 — 1.43×, the exact reused constant from `heap-files-and-page-layout.mdx`.
    Did you have that?
  2. Cued recall

    A team picks Snowflake ids specifically because they are only 8 bytes, half a UUID's 16. A colleague objects that Snowflake still needs centrally coordinated machine ids, while UUIDv7 needs no coordination at all and is nearly as insert-friendly. Are they arguing about the same trade-off?

    How sure are you, before you look?
    No — they're each naming a real but DIFFERENT axis. The 8-vs-16-byte difference is a storage-footprint argument: it's real, and it compounds across every foreign key that copies the id. The coordination argument is about generation, not storage or locality: Snowflake needs distinct machine/worker ids handed out somewhere (a coordination problem, however small) while UUIDv7 can be generated independently on any node with no registry at all. A team can want small ids and coordination-free generation simultaneously, and no single scheme here gives them both — Snowflake trades independence for size, UUIDv7 trades size for independence, ULID sits at UUIDv7's size with a shorter text encoding.
    Did you have that?
  3. Near transfer

    `heap-files-and-page-layout.mdx`'s own trade-off slot already says a random key (its example: "a UUIDv4") avoids the write-concurrency hot spot that a monotonic key creates, at the cost of 1.43× more pages. A team reads that and decides they should switch FROM UUIDv7 TO UUIDv4 specifically because their table has heavy concurrent insert load and they want to avoid contention on one hot rightmost page. Does the number support that move?

    How sure are you, before you look?
    It supports the mechanism, but probably not the conclusion once ULID's own random suffix is accounted for. UUIDv7 and ULID are not fully monotonic in the way an auto-increment counter is — only their LEADING timestamp bits are ordered; within the same millisecond, the trailing random bits still scatter inserts across whatever small range of pages that millisecond's ids land in, which already spreads write pressure off a single page under real concurrent load. Moving all the way to UUIDv4 solves a hot-page problem this scheme only partially has, while paying the full 1.43× space cost this lesson quantifies, in exchange for a concurrency benefit that a timestamp-prefixed scheme already gets most of. The move trades a fully-solved problem for a partially-relevant one.
    Did you have that?
  4. Far transfer

    The abstraction is: a value has to satisfy two independent constraints — it must be unique, and its bit pattern determines where it lands in a structure that is organized by value — and satisfying the first constraint by pure randomness actively fights the second one, while embedding an already-ordered quantity into the value's leading bits satisfies both at once. Name an instance outside computing.

    How sure are you, before you look?
    A library's accession number versus the Dewey decimal call number on the same book's spine. A librarian assigning brand-new accession numbers sequentially (0001, 0002, 0003, as each book arrives) never has to renumber the shelf — every new number is already the largest one, so it goes at the end of the accession log with no reshuffling. If instead each new book were stamped with a random 6-digit number for "uniqueness," the number would still uniquely identify the book, but inserting it into any physically-ordered list keyed by that number would land it in a random gap among books already shelved — forcing a shift every time, the exact page-split cost this lesson prices for a database. The call number solves this by encoding an already-ordered fact (subject classification) into the leading digits, the same move UUIDv7 makes by putting a timestamp first.
    Did you have that?
