Tier 5 · Moving data around Batch joins

640 seconds shuffling two sharded datasets across the network, 0.2 seconds sort-merging each reducer's own slice of them afterward — and a GROUP BY that turns out to run the identical shuffle formula with one input set to zero

A join or a GROUP BY over data too big for one machine still needs the exact same two ingredients this curriculum already built separately: `shuffle-the-batch-primitive.mdx`'s distributed sort, which gets every record with a given key onto the same reducer no matter which shard it started on, and `join-algorithms.mdx`'s sort-merge cost, which prices what that reducer does with its own now-small partition afterward. This lesson is the composition, not a fourth algorithm: total cost is the shuffle (a function of the FULL dataset, over a shared network link that more machines can't widen) plus one reducer's local sort-merge (a function of its own PARTITION, which shrinks as more reducers split the work). Two wrinkles fall out of taking that composition seriously. Secondary sort — ordering records within a group, not just grouping them — needs a composite sort key, a distinct technique from sorting twice. And a GROUP BY is not a different operation from a join at all: it is the identical shuffle-then-local-reduce pattern with one input instead of two, which this lesson proves by showing the two cost formulas produce the same number, not by asserting the resemblance.

Read first — join-algorithmsshuffle-the-batch-primitive

01

640 seconds of shuffle, 0.2 seconds of local sort-merge — same job, two very different bills

Two datasets, 2,000,000,000 rows each side, 200 bytes/row — 400GB per side, 800GB combined — need to be joined on a shared key, sharded across a cluster with 200 reducers and a 10Gbps network link:

node -e "import('./src/sim/batch-joins.mjs').then(m => {
  const r = m.batchJoinCost({ bytesA: 4e11, bytesB: 4e11, rowsA: 2e9, rowsB: 2e9, numReducers: 200, networkBytesPerSec: 1.25e9, comparisonsPerSecond: 1e8 });
  console.log(r);
  console.log('shuffle/local ratio:', r.shuffleSeconds / r.localSeconds);
})"

Shuffle costs 640 seconds (about 10.7 minutes) moving the full 800GB across the network so that matching keys land on the same reducer. Local sort-merge costs 0.2 seconds — each of the 200 reducers merge-walks its own 10,000,000-row slice of each side, and join-algorithms.mdx already prices exactly that walk. Shuffle is 3,200× more expensive here, and that ratio isn’t a coincidence of these particular numbers — it’s the shape this whole lesson is about: shuffle prices the FULL dataset over a link every byte has to share; local sort-merge prices one reducer’s own PARTITION, which is already small by the time it gets there.

02

Assume a distributed join needs a distributed join algorithm

The belief this has to break
A join across a multi-terabyte, sharded dataset must run some fundamentally different, cluster-native join algorithm — the single-machine sort-merge join from join-algorithms.mdx is a toy that doesn't scale to this.

It doesn’t need a new algorithm at all — it needs one new STEP placed in front of the old one. Once every record sharing a key has been routed onto the same reducer (shuffle-the-batch-primitive.mdx’s distributed sort, reused unchanged as shuffleDataVolumeSeconds), that reducer is holding a small, single-machine problem: exactly the one join-algorithms.mdx already solved. DDIA’s own MapReduce walkthrough says as much directly — “the reducers can now perform the actual join logic easily… this algorithm is known as a sort-merge join” (Kleppmann, DDIA, 2nd ed., p. 472) — the “easily” is doing real work in that sentence: easy because the hard part (getting the right rows to the right machine) already happened in the shuffle, not because the join itself got simpler.

Predict A batch join across two sharded datasets runs on 200 reducers. The team doubles the cluster to 400 reducers, same data, same network. What happens to the shuffle cost and the local sort-merge cost?
Shuffle cost is a function of the FULL dataset's bytes crossing a shared network link — that total does not change just because more machines are splitting the work afterward, so it stays flat. Local sort-merge cost is a function of one reducer's own PARTITION, and doubling the reducer count halves the average partition size, which halves sortMergeCost's already-small operation count. The two terms respond to reducer count in opposite ways precisely because they are priced against different things: total bytes for one, per-machine rows for the other.
Show it without answering

At the rig’s defaults — 1,000,000,000 rows/side, 100 reducers — the shuffle bar dwarfs the local bar by three orders of magnitude. Drag reducers up and the local bar keeps shrinking while the shuffle bar doesn’t move; flip to GROUP BY mode and the shuffle bar changes to exactly half its join-mode value (one input instead of two) while the underlying formula stays identical.

03

The phone books get too big for one desk

join-algorithms.mdx cross-referenced two phone books small enough to alphabetize side by side on one desk. Now make them the size of a whole country’s directory — too big for any one desk, or any one person, to hold at all. The fix a real sorting facility uses is exactly the shuffle: every page gets physically routed, by the first letter of the surname on it, to one of several regional depots — every “Smith” entry, from every source page, ends up at the same depot, no matter which original book or city it came from. Once a depot has its own (now desk-sized) stack, its own clerk does precisely the side-by-side merge-walk join-algorithms.mdx already prices — that stack is small again, because the routing already happened.

If a depot needs its stack in a SPECIFIC order once it arrives — say, chronological by the date each entry was filed, not just alphabetical by surname — the fix isn’t to let the pages arrive in whatever order and re-sort them on the clerk’s desk. It’s to write BOTH the surname and the date on the routing label before a page ever leaves its source, so the depot’s stack comes out already in date order within each surname. That’s a secondary sort: a decision made at ROUTING time about a second, finer-grained order, not a second pass after the fact.

04

The model: shuffle to co-locate, a local sort-merge to finish, secondary sort as a composite key

BATCH JOIN     shuffle BOTH inputs by key, then each reducer sort-merges its own partition
               shuffle:  shuffleDataVolumeSeconds(bytesA + bytesB, networkBytesPerSec)
               local:    sortMergeCost(rowsA/numReducers, rowsB/numReducers, ...) / comparisonsPerSecond
               total:    shuffle + local — dominated by shuffle once the dataset is large

GROUP BY       shuffle ONE input by key, then each reducer locally reduces its own partition
               shuffle:  shuffleDataVolumeSeconds(bytesA, networkBytesPerSec)
               local:    sortMergeCost(rowsA/numReducers, 0, ...) / comparisonsPerSecond
               same formulas as a join, with the second input's size pinned at 0 — not an analogy

SECONDARY SORT composite sort key (primary = group, secondary = within-group order)
               overhead: rows · log2(avgGroupSize) · 0.5 — zero at avgGroupSize <= 1
               wins when: records for a key must arrive in a specific order, not just grouped

joinShuffleSeconds(bytesA, bytesB, networkBytesPerSec) = shuffleDataVolumeSeconds({ mapOutputBytes: bytesA + bytesB, networkBytesPerSec })

shuffleDataVolumeSeconds is shuffle-the-batch-primitive.mjs’s own function, reused unchanged — a join’s shuffle is that file’s “move this many bytes across the shared network link” cost, fed the COMBINED size of both inputs, since both sides have to cross the network before matching keys can land together on one reducer.

groupByShuffleSeconds(bytesA, networkBytesPerSec) = shuffleDataVolumeSeconds({ mapOutputBytes: bytesA, networkBytesPerSec })

The identical function, fed only ONE input’s bytes. This file’s own tests check that groupByShuffleSeconds(X) and joinShuffleSeconds(X, 0) return the exact same number for a grid of Xs and bandwidths — a proven identity, not a resemblance asserted in prose.

batchJoinCost = joinShuffleSeconds(…) + sortMergeCost(rowsA/numReducers, rowsB/numReducers, …) / comparisonsPerSecond

sortMergeCost is join-algorithms.mjs’s own function, reused unchanged, called on one reducer’s PARTITION — rowsA/numReducers and rowsB/numReducers — never the full dataset. The shuffle term depends on the full dataset and a shared link more reducers can’t widen; the local term depends only on one reducer’s own slice and falls linearly as numReducers grows. comparisonsPerSecond converts that reused operation count into seconds so both dominant costs sit in one unit.

secondarySortOverhead(rows, avgGroupSize) = rows · log₂(avgGroupSize) · 0.5

Zero when avgGroupSize ≤ 1 — no groups, no ties, nothing for a secondary key to break. Above that, it prices exactly the within-group comparisons a composite (primary + secondary) sort pays that a primary-only sort of the identical rows never has to.

node -e "import('./src/sim/batch-joins.mjs').then(m => {
  const shared = { bytesA: 4e11, rowsA: 2e9, numReducers: 200, networkBytesPerSec: 1.25e9, comparisonsPerSecond: 1e8 };

That isn’t two algorithms that happen to agree; groupByShuffleSeconds and joinShuffleSeconds are two different-shaped public functions (one dataset argument vs. two) that reduce to the same private arithmetic — a GROUP BY’s cost model IS a join’s cost model, evaluated at bytesB = 0.

06

The trade-off: this model prices two things honestly and defers two others on purpose

This lesson prices the shuffle’s data-volume cost and the local sort-merge’s operation count — it does not re-price shuffle’s OWN two other costs, and it shouldn’t. shuffle-the-batch-primitive.mdx already prices the M×R connection-setup overhead (a separate cost axis from data volume) and the spill-to-disk penalty when one reducer’s partition doesn’t fit in memory, plus what a hot key does to a shuffle stage’s completion time. A batch join or GROUP BY pays every one of those costs for exactly the reasons that lesson gives — this file adds nothing to them because there’s nothing join- or group-by-specific about any of the three; assuming a perfectly uniform, in-memory shuffle here is the same honest simplification that lesson’s own uniform baseline makes, not a gap unique to this one.

comparisonsPerSecond is an illustrative unit-reconciliation constant, not a measured machine number. join-algorithms.mjs’s own sortMergeCost is deliberately unit-agnostic — an operation count, not a wall-clock time (its file says so directly) — because the point there is comparing cost SHAPES, not predicting a specific runtime. Converting that count into seconds here is what lets it sit next to the shuffle’s own (genuinely time-based) cost, and it is exactly why the ratio in Slot 1 is “300 gigabytes vs. 3,200×,” a real number, and not “this graph looks bigger than that one.”

Secondary sort’s overhead share tells a different story once the primary key is already free. Everything above compares composite sort against a primary-only sort built from scratch. If the primary key instead arrives already sorted — because the shuffle’s own partitioner handed it over for zero marginal cost, the normal case at batch scale — then secondary sort isn’t a growing minority share anymore; it’s the ENTIRE remaining sort bill the moment there is more than one record per key, a jump from 0% to 100% rather than a slow climb. That’s not a contradiction: it just means “100% of the sort work” and “a lot of work” are different claims once the sort work left to do is small in the first place.

07

In the wild

DDIA’s own “Joins and Grouping” section names secondary sort directly, in the exact scenario this lesson prices. Continuing its user-activity/user-database join example: “The MapReduce job can even arrange the records to be sorted such that the reducers always see the record from the user database first, followed by the activity events in timestamp order. This technique is known as a secondary sort” (Kleppmann, DDIA, 2nd ed., p. 472) — a composite sort key decided at shuffle time, exactly this lesson’s model, not a re-sort after the fact.

The same section states the group-by-as-shuffle reframing almost as an aside, immediately after the join example — this lesson’s whole “aha” is DDIA’s own next paragraph, made numeric. Continuing the identical pipeline with a second job that shuffles by URL instead of user ID: “the reducers iterate over all the page views… keeping a counter for the number of views by each age group and incrementing the appropriate counter for each page view. This way, you can implement a group by operation and aggregation” (Kleppmann, DDIA, 2nd ed., p. 473). DDIA’s own “Dataflow Engines” section makes the same point about modern engines directly: they “offer higher-level operators such as join and group by… [and] internally, these operations are implemented using the shuffle algorithms” (p. 468) — join and group-by, named side by side as uses of one mechanism, which is precisely what groupByShuffleSeconds/joinShuffleSeconds’s proven convergence makes concrete rather than assumed.

Reuse, not re-derivation, all the way down. The shuffle term is shuffle-the-batch-primitive.mjs’s shuffleDataVolumeSeconds, unchanged; the local term is join-algorithms.mjs’s sortMergeCost, unchanged; this lesson’s only new material is the secondary-sort-overhead model and the proof that a join’s and a group-by’s cost formulas meet exactly at a size-0 phantom input. stream-joins.mdx is this lesson’s streaming counterpart, not its prerequisite — that lesson’s whole problem (a matching event that hasn’t arrived YET) doesn’t exist here, where both inputs are already complete before the job starts; the near-transfer question above is about exactly that boundary.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • A distributed join or GROUP BY is two steps, not one algorithm: SHUFFLE co-locates every record for a given key onto one reducer (`shuffleDataVolumeSeconds`, reused unchanged from `shuffle-the-batch-primitive.mjs`), then a LOCAL sort-merge finishes the job on just that reducer's own partition (`sortMergeCost`, reused unchanged from `join-algorithms.mjs`) — no new algorithm gets invented at cluster scale, only a new step placed in front of the old one.
  • Shuffle cost is a function of the FULL dataset's bytes moving over a SHARED network link, so adding more reducers does not shrink it. Local cost is a function of one reducer's own PARTITION and falls as 1/numReducers. That asymmetry is why shuffle is the dominant, sticky cost at scale: more machines only ever attack the term that was already the smaller one.
  • SECONDARY SORT makes the shuffle's sort key a COMPOSITE — primary key for grouping, secondary key for within-group order — so records for one key arrive at the reducer already in a specific order (e.g. chronological), not just grouped together. That is a distinct partitioning/sorting technique decided before the shuffle runs, not "sort it again after arrival," and its extra tie-breaking comparisons cost something only once average group size is large enough for within-group order to be real work (zero at group size 1).
  • A GROUP BY is not a different operation from a join — it is the SAME shuffle-then-local-reduce pattern applied to one input instead of two. `groupByShuffleSeconds`/`groupByCost` and `joinShuffleSeconds`/`batchJoinCost` are independently-stated formulas that converge to the identical number once the join's second input is a size-0 phantom, proven by this lesson's own tests, not merely asserted as an analogy.
  • Because the shuffle already sorts each reducer's input by key as a side effect (the same "already sorted, so the sort cost is zero" branch `join-algorithms.mjs`'s `sortMergeCost` already prices), the local step at batch scale almost always pays only the merge walk, not a fresh sort — which is exactly why a batch sort-merge join is cheap once the shuffle has done its (expensive) job.

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A batch join over two 500-million-row datasets (150 bytes/row, 10Gbps network) runs across 500 reducers. Using `batchJoinCost`, what are the shuffle and local costs, and what happens to each if the job is rerun on 5,000 reducers instead — same data, same network?

    How sure are you, before you look?
    At 500 reducers: batchJoinCost({'{'} bytesA: 75e9, bytesB: 75e9, rowsA: 5e8, rowsB: 5e8, numReducers: 500, networkBytesPerSec: 1.25e9, comparisonsPerSecond: 1e8 {'}'}) = 120 seconds of shuffle (moving 150GB total) and 0.02 seconds of local sort-merge per reducer — shuffle is 6,000× more expensive here. At 5,000 reducers (10× more), shuffle stays at exactly 120 seconds — the same 150GB still has to cross the same network link no matter how many machines split the work afterward — while local cost falls to 0.002 seconds, a clean 10× drop matching the 10× smaller partition. The job's wall-clock time barely moves (120.02s → 120.002s), because the term that was already tiny got ten times tinier while the term that actually mattered didn't change at all.
    Did you have that?
  2. Cued recall

    A user-events dataset needs a secondary sort so each user's events arrive chronologically, not just grouped. At 20,000,000 rows in one reducer's partition, how does `secondarySortOverheadShare` compare at an average of 50 events per user versus exactly 1 event per user (no grouping at all)?

    How sure are you, before you look?
    At 1 event per user: secondarySortOverheadShare(20e6, 1, false) = 0% — every key is its own group, there is no tie for a secondary key to break, so composite sort costs exactly what a primary-only sort costs. At 50 events per user: secondarySortOverheadShare(20e6, 50, false) ≈ 10.4% — real, but a minority of the sort's own cost, and the sort itself is usually the smaller of this lesson's two terms in the first place. Secondary sort is priced honestly here, not waved away — it is also honestly a second-order cost next to the shuffle.
    Did you have that?
  3. Near transfer

    `stream-joins.mdx` buffers unmatched events, holding one side until its partner arrives or a join window expires. A team reasons: "batch-joins must be the same problem, just without a time limit — an unbounded buffer instead of a windowed one." Is that the right way to carry the streaming lesson's finding over to batch scale?

    How sure are you, before you look?
    No — and the difference isn't "how big the buffer is," it's that batch has no buffer-for-a- match problem at all. A stream join buffers because the matching event on the OTHER side might not have arrived YET — the dataset is still incomplete, unfolding in time. A batch join's two inputs already exist, complete, sitting in a distributed filesystem before the job even starts; there is no "still waiting for it to show up" state to hold, because nothing is going to show up that isn't already there. What batch scale actually adds is a SIZE problem, not a TIME problem: the matching rows already exist, they're just spread across different shards, and the shuffle's whole job is getting them onto the same machine — a co-location problem with a definite, computable cost (`joinShuffleSeconds`), not an open-ended wait with an unmatched-event residue. Carrying "buffer until it arrives" over from streaming to batch mistakes a completeness problem for a locality problem — they just don't look alike once you ask what each one is actually waiting on.
    Did you have that?
  4. Far transfer

    The abstraction is: before you can do any per-group work cheaply, first route every item to the one place that will handle its whole group — after that, the actual work per group is small and local. Name an instance outside computing.

    How sure are you, before you look?
    A company consolidating expense reports by department. Every regional office files its own reports as they come in, mixed together by whoever happened to submit one that week — if one central accountant tried to read every office's raw pile looking for their own department's spend, they'd re-scan everyone else's reports every time. Instead, all offices first route their reports into one shared inbox per DEPARTMENT (the shuffle: co-locating everything with the same "department" key), and only then does each department's own clerk tally just their own inbox's stack (the local reduce — cheap, because it's now a small pile of only the records that matter to them). Wanting the department's spend broken down further by MONTH, in order, is exactly a secondary sort: you'd ask offices to write both the department AND the date on each report before it's routed, so each clerk's inbox arrives already ordered, rather than sorting the pile again after it lands on their desk.
    Did you have that?
