Tier 4 · Distributed systems mechanics Sharded log + processors

One deterministic consumer per partition replaces a distributed transaction — until skew makes it carry 27× its fair share

`message-ordering-per-key.mdx` guarantees every event sharing a key lands in one partition, in a fixed order. `determinism-as-design-tool.mdx` names the property that lets a replica reproduce a result by replaying its input instead of copying it. This lesson is what happens when you combine those two already-priced properties to enforce a GLOBAL constraint — "usernames must be unique," "a balance must never go negative" — without a distributed transaction: route every event that could conflict onto the same partition, let exactly one deterministic processor decide accept-or-reject against its own local state, and skip the coordination round entirely. It also computes the one cost that design doesn't remove: a single consumer per partition is still a single consumer, and `hot-partitions.mdx`'s ceiling applies to it exactly as it applies to a database shard.

01

Two lessons this course already priced, combined into a third thing

message-ordering-per-key.mdx computed a guarantee: events sharing a partition key arrive at their consumer in one fixed order, no coordination needed across partitions. determinism-as-design-tool.mdx computed a property: the same input, replayed, produces the same output, every time, on every replica. Neither lesson claimed to solve “enforce a uniqueness constraint across a sharded system.” Put the two together and they already have — this lesson is that combination, made concrete, against a real constraint: usernames must be unique.

02

Assume a global constraint needs a global lock

The instinct: “usernames must be unique” sounds like it needs a single source of truth everyone checks before writing — a lock, a unique index behind a single leader, or a distributed transaction spanning every shard that could hold a conflicting claim. coordination-avoidance.mdx already confirmed the instinct isn’t wrong about the NEED — a uniqueness constraint genuinely fails the invariant-confluence test and needs coordination, full stop. The gap is in assuming “needs coordination” only has one expensive answer.

Predict Two users, in two different data centers, both try to claim the username 'alex' within the same second. Both claim-username events are routed by a hash of the username to the same log partition, where a single stream processor consumes that partition sequentially. What resolves which claim wins, without a distributed transaction?
Because both events are routed by the SAME key (the username) to the SAME partition, they are guaranteed to reach exactly one consumer, in one fixed order. That single processor reads its own local in-memory state ('is this username already claimed?') and accepts whichever request the log happens to have ordered first, rejecting the other — deterministically, and identically on every replay of the same log. No cross-data-center round trip is needed because there was only ever one decision-maker for this specific username, by construction of the routing.
Show it without answering

Step through the rig’s fixed log and uniquenessConstraintCheck accepts the first claim on alice, bob, carol, and dave — four usernames, four winners — and rejects every later claim on a username already taken, using nothing but the processor’s own local map. At the rig’s default 64 partitions and partition-key skew s = 1.5, the single hottest partition’s one consumer has to sustain 42,312.9 events/second out of a 100,000/s total — 27.1× a fair share of 1,562.5/s — and adding partitions past about 2.4 does not move that number.

03

A single ticket window outruns a shouting match, until the window itself is the queue

Ten people want the last seat on a train. Tell them to shout their claim at whichever counter is nearest, and two counters can each independently believe they’ve sold the last seat — a double-sold seat, exactly the race a cross-counter agreement protocol would exist to prevent. Route every claim on that specific train’s last seat to one queue at one window instead, and the agent behind it resolves claims one at a time, in whatever order they reached that window — no negotiation between counters, ever, because only one party was ever deciding.

The same office runs many such single-window queues in parallel, one per train — each internally conflict-free for the identical reason, and none of them coordinating with any other. But any one window’s own line is still capped by how fast that one agent can process it, no matter how many other windows exist elsewhere in the building. That’s the ceiling half of this lesson, arriving for free out of the same picture.

06

The trade-off — cheap coordination is not free coordination

This mechanism is genuinely cheaper than a distributed transaction, and the reason is specific, not vibes: it never needs more than one party to agree, because routing already guaranteed only one party would ever see a given conflict. A distributed transaction pays 2 round trips per participating shard and has zero fault tolerance because commit requires every single participant — distributedTxnAvailability’s exact q = n edge case. This mechanism’s write is a normal, local, asynchronous append whose availability doesn’t decay with anything, because nothing outside the local partition is ever consulted before deciding.

The cost that doesn’t go away is the one hot-partitions.mdx already priced, unmodified. Buying more partitions is not a lever against a bad partition-key choice, because only one consumer ever processes any one partition — the same “adding nodes past 1/p₁ buys nothing” ceiling that lesson computed for a database shard applies identically to a stream-processing consumer, at the identical crossover math.

Recovery is cheap for the identical reason state replication is cheap in determinism-as-design-tool.mdx: because the processor’s decisions are a pure function of the log alone, a crashed processor is reconstructed exactly by replaying its partition’s log from the last checkpoint (replayDeterministic, reused unchanged) — no separate snapshot-and-reconcile machinery, because nothing about the decision ever depended on anything the log didn’t already contain.

07

In the wild

This is not an abstract synthesis — it’s DDIA’s own worked example, verbatim in structure. Kleppmann and Riccomini describe exactly this mechanism, using exactly this example: “in the case of several users trying to claim the same username: (1) Every request for a username is encoded as a message and appended to a shard determined by the hash of the username. (2) A stream processor sequentially reads the requests in the log, using a local database to keep track of which usernames are taken… (3) The client that requested the username watches the output stream and waits for a success or rejection message” (ch.13, pp.567–568). The book states the general principle directly: “any writes that may conflict are routed to the same shard and processed sequentially” — and notes it scales by adding shards, “as each shard can be processed independently,” which is exactly perKeyOrderingThroughput’s reused parallelism win.

Jay Kreps named the underlying idea — the log as the source of truth a system’s derived state is rebuilt from — before “stream processing” was the industry’s default vocabulary for it. Jay Kreps, The Log: What every software engineer should know about real-time data’s unifying abstraction (2013) argues that treating an ordered, append-only log as the primary record, with every downstream view (a database index, a cache, a search index) as a deterministic derivation of it, is what lets those views be rebuilt from scratch rather than kept manually in sync — the same “replay reproduces the output” property determinism-as-design-tool.mdx names directly.

message-ordering-per-key.mdx’s own DDIA citation already anticipated this lesson’s mechanism from the consumer’s side: “If the event log and the application state are sharded in the same way… a straightforward single-threaded log consumer needs no concurrency control for writes” (ch.12, p.511) — this lesson is what that sentence buys once the “application state” being protected is a uniqueness constraint specifically, rather than concurrency control in general.

Free recall — do this before you scroll back

Write down everything you remember from this lesson. Don't look. Unstructured, no cues, nothing to recognise — this is the hardest and highest-yield thing here, and any hint spends it.

  • The mechanism has two parts, and each one is a reuse, not new invention: (1) ROUTE every event that could conflict on the same constraint — every "claim username X" — to the SAME log partition, by keying on the constrained value itself, exactly `message-ordering-per-key.mdx`'s per-key ordering guarantee; (2) let exactly ONE deterministic processor consume that partition, one event at a time, in the log's fixed order
  • Because there is only ONE consumer processing that partition, in a fixed order, there is no race condition left to coordinate away — the processor checks its own local, in-memory state ("has this username already been claimed by an earlier event in this partition?") and the check is correct by construction, not by locking
  • Ordering (from routing by key) plus determinism (same log always produces the same accept/reject decisions, `determinism-as-design-tool.mdx`'s own property) together substitute for a distributed transaction or a distributed lock entirely — this is exactly `coordination-avoidance.mjs`'s framework in action: a uniqueness constraint IS an operation that needs coordination, and this is the specific, cheap mechanism that supplies it, instead of 2PC/Paxos/a distributed lock
  • The mechanism has a real throughput ceiling, not a hidden one: only ONE consumer ever processes a given partition, so if claim events concentrate on a few partition keys (coarse partitioning, or a poorly chosen key), that single consumer becomes exactly `hot-partitions.mdx`'s ceiling — `hotNodeFloor`/`hotKeyShare`, unchanged — applied to a stream-processing consumer instead of a database shard
  • A crashed deterministic processor is reconstructed EXACTLY by replaying its partition's log from the last checkpoint — `determinism-as-design-tool.mjs`'s `replayDeterministic`, reused unchanged — because the processor's decisions are a pure function of the log, not of anything else it might have read along the way
  • The trade this mechanism makes against a synchronous distributed transaction is latency and blocking behavior for scale: a distributed transaction across N shards pays 2 round trips per hop and has ZERO fault tolerance (`distributed-transactions-vs-eventual-consistency.mjs`'s `distributedTxnLatency`/`distributedTxnAvailability`, reused unchanged), while a sharded-log append is a normal, local, async write whose availability does not decay with participant count at all

Score yourself on the list, not on how much you wrote. A missing item is a located gap, which is worth more than a page of recall that skirted it.

  1. Cued recall

    A team wants to enforce "each email address can only be associated with one account" at scale, without a distributed transaction. They propose: shard user accounts by account id, and have each shard's stream processor check "is this email already taken?" against its own local database before accepting a signup. Does this work?

    How sure are you, before you look?
    No — and the bug is exactly the routing half of this lesson's mechanism, done backwards. Sharding by ACCOUNT id means two signups for the SAME email but different (not-yet-created) account ids can land on two DIFFERENT shards, each shard's processor sees "not taken" in its own local state, and both accept — the email ends up claimed twice. The fix is to shard by the CONSTRAINED VALUE itself (a hash of the email), not by an unrelated key, so every claim on that exact email is guaranteed to reach the same partition and the same single processor. Sharding by the wrong key doesn't just slow this mechanism down, it breaks the guarantee outright.
    Did you have that?
  2. Cued recall

    A junior engineer reviews this mechanism and says "so a distributed transaction and a sharded-log-plus-deterministic-processor are actually solving two different problems — one gives you atomicity, the other gives you ordering." Why is that framing wrong?

    How sure are you, before you look?
    Because both are answers to the SAME question: how does a system decide, safely, which of several conflicting concurrent operations wins? A distributed transaction answers it by making every participant agree before committing (2PC/3PC, `distributed-transactions-vs-eventual-consistency.mdx`'s cost model). This mechanism answers the identical question by making sure only one party ever has to decide in the first place — route every conflicting event to one partition, let one deterministic consumer resolve it in log order. They are two different-priced answers to one question, not two different questions.
    Did you have that?
  3. Cued recall

    `uniquenessConstraintCheck`'s test file shows that reversing the order of two claim events for the same username changes WHO wins, even though the same two requesters submitted the same two requests. Is that a bug?

    How sure are you, before you look?
    No — it's the mechanism working exactly as designed, and naming it a bug misunderstands what the guarantee actually is. The mechanism doesn't promise a globally "fair" or "first-in-real-time" winner; it promises a DETERMINISTIC one — whichever event the log happens to order first wins, consistently, on every replay. The log's order is itself decided upstream (by whichever process appended first, or by the broker's own ordering), and once that order is fixed, this processor's job is only to apply it consistently, not to re-adjudicate what "fair" would have meant.
    Did you have that?
  4. Near transfer

    `coordination-avoidance.mdx` already established that a uniqueness constraint is NOT invariant-confluent — two concurrent check-then-insert operations can each independently see "not taken" and both proceed — so it "genuinely needs coordination," full stop. Doesn't that mean this lesson's mechanism, which skips a distributed transaction, is cheating that framework's own conclusion?

    How sure are you, before you look?
    No — it's satisfying that same conclusion by a cheaper route, not skipping it. `coordination-avoidance.mdx`'s classification only tells you WHETHER coordination is required; it deliberately does not prescribe HOW to supply it, and this course has already priced several answers (a lock, a consensus round, a distributed transaction). This lesson is a fourth: route every conflicting event to one partition and let one deterministic consumer serialize them. There is still exactly one decision-maker resolving every conflict — that IS coordination, just supplied by partition-key routing and a single-threaded consumer instead of by a lock manager or a two-phase commit protocol. The classification was never wrong; this lesson only supplies a specific, cheap mechanism for the "yes" branch.
    Did you have that?
  5. Far transfer

    The abstraction is: rather than having every party check in with every other party before deciding, route every decision that could conflict to the SAME single arbiter, who resolves them one at a time in a fixed order — turning an N-way negotiation into a single queue. Name an instance outside computing.

    How sure are you, before you look?
    A single ticket window (not a numbered-ticket lottery) for a scarce resource, versus a free-for-all rush. If ten people want the last seat on a train and are told to shout their claim at whichever counter is nearest, two counters can each independently believe they've sold the last seat — a double-sold seat, the exact race a distributed transaction would need cross-counter agreement to prevent. Route every claim on THAT SPECIFIC train's last seat to one queue at one window instead, and the agent behind it resolves claims one at a time, in whatever order they arrived at that window — no negotiation between counters is ever needed, because only one party was ever deciding. The same office can run many such single-window queues in parallel for many different trains (many partitions), each one internally conflict-free for exactly the same reason — and any one window's line is still capped by how fast that one agent can process it, no matter how many other windows exist.
    Did you have that?
